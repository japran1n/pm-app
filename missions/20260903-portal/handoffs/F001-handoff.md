## Decisions made
- Added `public.is_project_portal_enabled(target_project_id uuid)` as a new SECURITY DEFINER predicate (pinned `search_path = public, pg_temp`) rather than inlining a `projects` subselect everywhere `portal_enabled` needs checking — matches this schema's existing one-predicate-per-concept convention (`is_project_client`, `is_project_visible_to`, etc.) and keeps the check in exactly one place for the next migration that needs it (F002-F006 all read `portal_enabled` from somewhere).
- Folded `portal_enabled` into the CLIENT branch only of `tasks_select_active_members`'s OR clause (`not is_project_client(...) OR (client_visible AND is_project_portal_enabled(...))`), preserving the original migration's documented short-circuit: for every team role the added conjunct is never evaluated, so there is no behavior change and no extra query cost for the team's own board/list views.
- Also redefined `is_task_visible_to` (originally from 20260902010000, last touched by 20260908010000's pg_temp pin) with the same fold, because it backs comments/attachments and every other "does this task's visibility extend to me" read a client can reach. Without this, a client could still read comments on a shared task belonging to a portal-disabled project even though the task row itself is hidden by the policy above — verified this gap exists and is closed via a dedicated integration test ("AS-007: portal_enabled = false also hides a shared task's comments from the client").
- `project_phases` team SELECT uses `is_project_visible_to(project_id) AND NOT is_project_client(project_id)` (the same shape `time_entries`/`task_activity`/etc. use in 20260902020000) rather than reusing `is_project_workspace_writer` for SELECT — writer excludes `viewer` too, and a viewer should still be able to READ phases, just not write them.
- `project_phases` INSERT/UPDATE/DELETE uses `is_project_workspace_writer(project_id)` alone (no additional `is_project_visible_to` check), matching the exact pattern `tasks_insert_active_members`/`tasks_update_active_members` already use — the writer predicate's own join through `projects` already ties `project_id` to a real project, so a second visibility check would be redundant.
- `getProjectPhases` explicitly filters `.eq("client_visible", true)` on the `project_phases` query and `.eq("client_visible", true)` on the associated `tasks` query, rather than leaving both entirely to RLS. This is a deliberate, narrow exception to this file's own stated "the database hides rows, don't re-implement that here" convention: AS-011/AS-012 are business-logic requirements about what the PROGRESS FIGURE and PHASE LIST *mean* (client-visible-only), not access-control boundaries — they must hold the same way even for a future team-side caller of this same function (e.g. a PM previewing the client's numbers), which RLS alone cannot guarantee since a team caller's RLS grant is broader than a client's.
- `seed_default_phases(p_project_id uuid)` is `SECURITY DEFINER` + re-verifies the caller is an active non-`client` workspace member inside the function body (same "security definer bypasses RLS, so re-check explicitly" shape as `apply_status_template`, 20260903010000) rather than relying solely on the `project_phases_insert_team` RLS policy — this lets the RPC be granted to `authenticated` broadly while still gating who can actually seed a given project's phases.
- Seeded phase `position` values are plain `1..10` (not the `saved_views`-style `*1000` spacing) because the spec's own column definition for `project_phases.position` is `integer not null`, and 10 fixed phases with no drag-reorder UI in THIS feature don't need reorder headroom yet — a future phases-reorder feature (F002) can renumber on write, same as `apply_status_template` does today for `project_statuses.position` (which IS `double precision` and does use spacing, precisely because that table supports live reordering).
- Did not touch `projects_select_*` RLS: a client keeps seeing the bare `projects` row for a portal-disabled project (name, dates) via existing `is_project_visible_to`/`project_members` grants — `portal_enabled` only gates `project_phases` and `tasks` (and transitively `comments`/`attachments`/etc. via `is_task_visible_to`), per the spec's explicit RLS section (project_phases + tasks only). `getPortalProjects` is the actual app-facing gate for the project list itself (`.eq("portal_enabled", true)`), matching the spec's section-7 instruction verbatim.

AUTONOMOUS_DECISION: `seed_default_phases`'s idempotency check is "does this project have ANY phase row" (not "does it have exactly these ten named phases"). The spec says "Idempotent: calling it on a project that already has phases returns without inserting (do not duplicate)" — read literally as any pre-existing phase (e.g. one a PM created by hand) blocking the seed, not specifically a re-run of the seed itself. Verified via the integration test that a second RPC call inserts nothing.
