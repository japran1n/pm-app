## Decisions made
- **Bucket fallback mapping**: `not_started` → `waiting`, `in_progress` → `progress`, `done` → `done`. No category value can ever produce `blocked` — that bucket is reachable only through an explicit `client_bucket` override, by design (the spec's own "category cannot express this" reasoning applies doubly to `blocked`, which has no category counterpart at all, not just to `waiting`). Verified against `docs/team-app-for-portal-plan.md`'s real status table (`grep -n "Blocked\|Awaiting Client Feedback" docs/team-app-for-portal-plan.md`, lines 71/73): "Awaiting Client Feedback" is category `in_progress` on the team's own board but must read as "Čeka vas" (waiting on you) to a client — exactly the case an override, not a fallback, has to cover.
- **`resolveClientBucket` lives in `components/portal/status-label.ts`**, not a new file, per the spec's explicit "fold its logic in rather than leaving two sources of truth." Did **not** refactor the existing `clientStatusLabel`'s name-regex-based "review" detection to route through this new bucket function, even though that regex is exactly the kind of by-name recognition this feature's design constraint prohibits for *new* code — `clientStatusLabel` is pre-existing (comment says "F009", a different mission's numbering), already used by `components/portal/task-list.tsx`, and `components/portal/task-list.test.tsx` has a test (`test_AS_021_status_change_to_done_moves_row_and_updates_heading_live`) whose own in-file comment explicitly documents and locks in "In review" always rendering "Waiting on your review" via that regex. `task-list.tsx`/`task-list.test.tsx` are not in this feature's file scope (not in the spec's "Files (approximate)" list), so touching them would be an undocumented scope expansion into a different, already-shipped feature. Flagged as Out-of-scope work below instead.
- **`StatusPill`'s visible label is the status's own `name`** (the literal string the team's board shows), not a translated generic phrase like `clientStatusLabel` produces. This is the one piece of AS-015 ("the same status the team sees, with no second mapping that can diverge") that a generic bucket-label would violate — `clientStatusLabel` exists specifically to *translate* vocabulary for `task-list.tsx`'s group headings, a different, intentional design choice for a different surface (grouping many tasks under one heading vs. labelling one row's own status).
- **`updateColumn`'s `clientDescription`/`clientBucket` are optional, not required**, and the DB write only includes the keys actually supplied (an omitted key leaves the column's existing value untouched — see `lib/actions/statuses.ts`'s `updatePayload` object). Discovered this was necessary when making them required broke three pre-existing, out-of-scope integration test files (`tests/integration/f219-status-management.test.ts`, `f325-status-rename-sync.test.ts`, `f327-project-lead-column-management.test.ts`) that call `updateColumn` directly with only `name`/`color`/`category`. Re-ran all three after the fix — all green (see Commands run).
- **Migration bug caught and fixed before commit**: the first draft of `20260911010000_status_client_bucket.sql` copied `seed_default_project_statuses`'s seed colours from the *original* `20260824010000_project_statuses.sql` (`#94a3b8`/`#3b82f6`/`#f59e0b`/`#22c55e`), not realizing `20260828030000_status_rename_sync_and_seed_colors.sql` had already redefined the same function with different, palette-aligned colours (`#64748b`/`#3b82f6`/`#d97706`/`#16a34a`). Running `create or replace` with the stale colours silently regressed that earlier fix — caught by running `tests/integration/f325-status-rename-sync.test.ts` (not in this feature's own file scope, but it calls a function this migration touches) before considering the migration done; it failed with the exact stale-colour mismatch. Fixed by re-reading `20260828030000`'s actual current body and using its colours verbatim, then re-executing the corrected SQL directly against the live project (the migration's version was already recorded by the first `db:apply`, so a second `db:apply` would have no-opped — see Commands run). This is the reason this feature's own review process re-ran three integration test files well outside its declared file scope: any `create or replace function` on a shared function is a place a later feature can silently regress an earlier one's fix, and the only way to catch that is running the earlier feature's own tests.
- **Pill-fill surface tokens (`--status-*-bg`) use `color-mix(in srgb, var(--status-x) N%, transparent)`** rather than a second flat hex per theme. This keeps the "these four hex values are the ONLY hex literals allowed in your diff" constraint honoured literally (the `-bg` tokens are formulas referencing the four base tokens, not new colours) while still giving each theme its own token declaration as the spec requires ("declare every token in the base `:root` before `.dark` redefines it" — both blocks declare all eight pairs). Light uses 16% mix, dark uses 18% (a near-black ground needs slightly more tint for the fill to read against `--card`/`--sidebar`).

## Notes for the next worker
- `resolveClientBucket(category, clientBucket)` is exported from `components/portal/status-label.ts`, not a new file — import it from there, not from `status-pill.tsx`.
- Base UI's `Tooltip.Root` defaults to a 600ms hover-open delay when not wrapped in a `TooltipProvider` (confirmed via `node_modules/@base-ui/react/tooltip/utils/constants.js`'s `OPEN_DELAY = 600`). `status-pill.test.tsx` opens tooltips via `fireEvent.focus` (Floating UI's `useFocus` opens immediately, no delay) rather than hover, to avoid needing fake timers — worth reusing that pattern for any future tooltip-content test in this repo, since no existing test before this feature actually opened a tooltip popup to assert its contents.
- Zod v4's built-in `.uuid()` validates real UUID version/variant nibbles (`[1-8]` then `[89abAB]`), not just hex-dash shape — an all-`1`s placeholder UUID like `11111111-1111-1111-1111-111111111111` fails it. Use something like `11111111-1111-4111-8111-111111111111` (version 4, variant 8) in test fixtures instead; this cost real debugging time in this feature (see `lib/validation/statuses.test.ts`'s fixture).
- Before doing a `create or replace function` on any shared SECURITY DEFINER function this mission's migrations have already touched more than once (e.g. `seed_default_project_statuses`, `is_task_visible_to`), grep every migration file that mentions its name and read the *most recent* one's actual current body — don't copy from the function's original definition. This feature's own migration draft got this wrong once (see Decisions made) and was only caught by running an out-of-scope integration test before considering the work done.
