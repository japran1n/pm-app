## Decisions made

**Defect 1 (`seed_default_phases`, NM-1).** Added `public.is_project_visible_to(p_project_id)` immediately after the existing role check, plus a `deleted_at is null` guard on the initial `projects` lookup — both are exactly what `seedDefaultPhasesImpl`'s `withAuthz` call enforces (`lib/actions/phases.ts:185-190`, `requireWrite: true` + `requireVisibility: true`; `loadProjectExtra` at `:152-160` rejects a soft-deleted project before ever reaching the RPC). `is_project_visible_to` is the same predicate every other project-scoped SELECT policy in this schema already uses (`20260908010000:37-64`), so no new predicate was invented.

**Defect 2 (`client_requests` UPDATE/DELETE author policies, NM-3).** Added `public.is_project_portal_enabled(project_id)` to both the `using` clause of `client_requests_update_author_while_submitted` (and its `with check`, matching the INSERT policy's shape from F006b's own `20260913010000`) and the `using` clause of `client_requests_delete_author_while_submitted`. Deliberately left `client_requests_update_team` untouched — the team must still be able to triage/manage a request on a portal-disabled project internally; F006b's own SELECT fix draws the identical author-vs-team distinction.

**Defect 3 (`assert_portal_task_actionable_by_client`, NM-4).** Added one `if not public.is_project_portal_enabled(v_project_id) then raise exception 'task not found';` branch, using the exact same "task not found" oracle every other rejection branch in this function already uses — a client of a portal-disabled project must not be able to distinguish "portal off" from "task doesn't exist" or "task not pending" by the error message alone. Both `approve_portal_task_atomic` and `request_portal_task_changes_atomic` delegate their entire authorisation check to this one helper (`20260906010000`'s own header comment), so fixing it here closes both RPCs in one place, and both are proven independently in the new tests.

**Defect 4 (`create_channel_atomic`).** Read the original `20260905090000_create_channel_atomic.sql` in full, as instructed — confirmed its only mention of `auth.uid()` is a comment ("the creator id and member ids are passed explicitly as arguments rather than read from auth.uid()"), never an actual check, in either the original or either of this mission's two subsequent re-creations (`20260910010000`, `20260914010000`).

Grepped for the equivalent guarded RPC before choosing a shape, per the task's explicit instruction. The one that matches — SECURITY DEFINER, granted to **both** `authenticated` and `service_role`, where the `service_role` caller (an admin-client Server Action that already re-verified everything itself) must be exempt but a direct `authenticated` caller must not — is `public.create_notification()`, fixed in `supabase/migrations/20260823030000_fix_create_notification_spoofing.sql:88-111`: it pins the actor to `auth.uid()` and requires the caller to be an active member of the target workspace, gated entirely behind `if p_system then ... else if auth.uid() is null then raise ... end if ...`. The identical `auth.uid() is null` branch shape (there keyed off a `p_system` flag rather than an implicit service-role detection, since that migration added a new parameter) recurs in `supabase/migrations/20260823060000_fix_write_task_activity_entry_forgery.sql:60-70`. `create_channel_atomic`'s own signature couldn't take a new `p_system` parameter without a breaking `drop function` (no production caller exists to migrate, but the file's own precedent at `20260910010000` treats a signature change as the more invasive option only when required) — and it doesn't need one: a `service_role` JWT genuinely carries no `sub` claim, so `auth.uid() is null` already IS the correct, unambiguous "this is the trusted admin-client caller" signal, with no flag required. So the fix wraps the entire new check block in `if auth.uid() is not null then ... end if`, verified against `lib/actions/chat-channels.ts:75-153` (the RPC's only production caller — confirmed by repo-wide grep, no UI wires this RPC up directly yet) which always calls it via `createAdminClient()` after its own membership/visibility re-check.

Implemented exactly the three checks the spec names, no more: (a) caller is an active member of `p_workspace_id` with `role <> 'client'` (`viewer`/`guest`/`member`/`admin`/`owner` all pass — spec says "non-client", not "writer", and I did not narrow it further); (b) `p_created_by is distinct from auth.uid()` is rejected; (c) every `p_member_ids` entry must itself be an active `workspace_members` row for `p_workspace_id`. Did **not** add a project-visibility check for `p_project_id` inside the RPC — the spec's three named checks don't include one, and `chat-channels.ts`'s own Server Action already does that check before calling the RPC on the admin client (unaffected either way, since `auth.uid()` is null for that call path). Noted as a real gap for a *direct* `authenticated` caller passing a `p_project_id` for a private project they can't see — flagged below, not fixed, since the spec was explicit about the three checks it wanted and adding a fourth unasked-for one is exactly the kind of silent scope expansion the task instructions warn against.

## Out-of-scope work needed

- **`projects_update_active_members` (`supabase/migrations/20260818004709_rls_projects.sql:45`) has no role gate whatsoever — `is_active_workspace_member` (`20260817222822:21`, redefined `20260819065751:76`) admits every active role, including `client` and `viewer`, with zero exclusion.** This is the most serious finding of this sweep: a `client` (or `viewer`) can `PATCH /rest/v1/projects?id=eq.<any project in their workspace>` directly and rewrite **any** column — including `portal_enabled` (the exact gate this entire mission's client-visibility model depends on), `visibility` (turning a private project workspace-visible, defeating `is_project_visible_to`'s private-project branch), `name`/`client_description`, and `deleted_at` (a client could soft-delete a project outright). AS-029 ("any member, not just admins, can edit name/description/dates") is presumably *why* this policy was written this loosely, but AS-029 predates the `client` role's introduction (`20260902010000`) by two weeks — this looks like exactly the kind of role gate `20260821194500`'s own hardening pass added to `tasks`/`comments`/`attachments`/`time_entries` but never reached `projects` itself. Not fixed here because it is not one of this feature's four named defects and `projects` is a much higher-blast-radius table than any of the four I did touch — a follow-up should add `wm.role not in ('client', 'viewer')`-equivalent scoping (verify against AS-029's exact intent first — does a `viewer` need to keep editing project metadata, or was that role excluded already and only `client` is the actual gap?) to `projects_update_active_members`, and write a direct-PostgREST regression test proving a client can no longer flip `portal_enabled`/`visibility`/`deleted_at` on a project, with a positive control proving a legitimate member/admin edit still works.
- **`decide_approval_atomic` (`supabase/migrations/20260916010000_approval_requests.sql:348-479`) never checks `is_project_portal_enabled` or `is_project_visible_to`** — only that the caller matches the named `project_decision_owners.user_id`. A decision owner row can be set by the team (`is_project_workspace_writer`-gated, `project_decision_owners_insert_team`) pointing at any user id, with no constraint tying that user to an active `project_members` row or to the project's portal state. F007 is a separate feature from a different point in this mission with its own assigned assertions (AS-019/020/022/023/024) — not touched here. A follow-up should add both checks (matching this migration's own `assert_portal_task_actionable_by_client` fix) and a direct-RPC test with a decision owner on a portal-disabled project.
- **`checklist_items` INSERT/UPDATE/DELETE (`20260819075456_create_checklist_items.sql:90`, `20260819080358_checklist_items_update_delete_policies.sql:34,51`) use `is_task_workspace_member` — the read-only membership predicate, not `is_task_workspace_writer`** — so any active member including `client`/`viewer` can add, rename, check/uncheck, reorder, and delete checklist items on **any** task in the workspace, including tasks that are not `client_visible` or on a portal-disabled project (this predicate checks neither). Pre-existing from F151/F152 (`20260819`), three weeks before this mission (`20260903-portal`) started — not one of this feature's four named defects, and a different table/feature entirely. A follow-up should repoint all three policies at `is_task_workspace_writer` (the same fix `20260821194500` already applied to `comments`/`attachments`/`time_entries` the same week, but apparently missed this table), then decide separately whether a client needs any checklist-item read/write access on the portal at all — today the portal grants none, so this is likely a pure closure with no legitimate caller to preserve.
- **`project_phases` write policies have no `is_project_visible_to` conjunct** (`M1-scrutiny-2.md`'s carried-forward major M3, `20260909010000:162-183`) — explicitly not one of this feature's four named defects (the spec names only `seed_default_phases`, not the three RLS policies it sits in front of), and explicitly listed as still-open in that same report's own "carried majors" section. Left untouched.
- **Project-visibility check on `create_channel_atomic`'s `p_project_id`** — the spec's three named checks (caller role, `p_created_by`, `p_member_ids`) don't include one, so a direct `authenticated` caller could still create a channel scoped to a private project they can't see. `chat-channels.ts`'s own Server Action already re-checks this before calling the RPC (unaffected, since it calls on the admin client where `auth.uid()` is null). Noted rather than silently added, per the instruction not to expand scope beyond what was asked.
