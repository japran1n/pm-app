## Decisions made

### A. `approval-actions.test.tsx`
- **Mechanism (same as F074's AS-016 finding, now confirmed to generalize):** the real Base UI `Button` enforces `disabled` entirely inside its own click-handler closure (`useButton`'s `getButtonProps().onClick` captures `disabled` at render time, not from the DOM node). Stripping the DOM `disabled` attribute with `removeAttribute("disabled")` therefore does not reliably let a second click through — whether it does depends on whether React's `isPending` transition has already settled by the time the click fires, which is scheduling-dependent, not something the test controls. `test_AS_014_ref_is_cleared_after_ok_false_allowing_retry` was the one surviving test in this file still using that pattern (its sibling `..._after_a_rejected_action_...` was fixed this way by F074; this ok:false-path test was not, which is why it started failing once the rejected-action sibling stopped).
- **Fix:** converted the test to the exact `vi.doMock("@/components/ui/button", ...)` stub-Button pattern already used by the other three retry tests in this file (`test_AS_014_ref_is_cleared_after_a_rejected_action_allowing_retry`, `test_AS_016_ref_is_cleared_after_a_rejected_action_allowing_retry`, `test_AS_016_ref_is_cleared_after_ok_false_allowing_retry`). The stub always forwards `onClick` regardless of `disabled`, so the second click deterministically reaches `handleApprove`, and only `inFlightRef.current` (the actual thing AS-014 is about) can still be blocking it. No `waitFor` timeout was widened — this removes the race instead of shrinking the window it can occur in.
- **Class-level check:** grepped the whole repo for `removeAttribute("disabled")` across all test files. Only one occurrence existed before this change (the one just fixed); zero after. No other test file in the repo clicks a second time after a failed action while relying on stripping a `disabled` attribute — this was the last instance of the pattern, not one of several.

### B. `f020b-projects-allowlist-guard.test.ts`
- **Root cause, found by reading `.github/workflows/*.yml` (not by inspecting the guard function or RLS policies again — those were already correctly diagnosed by F088):** in CI, `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY` — what the file's outer `beforeAll` uses via `admin`/PostgREST to create `workspaceId` / `projectId` / `ownerId` — are generated fresh each run by `supabase status -o env` against an **ephemeral local Docker Supabase stack** (`supabase start`). `SUPABASE_PROJECT_REF` / `SUPABASE_ACCESS_TOKEN` — what the self-maintaining probe's `rawSql` helper uses via the Management API (`https://api.supabase.com/v1/projects/<ref>/database/query`) — are **repository secrets that point at the real hosted project**, a permanently different database. The workflow file's own top comment documents this exact local-vs-hosted split for five other Management-API "catalog" suites, but f020b's self-maintaining test wasn't one of the five and mixed the two: it created its fixture row on the local stack, then asked the hosted project to `UPDATE ... WHERE id = '<that uuid>'`. The row was never in that database — not removed by a race, never inserted there at all — which is exactly what `PROBE_ROW_NOT_MATCHED` ("the UPDATE affected 0 rows") reports. F088's owner-actor fix was a real, correctly-diagnosed RLS finding (proven by direct reproduction against the hosted project in that handoff) and remains necessary, but it could not have fixed this failure because the fixture row it was reasoning about doesn't exist in the database the probe actually queries in CI. My local reproduction attempts against my own `.env` (which points entirely at the hosted project, no local stack) could never have shown this either — locally, both the fixture and the probe target the same, single hosted database, so the mismatch only exists in CI's environment. This matches the honest disclosure at the bottom: I cannot run `supabase start` here (no Docker), but the CI workflow file itself was sufficient to prove the mechanism without needing to reproduce it.
- **Fix, following the "own the fixture end to end" framing:** rewrote the self-maintaining probe to build a workspace, a real `auth.users` row (owner), a `workspace_members` row, and a project entirely through `rawSql` (Management API — the same channel, hence the same database, the probe's own `UPDATE` runs against), immediately before running the probe, and to tear all four down in a `finally` block so cleanup runs even if an assertion throws. This follows the exact precedent already established in this suite family for creating real `auth.users` rows via raw SQL (`tests/integration/overdue-notification-sweep.test.ts`, lines ~113-124, `insert into auth.users (...) values (gen_random_uuid(), ..., crypt(...), ...) returning id;`) rather than inventing a new idiom. The outer `beforeAll`'s `workspaceId`/`projectId`/`ownerId` (used by every other test in the file, which all go through PostgREST/`admin` and therefore stay internally consistent with each other) are untouched.
- **Did not weaken the assertion.** The `PROBE_ROW_NOT_MATCHED` / `GUARD_DID_NOT_FIRE` distinction is unchanged — it is still what would catch a genuine RLS-visibility regression versus a genuine guard hole. No retry, sleep, or re-fetch loop was added; the fix removes the cross-database mismatch rather than tolerating it.
- **Verified cleanup is real and complete**, per the task's explicit safety requirement (this suite mutates the real hosted project): ran the file 4 times consecutively against the live hosted project, then, in a separate throwaway diagnostic script (not committed), queried `information_schema.columns` for `f020b_probe_never_committed`, `public.workspaces` for `slug like 'f020b-probe-%'`, and `auth.users` for `email like 'f020b-probe-owner-%'` — all three returned empty every time. Repeated runs are safe: `finally` guarantees cleanup runs on both success and assertion failure, and the temporary column addition itself is rolled back inside the same DO block's own transaction abort (`ROLLBACK_PROBE_TRANSACTION`), unrelated to whether the JS-level cleanup fires.
