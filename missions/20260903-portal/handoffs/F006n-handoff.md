## Decisions made

- **Two different auth shapes for two different call paths, both verified by reading the caller, not assumed:**
  - `bulk_delete_tasks_atomic`, `duplicate_task_atomic`, `restore_task_atomic`, `set_task_assignees_atomic` are all invoked by their Server Actions via `createAdminClient()` / the `admin` client (service_role) — confirmed by grep (`admin.rpc("bulk_delete_tasks_atomic"`, `ctx.admin.rpc("duplicate_task_atomic"`, `ctx.admin.rpc("restore_task_atomic"`, `admin.rpc("set_task_assignees_atomic"` in lib/actions/tasks.ts). `auth.uid()` is null on a service_role call, so each of these four wraps its new checks in `if auth.uid() is not null then ... end if;` — **verified precedent, not claimed from memory**: `supabase/migrations/20260918010000_f006i_authz_round_2.sql:227` (`create_channel_atomic`) uses the identical `if auth.uid() is not null then` guard, and its own header comment (`20260918010000:186-206`) names `create_notification` (`20260823030000_fix_create_notification_spoofing.sql:88-111`) and `write_task_activity_entry` (`20260823060000_fix_write_task_activity_entry_forgery.sql:60-70`) as the two earlier functions establishing the same shape.
  - `accept_client_request_atomic` is invoked via `supabase.rpc(...)` — the caller's own session, not the admin client — confirmed by grep (`lib/actions/client-requests.ts:284`, `supabase.rpc("accept_client_request_atomic"`, and the migration's own pre-existing header comment: "Runs as the calling user (auth.uid())"). `auth.uid()` is always the real caller here, so its check runs unconditionally, no branch needed — same shape `assert_portal_task_actionable_by_client` already uses (`20260918010000_f006i_authz_round_2.sql`, NM-4 section).

- **`bulk_delete_tasks_atomic`'s direct-caller branch re-filters `p_task_ids` rather than raising on any disallowed id.** Read `bulkDeleteTasks` first (lib/actions/tasks.ts:4358-4499): it has an explicit partial-success contract (`succeededIds`/`failedIds`, some tasks in a batch can fail while others succeed). A hard `raise exception` on the first unauthorised id in the array would change that contract for the legitimate mixed-batch case. Mirrored instead: the RPC computes its own allowed subset from `is_task_workspace_writer` + `is_project_visible_to`, exactly what `bulkDeleteTasks` computes before calling it, and silently excludes anything that doesn't pass — a caller with zero allowed ids gets `'{}'` back, not an error, matching what happens today when the Server Action itself filters everything out (`allowedIds.length === 0` → `{ ok: true, data: { succeededIds: [], failedIds } }`).

- **Used two existing helper predicates rather than inlining the same joins five times**, both verified by reading their definitions (`supabase/migrations/20260908010000_pin_pg_temp_on_client_visibility_predicates.sql:37-115`):
  - `is_task_workspace_writer(task_id)` — `role not in ('viewer','client')`, i.e. exactly `canWrite` (`lib/auth/permissions.ts:171-174`) at the DB level, already scoped to an active membership. Used for `bulk_delete_tasks_atomic` (per task id) and `duplicate_task_atomic`/`restore_task_atomic` (their calling actions both gate on `canWrite`, confirmed: `duplicateTaskImpl`/`restoreTaskImpl`'s `withAuthz({ requireWrite: true, ... })`, and `withAuthz`'s default `writeCheck` is `canWrite`, `lib/actions/authz.ts:163`).
  - `is_project_visible_to(project_id)` — used by all three above (their actions all pass `requireVisibility: true` / do the equivalent private-project `project_members` check by hand for the bulk path).
  - `set_task_assignees_atomic` needed a **stricter** bar than `is_task_workspace_writer` gives: its calling action (`requireAssignActionContext`, lib/actions/tasks.ts:383-458) checks `canEditTask`, which additionally excludes `guest` (`lib/auth/permissions.ts:186-190` — `canEditTask` bars viewer AND guest AND client; `canWrite` only bars viewer AND client). No existing SQL helper encodes `canEditTask`'s exact rule, so this one function inlines `role not in ('owner','admin','member')` directly rather than reusing `is_task_workspace_writer`, which would have wrongly admitted a `guest`.

- **Pinned attribution on the four service_role-path RPCs when called directly.** `bulk_delete_tasks_atomic` and `set_task_assignees_atomic` accept a caller-supplied `p_deleted_by`/`p_assigned_by`. Beyond just gating access, a direct `authenticated` caller could otherwise attribute a delete/assignment to an arbitrary user id. Inside the `auth.uid() is not null` branch, both now overwrite that parameter with `auth.uid()` before using it — the same spoofing concern `create_channel_atomic` closes for `p_created_by` (`20260918010000_f006i_authz_round_2.sql`, item 4's header comment). Not explicitly required by the feature spec's "mirror the calling action" instruction (the Server Actions already pass the correct id honestly), but it's the same class of gap this feature exists to close and costs nothing extra given the branch already exists.

- **`accept_client_request_atomic` — what changed, called out explicitly for F016 (per the feature spec's own instruction):**
  - Added: workspace-membership lookup via a join to `projects` (the original had none at all beyond `auth.uid() is not null`), a `teamCanTriage`-equivalent role bar (`role not in ('viewer','client')`, mirroring `lib/actions/client-requests.ts:196-199` exactly, including the redundant-but-explicit "a client cannot accept their own request" second check the spec asked for by name), and an `is_project_portal_enabled` gate.
  - The portal gate is **new behaviour the Server Action itself doesn't have today** (`acceptClientRequest` never checks `portal_enabled` — confirmed by reading the full function, lib/actions/client-requests.ts:253-300). This was explicit in the feature spec ("`accept_client_request_atomic` additionally needs the `portal_enabled` gate"), not something I inferred. No regression risk: `client_requests` rows can only be *created* on a portal-enabled project in the first place (`20260913010000_client_requests_portal_enabled_gate.sql` gates INSERT), so a legitimate accept flow always has portal on; the gate only bites the rare "portal was turned off after the request was submitted" case, tested explicitly (`f006n-unguarded-task-rpcs.test.ts`, "a request on a portal-disabled project is rejected even for a legitimate member").
  - Structure for F016: membership lookup → role bar → (explicit client-cannot-accept-own-request bar) → portal gate → already-accepted check → row lock/mutate. Left the comment block in the migration itself naming this sequence and suggesting the pricing check land right after the portal gate, before the row lock, so F016's worker doesn't have to re-derive the auth preamble from scratch.
  - Also pinned `search_path = public, pg_temp` (the original was `search_path = public` only, no `pg_temp`) — consistent with every other hardened function in this mission (F006i/F006l precedent) and closes the same `pg_temp`-shadowing class of risk, though not itself part of this feature's named finding.

- **`revoke all ... from public`** (not just `revoke execute`) kept on all five, matching the exact wording every one of the five's *original* migrations already used (`revoke all on function ... from public;`) — confirmed by reading each original file before rewriting; not switched to the narrower `revoke execute` form so the diff is minimal and the effective privilege set is unchanged from before (all five had `revoke all` already; F006n's job was adding checks, not changing the revoke).
