## Decisions made
- **Snapshot mechanics resolved without a schema change.** `approval_requests.title`/`.description` have no live FK/trigger binding back to the subject task or doc (verified by reading `supabase/migrations/20260916010000_approval_requests.sql` in full) — nothing ever re-syncs them after INSERT. Writing the dialog's (subject-prefilled, team-editable) title/message into those two columns at insert time is therefore *already* an immutable snapshot by construction. This resolves what first read as a conflict in the spec's section 3 ("task subject → store title + description") vs. section 1 ("Fields: what is being approved … message to the client") — the same two columns satisfy both: title = "what is being approved" (defaults to the task's title), description = "message to the client" (defaults to the task's description). Only a doc's full body doesn't fit that shape (arbitrarily large, and a client should see the document as it was, not a truncated echo in a text column) — that's the only case that gets an out-of-band Storage snapshot.
- **Doc-body snapshot: only the bucket is reused, not the RLS policies.** `supabase/migrations/20260818050100_create_attachments.sql`'s `task-attachments` bucket policies are keyed to a `{task_id}/…` path joined against the `attachments` table — that shape does not describe a doc-body snapshot at all (no task, no `attachments` row). Per the spec's own "reuse the existing attachments storage bucket and its policies," I reused the BUCKET literally (same bucket id, `task-attachments`) and namespaced the object under `approval-requests/{request_id}/doc-snapshot.md` (not a valid task uuid as the first path segment, so it can never collide with or be reached by either existing storage.objects policy). The actual write goes through the admin/service-role client, which bypasses Storage RLS the same way it bypasses table RLS everywhere else in this codebase (`lib/actions/profile.ts`'s `uploadAvatar` is the same shape). **This is a real, honestly-flagged gap, not a silent one:** no storage.objects SELECT policy grants a client or a team member's own session read access to this path today — only the admin client can read it back. F009 (Portal: Approvals view) needs to either add a SELECT policy scoped through `approval_requests`' own existing SELECT policies (the same join shape the original attachments policy used), or read it via a server-side signed-URL action gated by that same authorization. See "Out-of-scope work needed" below.
- **AS-020's error message and the DB backstop.** `isTaskClientVisible()` (`lib/queries/approvals.ts`, built by F007 specifically for this call site — see that feature's own handoff) is the single source of truth this action's check uses, per F007's explicit "Out-of-scope work needed" note. The database's `approval_requests_insert_team` policy enforces the identical rule a second time for a raw PostgREST insert; this action's own check exists only to produce a specific, actionable error message before that round trip.
- **Decision-owner gate is enforced server-side too, not just in the dialog.** The spec's section 1 says the dialog "blocks submission" when there's no owner for the chosen decision type; I additionally re-check this in `requestApproval` itself (a `project_decision_owners` lookup before the insert), matching this mission's repeatedly-stated concern about "a gate applied in one query and forgotten in the next" (F007's own migration header makes the identical point about AS-020). Covered by an explicit failure test ("raising a request for a decision type with no project_decision_owners row is blocked… and writes no row").
- **`withdrawApproval` implemented here, per F008's own "Files (approximate)" list**, even though F007's handoff flagged a caveat: "the RLS update policy only permits pending → pending, a withdraw RPC/action will need its own path." That caveat is about a raw, RLS-scoped client write; `withdrawApproval` writes through `ctx.admin` (service-role, bypasses RLS) exactly like every other mutating action in this codebase (`lib/actions/phases.ts`), so the RLS policy's narrowness never applies to it. The `prevent_approval_request_settled_update` trigger (which fires for every caller, including service-role) still correctly rejects a second withdraw of an already-settled request — covered by a test. F010 (Team UI: approvals queue) is expected to be the feature that puts a "withdraw" button in front of this action; it did not exist before this feature.
- **No team-side "project's approvals area" route exists**, and F008's own "Files (approximate)" list names "project settings route" with no separate approvals-area route — so the standalone artifact entry point (section 1's third bullet) was added to project settings, next to the new "Who approves what" section, rather than inventing a new page. Grounded in the spec's own Files list, not assumed.
- **Doc "kind" default does not exist in this schema.** The spec's example "a doc of kind `training` is `content`" presumes a `docs.kind` column that does not exist anywhere in `supabase/migrations/20260904010000_docs_system.sql` or any later docs migration (grepped for "kind" across `lib/queries/docs.ts`, `lib/actions/docs.ts`, and every docs migration — no match). Doc-subject requests default to `decisionType = "content"` (docs are written material; a reasonable, always-valid, user-editable default) rather than inventing a heuristic with no data to back it. The task-side default (`taskTypeSystemKey === "page"` → `"brand"`) IS backed by real, already-existing schema (`tasks.task_type_id` → `system_key`, F006c) and is implemented exactly as spec'd.
- **Decision-owner picker's UI gate mirrors the action's actual `withAuthz` gate.** `setDecisionOwner`/`requestApproval` both use `withAuthz`'s default `canWrite` (not `canManageProjectMembers`, which the project settings page uses for the member list next to it) — the settings page's new section computes `canWrite({ role: workspaceRole })` separately from `canManage`, per AS-230's "one permission helper backs both UI gating and the server-side re-check" rule: the UI predicate must match whichever predicate the action itself actually enforces, not a different one that happens to live on the same page.
- **`getDecisionOwnersForDialog` needed a standalone `projectIdSchema`.** `requestApprovalSchema` is wrapped in `.superRefine()`, which returns a `ZodEffects` — `.pick()` (the pattern `lib/actions/phases.ts`'s `getProjectPhaseOptions` uses against `createPhaseSchema`, a plain `z.object`) isn't available on it. Added a separate plain-object schema instead of restructuring the refined schema.
