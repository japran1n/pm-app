### Regression 2 — F009b's AS-022 tests expect the old error code
Read `20261021010000_f009d_no_owner_refusal_message.sql`'s own header in full: F009d deliberately split the "owns no decision type" branch out of `assert_portal_task_actionable_by_client`'s shared `'task not found'` (P0001, implicit) oracle into its own named `42501` with an explicit message, matching `decide_approval_atomic`'s existing `RLS_DENIED = 42501` for the identical situation on the Approvals-view surface. This is deliberate and correct, not an accident:
- `42501` (`insufficient_privilege`) is the semantically honest Postgres code for "you are authenticated, visible, and looking at a real pending item, but you personally are not authorized to decide it" — the caller has already passed membership, visibility, portal-enabled, and pending-state checks (all of which stay merged under the oracle-neutral P0001 `'task not found'`, deliberately, to avoid leaking existence/visibility facts) by the time this branch runs, so naming the refusal leaks nothing new.
- F009d's own stated goal (per its migration header and its handoff) was exactly to stop this refusal from reading as a generic "Something went wrong" — an oracle-neutral, uncoded P0001 defeats that purpose by keeping it indistinguishable from a real backend failure to any caller/test keyed on error code.
- Grepped `lib/`, `app/`, `components/` for `P0001`: zero hits. Nothing in the application branches on that code for this or any path, so retargeting these three tests at `42501` does not require any code change beyond the tests themselves.

Updated the three affected tests (two "owns nothing" tests for `approve_portal_task_atomic` and `request_portal_task_changes_atomic`, plus the "both surfaces agree" pairing test) to assert `RLS_DENIED` (42501) and the F009d message, instead of `TASK_NOT_FOUND` (P0001). Left the "client of another project" and "portal disabled project" tests unchanged at P0001 — those hit different branches of the same function (non-member, portal-off) that F009d explicitly left merged under the oracle, confirmed by re-reading the migration's own branch-by-branch header.
