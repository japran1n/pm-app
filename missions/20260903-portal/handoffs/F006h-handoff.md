## Decisions made

**Defect 1 (BX-1) — forward-only corrective migration, not editing the applied file.**
Chose `supabase/migrations/20260917010000_task_type_system_key_backfill_collision_fix.sql`, a new migration, over editing `20260915020000_task_type_system_key_backfill_widen.sql` in place. Reasoning (also written into the corrective migration's own header comment):
- `20260915020000` is already recorded as applied on the live database this mission targets (confirmed: `npm run db:apply` for it would have printed "already applied — nothing to do" per `scripts/apply-migration.mjs:57-60`, and this session's two new files applied cleanly against that same already-migrated database). Editing that file's *content* in place has zero effect on any database where it is already recorded — the version ledger keys off the 14-digit timestamp/filename, not a content hash, so `apply-migration.mjs` never re-runs a recorded version regardless of what the file now contains.
- The mission's own prior scrutiny report already reached this conclusion and wrote it down: `missions/20260903-portal/milestones/M1-scrutiny-2.md` line 374, FU-15: "Add a new migration (do not edit `20260915020000`; it may already be recorded as applied on some instances)". This is a grep-verified, named citation, not an inferred precedent.
- A new migration protects every environment uniformly: one that already ran the buggy file (this one) gets the fix for the first time here; one that has not yet reached `20260915020000` will still hit the SAME bug there first (unchanged — editing history is deliberately not being done), but since Postgres runs the whole file as one implicit statement via `scripts/apply-migration.mjs:63`, a 23505 there changes nothing — the failing file leaves `task_types` exactly where `20260912010000` left it, which is exactly the starting state this corrective file's own guard is written for. So the corrective file still converges that database to the correct end state on the very next migration it can apply, even though `20260915020000` itself remains a permanently-failing, un-recorded step for that specific colliding shape (by design — the decision was not to make that step succeed, only to make its failure harmless and recoverable).
- **What "migrates cleanly to head" actually means for this decision, stated precisely so it isn't glossed over:** it does NOT mean the historical `20260915020000` file itself stops erroring on a database that already holds the colliding shape when that file is applied to it for the first time — it still errors there, deterministically, forever, because that file is not being edited. What it means is that the corrective migration converges any such database to the correct final state with no error and no operator remediation beyond skipping (not fixing) that one historical file, exactly the way FU-15 frames it. The **proof** below constructs and runs exactly this sequence.

Two corrections in the new file beyond the missing collision guard (per FU-15's own recommendation): (a) `not exists (select 1 from task_types t2 where t2.workspace_id = t.workspace_id and t2.system_key = 'page')` excludes a workspace that already has a tagged row from the candidate set entirely, rather than only de-duplicating among candidates; (b) `, id` appended to the `distinct on` `order by` for a deterministic tiebreak. The file is idempotent by construction (re-running is a no-op — proved in the regression test).

**Proof, not assertion, per the DoD's explicit instruction.** No Docker is available in this environment (`docker`, `colima`, `podman`, `lima` all absent — checked directly), so `supabase start` (the mechanism `.github/workflows/ci.yml`'s W6 rewrite uses for CI, per `missions/20260828-hardening/handoffs/W6-handoff.md`) could not be used to replay the FULL 159-file migration history against a throwaway stack. A local Postgres 16 (Homebrew, already running) with `psql`/`initdb` WAS available, so I built a minimal Supabase-compatible scaffold (an `auth` schema with a stubbed `auth.uid()`/`auth.users`, and the `authenticated`/`anon`/`service_role` roles — exactly the primitives the task_types migration chain references) and replayed the ACTUAL, VERBATIM migration files that create or alter `task_types` and its dependency closure, in true chronological order: `20260817222532_create_workspaces.sql`, `20260817222822_rls_workspaces.sql`, `20260818004413_create_projects.sql`, `20260818013434_create_tasks.sql`, `20260903040000_task_types.sql`, `20260912010000_task_type_system_key.sql` — grep-confirmed (`grep -rl "task_types" supabase/migrations/*.sql`) to be the complete, ONLY set of files that touch `task_types`'s structure besides the widen migration itself. Against that real Postgres instance I: called the real `create_workspace_with_owner` RPC (seeding the tagged `Page` row exactly as production does), inserted an untagged `Sida` row, applied the real unmodified `20260915020000` file and watched it fail with the exact `23505` on `task_types_workspace_id_system_key_idx` the report describes, confirmed the failed file left no partial state, then applied the real `20260917010000` corrective file and confirmed: no error, the tagged `Page` row untouched, the `Sida` row deliberately left untagged, a second run is a no-op, and a SEPARATE workspace with no pre-existing tagged row still gets its lone untagged candidate tagged (the original migration's actual purpose, unregressed). This exact sequence is now a committed, re-runnable regression test: `tests/integration/f006h-migration-collision-regression.test.ts` (ran it — 2/2 pass, output captured in Commands run above).

**Defect 2 (AS-009/AS-012, template phase visibility) — `client_visible` added as a third captured field, defaulted `true` for pre-existing data, no RPC signature change.**
- `projectTemplatePhaseSchema` (`lib/validation/templates.ts`) gained `client_visible: z.boolean().default(true)` — `.default()` not `.optional()` so a template payload saved before this fix (no `client_visible` key on a phase element at all) still parses, and resolves to the same `true` `create_project_from_template` already defaulted it to before this fix — zero behavioural change for pre-existing data.
- `saveProjectAsTemplate` (`lib/actions/templates.ts`) now selects `client_visible` alongside `name, client_description` and threads it into the payload.
- `create_project_from_template` (`supabase/migrations/20260917020000_create_project_from_template_phase_visibility.sql`) inserts `client_visible` from the jsonb (`coalesce((v_phase->>'client_visible')::boolean, true)` — same defaulting logic as the Zod schema, applied at the SQL layer for direct-RPC callers). No signature change (still 6 args, same order) — `create or replace function` used directly rather than the drop-and-recreate `20260915010000` needed, since Postgres only forces a drop when the parameter list itself changes.
- Confirmed via `npm run db:gen-types` that `database.types.ts` is byte-identical after applying both migrations (`p_phases` was already typed as opaque `Json`, so no generated-type change was expected or produced).
