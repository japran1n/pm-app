## Decisions made
- **Reused `AttachmentDropzone` and the `task-attachments` bucket/path convention, but NOT the `uploadAttachment` Server Action.** Grepped `lib/auth/permissions.ts`: `canWrite(ctx) = ctx.role !== "viewer" && !isClient(ctx)` — a portal client is unconditionally rejected by `canWrite`, and `uploadAttachmentForUser` (`lib/attachments/upload.ts:177`) gates on exactly that check. The spec's "reuse the existing storage bucket and policies" is satisfied by reusing the SAME bucket name, the SAME `{task_id}/{filename}` object-path convention, and the SAME size/MIME validation schema (`uploadAttachmentSchema`) inside a new action (`lib/actions/portal-deliverables.ts`) that authorizes the caller itself (active membership + `isProjectVisibleToCaller` + `portal_enabled`) instead of `canWrite` — mirroring `getAttachmentSignedUrl`'s own three-check shape for a client read path, applied here to a client write path.
- **A new RPC, `mark_deliverable_delivered_atomic`, does the actual state transition — not a plain RLS-respecting UPDATE.** This is the real enforcement of "a client cannot set a deliverable to accepted through any path": the function's own SQL signature (`p_deliverable_id uuid` — no decision/state argument at all) makes reaching `accepted` through it structurally impossible, not merely validated against. Authorization mirrors `accept_client_request_atomic` (20260921010000) exactly: re-select the caller's real role, gate on `is_project_visible_to` + `is_project_portal_enabled`, same predicates every other client-write RPC in this schema already uses. Proven by `tests/integration/f014-mark-deliverable-delivered.test.ts`'s negative tests, including one that calls the RPC with a `p_decision` argument it does not accept (function-not-found, not a silent ignore) and one that proves `accept_deliverable_atomic` (F013's own RPC) independently still rejects a client.
- **"What it holds up" (AS-029, AS-031) is derived through the admin client, gated on `client_visible`, mirroring `getPortalLiveNow`'s existing precedent exactly** (`lib/queries/portal.ts:709-797`, grepped and read before writing `resolveHoldsUpContext` in `lib/queries/deliverables.ts`): a task's own page slug/title is used only when the task is `client_visible`; otherwise the fallback is the task's PHASE name, also gated on the phase's own `client_visible` column — never an internal task's title or an internal-only page slug leaking through a "holds up" label. This is the SAME derivation function both the Your list row's short label ("Holds up build of /blogg") and the risk banner's full sentence use, so the two can never independently disagree on what a task "counts as" (this feature's own instruction: "Derive it — never ask the PM to type it").
- **The progress header's four segments reuse `StatusDistribution` (F005) via a mapping from the five-value `state` column onto the four existing `ClientBucket`s**, rather than writing a second distribution component (explicitly prohibited by both `plan.md`'s Design constraint #2 and this feature's own spec): `accepted`/`waived` -> `done`, `delivered` -> `progress` (sent, awaiting our review), not-yet-delivered-and-not-due -> `waiting` (open, on the client), not-yet-delivered-and-past-due -> `blocked`. This is also what each outstanding row's own left-rule token is derived from — one classification, not two.
- **The risk banner shows at most ONE risk** (the single worst/earliest-due overdue blocking deliverable), not a list of every overdue item — this feature's own spec, verbatim ("naming the worst one and what it moves"), and matches the existing `PortalRisk[]` return shape (`getPortalRisks` still returns an array, so a second risk *source* — e.g. an aging approval, F007/F009's own unbuilt work — can be appended later without changing `RiskBanner`'s props at all).
- **The risk sentence's "what moves" is the project's `target_launch_date`**, not the deliverable's own due date — re-read the spec's own literal example ("The Blogg page cannot be built without its copy, and 18 Nov moves with it") and concluded the date that "moves" has to be the client's own overall commitment, not the internal item's due date (which has already passed by the time this banner fires at all). Falls back to "the launch date moves with it" (no specific date) when the project has no `target_launch_date` set, rather than omitting the clause entirely — the banner's own point is "there is a real consequence", which stays true even without a specific date to cite.
- **AS-003 required no code change.** F012's own handoff already made `deliverablesPastDue` a real, RLS-respecting count, and F003/F006f already wired it into the sidebar with tested badge-rendering behaviour (`components/portal/portal-sidebar.test.tsx`). This feature's own spec section 5 ("goes live here") is satisfied by AS-031/AS-029/AS-030's work giving the underlying deliverables table real client-facing meaning — grepped and re-ran the existing tests to confirm rather than re-implementing anything.

## Autonomous decisions
AUTONOMOUS_DECISION: Built a new client-authorized Server Action + RPC pair instead of reusing `uploadAttachment`/`accept_deliverable_atomic` as literally-named functions, because `canWrite` (the gate on the former) and `is_project_workspace_writer` (the gate on the latter's accept path) both unconditionally exclude the `client` role by design — reusing either verbatim would have made the feature non-functional for its own primary user. The spec's "reuse the existing storage bucket and policies" is honoured at the level of the BUCKET, PATH CONVENTION, and VALIDATION SCHEMA, all literally reused; only the authorization gate (which the spec does not name) differs, and is documented in each new file's own header comment with a grep-backed citation of exactly which existing predicate would otherwise have blocked a client.
AUTONOMOUS_DECISION: Mapped the progress header's four segments and each row's left-rule token from `state` + `due_at` onto the existing four `ClientBucket`s (see Decisions made above) — the spec named "accepted, still open, past due" (three) but also said "four-segment bar", so a fourth segment ("delivered, awaiting review") was inferred as the gap and mapped to the `progress` bucket, since a delivered-but-unreviewed item is neither "still open" (client already acted) nor "past due" (the immediate deadline is met) nor yet "accepted".
AUTONOMOUS_DECISION: The risk sentence's date is the project's `target_launch_date`, not the deliverable's own `due_at` — see Decisions made above for the reasoning; this was the one genuinely ambiguous reading of the spec's literal example and no other date field in this schema fits "what moves" as well.
