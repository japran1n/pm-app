## Decisions made

- **Root cause pinned exactly per the spec: `projects_assign_key` (BEFORE INSERT, `20260819061129:196-200`) sorts before `projects_enforce_field_role_allowlist` (BEFORE INSERT, `20261017010000:246-247`) by trigger name (`assign_key` < `enforce_field_role_allowlist`), so by the time the guard runs on INSERT, `NEW.key` already holds a real generated key (`assign_project_key()`, `20260819061442:33-45`, overwrites it whenever null or the schema's sentinel default `''`, `20260819061442:26-27`) — distinct from the column's own `''` default — and the guard's generic "any other column must match its default" branch (INSERT-only, `20261017010000`/`20261019010000`) raises `42501` for every authenticated project insert.**
- **Fixed with the bypass-flag technique F025c established, not a new allow-list entry, matching the spec's explicit instruction** — reused the existing `app.projects_field_guard_bypass` GUC (F025c) rather than inventing a second flag, since `key` and `task_counter` are the same class of problem (an application trigger's own legitimate write, not a person's).
- **Deviated from F025c's exact bracket shape, deliberately, and this is the one genuinely non-obvious decision in this feature.** F025c's `assign_task_number()` sets the flag "on", performs its own separate `UPDATE projects`, then turns the flag "off" itself, all within its own function body — the guard it re-enters is invoked once, for that one statement, on a *different* row (`tasks` is the table being inserted into; the `UPDATE` on `projects` is a side effect). `assign_project_key()` has no such separate statement: it writes `NEW.key` directly, inside the SAME BEFORE INSERT trigger chain as the guard, on the SAME row, in the SAME statement. Two consequences followed, discovered in this order by actually running the tests, not reasoned in advance:
  1. **The on/off bracket cannot live inside `assign_project_key()`'s own body.** Turning the flag "off" before `assign_project_key()` returns means it is already "off" by the time the guard trigger fires next (same statement, immediately after, by trigger name). Fix: `assign_project_key()` sets the flag "on" and leaves it on; the guard consumes it itself (turns it back "off" the instant it observes it "on") at the top of `enforce_projects_field_role_allowlist`, which already runs immediately after in the same statement. This closes the leak-into-a-later-statement risk (`is_local = true` only reverts a GUC at transaction end, not statement end) without requiring `assign_project_key()` to coordinate with a trigger it has no direct call into.
  2. **A blanket bypass (early `return new` when the flag is "on") is WRONG for the INSERT case, and this was caught by a test, not spotted by inspection.** I first wrote the guard's bypass check as `return new` unconditionally, matching F025c's shape exactly. This made `tests/integration/f020b-projects-allowlist-guard.test.ts`'s own regression test — "a client is rejected setting baseline_frozen_at on INSERT" — go from "passing for the wrong reason" (pre-fix: rejected because of the `key` collision, not the `baseline_frozen_at` check) to **actively passing the client's forbidden write through** (post-naive-fix: `assign_project_key()` sets the bypass flag because the client supplied no `key`, and the guard, seeing the flag "on", returned `new` unexamined — skipping the `baseline_frozen_at` writer-role check on the SAME row, in the SAME statement, entirely). This is exactly the "blanket bypass reopens a hole" risk the spec's own framing warned about, just one level deeper than the allow-list-widening risk it named explicitly. Fixed by scoping the flag's effect for the INSERT case: instead of returning early, the guard adds `'key'` to its identity-column set for that one invocation only (a local variable, `v_key_bypass`, not a schema or allow-list change), then runs every other check — the default-diff loop for all other columns, and the writer/owner-admin role checks — exactly as before. The two behaviors (whole-row skip for `assign_task_number()`'s UPDATE vs. column-scoped skip for `assign_project_key()`'s INSERT) are told apart by `TG_OP` inside the guard's single shared bypass-check block, which is safe because each setter only ever fires the trigger operation named: `assign_task_number()` only sets the flag around an UPDATE on `projects`; `assign_project_key()` only sets it inside a BEFORE INSERT trigger.
- **Verified the fix is not a hole via the same test that caught the naive version**, plus the new clean-insert test: the client/baseline_frozen_at-on-INSERT test now asserts the SPECIFIC writer-role rejection message (`"Only workspace members with write access can change a project's launch, warranty or baseline-freeze fields"`) and explicitly asserts the generic "not an allow-listed column" message is NOT present — proving the `key` collision is gone AND the intended check still fires, on the same row, in the same statement, for a caller that supplies no `key` at all (the exact case a naive fix breaks).

- **Why the F025c precedent could not be copied verbatim, grep-verified, not assumed:** `assign_task_number()`'s bracket (`perform set_config(..., 'on', ...)` / `UPDATE projects ...` / `perform set_config(..., 'off', ...)`, all three statements inside the SAME function body, `20261019010000_f025c...sql:216-232`) works because that function is a trigger ON `tasks`, and its `UPDATE projects` is a second, independent SQL statement it issues itself — it controls both edges of the bracket. `assign_project_key()` is a trigger ON `projects` itself, in the same BEFORE INSERT chain as the guard it needs to step around; it can set the flag but cannot close the bracket before the guard reads it, and — the part that actually broke a test when tried the naive way — it cannot safely skip the WHOLE guard for the row, because other columns of that same row (e.g. `baseline_frozen_at`) may carry a caller's illegitimate write in the very same INSERT.
