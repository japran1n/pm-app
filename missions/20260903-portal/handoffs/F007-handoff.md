## Decisions made
- `approval_requests.subject_id` carries no foreign key (polymorphic across `tasks`/`docs`/`project_phases` depending on `subject_type`), matching the identical, already-established precedent in `audit_log.target_id` (`20260821211226_create_audit_log.sql:65-74`) for the same "points at one of several tables via a sibling discriminator column" shape.
- Found and closed a real gap while writing the RLS section: the spec's "Team: ... project visible" description for UPDATE, read literally (`is_project_workspace_writer(project_id)` alone), would let ANY project-writer team member set `state = 'approved'` and `decided_by = <themselves>` directly through their own session — completely bypassing `decide_approval_atomic`'s AS-022 ownership check. `decide_approval_atomic` itself is unaffected (SECURITY DEFINER functions bypass RLS as the function owner, same as `approve_portal_task_atomic`/`accept_client_request_atomic`), but the team UPDATE *policy* on the table itself would have opened a second, unguarded path to the exact outcome AS-022 says only the named decision owner may reach. Fixed by narrowing `approval_requests_update_team`'s WITH CHECK to `state = 'pending' and decided_by is null and decided_at is null` — a team member can still edit a pending request's own metadata (title/description/due_at/phase_id), but cannot settle it by any route except the RPC. Covered by a new regression test (`AS-022 regression: a team member ... cannot self-approve via a direct UPDATE`).
- AS-020 enforced at the database layer (a CHECK-shaped `exists(...)` clause inside `approval_requests_insert_team`'s WITH CHECK), not only left to F008's future Server Action — a raw PostgREST insert bypassing the app entirely is rejected the same way. This mirrors the mission's explicit warning about gates "applied in one query and forgotten in the next."
- Client SELECT's extra `client_visible` gate applies ONLY when `subject_type = 'task'`, per the feature spec's own clarified instruction, not to doc/phase/artifact subjects — raising a doc/phase/artifact-subject approval IS the team's deliberate act of sharing it (there is no separate `client_visible` flag on a doc to check anyway; `docs` has no such column in this schema as of this feature).
- `decide_approval_atomic` defensively re-derives whether the subject task actually belongs to the approval's own project before passing `p_task_id` to `create_notification` — that RPC's own F320 hardening (`20260823110000`) hard-rejects a `task_id`/`workspace_id` mismatch, which would otherwise abort an entire, otherwise-valid decision if `subject_id` (which carries no FK) ever pointed at a stale/foreign task id.
- `write_audit_log_entry` (`20260821211226`) and `create_notification` (`20260823030000`, hardened through `20260823110000`) are called via `perform public.<fn>(...)`, never a direct `insert into audit_log`/`insert into notifications` — both tables have no INSERT policy for any role by design, exactly as the feature spec's step 4/6/7 instructs.
- `decide_approval_atomic` validates `p_decision in ('approved', 'changes_requested')` explicitly — `'withdrawn'` is a team-only transition (F010's remind/withdraw), not reachable through this RPC, and `'pending'` is nonsensical as a target decision.
- `getPortalBadgeCounts` (`lib/queries/portal.ts`) now counts `approval_requests` where `state = 'pending'`, replacing the `tasks.pending_client_approval` proxy F003 shipped as a stub-turned-first-body (this is the exact hand-off the F003/F006 comments on that function anticipated). This is the same table `getOpenApprovalsForClient` reads, so the sidebar badge and the approvals list it links to can no longer disagree the way the M1 scrutiny report's original AS-002 finding described (a different, now-fixed defect from a prior feature).
- No DELETE policy on `approval_requests` for any role, matching `audit_log`'s "no UPDATE/DELETE policy at all, for any role" posture — a settled approval is history; a pending one a team member wants to retract should transition to `'withdrawn'` (F010), not vanish.
- `project_decision_owners` gets a full team CRUD policy set (`is_project_workspace_writer` for insert/update/delete, `is_project_visible_to && not is_project_client` for select) even though no UI in this feature writes to it yet — the spec's RLS section requires the table to be readable/writable by the team, and a future settings UI (not spec'd as part of this feature) will need exactly this shape; seeding for this feature's own tests goes through the admin client.

That write would go through the same `approval_requests_update_team` policy this feature added (it permits `state = 'pending'` only, so a withdraw RPC will need its own SECURITY DEFINER function, or the update policy will need widening — worth deciding explicitly in F010 rather than assumed here).
- F011 (Request changes creates work) needs to extend `decide_approval_atomic` (or add a second RPC) to create a task from a `changes_requested` decision's note, assigned to the original requester, linked back to the approval — this feature only records the decision and the note; it does not yet create any follow-up work.
- No settings UI exists yet for assigning `project_decision_owners` rows (who owns which decision type per project) — this feature only ships the schema/RLS; a PM currently has no in-app way to set this up, only the admin client (used for this feature's own test fixtures).
- `project_phases.id` is referenced by `approval_requests.phase_id` but nothing in this feature ever sets it — left null-capable per the spec's column list; a future feature phase-scoping approvals (not currently planned) would set it.
