## Autonomous decisions
AUTONOMOUS_DECISION: Chose to gate `toggleReaction()` on both channels being `SUBSCRIBED` rather than firing it as soon as the filtered channel is ready (with the probe just joining "whenever"). Rationale: if the probe subscribes late, a null result from it is uninformative — the experiment must give the probe the same fair chance the filtered channel gets, or a "neither receives" outcome could actually mean "the probe wasn't listening yet," which is a different failure mode than "the transport lost it." This does slightly change the filtered channel's own SUBSCRIBED->toggle timing (it now also waits on the probe's channel handshake), but per the F073/F074 comments already in this file, an extra local channel handshake is ~7ms — negligible against the existing 45000ms `HARD_TIMEOUT_MS` ceiling and irrelevant to the elapsed-time measurement, which is still timed from the filtered channel's own `t0`/`SUBSCRIBED`, not from the probe's.

## Notes for the next worker

**Correction to the prompt's premise, provable by grep:** the prompt asked me to check whether `tests/integration/comment-format-realtime.test.ts`'s `postgres_changes` subscription to `comments` (the passing test) omits a row filter. It does not. `grep -n 'filter: \`task_id=eq' tests/integration/comment-format-realtime.test.ts` returns one hit, at line 322, inside that file's `AS-312: an independent Realtime subscriber on comments:<taskId> receives a new formatted comment's body_json via postgres_changes INSERT` test — it uses the identical `filter: \`task_id=eq.${taskId}\`` shape as the failing reaction test. So "filtered vs unfiltered" is **not** in fact the documented difference between the passing `comments` test and the failing `comment_reactions` test; both already filter. That does not make the F101 experiment worthless — it is still the case that no CI run has ever confirmed a filtered `comment_reactions` postgres_changes subscription delivers on this stack post-F098 (the leak's removal), and the unfiltered probe is still a clean, minimal-risk way to bisect "is filtering itself broken on this stack" from "is something else broken" — but the working theory that `comments` passes *because* it's unfiltered is false and should not be carried into the next worker's reasoning. It also means: if the probe channel *also* fails to receive, that is now a stronger signal that something is broken beyond `filter=` handling specifically (since the sibling `comments` test with an identical filter shape passes), pointing at something particular to `comment_reactions` (its RLS policies, `REPLICA IDENTITY FULL`, or table-specific WAL/publication behavior) rather than at filter parsing in general.

**What each of the three outcomes proves, and what to do next:**

1. **Unfiltered probe receives, filtered channel does not** (`[AS-369][F101-probe] ... received ...` appears, `[AS-369] postgres_changes event NOT received ...` appears): the local stack's filter evaluation (`task_id=eq.<uuid>`) is specifically broken for `comment_reactions` on this stack, despite the identical filter shape working for `comments` in the sibling file. Next: compare `comment_reactions` and `comments`' column types/casts for `task_id` (e.g. a UUID-vs-text coercion difference in the Realtime filter parser) and check the local Realtime container's version/config against what filter changes it supports for `comment_reactions` specifically — start from `pg_publication_tables`/column list already gathered in this feature's diagnostic step, not from scratch.
2. **Both receive**: the filter is fine, and whatever was blocking delivery before F098's leak-closure fix is something else — re-open the search for a stack-specific bottleneck (WAL throughput, worker contention, connection pool limits under `test:realtime`'s serial execution) rather than filtering. Given F098 already closed the leaked channel that was producing false "arrivals," and no leak remains, this outcome would mean delivery genuinely works and the historical failures need a fresh root-cause pass unrelated to filters or leaks.
3. **Neither receives**: the problem is upstream of filtering and upstream of the leak — likely nothing in `comment_reactions` writes ever reaches any subscriber on this local stack at all (even though the `comments` sibling test's subscription — also filtered, also to a table in the same publication — does work). Next: since both tables are confirmed in `pg_publication_tables` with correct `pubinsert`, the next thing to check is table-specific: `comment_reactions`' `REPLICA IDENTITY FULL` (stronger than `comments`' `default`) is worth testing as a variable in isolation — try temporarily setting `comment_reactions` to `REPLICA IDENTITY DEFAULT` locally (in a scratch/throwaway migration, not committed) and re-running the probe to see if that specific difference is causal, since it is the only schema-level difference the diagnostic surfaced between the passing and failing tables.

**Finding on the sibling scoping test (as requested):** `test_AS_369_the_subscription_is_scoped_at_the_transport_level_a_second_tasks_channel_never_receives_a_reaction_event_for_this_task` (same file, second `it`) asserts two things: `expect(received).toBe(true)` (the scoped channel, filtered to *this* task, DOES receive its own task's toggle) and `expect(leaked).toBeNull()` (a channel filtered to a *different*, unrelated task never receives it). If filtered `comment_reactions` subscriptions never deliver on this stack at all (outcome 1 or 3 above), then `received` would be `false`, `expect(received).toBe(true)` would **fail**, and the test would not pass — so this second test is not silently vacuous today: if the main hypothesis (filtered delivery is broken) is true, this test already fails loudly rather than passing for the wrong reason, because it has a positive-control assertion (`received === true`) baked in ahead of the negative one (`leaked === null`). The risk the prompt described (a test that "passes by receiving nothing") would only materialize if filtered delivery is broken in a way that is *asymmetric* by task_id — e.g. if a stale/leaked channel from an earlier test (this file's own first `it`, or another integration file running concurrently) happens to still be bound and coincidentally deliver the event that makes `received` true, while the truly-independent `otherTaskId` channel correctly gets nothing. That can't be ruled out by reading the code alone; it depends on runtime channel-leak state, which is exactly what F098's cleanup already reduces (both tests in this file now explicitly close their channels: `reactionChannel` at the end of the first `it`, `scopedChannel`/`unsubscribeOther` in the second `it`'s `finally`). Given F098's cleanup is in place, I judge the "passes for the wrong reason" risk on this second test to be low today, but it should be re-examined once outcome 1/2/3 above is known — if outcome 1 (filtered specifically broken) is confirmed, immediately re-check whether `received` in the second test is coming from a genuine same-run delivery or a residual channel from the CI run's other concurrent test files, since `test:realtime` is documented (F092) to run this file alone but other suites in the same job may still hold `comment_reactions` rows/channels open depending on job ordering.
