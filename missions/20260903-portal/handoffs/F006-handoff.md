## Decisions made
- **AS-002's `approvalsAwaiting` counts `tasks.pending_client_approval = true`, not a new table.** F007's dedicated `approval_requests` table doesn't exist until M2, and plan.md assigns AS-002 to F006 alone (grepped every feature entry in `plan.md`; no other feature lists AS-002 or AS-003). `pending_client_approval` is the exact same real signal this app already treats as "an approval awaiting the client's decision" everywhere else in the portal — `getPortalOverview`'s own "waiting on you" list and `PortalOverviewLive`'s realtime predicate both key off it verbatim, and this feature's OWN spec text says the same thing about the waiting-on-you strip: "it shows tasks flagged pending_client_approval as it does today; F009 replaces the source with approval_requests without touching this component's shape." Applying that exact reasoning to `getPortalBadgeCounts`'s body (not touching any caller, per F003's own explicit extension-point design for this function) is not a fabricated number — it is the one real table this concept currently has, and F009's hand-off note applies to this function's body too, not only `PortalOverviewLive`'s.
- **AS-003's `deliverablesPastDue` stays a documented zero.** Unlike approvals, there is no existing table or column anywhere in this schema that means "a thing the client owes" (grepped for anything resembling it; `client_requests` is the client's own submitted requests, a different concept). AS-028 ("a project can hold a list of items the client owes...") is F012's wholly new entity (M3). Zero is the honest, vacuously-true count for an entity that doesn't exist yet — not a placeholder standing in for a real number, and not silently invented from an unrelated table the way that would have been a real risk here.
- **`getPortalLiveNow` and `getPortalTeam` read through the admin client from the FIRST query, not just for a display-value lookup.** Every other admin-client read this file already had (`getPortalPages`'s assignee role, `resolvePeople` itself) is resolving a DISPLAY value for a row the client already reached through their own RLS-scoped read. That justification does not apply here: `active_timers_select_active_members` and `project_members_select_active_members` (both hardened in 20260902020000) exclude a client role from reading ANY row on these two tables (the first, entirely; the second, every row but their own) — there is no client-visible row on either table to begin from. Both functions instead scope themselves to `project_id`/`workspace_id` (a project the caller already reached through `getPortalProjects`' own `portal_enabled` + membership gate one query earlier in the same request) and re-derive, in TypeScript, the one thing RLS would otherwise have enforced: excluding any row belonging to a client of this same workspace, so a client never sees their own — or a co-client's — presence/membership reflected back at them. Documented at length in both functions' own doc comments so a future reader doesn't mistake this for the same "already-permitted display value" pattern the rest of the file uses.
- **`getPortalLiveNow`'s label falls back to the phase's own name** (not a generic phrase) when the active task is not client-visible, per this feature's OWN clarified spec text verbatim: "a task name only when the task is client-visible, otherwise the phase name." (The older Serbian source doc, `docs/client-portal-sixstar-plan.md` P3, describes a generic "radi se na razvoju" phrase instead — this feature's own newer, mission-specific English spec is the authoritative one and was followed literally, not the older doc.) A task with neither a client-visible flag nor a `phase_id` falls back to a generic, honest "Working on the project" rather than fabricating a label.
- **`getPortalTeam`'s role label is `project_members.project_role` (`lead`/`member`) translated to "Project lead"/"Team member"**, not the assignee's workspace role (owner/admin/member/...) that `getPortalPages`'s "who has it" cell uses (F005). A client-facing "who is on my project" card reads better with a role tied to THIS project than the agency's internal workspace hierarchy — "Admin" or "Owner" is internal jargon a client has no context for, where "Project lead" directly answers "who do I talk to."
- **Phase-state colour mapping**: `active` -> `--status-progress`, `blocked` -> `--status-blocked`, `done` -> `--status-done` (the F004 status tokens, reused verbatim — no new hex literal). `not_started` has no status-token counterpart (the four `--status-*` tokens are the client-facing STATUS-PILL bucket vocabulary — waiting/progress/blocked/done — a different axis that happens to share three of four NAMES with phase STATE) and renders muted (`fill-muted`/`text-muted-foreground`/`bg-muted-foreground/50`), per this feature's own explicit "not-started phases are muted" instruction. Every bar's state is also stated as text in the row label and the legend — colour is never the only signal (plan.md's Design constraint #4).
- **Dateless-phase fallback**: a phase missing either `plannedStart` or `plannedEnd` gets an equal-width slot sized `chartWidth / (count of dateless phases in this project)`, positioned in the SAME order the phases array already arrives in (by `position`, from `getProjectPhases`). Because every phase is its own ROW (not sharing an x-axis position with any other phase visually), a dateless phase's fallback bar never collides with a dated phase's real-positioned bar — there is no reconciliation needed between the two coordinate schemes, which is what makes "equal-width slots... rather than collapsing to zero width" straightforward to implement correctly.
- **The "today" rule always lands inside the drawn range.** `computePhaseTimelineLayout` extends `rangeStart`/`rangeEnd` to include today before computing the axis, so a project whose only planned phase is entirely in the future (or entirely in the past) still shows the rule somewhere on the chart rather than off either edge.
- **One shared tooltip, positioned as an SVG `foreignObject` inside the same scrollable `<svg>` the bars live in** (not a floating, cursor-tracking `position: fixed` element). This keeps exactly one tooltip DOM node for the whole chart (this feature's own explicit instruction) and means the tooltip scrolls together with the bar it annotates for free — no separate scroll-offset bookkeeping needed, which a viewport-fixed tooltip would have required.
- **The row-label column (phase number, name, state, %) is a separate, non-scrolling flex column to the LEFT of the scrollable SVG**, not baked into the SVG itself. This is what makes "the chart scrolls horizontally inside its own container; the page body never scrolls sideways" true even at 375px — the labels stay readable without needing to scroll, and the page's own body never gains a horizontal scrollbar because only the inner `overflow-x-auto` div (the bar area) does.
- **`PortalOverviewLive` is rendered on this page completely unmodified and unfiltered** (same `workspaceId`/`initialOverview` shape the pre-existing workspace-root chooser page already used), per this feature's own explicit "reuse the existing realtime plumbing... F009 replaces the source... without touching this component's shape" instruction. Considered pre-filtering `initialOverview`'s two arrays to this project's own tasks before passing them in, but rejected it: the component's realtime reconciliation (`usePortalOverviewRealtime` + `reconcilePortalRealtimeTask`) has no project filter internally, so a pre-filtered initial list would only stay project-scoped until the next realtime event silently reintroduced a cross-project task — a worse, INCONSISTENT UX than staying workspace-wide throughout the session. In the common case (the single-project auto-redirect F003 already does for most clients) this is a non-issue; flagged as an out-of-scope gap below for a multi-project workspace.
- **Calling `getPortalActivitySummary(workspace.id, user.id)` from this page is what actually fixes a real, pre-existing bug**: F003's single-project auto-redirect (`if (projects.length === 1) redirect(...)`) skips the workspace-root chooser page entirely for the common case, and that page is the ONLY caller that previously invoked `getPortalActivitySummary` — meaning `workspace_members.portal_last_seen_at` was NEVER being written for a single-project client before this feature. Calling it here as this feature's own spec instructs ("the existing getPortalActivitySummary output... instead of the current single sentence") closes that gap as a natural side effect, not a deliberate separate fix — flagged explicitly here so it isn't mistaken for accidental scope creep.

## Out-of-scope work needed
- **A multi-project workspace's per-project Overview shows a workspace-WIDE "waiting on you"/"delivered this week" strip**, not one scoped to just the project whose Overview the client is looking at — a direct, documented consequence of the "reuse... without touching this component's shape" instruction (see Decisions made). A future feature that wants this project-scoped needs to add a `projectId` filter parameter to `PortalOverviewLive`'s own realtime reconciliation, not just pre-filter its initial props — flagged for whichever feature touches that component next (not this one; it's out of F006's declared file scope).
- **`getPortalActivitySummary` is now called from BOTH the workspace-root chooser page (multi-project fallback) AND this per-project Overview page**, and it writes `portal_last_seen_at` as a side effect of being read. A client with 2+ projects who visits the chooser first, then clicks into a project, will see the SECOND call's "since your last visit" summary come back nearly empty (the first call already advanced the timestamp seconds earlier) — a real, if minor, "self-consuming" UX gap in the multi-project case. Not fixable within this feature's own file scope (`[workspaceSlug]/page.tsx` is F003's file, not F006's) — a future feature should either drop the chooser page's own call (now redundant once a project is entered) or make `getPortalActivitySummary` project-scoped.
- **`getPortalBadgeCounts` and `getPortalLiveNow`/`getPortalTeam`/`getPortalRisks` are each called independently by both the layout (`p/[projectId]/layout.tsx`, F003) and this Overview page** for the badge counts, and by this page alone for the other three — meaning `getPortalBadgeCounts` runs twice per request (once for the sidebar badges, once for this page's "Waiting on you" tile value). This mirrors the SAME independent-per-route-segment resolution convention F003's own `page.tsx`/`layout.tsx` pair already established (each independently re-resolves the project via `getPortalProjects`) — accepted as consistent with existing precedent rather than optimized away, since de-duplicating across a layout/page boundary would need React's `cache()` wrapper or a shared request-scoped memo, which no query in this file currently uses.
- **F014 (Your list view, M3) is the feature that gives `getPortalRisks` a real body** (blocking deliverables past due + stale approvals) — `RiskBanner`'s own props shape (`{ risks: PortalRisk[] }`) does not need to change when that happens; only `getPortalRisks`'s implementation does, per this feature's own extension-point pattern (documented in that function's own comment).
- **F019 (Hours view, M4) is the feature that gives the "Hours used" tile and the right rail's hours card a real value** — both are currently hard-coded (`"—"` / "Available with the next release"), with no data prop path into either at all, by design (see Decisions made's "never a fabricated figure" note on `OverviewTiles`).
