## Decisions made

- **Item 1 (what "sent" means): a new explicit `quote_sent_at timestamptz` column, not `approval_request_id is not null`.** `approval_request_id`'s job is "which approval carries this quote," not "has this quote been shown to the client" — the two facts only move together today because `send_change_request_quote_atomic` happens to write both in one statement. Grep-verified they already diverge for a *different* reason: `20261005010000` (F016f, "Defect 3a", lines documenting the withdraw-and-null-prior-approval step) already NULLs `approval_request_id` on re-quote for bookkeeping unrelated to client visibility. A future change to how approvals are modelled (a second way to raise one, or a reason to null the FK unrelated to sending) would silently flip visibility with no line of code saying so. `quote_sent_at`, written only by the one function that puts a price in front of the client and only on its `scope_verdict = 'change_request'` branch, is a fact about client-visibility itself — testable in isolation, immune to any future change in approval modelling. Matches the spec's own preference ("prefer making the state explicit ... unless you find a concrete reason not to") — no concrete reason turned up reading F016/F016f/F016j.
- **Gate implemented as a `security_invoker` view (`client_requests_client_read`), not a query-level filter, because plain Postgres RLS cannot do it.** A `USING` clause is row-only — it can keep or drop an entire row, not null four columns for one caller while returning them whole for another on the SAME row. Hiding the whole row would take the request itself away from the client who filed it, not just its unsent price (violates the spec's own "the client still sees the request exists"). `client_requests_select_author_or_team` (20260902030000) is untouched — it still decides which rows a caller sees. The view is the closest single Postgres object to "gate it in the policy": `security_invoker = true` means the base table's own RLS runs under the CALLING user's identity for every row the view touches (verified this is load-bearing, not decorative — a `security_definer` view would bypass RLS entirely and was rejected), and it is the one and only place these four columns are computed from `client_requests`. Every reader gets the same masking by construction, matching this mission's own stated pattern of a single choke point (F016j's own allow-list inversion argues the identical principle for write-side columns).
- **The team's own read is unaffected by construction, not by a second code path.** The view's `case` expressions test `not public.is_project_client(cr.project_id)` — for a team caller that is always true, so the `case` always takes the unmasked branch. One view, one set of `case` expressions, both audiences — not a team view and a client view that could drift apart.
- **`quote_sent_at` is protected against author writes with zero edits to F016j's guard.** `enforce_client_requests_triage_columns_immutable_by_author` (20261008010000) computes its INSERT reference row from `pg_attrdef` and its UPDATE diff from `to_jsonb(new) - allow_list` / `to_jsonb(old) - allow_list`, both generic over every column on the table. A brand-new column not in either allow-list (`v_insert_allow` / `v_update_allow`) is covered automatically — verified by reading that migration's own header, which states exactly this as its purpose ("a column added next year is then protected by default"). No migration edit was needed or made to that guard.
- **`getProjectChangeRequests` (the portal's only client-reachable read of these columns) now selects from the view, not the base table.** Grepped every `from("client_requests")` call site (`lib/queries/client-requests.ts`, `lib/queries/portal.ts`, `lib/queries/project-records.ts`, `lib/actions/client-requests.ts`) — `client-requests.ts`'s `getWorkspaceClientRequests` is team-only by the file's own header comment ("Clients never reach this query — the policy's team branch excludes them, and the page it feeds lives under /w/*"), `portal.ts`'s `getPortalRequests` never selects the quote columns at all, and `lib/actions/client-requests.ts`'s four `from("client_requests")` calls are all writes (insert/update), not reads of these columns. `project-records.ts:getProjectChangeRequests` was the only client-facing read of `quoted_hours`/`quoted_amount`/`quote_currency`/`quote_valid_until`, confirmed by its own header comment citing AS-043/AS-048 and the Scope view. Left unswitched, deliberately: the team-only functions, since switching them costs nothing but the view's `case` already makes them a no-op for a team caller — the smaller-diff choice was to touch only the one function whose caller can actually be a client.
- **Manual verification the DoD calls for ("F025's sweep fails when the gate is reverted") was actually run, not asserted.** Temporarily reverted `getProjectChangeRequests`'s `.from("client_requests_client_read")` back to `.from("client_requests")` and reran `f025-portal-route-walk.test.ts`: it failed with `marker "918273.45" leaked through ... getProjectChangeRequests`. Restored the fix and reran: 2/2 passing again. This also surfaced and fixed a real pre-existing bug in the sweep itself (see next bullet) — without that fix the sweep passed vacuously even with the gate reverted, because it never called `getProjectChangeRequests` at all.
- **Extended F025's sweep (spec item 4) by fixing a trailing-comma bug in its own signature parser, not by adding a new marker.** `deriveCallArg`'s multi-param check (`params.includes(",")`) was tripped by every Prettier-formatted single-argument export written as `function f(\n  projectId: string,\n)` — the trailing comma made a genuinely single-arg function look multi-arg and skip it. `getProjectChangeRequests` is written exactly that way, so F025's own sweep had *never* called it, and its own marker 4 (an unsent quote's `quoted_amount`, already planted in the fixture before this feature) was passing vacuously for that leg. Fixed by stripping a trailing comma before the check (`match[1].trim().replace(/,\s*$/, "")`); confirmed by the revert-and-rerun above that the sweep now actually detects the leak this feature closes.
- **New dedicated test file (`f025b-quote-sent-gate.test.ts`) covers the DoD's explicit primary/failure directions beyond what the sweep's single marker proves:** unsent quote reads null through both the query-shaped select and a direct `select("*")` against the view (the "or a direct PostgREST call" clause); the team's own read is unaffected both before and after sending; sending through `send_change_request_quote_atomic` flips the client's read to the real values; and a quote cleared back to unsent (mirroring the RPC's own two-statement clear-then-set shape) masks again — proving `quote_sent_at`/`approval_request_id` move together as the migration's own header claims, not merely that the RPC happens to leave them in sync today.
