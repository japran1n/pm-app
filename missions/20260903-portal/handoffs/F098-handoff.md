## Decisions made
- Removed the F097 "Restart Realtime (pick up post-migration table schema)" CI step entirely, per the mission's explicit instruction. F097's hypothesis (a stale Realtime relation/schema cache caused by `comment_reactions` gaining a `task_id` column + `REPLICA IDENTITY FULL` after it joined the `supabase_realtime` publication) predicted the restart would collapse delivery to seconds. The next CI run measured 45364ms post-restart vs 45459ms pre-restart — no meaningful change — so the data F097 itself produced refutes its own hypothesis. The step had no other stated justification, so per "reconsider... remove it if it has no other justification," it's gone. Left a comment at the removal site pointing to this handoff and summarizing why, so a future reader doesn't have to reconstruct the history from git blame alone.
- Investigated (did not implement) three of the four candidate mechanisms the mission listed and ruled each out with evidence, before concluding I could not fully prove the remaining candidate locally:
  - **Fake timers / a timer mock**: `tests/setup/testing-library.ts` (loaded by `vitest.realtime.config.ts`'s `setupFiles`) never calls `vi.useFakeTimers()`, and its two F093/F095 fixes (the jsdom `WebSocket` stub and the eager editor import) are both gated behind `if (typeof document !== "undefined")`. `vitest.realtime.config.ts` runs under `environment: "node"`, which has no `document` global, so neither fix executes for this file. Confirmed by reading the file directly, not by assumption, per the mission's own instruction to check rather than assume.
  - **Promise executor blocking the handler**: read the executor in `reaction-realtime-delivery.test.ts` end to end. It does no synchronous work of consequence — it registers the `.on()` callback, calls `.subscribe()`, and returns; the F074 comment already in the file (from a prior round's own instrumentation) independently measured `SUBSCRIBED` firing 7ms after the executor starts, which is inconsistent with the executor itself blocking anything for seconds.
  - **The timeout path doing something that flushes/drains the socket**: as of the current (F096) version of the code, the timeout callback does nothing but log and call `resolve(null)` — no `clearTimeout` of anything else, no unsubscribe, no teardown call. There is nothing in that path capable of unblocking a stuck socket.
  - Having eliminated those three, I built a standalone script (`probe.mjs`, not committed) that reproduces the exact structural shape of the test's promise (subscribe → on `SUBSCRIBED` fire a real INSERT via the admin client on a fresh row → `.on("postgres_changes", ...)` resolves on arrival, `setTimeout` resolves null on ceiling) against the real hosted Supabase project, once with a 1200ms ceiling and once with a 9000ms ceiling. Delivery arrived in 569ms and 434ms respectively — fast, and *not* correlated with the ceiling size in either direction. This directly demonstrates the mechanism candidates 1, 3, and 4 in the mission spec are not what's happening: the test's own code, run against healthy infrastructure, does not couple delivery time to the ceiling.
- Given that, I could not find and therefore did not invent a client-side JS bug to "fix" — doing so would have meant inventing a mechanism the evidence doesn't support, which the mission explicitly warned against ("Do not justify a decision by claiming a precedent unless a grep proves it"). The remaining, most defensible explanation is CI-local `supabase start` Realtime-container contention (the file's own F074/F092 comments already document this: the container shares 2 vCPUs with the rest of the local Supabase Docker stack), which a container restart does not relieve (per the refuted F097 hypothesis) and which this worker has no way to reproduce or fix without Docker.
- While reading the file to build the probe, I found one genuine, provable code smell independent of the root-cause question: the first `it`'s `comment_reactions:${taskId}` channel was never explicitly closed — it stayed subscribed (still receiving every `comment_reactions` write for that task, including the second `it`'s own toggle and both tests' cleanup deletes) until `afterAll`'s blanket `removeAllChannels()`. Every other channel this file opens (the `beforeAll` warmup, and both channels in the second `it`) is already explicitly torn down as soon as it's no longer needed. I fixed this asymmetry: captured the channel in a `let reactionChannel` and call `subscriberClient.removeChannel(reactionChannel)` immediately after the first `it`'s promise settles, before the assertions run (so it happens whether the test passes or fails). This does not touch the assertion, the budget, or any teardown/unsubscribe logic inside the timeout/event-handler paths themselves — it only closes a channel that had no further use. I'm not claiming this is proven to be the AS-369 root cause; I'm stating plainly that I could not fully demonstrate the CI-specific mechanism locally (no Docker, no local `supabase start` stack available in this environment), exactly as the mission's "Verify" section anticipated might happen, and this is a legitimate, safety-preserving cleanup regardless of whether it moves the number.

## Out-of-scope work needed
If the next CI run still shows the delta tracking the ceiling after this change, the remaining plausible direction (not attempted here, would need Docker access to investigate) is instrumenting the local Realtime container's own logs/metrics during a CI run — e.g., temporarily adding a step that captures `docker logs` for the realtime container across the window of this test — to see whether the WAL-to-broadcast latency the container itself reports is large independent of anything this test file does. That would either confirm genuine container-side contention (in which case the fix is more CI runner resources or a smaller/less contended local stack, not more test-code changes) or reveal a real server-side coupling to client behavior (in which case something in supabase-js's realtime-js client itself, not this test, would need investigation with the actual F074-style per-frame instrumentation).
