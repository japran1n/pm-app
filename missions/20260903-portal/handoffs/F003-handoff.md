## Decisions made
- **The full sidebar+topbar shell lives in a NEW `p/[projectId]/layout.tsx`, not in `[workspaceSlug]/layout.tsx`.** Next.js layouts only receive route params for their own and ancestor segments — `[workspaceSlug]/layout.tsx` has no `projectId` and structurally cannot scope a sidebar to "the current project" (AS-005's chips, the project card). `[workspaceSlug]/layout.tsx` keeps exactly its pre-existing job (guards) and now renders no chrome of its own; the project-scoped shell lives one level down, where `projectId` actually exists. This is the one place this feature's literal file list ("app/(portal)/portal/[workspaceSlug]/layout.tsx — replace... with a two-column grid") doesn't match what Next.js's routing model allows — documented here rather than silently forced, per this feature's own "if a spec item proves wrong, write that in the handoff" instruction. The spec's own "Files (approximate)" section already anticipates "new route folders", which is what this is.
- **The workspace-root project chooser (`[workspaceSlug]/page.tsx`) keeps its own small header** (brand, ThemeToggle, sign-out — no 8-item nav, since there's no project to scope nav links to yet). This is the one page reachable under `/portal/<slug>` that isn't inside the new project-scoped shell (0 or 2+ portal-enabled projects). Exactly one portal-enabled project now redirects straight past this page into `p/[projectId]` (the spec's own "Project scope" instruction).
- **`p/[projectId]/page.tsx` (Overview) keeps its pre-existing REAL content** (project progress bar + live task list), per the spec's explicit "Keep the existing /p/<projectId> route working by making it the overview" instruction — not replaced with an EmptyState stub. F006 (Overview view, M1) is the feature that rebuilds this into the prototype's fuller tiles/phase-timeline/risk-banner overview; F003's job was the shell around it, not its content.
- **The other seven routes (Approvals, Your list, Pages, Hours, Results, Scope & decisions, Your site) render a shared `PortalComingSoon` EmptyState** ("Coming in this project" title, honest per-section description) rather than each hand-rolling its own copy — a future feature deletes one import per route it implements, nothing else changes.
- **Badge tone**: the "Your list" (deliverables past due) badge uses the existing `Badge variant="destructive"` token, not a new color — the spec's own Notes say "badge for overdue counts uses the blocked status token", but `--status-blocked` doesn't exist yet (F004, not yet run, is the feature that adds `--status-*` tokens per plan.md's Design constraint #3). `destructive` is this app's own existing semantic-danger token, reused as a placeholder rather than inventing a new color ahead of F004 — flagged for F004 to swap in once it lands (see Out-of-scope work needed).
- **Launch-confidence chip is intentionally uncolored** (`Badge variant="outline"` for both chips) for the same reason — AS-005 only requires the header to *display* the date/confidence, not color-code it, and inventing a per-component color ahead of F004's token work would violate plan.md's Design constraint #3 ("Never re-pick them per component").
- **Mobile**: the sidebar collapses to a horizontal scrolling nav strip (not a hamburger `Sheet`, unlike `app-sidebar.tsx`'s own mobile pattern) — this feature's own spec is explicit ("the sidebar becomes a horizontal scrolling nav above the content"). Identity/theme/sign-out are kept in a compact top row of that same mobile strip rather than dropped, so they stay reachable without an extra tap.
- **`getPortalBadgeCounts(projectId)` is a pure zero-returning stub**, per the spec's own instruction ("write it so those features only change its body"). F007 (approvals) and F012 (deliverables/obligations) are expected to fill in its two counts without touching any caller.
- **`getPortalCurrentUserProfile(userId)`** (new, `lib/queries/portal.ts`) reads the client's own `profiles` row for the sidebar footer's name/avatar — reads through the ordinary RLS-respecting client, relying on the existing `profiles_select_self_or_shared_workspace` policy's unconditional `id = auth.uid()` self-read branch (20260902020000). No new policy needed.
- **Fixed a footgun while writing `PortalTopbar`'s active-item lookup**: a naive `.find(item => pathname.startsWith(item.href + "/"))` fallback would always match "Overview" first for any deeper route (Overview's href is a literal prefix of every other item's href), since it's first in array order. Excluded `exact`-flagged items from that fallback (mirrors `isItemActive`'s per-item `exact` check in `portal-sidebar.tsx`, which was already correct). Not currently reachable in practice — every route this feature adds is exactly one segment deep, so `pathname === item.href` always resolves first — but left in as correct defensive code for a future feature that adds a nested sub-route (e.g. an approval detail page).
