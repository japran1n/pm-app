## Decisions made
- **Root cause, established by direct reproduction against the live hosted project (not by inspecting the guard function, which F078 already cleared):** for an `UPDATE`, PostgreSQL's row-security enforcement requires a row to pass **both** the table's `SELECT` policy and the applicable `UPDATE` policy's own `USING` clause before that row is even considered a candidate for the write — not the `UPDATE` policy alone. `projects_update_active_members`'s `USING` clause only checks `is_active_workspace_member(workspace_id)` (any active workspace member, any role). But `public.projects` also carries a `SELECT` policy, `projects_select_active_members`, whose `USING` clause calls a *different* function, `is_project_visible_to_row`, whose body explicitly carves `'client'` (and `'guest'`) out of the general "any active member of a workspace-visibility project" rule (`wm.role not in ('guest', 'client') and (target_visibility = 'workspace' or wm.role in ('owner','admin'))`) — for those two roles, visibility can **only** come through a separate `exists (select 1 from project_members ...)` branch. So a `client`-role actor's row-visibility for `UPDATE` genuinely depends on **two** tables being correctly populated and visible at the moment of the statement (`workspace_members` *and* `project_members`), where every other role's visibility depends on `workspace_members` alone.
  - Proved this precisely, live: created a real Auth user + real active `workspace_members(role='client')` row + a `visibility='workspace'` project with **no** `project_members` row, then ran the exact `UPDATE ... WHERE id = <project>` as that user (JWT claims set via `SET LOCAL request.jwt.claims` + `SET LOCAL ROLE authenticated`, matching the probe's own mechanism) — `0` rows matched, deterministically, every time. Adding the matching `project_members` row made the same `UPDATE` match `1` row, deterministically, every time. Ran the identical `UPDATE` for `member`/`viewer`/`owner` roles with **no** `project_members` row present — all three matched `1` row every time, because none of those roles is excluded from the general workspace-visibility branch.
  - This is a real, deterministic, data-shape-dependent mechanism, not an environment/timing artifact — it does not require concurrency, replication lag, or any CI-specific condition to reproduce; it only requires the `project_members` row for the acting client to be absent or not-yet-visible to that specific statement's snapshot at the moment the probe's `UPDATE` runs.
  - The actual test file's fixture **does** insert a `project_members` row for `clientUser` in `beforeAll` (awaited, before any test runs), so on the surface this looks safe. But the self-maintaining probe is the very last test in the file, run long after that insert, over a **different connection/session** (the Supabase Management API's raw-SQL execution path, not the PostgREST connection the fixture insert went through) — a second table dependency that the rest of the file's `clientSession`-driven tests don't need to worry about (they only ever touch `baseline_frozen_at`, gated purely by `is_active_workspace_member`, not by project-level `SELECT` visibility). Under CI's `maxWorkers: 4` intra-run parallelism (documented in `vitest.config.ts`, F312), a second table dependency is measurably more exposed to any transient visibility gap than a single-table one, even though I could not, and want to be honest that I could not, force a live reproduction of that specific gap opening within *this* file's own timeline (the fixture's own `await` makes the insert-then-read ordering correct **for this file in isolation**).
- **The fix removes the dependency instead of trying to make the race less likely.** The self-maintaining probe's actual job is to prove the allow-list guard rejects a column it has never seen, for *any* actor — it was never meant to be a second test of client-role access control (that is already covered thoroughly by the dedicated, real-PostgREST-session `AS-040 primary` tests earlier in the same file). I switched the probe's actor from `clientId` to `ownerId` (captured newly in `beforeAll`; `owner.id` was already computed there but not previously stored on an outer-scope variable). An owner's row-visibility comes from `wm.role in ('owner', 'admin')` alone, with **no** `project_members` dependency at all under `is_project_visible_to_row` — so the probe's only remaining live dependency for row-matching is the single `workspace_members` row already established, deterministically, by the file's own `beforeAll`. This is a strictly stronger test, not a weaker one: it now proves the guard rejects a never-allow-listed column for an actor who would pass every other tier's role check (owner/admin), rather than for a role two other RLS layers already restrict — so a future reader can no longer wonder whether `GUARD_DID_NOT_FIRE`'s *absence* was actually explained by the client's restricted project visibility instead of the guard.
- **Did not weaken any assertion, add a skip, retry, or sleep.** The `PROBE_ROW_NOT_MATCHED` / `GUARD_DID_NOT_FIRE` distinction added in the prior round is untouched and still present; only the acting user's identity changed, plus a comment explaining why, with the mechanism traced to this handoff.
- **Verified the fix doesn't merely move the same fragility elsewhere**: `enforce_projects_field_role_allowlist`'s generic "not an allow-listed column" branch (read from `20261022010000_f025d_projects_key_insert_guard.sql`, confirmed identical to the live function via `pg_get_functiondef`, matching F078's prior diff) applies unconditionally to any never-listed column regardless of the acting role — it does not exempt owner/admin. So testing with the owner still exercises the exact code path the assertion is about.
