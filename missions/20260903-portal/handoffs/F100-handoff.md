## Decisions made

- Added a new CI step, "Diagnose supabase_realtime publication state (F099, AS-369)", immediately before "Realtime integration tests (serial, uncontended)", querying the **local** Supabase stack (not the hosted project) via `psql "$DB_URL"`. `DB_URL` is already exported into `$GITHUB_ENV` by the existing "Export local Supabase env vars" step (`supabase status -o env` emits it unprefixed alongside the three explicitly-overridden vars — confirmed by that step's own comment block, which names `DB_URL` explicitly as one of "the many other unprefixed ones the CLI also emits"). No new secret or credential handling was introduced.
- The diagnostic queries, and what each proves under the two live competing explanations:
  1. **`pg_publication_tables` membership** (`comments` vs `comment_reactions`, both filtered to `pubname = 'supabase_realtime'`). If `comment_reactions` is *absent* from this output while `comments` is present, that alone fully explains non-delivery: `20260823010000_create_comment_reactions.sql`'s own idempotency guard (`if not exists ... alter publication supabase_realtime add table public.comment_reactions`) checked `pg_publication_tables` for the row *at migration-apply time* — if some later migration or `supabase db reset` step re-created the table (it doesn't, per a grep — no `drop table comment_reactions` anywhere in `supabase/migrations/`) or if the guard's own `exists` check silently no-opped for a reason not yet found in the migration files, the table would simply never join the publication and the WAL sender would never emit change records for it, matching a permanent, mechanical non-delivery with no timing variance — exactly what run 33903580222 showed (never a "received", every run, not intermittently slow).
  2. **`pg_publication` flags** (`puballtables`, `pubinsert`, `pubupdate`, `pubdelete`, `pubtruncate` for `supabase_realtime`). Rules out (or confirms) the publication itself having `pubinsert = false` — which would make `comments` and `comment_reactions` both silently drop INSERT events at the publication level regardless of table membership. Since `comments`' own INSERT-delivery test passes on the same stack, a publication-wide `pubinsert = false` is already effectively ruled out by that fact alone, but the row is queried anyway so the evidence is direct rather than inferred.
  3. **`relreplident`** for both tables. `comment_reactions` is expected to show `'f'` (full) per `20260823080000_fix_comment_reactions_soft_delete_and_scoping.sql`'s `alter table comment_reactions replica identity full;`; `comments` is expected to show `'d'` (default, PK-based) since nothing in the migrations ever alters its replica identity. If `comment_reactions` instead shows `'d'` — i.e. the `REPLICA IDENTITY FULL` migration did not actually take effect on CI's stack — that would not explain INSERT non-delivery on its own (replica identity governs what old-row data is available on UPDATE/DELETE, not whether INSERT fires at all, and this test only waits on `event: "INSERT"`), but it would be a real, independently-actionable finding worth fixing regardless, and would strengthen the case that *something* about this table's post-publication-join ALTERs behaves differently on the local stack than expected.
  4. **`comment_reactions` column shape** (`information_schema.columns`), to directly confirm `task_id` exists, is `not null`, and has the type the migration intends — since the test's `filter: task_id=eq.<taskId>` silently matches nothing (rather than erroring) if the column is missing, wrongly typed, or the backfill in `20260823080000_...sql` didn't populate it for rows inserted by this test run.
  5. **`realtime.subscription`** row counts grouped by `entity`, wrapped in `|| echo ... not fatal` since the exact schema/table Realtime uses to track live `postgres_changes` bindings can vary by CLI/Realtime container version and this repo has no local stack to verify the exact name against beforehand — included as a secondary signal (are there zero live subscriptions against `comment_reactions` at diagnostic time, meaning the container itself never picked up the binding) without letting a naming mismatch fail the whole diagnostic step.
- Deliberately did **not** apply a fix in this commit. None of the six prior rounds' guesses held up, and of the two structural differences named in the task (publication membership, replica identity), only direct evidence from the target stack can say which — if either — is actually the cause here; guessing an `ALTER PUBLICATION ... SET (publish = ...)` or re-adding a container restart without that evidence would be exactly the "seventh guess" the task explicitly says is worth nothing. The diagnostic step is ordered to run on the identical stack, in the identical job, immediately before the failing test step, so its output is directly attributable to the same run.
- Confirmed via grep that no migration ever drops or recreates `comment_reactions` after `20260823010000_create_comment_reactions.sql` (`grep -rn "drop table.*comment_reactions\|create table.*comment_reactions" supabase/migrations/` returns only the one `create table if not exists` in that file), so a "the table doesn't exist yet when the publication guard runs" race was ruled out without needing the live diagnostic.
- Kept every prior round's earned work untouched, per instructions: the `filter: task_id=eq.<id>` (F305), the `beforeAll` warm-up (F073/F074), the serial `test:realtime` split (F092), the elapsed-time logging (F096), and F098's channel cleanup (`if (reactionChannel) { await subscriberClient.removeChannel(reactionChannel); ... }`). Did not re-add the F097 Realtime-container-restart step — its hypothesis was already tested and refuted by run 33895505689 vs the run after that fix landed (per the comment already in `ci.yml`), and the task explicitly says not to re-add it.

If a future round's diagnostic evidence calls for a migration, that migration must be written as a no-op against the real hosted project (e.g. guarded with the same `if not exists`/`drop policy if exists` idempotency pattern every migration in this repo already uses, so re-running it there where `comment_reactions` is presumably already correctly published and full-replica-identity is a no-op) — flagging this now so the next worker doesn't have to rediscover the constraint.
