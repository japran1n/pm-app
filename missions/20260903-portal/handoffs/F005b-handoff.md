## Decisions made
- **Seeded the page type inside `create_workspace_with_owner`, not via a new trigger on `workspaces` or a call from `lib/actions/workspaces.ts`.** Grepped every migration under `supabase/migrations` for a workspace-level "defaults" seed and found none — `task_types` (20260903040000) has zero seed rows anywhere, confirmed independently by F005's own handoff's identical grep. `create_workspace_with_owner` (20260817234323_workspace_create_rpc.sql, lines 43–77) is the one and only path that creates a workspace (the RLS hardening in that same migration revokes the `authenticated` role's table-level INSERT on `workspaces`, so no other path can even exist) — that literally is "the path that creates a workspace's defaults" the spec asked me to find, even though before this feature its only "default" was the owner's own membership row. `project_statuses`' default seed (`seed_default_project_statuses_on_insert`, 20260824010000, lines 152–168) is a PROJECT-creation trigger, not a workspace one — it does not apply to `task_types`, which is workspace-scoped by its own schema (`task_types.workspace_id`, 20260903040000). Added the seed insert to the same atomic transaction as the existing two inserts, `on conflict (workspace_id, system_key) where system_key is not null do nothing` for idempotency, following this mission's own "multi-table writes go through an RPC" design constraint (plan.md).
- **Only `page` is given a UI explanation in the settings-screen badge**; the other four values the migration's check constraint allows (`qa`, `component`, `content`, `seo`) fall back to a generic "the portal uses this type automatically" tooltip. None of them are wired to any query yet (verified: `grep -rn "system_key" lib/ app/ components/` finds only this feature's own `page`-matching code) — inventing per-key copy for keys nothing reads yet would be describing behaviour that doesn't exist.
- **Badge uses the existing `Badge` (`components/ui/badge.tsx`) and `Tooltip` (`components/ui/tooltip.tsx`) primitives**, the same `Tooltip`/`TooltipTrigger`/`TooltipContent` shape `StatusPill` (F004) already uses for its own database-sourced tooltip — no new UI primitive, per plan.md's "reuse before building" design constraint.
- **The migration's own doc comments cite `create_workspace_with_owner`'s file and line numbers and `seed_default_project_statuses_on_insert`'s file and line numbers directly**, rather than asserting a pattern by name, per this mission's standing "no precedent without a grep that proves it, name the file and line" instruction.
- **Backfill runs unconditionally in the migration** (`update ... where system_key is null and name ilike 'page'`), not gated behind an application code path — this is the same one-time, idempotent-by-construction backfill shape `20260828030000_status_rename_sync_and_seed_colors.sql` uses for its own colour backfill, and it is safe against the new partial unique index because `task_types_workspace_id_name_idx` (20260903040000) already guarantees at most one row per `(workspace_id, name)`, so at most one row per workspace can ever match the ILIKE.

## Out-of-scope work needed
- **The other four `system_key` values (`qa`, `component`, `content`, `seo`) are schema-only** — the check constraint allows them and the settings-screen badge would render a generic explanation for them, but nothing seeds or reads them yet. A future feature that wants a QA/component/content/SEO-specific portal view would seed and match on its own key the same way this feature does for `page`, and should give it a dedicated badge explanation at that point.
- **`docs/team-app-for-portal-plan.md`'s T3 sitemap-paste/CSV importer** (creating one `page`-type task per row with the right `page_slug`/`page_order`) is still not built — flagged as out-of-scope by F005's own handoff and unaffected by this feature. A fresh workspace now gets an empty but correctly-keyed "Page" type automatically; a PM still has to create page tasks by hand (or via a future importer) for the Pages view to show anything.
- **A workspace created before this migration and that never had any type named "page"** (case-insensitively) has no keyed page type after the backfill, and `create_workspace_with_owner`'s seed only fires on NEW workspace creation — it does not retroactively backfill existing workspaces beyond the name-match backfill in this migration. If the mission needs every pre-existing workspace to get a "Page" type regardless of naming history, that is a separate, explicit one-time backfill a future feature should write (this feature's own scope was "seed on workspace creation" + "backfill any existing row whose name matches," not "give every workspace one").
