## Decisions made
- **No new authorisation surface.** `client_requests`' INSERT policy stays client-only, exactly as F016 left it (its own handoff: "the one thing a client may write"). This feature adds `raise_change_request_from_assumption_atomic`, a SECURITY DEFINER RPC that bypasses RLS as its own owner — the identical pattern F016 already established for `send_change_request_quote_atomic`/`accept_client_request_atomic` (a team-writer-gated function performing a write RLS alone would not allow a team member to make). The preamble (membership select, `viewer`/`client` role bar, `client_gate(..., p_require_client_role => false, p_require_project_visible => false)` for the portal-enabled check) is copied near verbatim from `accept_client_request_atomic`'s current (20261001010000) version, per the spec's own instruction to match the existing bar rather than invent one.
- **`created_by` is resolved to an active client of the assumption's workspace, not the team caller raising it** — this was NOT my first design (I initially set `created_by` to the team caller, reasoning that F016e's Defect-2 fix (20261002010000) made the client-facing SELECT policy project-scoped rather than `created_by`-scoped, so which user authored the row no longer affected visibility). Writing and running the "manual verification" test surfaced a real, previously-latent bug this choice would have hit: `enforce_client_requests_triage_columns_immutable_by_author` (20261001010000/F016d) blocks the row's own author from writing its triage/quote/decision columns — a guard that had never fired before because every existing `client_requests` row is authored by a client and triaged by a *different* person, the team. Setting `created_by` to the team member who both raises AND later triages the same request would trip that guard the first time anyone tried to quote it. Resolved instead to any active client of the workspace (`is_project_client`'s own predicate is workspace-scoped, not `project_members`-scoped — confirmed via `lib/queries/approvals.ts`'s `getProjectClientMembers` header comment and 20260908010000's predicate), which keeps the row indistinguishable in every downstream write path from one a client filed themselves. This is exactly F016's own suggested follow-up (its handoff's Out-of-scope section: "`created_by` set to the client on the project... rather than the team member") — arrived at independently, then confirmed against that text.
- **Title/body pre-fill:** `title = left(assumption.text, 200)` (matches `createClientRequestSchema`'s own 200-char cap so the row is never one a client-authored request couldn't also have produced), `body = assumption.flagged_note` verbatim. No approval is raised at creation time — the row is created with `scope_verdict = 'change_request'` and nothing else quoted, so `QuoteDialog`'s own default (`request.scopeVerdict ?? 'change_request'`) shows the "Change request" tab pre-selected and the team fills in hours/price/track exactly as they would triaging a client-filed request. `send_change_request_quote_atomic` (unmodified) is what actually raises the `approval_requests` row, when the team clicks "Send quote".
- **Gate condition ("on an assumption the client has flagged") is `flagged_by_client_at is not null and state = 'assumed'`** — the exact same two-part condition `components/project/record-panel.tsx`'s own `AssumptionRow` uses to decide `isFlagged` (the highlighted styling + "Flagged by the client" text). The button only ever renders where that highlight already shows, and the RPC independently re-derives and enforces the same condition rather than trusting the client-rendered prop.
- **Invalidation on approval is folded into the existing `client_requests_sync_decision_from_approval` trigger** (the one place a client's decision on a quote is already mirrored back onto `client_requests`, per F016's own header: "the one and only place a client's decision is recorded... this feature does not add a second decision path"), not a new trigger. `CREATE OR REPLACE FUNCTION` replaces the whole body, so this migration carries forward the current live version's own defect-3a/3b fixes and F016d's guard-bypass flag unchanged (verified line-for-line against 20261002010000's own version) and adds exactly one new branch at the end: `if v_request.origin_assumption_id is not null then update project_assumptions set state = 'invalidated' where id = ... and state <> 'invalidated'`. Guarded by `state <> 'invalidated'` purely for idempotency (a stray re-approval should not error), not as a second source of truth for the state's own history — `project_assumptions.state` stays the same plain team-writable column F012 defined.
- **`raise_change_request_from_assumption_atomic` does not itself raise an `approval_requests` row or touch `client_requests_sync_decision_from_approval`** — it only inserts the `client_requests` row. The quote/approval lifecycle is entirely F016's own, unmodified.
- **Two real bugs found and fixed while building this feature, both scoped to this migration file only:**
  1. `returning id, created_at into ...` inside a function whose `RETURNS TABLE` also declares an OUT parameter named `created_at` is ambiguous in PL/pgSQL (`42702`) — fixed by qualifying `client_requests.id, client_requests.created_at` in the `RETURNING` clause.
  2. The `created_by`-resolution decision above (guard-trigger collision), caught by the test suite before it ever reached a handoff.

## Autonomous decisions
AUTONOMOUS_DECISION: Resolved `created_by` on the new `client_requests` row to an active client of the assumption's workspace rather than the team caller who raises it — the spec does not name either explicitly, but F016's own suggested follow-up did name this exact choice, and building it the other way first (team caller) surfaced a real trigger collision that this choice avoids entirely. See Decisions made for the full reasoning and the test that caught it.
AUTONOMOUS_DECISION: The button only appears for a flagged-and-unconfirmed assumption (`flagged_by_client_at is not null and state = 'assumed'`) — the same condition already driving the Record panel's existing "Flagged by the client" highlight, rather than any broader "any flagged assumption regardless of current state" reading. An assumption already `confirmed` or `invalidated` no longer shows the highlight in the existing UI, so there is nowhere for this action to attach without inventing a second flagged-indicator, which the spec does not ask for.
AUTONOMOUS_DECISION: No `approval_requests` row is raised at creation time — only at the point the team actually sends a quote through F016's own unmodified `send_change_request_quote_atomic`. The spec describes "opening the quote dialog pre-filled," which implies the team still reviews/fills in the commercial terms before anything goes to the client; raising the approval immediately, before a price exists, would contradict `send_change_request_quote_atomic`'s own existing "an amount and a validity date are required" gate.
