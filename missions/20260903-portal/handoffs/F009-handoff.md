## Decisions made
- **`components/portal/approval-actions.tsx` is NOT deleted, despite the spec's own "Reuse and then delete" instruction.** It is still imported by `app/(portal)/portal/[workspaceSlug]/p/[projectId]/t/[taskId]/page.tsx`, which renders it whenever `task.pendingClientApproval` is true — a still-live, still-necessary path for a task the team flagged via the pre-F007 `tasks.pending_client_approval` boolean toggle (F004/F005), which is a DIFFERENT mechanism from this feature's own `approval_requests` table and coexists with it (F008's own handoff confirms `PendingApprovalToggle` and `RequestApprovalDialog` are rendered as siblings on the task detail sheet, not as a migration of one into the other). Deleting `approval-actions.tsx` would 404/crash that still-reachable route, and that page is not in F009's own "Files (approximate)" list. This reading is also what the spec's own Definition of Done explicitly asks for: "Side-effect verification: the carried-over approval-actions tests still pass" — not "are replaced" — which only makes sense if the file (and its tests) still exist. Resolved in favour of the DoD's own explicit instruction over the Scope section's imperative; `components/portal/approval-card.tsx` is the new, F007/F008-shaped component this feature actually builds (same ref-guard + optimistic-apply + settle-in-place pattern, generalised from "one task" to "one approval request"), and its own test file (`approval-card.test.tsx`) carries that pattern's tests forward onto the new component rather than duplicating `approval-actions.test.tsx` verbatim.
- **`getPortalBadgeCounts` resolves the caller's own decision-owner rows via `auth.getUser()` inside the function itself**, rather than taking a `userId` parameter — matches this file's own existing convention (every other query in `lib/queries/portal.ts` calls `createClient()`/reads session state internally, never takes an already-resolved user id as a param) and needs no signature change at its one call site (`app/(portal)/portal/[workspaceSlug]/p/[projectId]/layout.tsx`).
- **The open-approvals list itself is intentionally NOT filtered by decision-owner** (only the badge count is) — the spec's own section 1 says a non-owner client sees the card with disabled buttons naming who decides, which requires the card to still be visible to them. Only AS-002's badge (the number, not the list) needed the owner-scoping fix.
- **`ApprovalCard`'s "Open" link is task-route for `subjectType: 'task'`, else `artifactUrl`** — `subjectType: 'doc'` requests have no dedicated portal doc-viewer route in this schema yet (grepped `app/(portal)` for a docs route — none exists), so a doc-subject card renders with no link at all rather than a broken one; this is a real, narrower gap than the spec's own prose implies and is called out below under "Out-of-scope work needed" rather than silently worked around.
- **`decideApproval`'s error message is the RPC's own exception text** (minus its `decide_approval_atomic: ` function-name prefix), not collapsed to one generic string — every exception `decide_approval_atomic` raises (20260916010000/20260920010000) is already written to be caller-safe (no column/table names), so "you are not the decision owner for this request" and "this request has already been decided" reach the client as distinct, actionable messages instead of one unhelpful "something went wrong."
- **`PortalOverviewLive`'s new `projectId` prop defaults to `null`**, preserving the multi-project chooser page's pre-existing workspace-wide behaviour exactly (it passes no `projectId`) — only the per-project shell (`p/[projectId]/page.tsx`) opts into project-scoping, both for its initial `deliveredThisWeek` seed (filtered client-side before the prop is passed, since `getPortalOverview` itself stays workspace-wide, unchanged, for the chooser page's own use) and for every live Realtime event admitted after mount.

## Out-of-scope work needed
- No portal doc-viewer route exists for a `subjectType: 'doc'` approval card to link to — `ApprovalCard` renders such a card with no "Open" link at all today (title/description only). A future feature adding a portal docs route should also wire this card's link for that case.
- F008's own handoff flagged that a doc-body artifact snapshot (`approval_requests.artifact_snapshot_path`, `Storage`) has no `storage.objects` SELECT policy granting a client or team session read access — only the admin client can read it back today. This feature's `ApprovalCard` does not attempt to read that path (it only links `artifactUrl`, which F008's dialog always sets for a doc/task-derived snapshot alongside the storage path); that gap is still open and belongs to whichever future feature needs to actually serve the snapshot content to a client.
- `getOpenApprovalsForWorkspace` (F010's team queue) and `withdrawApproval` (F008) are unaffected by this feature and remain exactly as F007/F008 left them.
- The task detail page's legacy `PortalApprovalActions`/`pending_client_approval` boolean flow (task-detail-sheet's `PendingApprovalToggle` on the team side) is left entirely untouched — see "Decisions made" above. A future feature could consider whether that flow should be migrated onto `approval_requests` too (e.g. every "mark pending" toggle raising a first-class `approval_requests` row instead of flipping the bare boolean), but that is a real design decision this feature does not make unilaterally.
- `getPortalRisks` (AS-031, M3) is unaffected; its pre-existing lint warning (`_projectId` unused) is untouched, matching F007's own handoff note.
