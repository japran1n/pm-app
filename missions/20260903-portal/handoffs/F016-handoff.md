## Decisions made
- **The gate lives inside `accept_client_request_atomic` itself**, following F006n's own "NOTE FOR F016" comment in `20260921010000_f006n_unguarded_task_rpcs.sql` almost verbatim: right after the existing `is_project_portal_enabled` check, before the row lock/mutate. Two new checks, in order: `scope_verdict = 'change_request' and client_decision <> 'approved'` (custom SQLSTATE `CR047`) and, only if that passes, `quote_valid_until < current_date` (custom SQLSTATE `CR048`) — distinct codes so the UI can render "not yet approved" vs "quote expired" rather than a generic failure, per the spec's own "a distinct error code the UI can render" instruction.
- **No second decision path.** The client's approval of a quote goes through F007's own `approval_requests`/`decide_approval_atomic` (`decision_type = 'commercial'`, `subject_type = 'artifact'` since a quote is not a task/doc/phase, `subject_id = client_requests.id`, `artifact_url` required by that table's own CHECK so it's set to the portal scope URL, computed client-side and passed through `sendChangeRequestQuote`'s `portalUrl` param). A new `AFTER UPDATE` trigger on `approval_requests` (`client_requests_sync_decision_from_approval`) is the ONLY place `client_decision`/`decided_by`/`decided_at` are ever written on `client_requests` — mirroring `decide_approval_atomic`'s own outcome, never an independent decision. The trigger is scoped tightly (`decision_type = 'commercial' and subject_type = 'artifact'` and `client_requests.approval_request_id = NEW.id`, an exact back-reference, not just a `subject_id` match) so it can never accidentally fire for some future unrelated commercial/artifact approval.
- **`project_scope_items` row on approval** is inserted by that same trigger (not by `accept_client_request_atomic`), because the spec's own wording ("On approval: `client_decision = 'approved'`, then the existing accept flow may run, and a `project_scope_items` row is added") ties the scope-item write to the approval event itself, not to acceptance — a client's "yes" is what makes the scope truthful, independent of whether/when the team actually clicks Accept afterwards.
- **No workspace hourly-rate setting exists anywhere in this codebase.** Grepped `supabase/migrations/*.sql`, `lib/`, `components/` for `hourly`/`rate` — the only hits are the F212 hourly-cron sweep (unrelated). Per the spec's own explicit instruction ("do not invent a rate setting if none exists... leave the field manual and say so in the handoff"), the quote form's amount field is a plain manual `Input`, never pre-filled from anywhere.
- **`send_change_request_quote_atomic`** (new RPC) is the team's one triage+quote write path, following `accept_client_request_atomic`'s own post-F006n shape (membership → role bar → portal gate → row lock → mutate) almost line for line, per that migration's own template instruction. A fresh quote (calling this RPC again on a request already `scope_verdict = 'change_request'`) resets `client_decision` back to `'pending'` — an old approve/reject cannot silently speak for a new price. `status` moves `submitted → in_review` on first triage, matching the existing team-triage convention (`declineClientRequest`/`acceptClientRequest` already move it themselves); it is never forced back once already `in_review`/`accepted`/`declined`.
- **The three-question track rule** (design/dev/content-only checkboxes → `proposeTrack()` in `components/client-requests/quote-dialog.tsx`) is client-side UI logic only, not a DB rule — the spec calls it "a good default and a bad master," i.e. advisory. The team's actual choice (`track`, `track_overridden`, `track_override_reason`) is what's persisted; `track_overridden`/`track_override_reason` are the log of the override, checked with a DB-level CHECK-free but RPC-level validation (`sendChangeRequestQuoteSchema`'s `superRefine`: an override reason is required whenever the team's chosen track differs from the proposed one).
- **"How the client will see this" preview** (`quote-dialog.tsx`'s `data-testid="quote-client-preview"` block) renders live from the same fields (`hours`/`amount`/`currency`/`validUntil`/`note`) the RPC will persist, using the exact same currency-formatting call (`Intl.NumberFormat`, `style: 'currency'`) `ChangeRequestsTable`'s own `formatAmount` uses on the portal side — the two are not the same function (client dialog vs. server-rendered table), but are deliberately written from the same formatting call so they cannot silently drift from each other.

## Out-of-scope work needed
- **"Raise a change request from this" on a flagged assumption (F015's own deferred item) was NOT built.** Investigated: `client_requests`' own INSERT policy (`client_requests_insert_own`, `20260902030000`) requires `created_by = auth.uid() and is_project_client(project_id)` — a team member cannot insert a row into `client_requests` at all today, by design (the table's own header comment: "the one thing a client may write"). Building the button honestly requires either (a) a new team-only INSERT policy/RPC that creates a `client_request` attributed to the team member raising it (a real, if small, RLS change this feature's own spec doesn't call out), or (b) some other mechanism entirely. Given this migration's own explicit instruction not to touch `client_requests`' write boundary beyond what's spec'd, and that inventing an authorization change silently is exactly the kind of thing this mission's rules say not to do without being asked, this is left as a named follow-up rather than guessed at. SUGGESTED FOLLOWUP: add `raise_change_request_from_assumption_atomic(p_assumption_id uuid, p_title text, p_body text)` — team-writer-gated (mirroring `send_change_request_quote_atomic`'s own preamble), inserting a `client_requests` row with `created_by` set to the *client on the project* (looked up the same way `resolvePeople`/`project_members` already resolve one) rather than the team member, `kind = 'change'`, pre-filled from the assumption's `text`/`flagged_note`, and wire the button into `components/project/record-panel.tsx`'s `AssumptionRow` `isFlagged` branch (F015's own handoff names the exact spot).
- **No dedicated component/unit test for `ChangeRequestsTable`'s AS-048 rendering was added** (no test harness/fixtures existed for that component before this feature — grepped `tests/` and `components/portal/*.test.*`, found none for this file). Verified manually by reading the rendered JSX against representative `ProjectChangeRequest` fixtures instead. A future worker adding portal component tests broadly should include this one.
- **No component test for `QuoteDialog`'s "how the client will see this" preview** was added either, for the same reason (no existing harness for this component tree) — the *manual verification* named by the spec's own definition of done ("the preview matches the portal exactly") was done by inspection: `quote-dialog.tsx`'s preview block and `change-requests-table.tsx`'s render both consume the same shape (`quotedHours`/`quotedAmount`/`quoteCurrency`/`quoteValidUntil`/`quoteNote` vs. `hours`/`amount`/`currency`/`validUntil`/`note`) with the same `Intl.NumberFormat` currency call.
- Track selection currently offers no explicit "which QA steps this produces" UI (design_change → dev QA + design QA · dev_change → dev QA · content_seo → requester confirms) — the `track` value is persisted and shown to the team, but no downstream task/QA-step wiring reads it yet. Not named as this feature's own scope (the spec describes the mapping as informational — "which in turn decides which QA steps the resulting task gets" — without naming a QA-step feature to wire it into), left for whichever QA/task-template feature is meant to consume it.
