## Decisions made

- **AS-081 precedence when BOTH `getUser()` and `resolveWorkspace()` fail:** the `!user` check runs first, exactly matching pre-change behavior (where `resolveWorkspace` was never even called until after the signed-in check passed). A signed-out caller against a nonexistent/foreign workspace still gets `notSignedInError`, not the workspace's own error. This is a deliberate choice (documented inline in `authz.ts`), not an accident of `Promise.all` ordering — verified by a dedicated test (`test_AS_082_signed_out_caller_is_refused_even_when_workspace_also_fails_to_resolve`).

- **`getAuthenticatedUser` is a private, module-scoped `cache()`-wrapped function inside `lib/actions/authz.ts`**, not exported from `lib/supabase/server.ts`. Two reasons: (1) the spec's root-cause section names only `lib/actions/authz.ts`; migrating the ~50 other `createClient()+getUser()` call sites across the codebase onto a shared cached helper is real, valuable follow-up work but out of this feature's declared scope. (2) Several existing unit tests mock the entire `@/lib/supabase/server` module and only stub `createClient` (e.g. `tests/unit/chat-mark-channel-read-action.test.ts`); adding a new required export there would have broken those mocks, which the spec explicitly forbids fixing by editing tests ("if a test needs editing to pass, STOP"). Keeping the cached wrapper local to `authz.ts` (still built from the same imported, mockable `createClient`) achieves AS-083 for every `withAuthz` consumer with zero blast radius on other tests.

- **Why `cache()` cannot leak one user's identity into another user's request — verified two ways, not just asserted:**
  1. *Source-level*: read both `react-server` and non-`react-server` builds of `cache()` in `node_modules/react`. In the real react-server runtime (what Next.js uses to compile/execute `lib/actions/authz.ts`, since it's imported by Server Actions), `cache()` keys its memo off `ReactSharedInternals.A` — the *current dispatcher* — via `dispatcher.getCacheForType(...)`. Next.js's own request/action-handling swaps this dispatcher fresh per request (the same mechanism `fetch()` deduplication and `getProjectById`'s existing `cache()` usage in `lib/queries/projects.ts` already rely on). If no dispatcher is active at all (e.g. this file executed under plain Vitest, which never goes through Next's request runtime), `cache()`'s own fallback is to skip memoization entirely and call the function fresh every time — confirmed by reading the fallback branch (`if (!dispatcher) return fn.apply(...)`). So the only two possible failure modes are "memoize per-request correctly" or "memoize nothing, ever" — there is no third code path that reuses a value across two different dispatchers/requests.
  2. *Empirical, against the real running dev server*: seeded two real users in the same workspace with different roles (owner — can write; viewer — cannot), authenticated both with real Supabase sessions (admin-generated magic links, the same technique `tests/e2e/board-reorder.spec.ts` already uses), and fired `moveAndReorderTask` (a `withAuthz`-wrapped, `requireWrite: true` action) from BOTH sessions at the same time via `Promise.all` (not sequential awaits) so the two requests genuinely interleave on the same Node event loop / same dev server process. Repeated 10 times back-to-back. Result: **10/10 — the owner's task moved every time, the viewer's never did.** If `cache()`'s per-request scoping were broken, the two failure modes would be the viewer's write incorrectly succeeding (picked up the owner's cached identity) or the owner's incorrectly refused (picked up the viewer's) — neither happened, in either direction, across all 10 concurrent pairs.

- **Item 3 (collapsing membership + visibility into one DB round trip) was deliberately SKIPPED.** `requireActiveMembership` and `isProjectVisibleToCaller` are each already the single shared implementation of their rule (used by every `withAuthz` action and, for visibility, mirroring `is_project_visible_to`'s SQL policy). Collapsing them into one new SQL function would mean a THIRD place (SQL) encodes "is this caller allowed," on top of the two that already exist by design (RLS policies + these TypeScript helpers, per this file's own header comment about why the admin-client bypass needs an app-layer re-check at all). The spec explicitly allows skipping this ("Stopping after items 1 and 2 is an acceptable, good outcome") and asks for the reasoning, which is: duplicating authorization logic across SQL and TypeScript is exactly how these rules drift apart, and steps 3→4 (membership then visibility) are a genuinely small fraction of total latency compared to the round trip removed in step 1.

- **Performance measurement (AS-085).** The dev server on :3000 was already running and was reused (not restarted) — its own console/log stream is a unix socket owned by the process that launched it, not a file this tool session can tail, so the exact `next.js: Xms, proxy.ts: Yms, application-code: Zms` log-line format named in the spec could not be captured verbatim. Instead: a real Chromium browser (Playwright) authenticated as a real seeded user (admin `generateLink` + cookie injection, the same real-auth technique already used by `tests/e2e/board-reorder.spec.ts`) drove the actual running app and measured real Server Action round trips client-side (network request start → finish, i.e. the same wall-clock total the server's own log line would have shown, since this is localhost with no real network hop). Measured twice before the code change and twice+ after (after letting the dev server hot-recompile and warm up once, discarded as warm-up).

  | action | before (n=4 dialog / n=2 drag) | after (n=4 dialog / n=2 drag) |
  |---|---|---|
  | `getProjectTaskTypeOptions` (New Task dialog open) | 594, 600, 580, 565 ms (avg 585) | 463, 525, 653, 516 ms (avg 539) |
  | `getProjectPhaseOptions` (same dialog open, 2nd call) | *(paired with the row above — both fire together)* | *(paired with the row above)* |
  | `moveAndReorderTask` (real cross-column drag, `todo`→`in_progress`) | 2038, 2126 ms (avg 2082) | 2447, 2057 ms (avg 2252) |

  Honest reading: the two dialog-open actions (`getProjectTaskTypeOptions`/`getProjectPhaseOptions`) are almost pure authz-preamble-plus-a-tiny-read — removing one round trip shows up as a real, if modest (~8%), reduction, in the expected direction. `moveAndReorderTask` shows **no clear improvement within measurement noise** — its own handler does a DB update, activity-log write, notification fan-out, and `revalidatePath` (see that action's own code comments), which dominates its total time; one authz round trip is a small fraction of that, and easily swamped by remote-Supabase network jitter at this sample size. This is reported as-is rather than massaged into a uniform "it got faster" story, per the DoD's "numbers show the reduction rather than asserting it." `getNotificationSnapshot` (the fourth action in the spec's original table) does **not** go through `withAuthz` at all (`lib/actions/notifications.ts` calls `createClient()`+`getUser()` directly) — it is unaffected by this fix, which is expected and out of scope, not an inconsistency; its before/after numbers were statistically the same (~280–460ms both times), which is the correct null result for an action this fix never touches.

- **`npm test` reports failures on this repo even on the unmodified baseline, under full parallelism.** Ran `npm test` twice with this change (45–46/531 files "failed" each time) and once against the unstashed pre-change `lib/actions/authz.ts` for direct comparison (66/532 files "failed"). The exact same authz-adjacent files fail in both conditions (`f002-phase-management`, `f008-request-approval-action`, `f009-decide-approval-action`, `f116-task-types`, `f327-project-lead-column-management`, `app-sidebar-project-nav-list`), and re-running those SAME 5 integration files with `--no-file-parallelism` (no contention) passes 66/66 on BOTH the baseline and the fix. `vitest.config.ts` itself documents this class of flakiness (F278: "default 5s timeout produced non-deterministic failures against the real remote Supabase project... two consecutive runs gave 41 and 36 failures"; F312 on Supabase Auth rate limits/connection pool contention under `maxWorkers: 4`). Conclusion: `npm test`'s parallel-run failures are pre-existing infrastructure flakiness (shared live Supabase project under load), not caused by this feature. The 25-file curated authorization suite run serially (284/284 PASS, 0 edits) and the full `tests/unit` run serially (1945/1947, the 2 failures being an unrelated pre-existing mock leak) are the clean signal.
