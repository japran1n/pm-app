## Decisions made
- **Chart form**: replaced the two-stacked-bars layout with a true single-row bullet chart (Stephen Few's shape, matching the plan's own §3.1 wording): the baseline renders as a light, full-row-height range behind; "Now" renders as a thinner, status-coloured bar in front, starting at 0; the target renders as a tick spanning the row. One scale per metric (`computeMetricBarLayout`'s `scaleMax` is derived per-call from that metric's own baseline/now/target/displayMax — never shared or reused across metrics, and there is no dual axis).
- **Direction honesty (the brief's specific hazard)**: bar length still encodes raw magnitude, so a `lower`-is-better metric that got worse (bounce rate 55→61) can still geometrically extend past its target tick — identical in shape to "beating the target." I did not try to invert geometry to fix this (that would make `higher` metrics read backwards instead), and I did not rely on colour alone to disambiguate. Instead every measured row carries three independent, non-geometric signals: (1) the status text ("Improved"/"Regressed"/"Unchanged", already existing), (2) a new trend icon (`TrendingUp`/`TrendingDown`/`Minus` from lucide-react) placed directly next to that text so the improved/regressed distinction survives greyscale, and (3) a new per-row caption ("Lower is better" / "Higher is better") under the metric name so a client who has never been told which metrics are lower-better still reads the row correctly from text alone. Verified via `test_AS_041_regression_case_lower_metric_worse_now_reads_as_regressed_not_progress`.
- **No colour-only encoding**: the trend icon (`querySelector("svg")` inside the status label, asserted in the new regression test) is the concrete "icon plus text alongside colour" the brief asked for.
- **Not-measured guard preserved verbatim**: `NotMeasuredBars` is untouched — same copy, same `data-testid="metric-not-measured"`, same "no baseline recorded yet" text, same absence of `metric-bar-chart` in that state (re-asserted by the new `test_AS_041_no_baseline_case_...` test). No zero-length bullet is ever drawn for an unmeasured metric.
- **Status palette untouched**: reused the existing `text-status-done`/`text-status-blocked`/`fill-status-done`/`fill-status-blocked` tokens verbatim (`app/globals.css`) — no hue was added or changed, and I did not touch dark-mode tokens per the explicit instruction not to fix the tracked lightness-band issue here.
- **Direct labels only on values that matter**: the SVG itself carries no printed numbers on any mark (baseline/now/target) — each mark instead gets an `<title>` hover tooltip (`Before: …` / `Now: …` / `Target: …`), and the one existing text row below the chart (Before/Now/Target, values only, not "every mark") is where numbers are printed, matching the pre-existing convention this component already used and the brief's "never a number on every mark" instruction.
- **Hover layer**: added native SVG `<title>` elements on the baseline rect, the now bar, and the target tick — a zero-JS hover layer consistent with this component being a plain server-renderable SVG (no client interactivity elsewhere in this file).
- **Accessibility**: kept `role="img"` + a single descriptive `aria-label` on the whole chart (now also stating the metric's direction in words, e.g. "before 55, now 61, target 45 — regressed", inside a parenthetical noting "(lower is better)"), and `role="presentation"` on the inner `<svg>` so screen readers don't double-announce. Recessive marks: the baseline range uses `fill-muted-foreground/25` (unchanged pattern, just a single full-height rect instead of two rows) and the target tick uses `stroke-foreground/60`, both thin/light relative to the solid status-coloured "now" bar, satisfying "recessive axes, thin marks, one thing draws the eye."
- Kept the same `data-testid`s (`metric-bar-chart`, `metric-target-tick`, `metric-comparison-card`, `metric-status-label`, `metric-not-measured`) so `results/page.tsx` and any other consumer needed zero changes — this feature's "Touches" is `components/portal/metric-comparison-card.tsx` (+ its test) only, per the task description; `results/page.tsx` was read to confirm it, unchanged, still renders one `MetricComparisonCard` per metric on a responsive 2-column grid, which already satisfies "one row per metric" at the page level.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose an explicit textual "Lower is better"/"Higher is better" caption per row (rather than, say, an inverted bar orientation for `lower` metrics, or a shaded "danger zone" band past the target) to solve the "a lower-is-better metric reading as progress" hazard. Rationale: inverting orientation per-metric would make the chart's own axis direction inconsistent between rows on the same page, which is a worse failure mode (a client comparing two metrics side by side would need to remember which ones are flipped); a shaded danger-zone band would add a second visual layer competing with the baseline range for the same "light band behind the bar" visual grammar. A one-line caption is unambiguous, requires no legend, and costs one line of vertical space per card.
AUTONOMOUS_DECISION: Kept `computeMetricBarLayout`'s exported field names (`beforeWidthPx`, `nowWidthPx`, `targetXPx`, `beforeYPx`, `nowYPx`) unchanged even though the geometry moved from two stacked rows to one overlaid row, to avoid an unnecessary rename of a function the existing test file already imports and asserts against by name; `beforeYPx`/`nowYPx` now both fall within the same single row's height rather than two different rows, which the existing tests never asserted on directionally (they only check `nowWidthPx`/`beforeWidthPx`/`targetXPx` magnitudes and clamping).
