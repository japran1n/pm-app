## Decisions made
- **The discriminated-result type.** Added `PortalQueryResult<T> = { ok: true; data: T } | { ok: false; error: string }` to `lib/queries/portal.ts`, applied to `getProjectPhases` and `getPortalBadgeCounts.approvalsAwaiting`. This mirrors the codebase's own existing `{ ok: true/false }` Server Action result convention — grep-verified, e.g. `ColumnActionResult` at `lib/actions/statuses.ts:188-201` (`{ ok: true; ... } | { ok: false; error: string }`) — reused for query reads here, not invented fresh.
- **Two, deliberately different, "approvals" queries — not one.** I considered making the sidebar's Approvals badge and the Overview tile+list share literally one query. I rejected it after reading `supabase/migrations/20260916010000_approval_requests.sql:28-45`: `approval_requests.subject_type` is polymorphic (`task | doc | phase | artifact`), so a raw `approval_requests` count can legitimately exceed the count of tasks awaiting approval (a pending doc/phase/artifact approval has no task to link the Overview's task-shaped list to). The sidebar badge (`getPortalBadgeCounts`) keeps counting `approval_requests` directly — matching AS-002's literal text, "the number of approval requests currently awaiting this client's decision" — while the new `getPortalWaitingOnYou` (used by the Overview tile AND the list) reads `tasks.pending_client_approval`, which the same migration explicitly documents as the field "the board and the portal overview both still read" (`20260916010000_approval_requests.sql:14-16`, grep-verified) — i.e. the migration's own author already intended the Overview to stay on this task-shaped signal, not to switch to querying `approval_requests` directly. The concrete defect M1-scrutiny-2 named — the TILE and the LIST directly below it on the same page disagreeing — is fixed exactly: both now read the one project-scoped `getPortalWaitingOnYou` result.
- **`getPortalOverview` (workspace-wide, `resolveClientBucket`-based) is untouched.** It still backs the multi-project chooser page (`app/(portal)/portal/[workspaceSlug]/page.tsx`), which has no per-project tile to disagree with, and it's what F006g's own cross-screen agreement test (`tests/integration/f005-portal-pages.test.ts::test_AS_015_AS_017_...`) calls directly. Re-scoping or re-predicating it would have risked that test and was outside this feature's two named defect sites.
- **`deliveredThisWeek` stays workspace-wide on the per-project page.** Only "waiting" was named as disagreeing in the M1 scrutiny report and in this feature's scope item 2 ("what is waiting on this client"). Project-scoping `deliveredThisWeek` too would touch F008's realtime reconciliation path (out of scope) for a field no assigned assertion covers — flagged below as out-of-scope work needed.
- **Honest-failure UI reuses existing idioms, not new components.** The Overview tile's `null` → "—" follows the exact convention `daysToLaunch === null` already uses two lines away in the same file (`overview-tiles.tsx`). The phases section's failure state reuses `EmptyState` (`components/empty-state.tsx`), the same primitive the workspace-chooser page already uses for "Nothing shared yet" — no second empty-state pattern invented. `PortalOverviewLive` grew one new optional prop (`waitingOnYouFailed`, default `false`, backward-compatible) rather than a new component, keeping AS-018/AS-019/AS-020/AS-024's existing realtime reconciliation logic (out of scope for this feature) completely untouched.
- **`getPortalBadgeCounts`'s `count ?? 0` at the success path (`portal.ts:531`) is not a residual defect.** It's reached only once `error` is already known falsy — Supabase's head-count query never returns a null count without an error — so it's guarding the SDK's nullable TypeScript signature, not swallowing a failure. Commented in place to make that explicit for the next reader.
