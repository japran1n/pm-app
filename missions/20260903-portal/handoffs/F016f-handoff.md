## Decisions made
- Extended the existing `enforce_client_requests_triage_columns_immutable_by_author` trigger to `before insert or update` rather than adding checks to `client_requests_insert_own`'s `with check`, per the spec's explicit instruction ("one place, both verbs"). `TG_OP = 'INSERT'` has no `OLD` row, so the INSERT branch compares `NEW` against each guarded column's own schema default instead of `OLD`: `client_decision` defaults to `'pending'` (checked with `is distinct from 'pending'`, not `is not null`), `track_overridden` defaults to `false` (checked with `is distinct from false`), every other guarded column defaults to `NULL` (checked with `is not null`). Getting this wrong (e.g. treating `client_decision`'s default as NULL) would have made every ordinary client insert fail, since PostgREST/Supabase always sends the column's actual default value, not an absence — verified this by running the new "ordinary request" positive test against the live database before declaring done.
- Verified via `grep -n "for insert" supabase/migrations/20260902030000_client_requests.sql` that `client_requests_insert_own` is the *only* INSERT policy on this table (no separate team-insert policy exists), so the trigger's `new.created_by = auth.uid()` condition is safe to apply unconditionally on INSERT — every row that reaches the trigger was inserted by a session whose policy already required `created_by = auth.uid()` to succeed at all.
- Restored `send_change_request_quote_atomic`'s routing through `client_gate` (F016d's shape, `p_require_client_role => false, p_require_project_visible => false`) and restored the `app.client_requests_triage_guard_bypass` `set_config` bracket around its own UPDATE — both were dropped by F016e one migration after F016d introduced them (scrutiny finding B6). The bypass was harmless to omit today only by coincidence (the RPC bars the `client` role, so `created_by = auth.uid()` can never hold for its own caller), but the new INSERT-and-UPDATE guard makes that coincidence load-bearing for any future path where a team member is also a request's own author — restoring the bypass removes that fragility rather than re-creating it.
- Added `tests/unit/f016f-client-gate-revert-guard.test.ts`: a credential-free static test that reads the full migration history, finds the LAST `create or replace function public.<name>(...)` for `send_change_request_quote_atomic` and `sweep_overdue_blocking_deliverables` (i.e. the body actually applied to the database, matching Postgres's own `create or replace` resolution), and asserts the applied body still calls `client_gate` / still carries the `t.project_id = cd.project_id` join predicate. This is deliberately NOT a DB-introspection test (no `pg_get_functiondef` RPC exists on this schema, confirmed by `grep -rln "pg_get_functiondef\|pg_proc" tests/` returning nothing) — it is the "make a future silent revert visible" mechanism the spec asked for, and it runs even without Supabase credentials, unlike every other test in this feature.
- Decided the sweep's comment/predicate disagreement question: restored the `and t.project_id = cd.project_id` predicate rather than deleting the comment. Read the *actually applied* comment (F016e's own `comment on function ...` at `20261002010000:387-388`, confirmed as the only one that survives via `grep -rn "comment on function public.sweep_overdue_blocking_deliverables"` across every migration) and found it does NOT claim the predicate exists — it only says "idempotent per task within a run, and per deliverable across runs via swept_at", with no mention of a project-scoped join. So there was no comment/code disagreement to resolve on the comment side by the time this feature started; only the predicate itself was missing from the body. Restored it anyway as defense-in-depth alongside the composite FK (cheap, still true, matches F016c's own original reasoning), and updated the comment to state explicitly that the predicate is present and was restored by F016f — so a future silent drop of this specific line now DOES create a comment/code disagreement that the next scrutiny pass (or this feature's own new static test) will catch.
- Left `swept_at`'s second UPDATE (the one that stamps every overdue blocking deliverable on the swept task) without the project predicate — it has no join to add one to (`where task_id = v_row.task_id`, no `tasks`/`projects` alias in scope there) and B3/AS-030's `swept_at` permanence defect is explicitly out of scope for F016f (it is FU's scope in the M3-scrutiny-2 report, not F016f's three listed defects).
