## Decisions made
- **The two pre-existing `chat-channels.ts` errors are an RPC-Args-nullability generator limitation, not an application bug.** `createChannel`'s call to `create_channel_atomic` passes `p_project_id`/`p_name` as `string | null` (both are legitimately null for a DM channel / a non-named channel). `supabase gen types typescript` never unions `| null` into any Function's `Args` type anywhere in this codebase's generated file (verified: grepped every `Functions` block; only `Returns` types ever carry `| null`, reflecting real column nullability) — a parameter is only ever marked *optional* (`?:`), and only when its SQL declaration has a `default`. `channels.project_id`/`channels.name` are themselves nullable columns (confirmed in the same generated file's `channels.Row`), and PostgREST already accepts an explicit JSON `null` for a required-typed parameter at the HTTP/SQL layer regardless of whether it has a default — so this code has been running correctly at runtime all along; only the generated TypeScript type was ever wrong.
- **Fix chosen: give `p_project_id`/`p_name` a `default null` in the RPC's own signature** (new migration `20260910010000_create_channel_atomic_nullable_args.sql`), which makes the generator emit them as optional, then changed `createChannel` to conditionally spread those two keys in only when there's a real value — never assigning an explicit `null` — exactly mirroring `lib/notifications/create-notification.ts`'s already-established pattern for `create_notification`'s own optional/nullable RPC args (`p_task_id`/`p_comment_id`/`p_payload`). This is the same, already-precedented shape this exact codebase uses for this exact generator limitation elsewhere; it is not a new design pattern.
- **I weighed this against this feature's own instruction ("if a fix needs a schema change, stop and document it") before making the migration.** I concluded this doesn't rise to that bar: the columns being written to (`channels.project_id`/`channels.name`) are *already* nullable — there is no open question about "should this be nullable," only a mechanical DDL gap (the RPC's parameter list never got a `default null` to match). No behavior changes for any existing caller (adding a default only affects *omitted* keys; every current caller keeps passing all six keys until this feature's own edit). Postgres requires defaultable parameters to trail non-defaultable ones, so `p_project_id`/`p_name` had to move to the end of the parameter list, which changes the function's argument-type signature — `create or replace function` (same signature) can't be used for that, so the migration does an explicit `drop function if exists (old signature)` + `create function (new signature)`, with grants re-declared explicitly (a bare `drop` does not preserve them, unlike `create or replace`). Verified this is safe because every real caller (`lib/actions/chat-channels.ts`, and PostgREST generally) calls RPCs with a named-argument JSON body, never positional SQL arguments — parameter order carries no behavioral meaning here. Ran a real end-to-end verification against the linked project (see Commands run) confirming both the DM-omitted-args case and the named-channel case insert exactly the rows expected, atomically, post-migration.
- **Considered and rejected:** (a) casting the RPC call's args object to a locally-widened type — inspected `@supabase/postgrest-js`'s actual `.rpc<FnName, Args extends Schema['Functions'][FnName]['Args']>` signature and confirmed the generic constraint requires the passed `Args` to be *assignable to* the generated (non-null) type, so a `string | null` field can never satisfy it regardless of how the cast is spelled — any such cast would need `as unknown as` or `any`, exactly what this feature's spec forbids; (b) hand-editing the generated `database.types.ts` to add `| null` to just these two fields — rejected because `tech-decisions.md`'s naming convention explicitly says generated types are "not hand-written," and the next `db:gen-types` run would silently revert it, reintroducing the bug with no signal.
- `lib/actions/phases.ts`: removed `untyped()` and all 13 call sites (mechanical — the regenerated types now carry `project_phases` and `tasks.phase_id` natively, so every `.from("project_phases")`/`tasks.phase_id` access through `ctx.admin`/`admin` type-checks with no cast). Rewrote the file's stale "Untyped-table note" header comment, which no longer describes reality, to a short pointer at F002b instead.
- Chose `scripts/gen-types.mjs` (a real script file, `npm run db:gen-types` -> `node --env-file=.env scripts/gen-types.mjs`) over an inline npm-script one-liner, matching this repo's own established convention (`db:apply`, `migrations:check`, `realtime:check` are all `node --env-file=.env scripts/<name>.mjs`, each with its own doc-comment header) rather than introducing a new, inconsistent style.
- Migration timestamp `20260910010000` continues the existing sequence (last migration in the repo was `20260909010000_portal_foundations.sql`).
