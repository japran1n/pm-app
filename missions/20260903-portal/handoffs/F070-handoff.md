## Decisions made
- **Mechanism (one sentence):** `supabase status -o env --override-name ...` formats every `KEY=VALUE` line shell-quoted (`NEXT_PUBLIC_SUPABASE_URL="http://127.0.0.1:54321"`), and appending that raw output straight into `$GITHUB_ENV` sets the var to a value with a literal leading/trailing `"` still attached, which fails `@supabase/supabase-js`'s `validateSupabaseUrl` (`node_modules/@supabase/supabase-js/dist/index.cjs:378-387`, which explicitly throws "Invalid supabaseUrl: Must be a valid HTTP or HTTPS URL." for any non-empty string that doesn't start with `http://`/`https://` — an empty/undefined value instead throws the *different* message "supabaseUrl is required.", which is why the error text alone proves the value was present-but-quoted, not missing).
- **Why `npm run build` didn't catch it:** Next.js's `NEXT_PUBLIC_*` inlining is a static string substitution at build time; nothing in the build eagerly constructs a Supabase client and calls `validateSupabaseUrl` against it, so a build with a garbled-but-nonempty string still succeeds. The break only surfaces at runtime/test time when code actually calls `createClient(...)`.
- **Why it wasn't a "different var name" or ".env-only" bug:** `lib/supabase/client.ts`, `lib/supabase/server.ts`, `lib/supabase/admin.ts`, and every `loadDotEnv()`-based integration test all read the exact same `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY` names CI exports (grep-verified — 248 test files use the identical `!(key in process.env)` guarded loadDotEnv() pattern, so a CI-committed `.env` isn't in play either: `.env` is gitignored and not present in CI). The GitHub Actions job's own displayed `env:` block for the Build and Test steps genuinely showed the values (rendered with surrounding quotes in the log, which is standard Actions log formatting for *every* var shown there, quoted or not — that display format alone doesn't prove or disprove literal quotes in the actual value, which is why the error-message reasoning above is the real evidence).
- **Fix:** insert `| sed -E 's/^([A-Za-z_][A-Za-z0-9_]*)="(.*)"$/\1=\2/'` between `supabase status -o env ...` and `>> "$GITHUB_ENV"` in the "Export local Supabase env vars" step, stripping one matching pair of quotes from each line's value. Left every other step and the general CI structure untouched.
- **Test approach:** rather than mocking the bug, the new unit test reads the actual `sed -E '...'` expression out of `.github/workflows/ci.yml` via regex and runs it (via `execFileSync`) against representative `-o env`-shaped input, so the test can't silently drift from what CI actually executes. It asserts: quotes are stripped, the resulting value passes an `^https?:\/\//i` check (the same shape `validateSupabaseUrl` requires), multi-line blocks are handled in order, an internal `=` inside a value (e.g. base64 padding) survives, and an already-unquoted line is left untouched (idempotence/defensiveness).
- I did **not** touch application code (`lib/supabase/*.ts`, any component, any Server Action). The diagnosis proves this is purely a CI workflow bug in how the env-export step feeds `$GITHUB_ENV` — application code reads `process.env.NEXT_PUBLIC_SUPABASE_URL` correctly and consistently everywhere it's used.
