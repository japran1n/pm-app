## Decisions made
- **Mechanism (per spec section 2's hard requirement):** minted a REAL Supabase session for the chosen client's own account, server-side, using `admin.auth.admin.generateLink({type:"magiclink"})` + fetching the resulting action_link to extract access/refresh tokens. This is the exact same technique `app/dev-login/route.ts` already uses in this codebase to mint a session for an arbitrary identity server-side (grep: `app/dev-login/route.ts:37` `admin.auth.admin.generateLink`) — extracted into `lib/auth/mint-impersonation-session.ts` so it's shared and independently mockable in tests. Unlike dev-login, this path is NOT gated to development — it's the feature's actual mechanism, gated instead by `requireWorkspaceAdmin` (owner/admin only) and by requiring the target to already be an active `client`-role member of the calling workspace.
- **Session delivery without touching every portal route:** the minted access/refresh tokens are stored in cookies scoped `path: "/portal"`. Because the browser only ever sends cookies to requests matching their path, every `/w/*` (team app) request is byte-for-byte unaffected — the preview cookies are simply never present there. `lib/supabase/server.ts`'s shared `createClient()` was given one new branch: if the (portal-scoped) preview cookies are present, it constructs a `createServerClient` with a no-op cookie adapter (`getAll: () => []`, `setAll: () => {}`) and calls `.auth.setSession()` on it — this session lives only in that one request-scoped client instance, never persisted back into any cookie, so it can never leak into the previewer's real team session or outlive the request. This is what lets the ENTIRE existing portal route tree (`app/(portal)/portal/[workspaceSlug]/**`, every Server Component and query in `lib/queries/portal.ts`) render completely unmodified, driven by the client's own RLS — no `previewAsClientId` parameter exists anywhere (verified: `grep -rn "previewAsClient" lib/queries lib/actions` returns nothing outside this feature's own files).
- **Banner placement:** rendered in `[workspaceSlug]/layout.tsx` (the outermost portal guard, wraps every route) rather than the project-scoped shell one level down, so it's visible on every portal page regardless of which view/project is open — satisfies "the banner is always visible" from the definition of done. No dismiss/close affordance exists on the banner itself; only an "Exit preview" action that actually ends the preview session (clears the three cookies) is offered, per the spec's explicit "not dismissable" requirement.
- **Audit write ordering:** `writeAudit` is called BEFORE `mintImpersonationSession`, using the previewer's own (non-impersonated) session client — this guarantees an audit row exists for every attempt that passed authz and resolved a real client, even if the session-mint step subsequently fails (tested: `test_AS_053_an_audit_row_is_written_even_when_session_minting_fails_afterward`).
- **Audit target_id convention:** used the `workspace_members` row id (not the user id) as `target_id`, matching the existing convention every other `workspace_member`-targeted audit entry in this codebase already uses (`lib/actions/workspaces.ts`'s `member.invited`/`member.role_changed`/`member.removed`, all pass a `workspace_members` row id, not a user id).
- **Server Actions return a redirect target rather than calling `redirect()` themselves** (`{ ok: true, redirectTo }` / `{ ok: false, error }`), matching this codebase's existing "action returns ok/data, caller navigates" convention (e.g. `lib/actions/portal-approval.ts`). This also made the action trivially unit-testable without mocking `next/navigation`'s throwing `redirect()`.
- **Client picker is workspace-scoped, not project-scoped:** `getPreviewableClients` lists every active `client`-role member of the workspace, not filtered by a specific project's membership — verified via `getPortalProjects` (the query the real portal itself uses) that client-role RLS/`portal_enabled` is the actual per-project gate, not a `project_members` row; the picker's optional project dropdown only decides the DEEP-LINK target, not who is offered as a client.
- **"View as client" shortcut gating:** shown only when `currentUserRole` is `owner`/`admin` AND the task/doc is already client-visible (previewing something the client can't see would land on the empty project chooser, matching this codebase's existing "gate on already-visible" convention next to `RequestApprovalDialog`/`ClientVisibilityToggle` in the same files). The real enforcement is still server-side (`startClientPreview`'s own `requireWorkspaceAdmin` re-check) — this is UX only, same "server re-checks independently" note already documented next to `RequestApprovalDialog` in `task-detail-sheet.tsx`.

## Out-of-scope work needed
- No E2E/browser-level test exercising a real generated magic-link end-to-end (would require a live Supabase project + real network call to the action_link, out of reach for a mocked unit-test run). The definition of done's "primary success test: integration — the preview's rendered data is identical to what a real session for that client returns" is architecturally guaranteed by construction (the preview literally uses the client's own session against the same route tree), but is not independently exercised by an automated integration test in this repo's current test infra. A future feature (or the M5 "leak sweep", F025) could add a Playwright/E2E spec that: (1) signs in as owner, (2) starts a preview via the UI, (3) captures the rendered portal DOM/props, (4) separately signs in as the real client, (5) asserts the two are identical for the same project.
- The workspace-level (non-project) doc editor page (`app/(workspace)/w/[workspaceSlug]/docs/[docId]/page.tsx`) has no `projectId` at all, so it was left without the "View as client" shortcut — there is no project-scoped portal route it could deep-link into. This matches the shortcut's own precondition (`RequestApprovalDialog` is similarly omitted there for the same reason) and is not a gap, just noting it explicitly since the spec mentions "in the task detail sheet and in the doc header" without distinguishing workspace-level vs project-level docs.

## Notes for the next worker
- `lib/supabase/server.ts`'s preview branch is the one shared-file change in this feature. It is a pure additive branch guarded by two cookie names that are (by construction, via `path: "/portal"`) never present outside portal requests — verified by reading the cookie-scoping behavior, not by a runtime path check, so there's no route-awareness bug surface to introduce later. Got this right on the first pass by writing the audit call before the mint step; worth flagging for anyone refactoring this file later.
