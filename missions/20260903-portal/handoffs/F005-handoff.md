## Decisions made
- **The "page" task type is matched by NAME (case-insensitive `ilike`), not a seeded id.** `task_types` (20260903040000) is an entirely workspace-owned taxonomy with no default rows — grepped every migration file under `supabase/migrations` for a `task_types` INSERT and found none. `docs/team-app-for-portal-plan.md`'s own T3 plan ("Seed tipova taskova: page, component, qa, ...") was never implemented as a migration seed and is not in this mission's M1–M5 feature list (`plan.md`). Until a future feature adds that seed, `getPortalPages` looks up `task_types` where `workspace_id = <project's workspace>` and `name ilike 'page'` (no wildcards — an exact, case-insensitive match) — a workspace that has never created a "Page" type simply has an empty Pages view, which is a vacuously-true reading of AS-014's own "lists every client-visible task of type page." The task detail sheet's own gate (`task.taskTypeName?.trim().toLowerCase() === "page"`) uses the identical case-insensitive comparison. Documented at the top of `getPortalPages`'s own section in `lib/queries/portal.ts`.
- **"Who has it" role is the assignee's WORKSPACE role** (owner/admin/member/viewer/guest → "Owner"/"Admin"/"Member"/"Viewer"/"Guest"), not a job title. Grepped `profiles`' own migration (`20260818200946_create_profiles.sql`) for a title/role column and found none — this schema has no per-person job-title concept anywhere. `workspace_members.role` is the only "role" this codebase actually has for a team member, so it's what renders muted beneath the name in the "Who has it" cell.
- **The assignee is `tasks.assignee_id` (the DB-maintained single-assignee mirror column, `set_task_assignees_atomic`, 20260905050000 — "earliest assigned, tie-broken by lowest user_id"), not the full `task_assignees` multi-assignee set.** "Who has it" is a singular idiom in both the spec and the prototype table (one avatar + one name + one role per row), and `assignee_id` is exactly the DB's own single-owner projection of that set — reusing it avoids a second per-row assignee-resolution path for a UI slot that only ever shows one person.
- **One batched `resolvePeople` call plus one batched `workspace_members` role query**, both keyed off the deduplicated set of assignee ids from the page rows — no per-row query. The role query uses the ADMIN client specifically: a client caller cannot read `workspace_members` rows other than their own (`workspace_members_select_*`, 20260902020000), but this is resolving a DISPLAY value for an already-permitted row (the assignee id came from a task this same client can already see), the identical justification `resolvePeople`'s own doc comment gives for using the admin client to resolve `profiles`.
- **`client_visible` is filtered explicitly inside `getPortalPages`, not left entirely to RLS**, mirroring `getProjectPhases`'s own documented exception in this same file (F001): AS-014's own contract ("every CLIENT-VISIBLE task of type page") is a business-logic definition of what this function returns, not only an access-control boundary, so it holds even for a team caller previewing the portal's own numbers. `portal_enabled`/cross-project isolation are NOT re-checked here (same as `getProjectPhases(projectId)`) — they're the caller's/RLS's job: the enclosing route re-resolves the project via `getPortalProjects` (which already gates on `portal_enabled`) before ever calling `getPortalPages`, and RLS's own folded `is_project_portal_enabled` check (F001, `tasks_select_active_members`) independently returns zero rows for a portal-disabled project regardless.
- **Page slug/order editing in the task detail sheet commits on blur**, using the sheet's existing shared `saveField`/`isSavingField` transition (the same one `dueDate`/`startDate`/`phaseId` already use), not title's own dedicated transition+Escape-cancel machinery — nothing in this feature's spec calls for a per-field spinner or cancel-to-revert, so the simpler of the sheet's two existing commit patterns was reused, composed with title's own "commit on blur" moment (needed here because these are free-typed text/number inputs, unlike the native date pickers `dueDate`/`startDate` commit on `onChange`). No new inline-edit pattern was invented.
- **The seven-step "How a page travels" strip is a separate, small, static component** (`page-travel-strip.tsx`) rather than folded into `pages-table.tsx` — it renders unconditionally below the table with no data dependency, so isolating it keeps `pages-table.tsx` focused on the one thing that's actually filterable/data-driven.
