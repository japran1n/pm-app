## Decisions made
- **Queries stay workspace-wide, unchanged, in the relocated `files`/`requests` pages.** `getPortalFiles`/`getPortalRequests` were never project-scoped (they already span every project in the workspace, grouped by project in the UI) — per this feature's own "keep queries and RLS assumptions exactly" instruction, `projectId` only selects which project's shell wraps the page; it does not filter the content. A client reaching `/p/<anyProjectId>/files` sees the exact same file list regardless of which project's shell they arrived through.
- **`t/[taskId]/page.tsx`'s own "back to project" link is untouched** — it already read `task.projectId` (from `getPortalTaskDetail`), which was already correct before this move (`/p/<projectId>` was already the project overview's URL). No behaviour change there.
- **The relocated page components accept but do not use the `projectId` route param** (files/requests ignore it entirely; task detail keeps using `task.projectId`, not the URL's `projectId`, for its own links) — the param only exists so the URL carries it and `p/[projectId]/layout.tsx` can resolve/authorize the project before these pages ever render. Not destructuring an unused param avoids an eslint unused-var warning without a `_projectId` prefix workaround.
- **Legacy redirect handlers for files/requests use `getPortalProjects(workspace.id).length`**: exactly 1 → straight to that project's new URL (mirrors F003's own single-project shortcut on `[workspaceSlug]/page.tsx`); 0 or several → the project chooser (`/portal/<slug>`), since there is no correct project to guess. The legacy task-detail redirect is different in kind: a task's own project is never ambiguous (`getPortalTaskDetail` returns it directly), so it always resolves straight to the new URL; a task that no longer resolves (deleted, or un-shared since the link was saved) 404s exactly as it did at the old location, rather than redirecting to a chooser that would just be a dead end for that specific link.
- **`tests/e2e/portal-approve.spec.ts`'s fixture was missing `portal_enabled: true` entirely** (a gap predating this feature — flagged in F003's own handoff as "independent of this feature", itself inherited from F001) — fixed here because scope item 5 ("update this test to the new route shape without weakening what it asserts") cannot be honoured against a fixture the portal can't even see. Fixing it surfaced a second, deeper interaction: with exactly one portal-enabled project, F003's own single-project shortcut on `[workspaceSlug]/page.tsx` skips straight past the project chooser into `p/[projectId]` — but the chooser is the ONLY place `PortalOverviewLive` (and therefore "Waiting on you", AS-018/AS-019, which this spec's own assertions AS-029/AS-030 depend on) renders; `p/[projectId]/page.tsx`'s own overview does not have that widget yet (F006, not yet run). Resolved by seeding a second, task-less portal-enabled project so `getPortalProjects` returns 2 and the chooser renders directly without the shortcut firing — the fixture change is additive (one more project + one more `project_members` row, both torn down in `afterAll`) and does not touch what AS-029/AS-030 assert.
