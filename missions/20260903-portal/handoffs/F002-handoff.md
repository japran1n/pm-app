## Decisions made
- Reused `withAuthz` (lib/actions/authz.ts) for every phase-CRUD action and for `setTaskPhase`, per this feature's explicit instruction. The CRUD actions (createPhase/updatePhase/deletePhase/reorderPhases/seedDefaultPhases/getProjectPhaseOptions) use `withAuthz`'s DEFAULT `canWrite` gate rather than `canManageColumns` (the closest semantic sibling, from statuses.ts): `withAuthz`'s `writeCheck` option is only ever invoked as `writeCheck({ role: membership.role })` — `projectRole` is never threaded in — so passing `canManageColumns` (which needs `projectRole` to grant a project LEAD access) would silently deny every lead who isn't also an admin/owner. `canWrite` needs only `role` and already satisfies this feature's Definition of done ("a viewer and a client are rejected by every phase mutation action"). `setTaskPhase`/`bulkSetTaskPhase` instead use `canEditTask` as the write check, matching `editTask`'s own gating for task-field edits (the phase field lives on `tasks`, not `project_phases`).
- `project_phases.position` is a plain `integer` column (F001's migration), not the `double precision` fractional-index columns `project_statuses.position`/`saved_views.position` use. `reorderPhases` therefore takes a `direction` ("up"/"down"), not a caller-computed position: the action loads the moved phase's immediate neighbor server-side and swaps their two integer position values in two sequential updates (no unique constraint on `(project_id, position)`, confirmed in the migration's own comment, so the brief intermediate duplicate-position state during the swap is safe). `components/project/phase-list.tsx`'s reorder UI mirrors `status-manager.tsx`'s move-up/move-down buttons exactly (no drag library added), just calling this direction-based action instead of computing a fractional midpoint.
- Task<->phase assignment (`setTaskPhase`, `bulkSetTaskPhase`, `getProjectPhaseOptions`) lives entirely in the new `lib/actions/phases.ts`/`lib/queries/phases.ts`, not `lib/actions/tasks.ts`/`lib/validation/tasks.ts` — those files are large and heavily cross-referenced (editTask's `EditTaskUpdates` union, `bulkUpdateTasks`' own payload type), and this feature's own "Files (approximate)" list names `lib/actions/phases.ts` as the home for the server actions, not `tasks.ts`. `task-detail-sheet.tsx` and `new-task-dialog.tsx` fetch the phase option list via `getProjectPhaseOptions` called directly from a `useEffect`, mirroring the exact "Server Action called from a Client Component's `useEffect`" pattern `task-detail-sheet.tsx` already uses for `getMentionCandidates` (lib/actions/comments.ts) — this avoids threading a new `phases` prop through every one of the sheet's/dialog's many Server Component callers (board/page.tsx, list/page.tsx, t/[taskKey]/page.tsx, board.tsx, task-list-table.tsx), none of which this feature's spec named as in-scope.
- `new-task-dialog.tsx` has no `phaseId` parameter added to `createTask`'s signature — the dialog calls `setTaskPhase` right after a successful `createTask`, the same "two-step write, second call only fires when actually needed" shape it already uses for `setTaskAssignees` when more than one assignee is selected.
- `bulkSetTaskPhase` (components/task/bulk-phase-action.tsx's "Move to phase" bulk action) is NOT built on `withAuthz` — it mirrors `bulkUpdateTasks`' (lib/actions/tasks.ts) own reasoning exactly: a bulk call can touch tasks whose auth context (workspace/role) needs checking per-task, and a forbidden task is reported in `failedIds` rather than failing the whole batch, which `withAuthz`'s single-resolveWorkspace-per-call shape doesn't support.
- `lib/supabase/database.types.ts` (the checked-in `supabase gen types` output) predates F001's migration entirely — it has no `project_phases` table and no `tasks.phase_id`/`page_slug`/`page_order` columns. Verified this is a pre-existing, already-tolerated gap (not something to silently work around): live-regenerating the file via `npx supabase gen types typescript --project-id <ref>` (confirmed additive-only — no table or function was removed relative to the checked-in file, only ~7 already-applied-but-uncaptured tables/functions like `doc_folders`/`docs`/`project_phases`/`seed_default_phases` appeared) surfaces exactly 2 PRE-EXISTING type errors in `lib/actions/chat-channels.ts`, an unrelated file this feature's spec does not authorize touching. Reverted that regeneration and instead added a small local `untyped()` cast helper in `lib/actions/phases.ts` (casts the ADMIN client to a bare, unparametrized `SupabaseClient` only at the specific `.from("project_phases")`/`tasks.phase_id` call sites) — this is the same shape `lib/actions/docs.ts` already uses for its own not-yet-typed tables (`doc_folders`/`docs`), just narrower (docs.ts avoids the admin client entirely for those tables; this file still needs the admin client for `withAuthz`'s writes, so only the cast, not a client swap, was needed). `lib/queries/phases.ts` needs no cast at all — it uses the request-scoped `createClient()`, whose return type has never carried a `<Database>` generic (see `lib/supabase/server.ts`), the same reason `lib/queries/portal.ts`'s F001-era `getProjectPhases` also needed no cast.
- Project settings had no reachable "Phases" (or "Board columns") entry point in the UI before this feature (verified: no route in the app links to `.../settings/columns` — F219 shipped it reachable only by direct URL, and `components/project-tabs.tsx`, the component this feature's spec names as where "the tab" should be added "next to the existing settings entries," is actually the Board/List/Docs tab switcher with no settings entries at all). See Autonomous decisions below for how this was resolved.
