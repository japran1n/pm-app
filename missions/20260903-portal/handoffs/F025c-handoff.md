## Decisions made

- **Defect 1 fix is a transaction-local bypass flag (`app.projects_field_guard_bypass`) on `enforce_projects_field_role_allowlist()`, set/reset around `assign_task_number()`'s own `UPDATE projects SET task_counter = ...` — not a new allow-list entry for `task_counter`.** This is F016j's exact technique (`app.client_requests_triage_guard_bypass`, `supabase/migrations/20261008010000_f016j_client_requests_allowlist_guard.sql:189-192` sets it `'on'`/`'off'` via `set_config(..., true)` around the trigger's own UPDATE, and the guard function checks it at its very top at line ~103). Grep-verified `task_counter` is not in any of the four named tiers (`v_identity_cols`/`v_member_cols`/`v_writer_cols`/`v_owner_admin_cols`) in `20261017010000_f020b_projects_allowlist_guard.sql`, so it fell into the generic "any other column, present or future" branch that rejects any change outright — for every task insert, not only the `accept_client_request_atomic` path the defect was found through. Confirmed by directly testing plain task creation by an ordinary member (no approval/client-request RPC involved) before the fix: same `42501`. This is why the fix is unconditional in `assign_task_number()` (fires for every task insert), not scoped to any one RPC.
- **Root cause of defect 1 identified precisely: `assign_task_number()`'s own SECURITY DEFINER UPDATE, not `accept_client_request_atomic` itself.** `accept_client_request_atomic` never touches `projects.task_counter` directly — it inserts a `tasks` row, and the `tasks_assign_number` BEFORE INSERT trigger (`20260819061129_project_keys_and_task_numbers.sql`, function updated by `20260819061442`) does the `UPDATE projects SET task_counter = task_counter + 1 ...` as its own internal bookkeeping. The bypass therefore lives in that trigger function's body, which is where the write actually originates, not in `accept_client_request_atomic` or any other RPC that happens to insert a task.
- **The bypass is a blanket escape, not a second allow-list entry, by design.** Wrapped the whole UPDATE statement in the flag rather than adding `task_counter` to `v_writer_cols` (or any tier), because a named entry only protects the one column known today — the spec's own instruction ("the next trigger-written column breaks it again") is exactly what a named entry would still leave open for a future trigger-written column. The flag-based bypass covers any future trigger that legitimately needs to write inside its own SECURITY DEFINER body, with zero edit to the guard's column lists, matching how F016j's identical flag already covers three different legitimate writers on `client_requests` (`send_change_request_quote_atomic`, `client_requests_sync_decision_from_approval`, `raise_change_request_from_assumption_atomic`) without three allow-list edits.
- **Self-maintaining property untouched, verified without editing the existing regression test.** `tests/integration/f020b-projects-allowlist-guard.test.ts`'s own "self-maintaining allow-list" test (adds a throwaway column inside a rolled-back transaction, asserts a client-role write to it is rejected) passes unmodified after this migration — the fix adds a flag check, not a named column, so the pg_attrdef-driven "any other column" branch and its self-maintaining guarantee are unchanged.
- **New dedicated failure tests prove the bypass is scoped correctly, not "wide open."** `tests/integration/f025c-...test.ts` adds two tests unrelated to any task insert — a client and (separately) an ordinary member both attempting a direct `UPDATE projects SET task_counter = ...` — and both still raise `42501`. This is the DoD's explicit "failure test" requirement: F020b's actual purpose (a client/viewer/ordinary member cannot write `task_counter` directly) survives.
- **Defect 2: established FIRST, as instructed, that the notification insert shares `decide_approval_atomic`'s own transaction — confirmed by reading the function body, not assumed.** `create_notification` (`20260823020000_create_notifications.sql:119-`) is a plain `security definer` SQL function called with `perform` inside `decide_approval_atomic`'s own body (`20260925010000_f009b_close_second_approval_path.sql:282-296`) — no sub-transaction, savepoint, `dblink`, or background job involved anywhere in the call chain. So before this fix, a client clicking Approve/Request changes got a hard `42501`-adjacent (`23514`) error back from the RPC and NOTHING was recorded: not the `approval_requests` state flip, not the resulting task already inserted earlier in the same transaction (for the `changes_requested` branch) — all rolled back with the failed notification insert. Confirmed live, pre-fix, by reproducing the exact failure end-to-end with a real signed-in session before writing the fix (same shape the new test now asserts the *positive* case for).
- **Root cause of defect 2 pinned to one migration by grep, not inferred.** `20260916010000_approval_requests.sql:318-320` widened `notifications_kind_check` to include `approval_decided`. `20260929010000_f015_flag_assumption_atomic.sql:128-135` widened it again for `assumption_flagged`, and its own header comment says so explicitly ("last widened by 20260916010000 for 'approval_decided'"). `20261012010000_f018_budget_threshold_sweep.sql:46-52` then dropped and re-added the same constraint to add the two budget kinds, but copied forward only the ORIGINAL five kinds from `20260823020000` (`mention, comment_reply, task_assigned, task_due_soon, watcher_update, budget_threshold_80, budget_threshold_100`) — silently reverting both `approval_decided` and `assumption_flagged`. Grep-verified: neither string appears in `20261012010000`'s replacement `CHECK` list. Grep-verified no migration after `20261012010000` touches `notifications_kind_check` at all.
- **Fix widens the constraint to the full union of every `kind` any migration has ever inserted, not just `approval_decided`.** Grepped every `p_kind =>` call site across `supabase/migrations/*.sql`; the union is exactly nine values: `mention, comment_reply, task_assigned, task_due_soon, watcher_update, approval_decided, assumption_flagged, budget_threshold_80, budget_threshold_100`. Restoring only `approval_decided` (the literal defect named in the spec) would have left `assumption_flagged` silently regressed too, an identical live bug this feature's own investigation surfaced but the spec did not name — fixed in the same migration since it is the exact same root cause (`20261012010000`'s dropped widenings) and the exact same one-line-per-kind fix, not a scope expansion into different code.

## Out-of-scope work needed

- **No new candidate regressions of this class were found while investigating**, but the pattern itself (a later migration re-adding a shared `CHECK` constraint by copying an OLD literal list instead of reading the CURRENT one) is worth a mission-wide note for future workers: any migration that does `drop constraint ... ; add constraint ... check (col in (...))` on a table another feature has already widened is at risk of this exact silent revert. `notifications_kind_check` is the only such constraint touched in this mission's migrations more than twice (grep-verified), so no other table currently carries this risk, but a future feature widening it a third time should read the CURRENT list via `\d notifications` or the latest migration, not recall it from memory.

## Autonomous decisions

AUTONOMOUS_DECISION: Named the bypass flag `app.projects_field_guard_bypass` (not e.g. `app.tasks_assign_number_bypass`) to mirror F016j's own naming convention (`app.client_requests_triage_guard_bypass` — named after the TABLE being guarded, not the writer using it), since a future second legitimate writer on `projects` should reuse the same flag rather than each writer inventing its own name.

## Notes for the next worker

- The bypass flag is set with `set_config(..., true)` (transaction-local `is_local = true`), exactly like F016j's — it cannot leak into a later statement on a pooled/reused connection and cannot be set by anything outside a SECURITY DEFINER function body running server-side (a caller cannot set a `set_config` GUC through PostgREST/RLS).
- If a future migration adds another `projects`-column-writing SECURITY DEFINER trigger (e.g. a second counter, a computed rollup), wrap its own internal UPDATE in the same `app.projects_field_guard_bypass` flag rather than adding the column to any of the four named tiers or inventing a new flag — this is now the established pattern for "the application's own write, not a member's."
- No MCP tools were used — this mission's Supabase MCP is not authorised; migrations were applied with `npm run db:apply` and types regenerated with `npm run db:gen-types`, matching every other worker in this mission per `missions/20260903-portal/plan.md`'s own Notes section.
- Debugging note for whoever touches client-role RLS tests on `projects` next: a client with only a `workspace_members` row (no `project_members` row) on a `visibility: 'workspace'` project is still workspace-visible per `is_project_visible_to`'s own `OR p.visibility = 'workspace'` branch — but a client with NO project-level fixture at all on a project created without `portal_enabled`/`visibility` set explicitly can end up with an UPDATE that matches 0 rows under RLS and returns `{ data: [], error: null }` (no error) instead of the trigger's `42501` — proving nothing about the guard. Always give a client-role test fixture an explicit `project_members` row (matching `f020b-projects-allowlist-guard.test.ts`'s own convention) before asserting on trigger-level rejection, or the test can pass for the wrong reason.
