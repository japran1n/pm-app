## Decisions made
- **Order of operations: create the task first, then upload the screenshot to it — not a free choice, effectively forced by the existing bucket's RLS.** The instructions explicitly required reusing the existing `task-attachments` bucket and its existing RLS rather than inventing a new storage path. That bucket's own INSERT policy (`supabase/migrations/20260818050100_create_attachments.sql`) authorizes an upload by parsing the *first path segment* of the object name as a live task id (`is_task_workspace_member(split_part(name,'/',1)::uuid)`) — there is no `attachments` row yet at upload time for a SELECT-style join to authorize against instead (that's the SELECT policy's job, for *later* reads). This makes "upload first" structurally impossible without a real task id already existing to put in the path, so "create then upload" is the only ordering compatible with the existing, unmodified RLS.
- **This ordering does not create the half-state the spec worried about ("a task that exists but references a screenshot that never made it to storage").** `tasks` has no attachment-reference column of its own — attachments are a separate child table joined by `task_id` (confirmed by reading `lib/actions/attachments.ts` and the F064 migration, not assumed). A task that exists with zero attachment rows is simply "a task with no attachments," a normal valid state, never a "broken reference on the task." The only place a real half-state could occur is inside the attachment upload+insert pair itself (a Storage object with no row, or a row with no object) — which is exactly what the reused (not reimplemented) `uploadAttachmentForUser`'s storage-first-then-insert-with-cleanup-on-insert-failure ordering (F065's own, pre-existing logic) already guards against.
- **AS-566 (oversized rejected BEFORE the task is created) is satisfied by doing the size check purely client-side, before the extension ever calls `POST /api/extension/tasks` at all** — not by reordering task-creation vs. upload (which the RLS constraint above rules out). `checkScreenshotSize()` (`extension/src/submit/upload.ts`) measures the real decoded byte length of the annotated/captured screenshot's base64 data URL and is called from `report-form.tsx`'s `handleSubmit` before the `fetch` to the tasks route — for an oversized screenshot, no task-creation request is ever made for that submission. The server-side check in the new `/api/extension/attachments` route (via `MAX_ATTACHMENT_SIZE_BYTES` and `uploadAttachmentForUser`'s own Zod re-validation) is defense in depth for a buggy/bypassed client, not the primary enforcement for "before the task is created" — a bypassed client that reaches the attachments route directly would find a task already created (its text-report submission), same as every other upload-after-create ordering in this codebase; the size limit itself is still enforced there for real, just not what makes "before" hold.
- **AS-567's forced failure targets a REAL, deterministic Supabase Storage-layer conflict, not the (already-proven, reused) "row insert fails after Storage succeeds" cleanup path from F065.** `uploadAttachmentForUser` gained a test-only `objectPathOverride` parameter (documented in its own doc comment as never used by any production caller) so the test can make two real uploads target the exact same object path — Storage's real `upsert: false` genuinely rejects the second write with a real conflict. This proves: the failing call returns `ok:false` without ever reaching the insert step, exactly one attachment row survives (not a duplicate, not zero), and the original object and the task are both untouched. The OTHER direction of the failure space (Storage succeeds, the subsequent row insert fails, and the object is cleaned up) is F065's own pre-existing logic, reused verbatim here, not reimplemented — it was not re-tested from scratch in this feature's own test file, since doing so would just be re-testing already-shipped, already-covered code under a different assertion ID for no added confidence.
- **A failed screenshot upload never rolls back or deletes the already-created task**, per the clarification's explicit "failure handling ... preserves the reporter's work; no silent no-ops." The reporter's text report is real and valuable the instant the task exists; discarding it because a screenshot attach failed would be strictly worse for the reporter than keeping the task and telling them the screenshot didn't attach. `report-form.tsx`'s success state carries an optional `attachmentWarning` string (rendered via a new `report-form-attachment-warning` testid) so this failure is stated, never silent, without hiding the fact that the task itself is real.
- **`MAX_ATTACHMENT_SIZE_BYTES` is mirrored (not imported) into `extension/src/submit/upload.ts`.** Confirmed by reading `extension/tsconfig.json` that the extension workspace has no path alias into the root app's `lib/` — same reason `report-form.tsx`'s `STATUS_OPTIONS` already mirrors `lib/actions/tasks.ts`'s status enum rather than importing it (F293's own precedent). Documented plainly in the constant's own comment, including "if this changes in `lib/validation/attachments.ts`, update this too — the server-side check is the real, authoritative boundary regardless."
- **F294's screenshot-resolution priority: `getAnnotatedResult()` first, falling back to `getLastCapture()`.** Matches F285's own handoff note exactly (an annotated result supersedes the pristine capture once it exists; a reporter who captured but never annotated still has something to upload). Re-verified by reading `extension/src/capture/store.ts` directly rather than trusting F285's handoff text alone — still accurate as of this feature.
- **New Route Handler `app/api/extension/attachments/route.ts`, not a direct client-side Supabase Storage call from the extension.** The existing web app's own attachment flow (`lib/actions/attachments.ts`'s `uploadAttachment`) already goes through server-side code (a Server Action) rather than the browser client uploading to Storage directly — mirroring that shape for the extension (a Route Handler doing the same server-side work) keeps exactly one real implementation of "validate, upload, insert, cleanup-on-failure" (`uploadAttachmentForUser`) shared by both callers, rather than a second, parallel client-side Storage-upload implementation living only in the extension that could drift from the web app's validation/cleanup behavior.
- **F274 (magic-byte/file-signature sniffing) has not landed** — grepped `lib/validation/attachments.ts` and the rest of `lib/` for "magic"/"sniff"/"file-signature" before starting; found nothing beyond unrelated "magic link" auth text, and no F274 handoff file exists yet. The same MIME-spoofing exposure F274's own spec calls out for avatars applies identically to this path (a caller could label arbitrary bytes as `image/png`) — noted here rather than expanding this feature's scope to implement sniffing itself, per the feature spec's explicit instruction.
