## Decisions made
- **`chrome.scripting.executeScript` needs the `scripting` permission declared in the manifest** in addition to (not instead of) `activeTab`/host_permissions for host access — verified against the current `chrome.scripting` reference docs (https://developer.chrome.com/docs/extensions/reference/api/scripting, "Permissions" section, checked 2026-08-20): the `scripting` permission gates the API surface itself; `activeTab` (or a matching `host_permissions` entry) gates which tab it's allowed to inject into. Added `"scripting"` to `manifest.json`'s `permissions` array. **No new `host_permissions` entry and no `<all_urls>`** were added — the picker relies entirely on the `activeTab` gesture chain (popup button click → `chrome.scripting.executeScript` against the resulting active tab), matching tech-decisions.md's explicit narrow-permission stance.
- **Injected function returns a Promise, resolved via `chrome.scripting.executeScript`'s own documented "waits for the promise to settle" behaviour** rather than a `chrome.tabs.sendMessage` round-trip — simpler, one fewer message-passing surface, and the popup has nothing else to do until the pick resolves anyway.
- **Confidence scheme (documented in `selector.ts`'s file header):** `id` (unique `#id`) > `data-attribute` (unique `tag[data-*="value"]`, preferring `data-testid` when present) > `nth-of-type-path` (structural `tag:nth-of-type(n)` chain up to the nearest ancestor with an id, or the document root). The record always carries which tier actually produced the selector — callers are never handed a bare selector string with no signal about how fragile it is.
- **Shadow DOM: explicitly unsupported**, per the clarification's simpler/narrower tie-breaker. Detected via `event.composedPath()[0]` (the real innermost target, correctly resolved even across an open shadow boundary) plus `element.getRootNode() instanceof ShadowRoot`. Reported as `{ ok: false, reason: "shadow-dom-unsupported" }` rather than generating a selector that could never re-locate the element through a plain `document.querySelector` (which cannot pierce a shadow boundary).
- **Iframes: explicitly unsupported, but via a different detection mechanism than originally planned** — see "Notes for the next worker" below for the empirical finding that forced this. Verified for real (same-origin iframe, `AS_547_clicking_inside_a_same_origin_iframe_is_reported_as_unsupported_not_a_wrong_selector`) that hovering the pointer into an `<iframe>`'s box is what's detectable from the top frame (a `mouseover` transition onto the `<iframe>` element itself), not a click — a click event whose mousedown+mouseup both occur inside an iframe's interior is **never delivered to the top frame's listeners at all**, same-origin or cross-origin. Concluding the pick as soon as the pointer enters an iframe's box (rather than waiting for a click that structurally cannot arrive) is what satisfies "never a silent no-op" here — waiting forever with no explanation would otherwise be the alternative.
- **Injected-code duplication:** `chrome.scripting.executeScript({ func })` serializes `func` and runs it in an isolated world with no closure over this module's other imports, so `element-picker.ts`'s `runPickerInPage` contains a small duplicated copy of `selector.ts`'s tiered algorithm (documented at both call sites, kept in lock-step by comment cross-reference). `selector.ts` remains the single canonical, unit-tested source of truth for the algorithm and its confidence scheme; the duplicate exists purely because of the `chrome.scripting` execution model. Considered `files: [...]` (a separately built/injected script) as the alternative — not used, to avoid adding a second Vite build entry for one small function, but flagged here for a future worker if the duplication becomes a maintenance problem.
- **Popup UI is independent of the screenshot-capture state machine** — a reporter can pick an element whether or not they've captured a screenshot, matching the spec's framing ("the extension records which DOM element the report is about" as a standalone fact, not something gated behind a capture).

## Notes for the next worker
- **Real harness/browser-behaviour finding worth reading before touching iframe detection again:** I initially assumed (per the feature spec's own framing) that a click landing inside an `<iframe>` would still reach the top frame's `click` listener with the `<iframe>` element itself as `event.target`, since `document.elementFromPoint` resolves an iframe's box to the iframe element from the ancestor document's point of view. That assumption was **wrong** and empirically disproven while writing `extension/tests/element-picker-selector.spec.ts`: a `mousedown`+`mouseup` sequence that both occur while the pointer is inside an iframe's box are delivered **only to the iframe's own document** — the top frame's `click` listener (even with `{ capture: true }`) never fires at all, regardless of whether the iframe is same-origin or cross-origin. What **is** reliably delivered to the top frame is a `mouseover` transition onto the `<iframe>` element the instant the pointer's hit-test first resolves to it (entering its box) — DOM hit-testing treats an iframe as an opaque element from the ancestor's perspective for that purpose, even though continuous `mousemove`/click delivery inside its interior is not forwarded. `runPickerInPage` in `element-picker.ts` now finishes the pick as soon as this `mouseover` fires, which is what makes `AS_547_clicking_inside_a_same_origin_iframe_is_reported_as_unsupported_not_a_wrong_selector` pass for real (not stubbed) — a genuine mouse move + click sequence over a real `<iframe id="cross-frame" src="about:blank">` in the test fixture.
- **`chrome.scripting.executeScript` does NOT have the same "cannot be granted without a real toolbar-click gesture" limitation `chrome.tabs.captureVisibleTab` has in this harness** (verified empirically, contradicting nothing but extending F283/F284's findings) — **when the target tab's origin is already covered by a declared `host_permissions` entry**, `chrome.scripting.executeScript` succeeds without `activeTab` ever being granted. This extension's manifest already declares `host_permissions: ["http://localhost:3000/*"]` (F281, for the connect flow), so `extension/tests/element-picker-selector.spec.ts` spins up a real local HTTP server on port 3000 (closed after each test) and drives the entire picker end-to-end for real — no stubbing of `chrome.tabs.query`/`chrome.scripting.executeScript` anywhere in the live-picker test group. **What still required care:** `launchPersistentContext` opens with one blank initial tab that must be closed (otherwise `chrome.tabs.query({ active: true })` can resolve to it instead of the real content page), and opening the popup as a Playwright `newPage()` (necessarily, since Playwright can't script a real toolbar-icon popup) makes the popup tab itself "active" in this harness's tab-strip model, unlike a real MV3 action popup which is never part of the tab strip at all — the test works around this by calling `contentPage.bringToFront()` immediately before clicking the popup's pick button, which correctly makes `chrome.tabs.query({ active: true, currentWindow: true })` resolve to the content page inside the popup's own click handler. No part of this feature's core mechanism (`chrome.scripting.executeScript`'s injection, promise-return handling, or the picker's own event listeners) had to be verified by code inspection alone — every assertion has a real, unstubbed browser test.
