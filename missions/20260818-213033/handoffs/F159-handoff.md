## Decisions made
- **Write/access-control rule for `task_assignees`**: routed every policy (SELECT, INSERT, UPDATE, DELETE) through `public.is_task_visible_to(task_id)` — the exact same helper and full-CRUD-sweep pattern F132 used for `checklist_items` (F132's own handoff explicitly asked the next `task_assignees` worker to do this from the start rather than reintroducing `is_task_workspace_member`). The clarified spec names no separate "who may assign" permission beyond project visibility, so per the ambiguity-resolution default (simplest option, no second source of truth) anyone who can see the task can assign/unassign on it — matching the existing boundary `lib/actions/tasks.ts`'s `reassignTask` already uses for `tasks.assignee_id` writes (task visibility/membership only, no separate assign-permission role).
- **`assigned_by` is nullable and left `null` for backfilled rows.** The legacy `tasks.assignee_id` column has no "who assigned this" data to backfill from, so guessing an actor (e.g. the task's `author_id`) would invent a fact not present in the source data. New assignments made after this migration (a future feature's Server Action) should populate it from the acting user.
- **`tasks.assignee_id` was left completely unchanged**, per the clarified spec's explicit instruction — only a deprecation comment was added via `comment on column`. No application code reading/writing `assignee_id` was touched.
- **Index**: only a new index on `user_id` was added. `task_id` is already the leading column of the composite primary key `(task_id, user_id)`, which Postgres already uses efficiently for "who's assigned to this task" lookups — a redundant single-column index on `task_id` would be pure overhead.
- **Migration timestamp**: generated as `20260821222659_...` by `supabase migration new`, then manually renamed to `20260822020000_task_assignees_table.sql` so it sorts after the two already-pending-but-unapplied migrations from earlier features (F142, F144) that were sitting in the repo before this feature ran, keeping chronological migration order intact.
- **No Server Action or UI was built.** The feature spec's file scope is `supabase/migrations/` + `lib/supabase/database.types.ts` (+ the integration test) only — a Server Action layer for reading/writing multiple assignees (needed for the app to actually use this table) is explicitly a later feature's job per the spec's own "Files (approximate)" list, which does not mention `lib/actions/`.
