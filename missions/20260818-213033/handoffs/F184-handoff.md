## Decisions made
- **Atomicity implemented as a single Postgres RPC (`create_project_from_template`), not multiple sequential client-side inserts.** A single PL/pgSQL function body executes inside one implicit transaction — the exact same idiom this codebase's `create_workspace_with_owner` (supabase/migrations/20260817234323_workspace_create_rpc.sql) already established for "two rows must both exist or neither does." Explicit test proof: a template with a malformed (empty-title) task raises the DB's own `tasks_title_not_empty` CHECK partway through the function's loop, which rolls back the ENTIRE call including the project row inserted first — confirmed by re-querying `projects` for the attempted name and finding zero rows.
- **Every seeded task gets its own key/number via F145's existing atomic trigger mechanism, not a manually-computed value.** The RPC's task inserts never set `number`; F145's `assign_task_number` BEFORE INSERT trigger fires per-row exactly like every other task-creation path in this codebase (createTaskFromTemplate, duplicateTask, plain createTask). Same for the project's `key` (F145's `assign_project_key` trigger).
- **The F218 "columns" gap (per the run instructions): built the project-template payload WITHOUT a columns concept.** F218 (custom project statuses) has not been built — every project today only has the fixed todo/in_progress/in_review/done statuses; there is no `project_statuses` table. `projectTemplatePayloadSchema` (lib/validation/templates.ts) therefore has NO `columns` field at all — inventing fake column data now would be a second source of truth F218 would have to reconcile. Every seeded task is created with the fixed default status `'todo'` (the RPC hardcodes `'todo'`, mirroring `createTaskFromTemplate`'s own default). The schema's doc comment explicitly tells a future F218 worker to add an OPTIONAL `columns` field (optional so existing saved templates without it keep parsing) and extend both `saveProjectAsTemplate` and the `create_project_from_template` SQL function once real columns exist. This is the "cleanest way to leave room for it without inventing fake column data" call from the run instructions.
- **How a project-kind template originates: built `saveProjectAsTemplate` — "save an existing project's current tasks as a template," mirroring F182's `saveTaskAsTemplate` at project scope.** The spec's draft scope only described the create-FROM-template direction; the clarification file's "simpler option, no new dependency" rule pointed here since F182 already established the exact producer/consumer pattern (a save action snapshotting current state into a `task_templates` row, a create action applying it) — reusing that shape at project scope needed no new concept, no new table (same `kind='project'` row F181 already reserved for this feature), and no second source of truth. `saveProjectAsTemplate` snapshots every non-deleted task in the source project (title/description/description_json/priority/checklist/estimate/tags — the same clonable fields cloneTaskFields/duplicateTask establish, minus assigneeIds), ordered by board position (status column order, then position within column), into a new `kind='project'` template row.
- **Project-template payload deliberately omits `assigneeIds`** (unlike F182's task-template payload, which has them): a project template is meant to be reused across arbitrary future projects, potentially in workspaces where the original assignees are not members at all — the spec's own field list (title/description/priority/checklist/estimate) doesn't mention assignees either. Per the "simpler option, no second source of truth" rule, this feature does not invent its own assignee-membership-resolution story on top of what F182 already built for individual tasks.
- **The RPC is SECURITY DEFINER, granted only to `service_role`** (not `authenticated`) — called via the admin client from `createProjectFromTemplate`, which itself re-checks membership + `canWrite` server-side first (same "admin client bypasses RLS, the app-level check is the ONLY enforcement" convention `createTaskFromTemplate`/`renameTemplate`/`deleteTemplate` already established in this same file). The function trusts its caller rather than re-deriving `auth.uid()` itself, matching that existing convention rather than inventing a second enforcement style within the same file.
- **"Save as template" UI placed on the projects list card's action row**, next to Edit/Archive — mirrors F183's own reasoning for placing its task-level equivalent on the task detail Sheet's footer ("no existing context-menu convention to mirror, use the nearest existing per-item action row").
- **New Project dialog uses a Tabs (Blank / Start from template) layout** when at least one project template exists in the workspace, falling back to the original single blank-only form when the list is empty (same "empty list → feature step is not offered" convention `NewFromTemplateButton`, F183, already uses by returning `null`).
