## Decisions made
- **Every call site of `lib/tasks/is-overdue.ts`'s `isOverdue` was found and converted** (the mission's explicit "half-converted app is worse than none" instruction): `components/task/task-card.tsx` (board card + list-table + drag overlay), `components/task/task-list-table.tsx` (list view + dashboard table, they share this one component), `components/task/task-detail-sheet.tsx` (4 call sites — due-date label, icon, sr-only text, input border). Searched with `grep -rn "isOverdue("` and `grep -rn "overdue"` across the whole tree; also checked the workspace-wide search page (`app/(workspace)/w/[workspaceSlug]/search/page.tsx`) and confirmed it renders only title/project/status/priority — no due date, no overdue state — so there was genuinely nothing to convert there.
- **The dashboard overdue tile's SQL path was NOT left on server time.** `get_overdue_count` (F075) computed `current_date` in the database's own timezone (effectively UTC). Per this feature's explicit instruction to decide how the timezone reaches SQL and record it here: added a `p_timezone text default 'UTC'` parameter, computing `(now() AT TIME ZONE p_timezone)::date` instead of `current_date` — Postgres's own IANA-timezone-database-aware conversion, the SQL-layer equivalent of `lib/time/user-timezone.ts`'s `todayInTimeZone`. `lib/queries/dashboard.ts`'s `getOverdueCount` now takes a `timezone` argument (default `"UTC"` at the JS wrapper level only, for pre-existing test callers — see below) and forwards it as `p_timezone`.
- **`create or replace function get_overdue_count(p_workspace_id uuid)` could not simply gain a trailing parameter.** Postgres identifies a function by its argument type list; appending `p_timezone` via `create or replace` would have created a SECOND, distinct `get_overdue_count(uuid, text)` overload alongside the original `get_overdue_count(uuid)` rather than replacing it — leaving two permanently-disagreeing definitions of "overdue" in the database (exactly the split-brain this feature exists to remove). The migration explicitly `drop function if exists get_overdue_count(uuid)` first, so there is exactly one `get_overdue_count` afterward, with `p_timezone` optional.
- **`p_timezone default 'UTC'`, not a required argument.** This keeps the migration additive (mission convention) and means F075's own pre-existing RLS/perf tests (`dashboard-rls-cross-workspace.test.ts`, `perf-budget.test.ts`, the original `overdue-count-rpc.test.ts` AS-131 tests) — which call the RPC with only `p_workspace_id` to prove workspace-scoping, not timezone behavior — keep passing unchanged. Every real app call site (`lib/queries/dashboard.ts` from the dashboard page) always passes the caller's actual `profiles.timezone`; the default only matters for callers this feature didn't touch.
- **New `lib/queries/profile.ts`'s `getCurrentUserTimezone(supabase)`** is the single place a Server Component resolves the caller's timezone — one `auth.getUser()` + one `profiles` select, given the page's own already-created `supabase` client (not a new session). Called exactly once per route entry (`board/page.tsx`, `list/page.tsx`, the workspace dashboard `page.tsx`), in `Promise.all` alongside that page's other independent fetches, then threaded down as a plain `timezone` prop — never re-queried per card/row, satisfying the mission's explicit "Server Components must read the caller's timezone ONCE per request" instruction. `components/dashboard/dashboard-task-table.tsx` (a nested Server Component composed inside the dashboard page, not its own route) receives `timezone` as a prop from its caller rather than calling `getCurrentUserTimezone` itself, for the same reason.
- **Client Component `timezone` props default to `"UTC"`** (`TaskCard`, `TaskListTable`, `TaskDetailSheet`, `SortableTaskCard`, `BoardColumn`, `Board` all thread it through, optional with this default) — same "safe default" convention this codebase already uses for `updatedAt`/`totalMinutes`/`currentUserId`. Every real page in the app passes the caller's actual timezone; the default only matters for the many pre-existing unit tests that render these components with `dueDate: null` (isOverdue short-circuits to `false` regardless of timezone) or a due date far enough in the past/future that no realistic timezone shift changes the verdict — none of them needed updating. `lib/tasks/is-overdue.ts`'s own `isOverdue` (the pure function) does NOT default `timeZone` — it's a required, explicit argument, per tech-decisions.md's "helpers are pure ... timezone is always an explicit argument" rule; only the React component layer (a different concern, ergonomics for composition) has a default.
- **`lib/time/user-timezone.ts` keeps its own small `isValidTimeZone`** (construction-based `Intl.DateTimeFormat` + catch, same technique F123 already established in `lib/validation/profile.ts`) rather than importing that file's private helper — a pure `lib/time` module must not depend on the Zod validation layer (this codebase's dependency direction is validation -> domain, never the reverse). Accepted as intentional, minor duplication of a 4-line check between two different architectural layers.
- **`startOfDayInTimeZone`/`endOfDayInTimeZone` resolve each boundary independently** rather than computing `endOfDay = startOfDay + 24h - 1ms` — the latter is wrong on a DST-transition day (a spring-forward day is only 23 real hours, fall-back is 25), which the DST unit test (`test_AS_207_start_and_end_of_day_resolve_the_dst_aware_utc_boundary`) catches directly (asserts the transition day is exactly 23 hours long). Implemented with a 2-iteration "guess the UTC instant, correct against the zone's own offset at that guess, correct once more against the corrected instant" technique (the same one `date-fns-tz`/Luxon use internally) rather than adding either as a dependency, per tech-decisions.md's "no new date library."
- **`isOverdueInTimeZone` compares via `date-fns`'s `parseISO` + `isBefore`**, not a raw string comparison, so the module's actual date arithmetic genuinely goes through `date-fns` as the Draft scope specifies ("built on date-fns... plus Intl for zone maths"). `parseISO`'s local-timezone interpretation of a date-only string doesn't affect correctness here because both sides (`dueDate`, `today`) are parsed identically, so their relative ordering is unaffected by whatever "local" means on the machine running the code.
- **`Board`'s `<DragOverlay>` `TaskCard` also receives `timezone`** — it's a separate render of `TaskCard` from the one inside `SortableTaskCard`/`BoardColumn`, easy to miss since it doesn't go through the same prop chain. Caught by re-reading `board.tsx` fully rather than pattern-matching only the first `TaskCard` usage found.
