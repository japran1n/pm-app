## Decisions made
- Extracted ONE new shared helper, `isProjectVisibleToCaller(admin, {projectId, visibility}, userId, role)`, placed directly above the existing `filterProjectVisibleUserIds`/AS-290 helper in lib/actions/tasks.ts, and wired it into every single-task action call site rather than re-implementing the rule per action — per the task's explicit "reuse, don't reimplement" instruction. It intentionally takes the caller's already-known `role` (from the action's own prior `requireActiveMembership` call) rather than re-querying `workspace_members`, since every call site already has that value — this makes it one extra query (`project_members`) only, and only when the project is actually private, mirroring the bulk paths' own "only query when private" optimization.
- Did NOT refactor `bulkUpdateTasks`/`bulkDeleteTasks`'s own inline copies of this rule to call the new helper — they are already correct and already tested; touching them would add regression risk with no security benefit. This means the rule now exists in two shapes in the file (the new single-task helper, and the two bulk paths' inline batch-shaped copies) rather than one — documented here rather than silently left. A future cleanup could unify them if desired, but is not required for correctness.
- Extended fix scope (within the same file) to `createTaskForUser` (and its `createTask` wrapper), which the finding B2 text didn't name but is the same bug class in the same file: an active workspace member could create a NEW task directly inside a private project they have no access to, with only `requireActiveMembership` + `canWrite` checked. Same helper, same fix pattern, same test structure (negative/positive/regression) added for it.
- Where a select already fetched `projects!inner(id, workspace_id)` but not `visibility`, added `visibility` to the select list (no new round trip) rather than a second query, mirroring how `editTask` already did this for its mention-sanitisation use of `visibility`.
- `duplicateTask`'s source-task select uses `projects(workspace_id)` (no `!inner`, no embedded `id`) — added `visibility` to that embed and used the already-selected top-level `sourceRow.project_id` as the `projectId` argument (rather than adding `id` to the embed) to keep the diff minimal.
- Failure messages: every check reuses the SAME string the action already returns for its role/membership failure immediately above it (e.g. editTask still says "Viewers don't have permission to edit tasks." even when the real reason is private-project visibility) — per the spec's explicit instruction not to leak whether a task exists vs. is merely invisible, and to match the existing generic-message convention (AS-146) already used throughout this file.
- Audited for a system/cron caller reaching any of the fixed actions with no `auth.uid()` (F309/F318 precedent): none found. `generateNextOccurrence` (the recurrence job) is called FROM `moveTaskStatus`, never the reverse, and inserts new rows directly via the admin client rather than calling `createTaskForUser`. The only external caller of `createTaskForUser` besides the `createTask` Server Action is `app/api/extension/tasks/route.ts`, which authenticates a real user via a bearer JWT (not a system/service caller) — unaffected by this change.

## Out-of-scope work needed
- **Same vulnerability class exists in sibling action files, NOT fixed here** (deliberately, per this feature's explicit `lib/actions/tasks.ts`-scoped Files boundary — fixing all of these in one pass would be a much larger, differently-scoped feature). Verified via grep that every one of these files checks ONLY `requireActiveMembership` before mutating task-scoped data through the admin client, with no re-check of the target task's project visibility: `lib/actions/checklist.ts`, `lib/actions/comments.ts` (addComment/editComment/deleteComment — comments.ts already fetches `visibility` per-call but only uses it for mention sanitisation, exactly the same pre-fix pattern editTask had), `lib/actions/dependencies.ts`, `lib/actions/attachments.ts`, `lib/actions/watchers.ts`, `lib/actions/time-entries.ts`, `lib/actions/comment-reactions.ts`, `lib/actions/purge.ts`. Recommend a dedicated blocker-class follow-up feature (e.g. F323) scoped to exactly these eight files, reusing this feature's `isProjectVisibleToCaller` pattern (exported or duplicated with the same doc-comment convention) and this feature's test structure (outsider-rejected-DB-unchanged / owner-succeeds / explicit-member-succeeds / workspace-visible-regression, driving the real Server Actions, never a raw RLS-scoped query) per action in each file.
- **Read-side confidentiality gap, not fixed here** (out of the "mutation" framing of this feature): `getTaskDetail` and `getOpenBlockers` in lib/actions/tasks.ts also use the admin client and check only `requireActiveMembership`, never project visibility — so any active workspace member can currently read a private project's task's full detail (title, description, comments via the detail sheet's own subsequent fetches, blockers) even though they can't mutate it after this fix. Recommend folding this into the same F323 follow-up (or a sibling read-path feature) using the identical `isProjectVisibleToCaller` check, returning "Task not found" (matching this function's existing not-found convention) rather than a permission-denied message, since a read-path leak should not even confirm the task exists.
- Two now-slightly-divergent inline copies of the private-project rule remain in `bulkUpdateTasks`/`bulkDeleteTasks` (pre-existing, correct, untouched) alongside the new single-task `isProjectVisibleToCaller` helper — a future cleanup could unify all three behind one helper if a maintainer wants to reduce duplication, but this is not a correctness issue.
