## Decisions made

- **Stable node identity via a client-generated `id` attribute.** Tiptap's stock `TaskItem` has no id. `onReadOnlyChecked(node, checked)` (Tiptap's own built-in hook for read-only checkbox clicks — `node_modules/@tiptap/extension-list/src/task-item/task-item.ts`) only hands back the ProseMirror node, not a stable document-position-independent handle. I extended `TaskItem` (`TaskItemWithId`) with an `id: string | null` attribute, assigned once via an `appendTransaction` ProseMirror plugin that only runs on the EDITABLE `RichTextEditor` instance (`assignTaskItemIds: true`) — never on `RichTextRenderer`, which must never mint a fresh id for a node whose id is already persisted server-side (that would desync the id the click reports from what's actually in the database). This is the simpler option versus deriving addressing from ProseMirror document positions (which shift under any edit and don't survive a save/reload) or ancestor-index paths (finicky `$pos.index(depth)` math, no real gain over a plain id).
- **`onReadOnlyChecked` is optimistic-by-design, not a sync gate.** It always returns `true` when `onToggleTaskItem` is provided and a real `id` exists (accepting the click at the DOM level immediately), then fires the persistence call in the background. `RichTextRenderer` never reaches back into the DOM after the async call resolves — the caller (`task-detail-sheet.tsx`) owns optimistic state (`descriptionJson`) + rollback via the `content` prop, exactly like every other field on that Sheet already does with `editTask` (title/description/dueDate/priority — see `saveField`). A failed save reverts by the parent setting `descriptionJson` back to the previous value, which `RichTextRenderer`'s existing content-resync `useEffect` picks up and re-renders correctly (Tiptap's `TaskItem` NodeView already syncs `checkbox.checked` from the node's attrs on every `update()`). This reuses an existing effect rather than adding a second revert mechanism.
- **A dedicated `toggleDescriptionChecklistItem` action, not `editTask`.** `editTask`'s `EditTaskUpdates` only has a `description` field (the legacy plain-text column) — there is deliberately no `descriptionJson` field on it (see `20260822090000_task_description_json.sql`'s header comment: flipping the derivation direction was explicitly deferred). Reusing `editTask` would have required either (a) adding a `descriptionJson` field to `EditTaskUpdates`, reopening the "source of truth" question that migration deferred, or (b) round-tripping the WHOLE document through a generic `description` write, contradicting this feature's own instruction to consider a targeted update given cross-user race risk. A narrow, single-purpose action keeps `editTask`'s contract untouched and writes only `description_json`.
- **Concurrency: read-modify-write with re-fetched current state, last-write-wins — an accepted, documented tradeoff, NOT the same guarantee F153's structured checklist has.** `toggleDescriptionChecklistItem` re-fetches `description_json` fresh (never trusts the client's possibly-stale copy) before computing the new document and writing it back in a single `UPDATE`. This is safe against a stale CLIENT overwriting a change it doesn't know about, but it is NOT atomic against two truly concurrent server-side toggles of DIFFERENT checkboxes on the SAME task (both could read before either commits, and the second write's full-document overwrite could clobber the first's change) — a real limitation of "read whole doc, modify one node, write whole doc back" without either a DB-side atomic `jsonb_set` RPC or a version/`updated_at` optimistic-concurrency check. I chose NOT to build the atomic RPC or a version column: per the clarified ambiguity-resolution answer ("take the simpler option that adds no new dependency and no second source of truth"), and because the feature spec itself flagged this as an acceptable, documented tradeoff for this feature's scope. This is the key way F173 differs from F151-F153's structured checklist: that checklist's items are separate ROWS (`task_checklist_items`), so two concurrent toggles of different rows never collide at the database level at all — there is no equivalent row-level isolation for a single JSON blob. If concurrent inline-checklist editing becomes a real product need, the fix is a DB-side `jsonb_set`-based RPC (single atomic UPDATE statement referencing the current column value under the row's own lock) — flagged below as out-of-scope follow-up, not attempted here to stay in scope.
- **Migration required to make `description_json` writable at all — not optional, not "nice to have."** `20260822090000_task_description_json.sql`'s trigger (`tasks_update_search_vector`) unconditionally overwrote `description_json` FROM `description` on every write, exactly as its own header comment predicted would need to change ("Once a later feature wires the rich-text editor into the write path and starts writing description_json directly, this trigger's derivation must be flipped — flagged in this feature's handoff as required follow-up work"). Without flipping it, `toggleDescriptionChecklistItem`'s write would have been silently discarded on the very next trigger invocation. `20260822130000_task_description_json_direct_write.sql` makes the derivation conditional: on UPDATE, if `description_json` changed and `description` did NOT (exactly `toggleDescriptionChecklistItem`'s write shape), keep the caller's `description_json` and derive `description_text` (the FTS projection) FROM it via a new `tiptap_text_from_doc()` helper (`jsonb_path_query`'s recursive `$.**.text` descent); on INSERT, if a caller supplies a non-null `description_json` directly (used by the integration test fixtures), keep it. Every OTHER existing write shape (the `editTask`/`createTask` path, which only ever sets `description`) is byte-for-byte unchanged — confirmed by re-running `tests/integration/edit-task.test.ts` (14/14 pass) and `tests/unit/fts-tasks.test.ts` after applying the migration. `description` itself is still never derived FROM `description_json` — flipping that direction too is out of scope (see below).
- **Visual distinction from F151-F153's structured Checklist** (per this feature's explicit scope note) is via CSS only (`app/globals.css`'s `[data-type="taskList"]` rules — dashed left rule, no list marker, no drag handles, strikethrough-on-check) rather than adding explanatory copy in the UI — the structured Checklist section already has its own distinct visual language (drag handles, add-box, progress), so the inline checkboxes just need to visibly NOT be that, not carry a disclaimer. AS-272's completion percentage is untouched — `checklistItems`/`ChecklistListItem` (F151-F153's actual source of truth) are never read or written by anything in this feature.
- Toolbar icon: `ListChecks` from `lucide-react` (already an installed dependency, no new package).

## Out-of-scope work needed

- **Wiring `RichTextEditor` into the description CREATE/EDIT UI.** `task-detail-sheet.tsx` still edits `description` via a plain `<Textarea>` — `RichTextRenderer` is only used for the read-only "Preview" of `description_json`. This means there is currently no in-app UI path to actually TYPE a `taskList`/`taskItem` into a description (the toolbar button I added is real and functional, but only reachable once a caller mounts `RichTextEditor` for the description write path — which is a pre-existing gap this feature did not create, flagged already in `20260822090000_task_description_json.sql`'s own header comment as "not yet wired into the task create/edit UI ... lands in a later feature"). AS-311 tests seed `description_json` directly (matching how `RichTextRenderer`'s Preview would render content from any future editor once it's wired up), which is why the integration tests insert `description_json` directly rather than driving a UI form.
- **Flipping `description` to be DERIVED FROM `description_json`** (rather than the reverse) once the item above lands — `20260822090000_task_description_json.sql`'s own header comment already flags this as required follow-up; `20260822130000_task_description_json_direct_write.sql` (this feature) only handles the narrower "some writes touch description_json directly" case, it does not change which column is authoritative for reads elsewhere.
- **An atomic DB-side `jsonb_set` RPC for `toggleDescriptionChecklistItem`**, to close the two-different-checkboxes-toggled-simultaneously race documented above under Decisions Made, if concurrent inline-checklist editing on the same task turns out to matter in practice.
- **Comments (F174) reusing the same editor** automatically inherit `TaskList`/`TaskItem` in their schema (shared `sharedExtensions()`) and the sanitisation allow-list addition, but I did not wire an inline-toggle-and-persist handler for comment bodies — F174's comment `body_json` write path (`lib/comments/rich-text.ts` / whatever action persists comment edits) was out of scope for this feature (F173's spec/Files list is task descriptions only) and I did not touch it. A future feature would need its own toggle action mirroring `toggleDescriptionChecklistItem`, scoped to `comments.body_json`, if inline comment-checklist toggling is desired.

## Autonomous decisions

AUTONOMOUS_DECISION: Chose a client-generated `id` attribute (not present in Tiptap's stock `TaskItem`) as the stable addressing mechanism for server-side toggle, rather than document-position-based addressing, since the spec left the exact addressing mechanism open ("your call") and this is the simplest option that survives save/reload without new infrastructure.

AUTONOMOUS_DECISION: Applied the migration required to make `description_json` directly writable (`20260822130000_task_description_json_direct_write.sql`), since without it the feature could not function at all (every direct write to `description_json` would be silently discarded by the existing trigger on the very next invocation) — this was explicitly pre-flagged as required follow-up work by the F170 migration's own header comment, not a new scope decision I invented.

AUTONOMOUS_DECISION: Accepted last-write-wins (documented above) rather than building an atomic DB-side RPC, per the clarified ambiguity-resolution default (simpler option, no new dependency, no second source of truth) and the feature spec's own explicit invitation to make this call.
