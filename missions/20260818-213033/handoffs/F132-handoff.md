## Decisions made
- **F131 (project_members table) had not been run yet** (no migration, no handoff) even though F132's spec lists it as a hard dependency and the clarification's "Notes for clarification" explicitly point at needing this table's helper function. Per the ambiguity-resolution rule (simpler option, no new dependency, recorded here) I shipped a minimal version of F131's own described schema (`project_id`, `user_id`, `project_role` check in `('lead','member')`, `added_by`, `created_at`, unique on `(project_id, user_id)`) plus SELECT (any active workspace member) / INSERT+DELETE (workspace owner/admin or existing project lead) policies, as its own migration (`20260821140520_project_members.sql`). This handoff does **not** claim AS-224 (F131's own assertion, "adding a member grants access") — no membership-management Server Action or UI was built. See Out-of-scope below.
- **`projects.visibility`**: additive column, `text check in ('workspace','private') default 'workspace'`, so every existing project keeps its exact current (implicit workspace-wide) behaviour with no backfill needed.
- **`is_project_visible_to(project_id)`**: new SECURITY DEFINER helper — true iff the caller is an active member of the project's workspace AND (the project is `'workspace'`-visible, OR the caller is a workspace owner/admin, OR the caller has an explicit `project_members` row for that project). This single function replaces `is_project_workspace_member` in every SELECT policy this feature touches (subsumes its "just active membership" check, since `visibility = 'workspace'` makes the visibility check a no-op for every project created before this feature).
- **`is_task_visible_to(task_id)`**: thin wrapper resolving a task's `project_id` and delegating to `is_project_visible_to`; replaces `is_task_workspace_member` everywhere it appeared.
- **Scope of the sweep, exactly as the spec's "Added scope" section specifies**: mission-1 tables (projects, tasks, comments, attachments, time_entries) — SELECT policies only, per the spec's literal wording. M13-created tables that predate this feature and were built against the old `is_task_workspace_member` pattern (`checklist_items`, `task_dependencies`) — every policy (SELECT, INSERT, UPDATE, DELETE) swept, per the spec's explicit "sweep every one of those policies too, not only SELECT" instruction, since a private project's checklist/dependency rows must not be writable by a workspace-only member either. `task_assignees`, `task_watchers`, `task_templates` are also named in that note, but F159/F163/F181 (the features that create those tables) have not run yet — there is nothing to sweep for them; flagged below for whoever finishes those features.
- **AS-229 enforcement is a BEFORE UPDATE trigger, not RLS alone.** RLS's `USING`/`WITH CHECK` clauses apply to the whole row, and `projects_update_active_members` (unrelated to this feature, AS-029) intentionally still lets any active member edit a project's other fields. A trigger (`enforce_project_visibility_change_role`) fires only when `new.visibility is distinct from old.visibility` and raises unless the caller is an active workspace owner/admin. Superseded in a follow-up migration (`20260821140929_...bypass.sql`) to add an `auth.role() <> 'service_role'` guard after discovering the admin/service-role client (used by this repo's tests and read-only lookups per `lib/supabase/admin.ts`) has `auth.uid()` = null and was being incorrectly blocked by the first version of the trigger.
- **`attachments_objects_select_active_members`** (storage.objects policy) was included in the sweep since it already joined through `is_task_workspace_member(a.task_id)` — left the object INSERT policy alone (it authorizes uploads by parsing `task_id` out of the object path directly, before an `attachments` row exists, so it was never `is_task_workspace_member`-scoped to begin with and is out of this feature's SELECT-only scope for mission-1 tables).

## Out-of-scope work needed
- **F131 (db-schema-project-members, AS-224) still needs its own Server Action / UI work**: adding/removing a project member through the app (not just the table + RLS shipped here as this feature's prerequisite). A future worker picking up F131 should treat the `project_members` table and its two RLS-authorization helper functions (`is_project_lead_or_workspace_admin`, and the SELECT/INSERT/DELETE policies) as already shipped by this feature — do not re-create the table or duplicate the policies; add only the Server Action (`lib/actions/project-members.ts` or similar) and any UI.
- **F126 (db-roles-expansion, AS-215/AS-238)** has not run yet either — there is no `'guest'` workspace role in the `workspace_members.role` CHECK constraint yet, so this feature's `is_project_visible_to` cannot yet distinguish "non-guest member" (AS-227's exact wording) from "any active member": today every active member is implicitly non-guest, so the assertion holds vacuously. Once F126 adds a `'guest'` role, `is_project_visible_to` should be revisited to explicitly exclude `role = 'guest'` from the "workspace visibility grants access" branch (guests likely need an explicit `project_members` row even for workspace-wide projects) — flagged here rather than guessed at, since F126's clarified role semantics for guests aren't available to this feature.
- **task_assignees / task_watchers / task_templates RLS sweep** — F159, F163, F181 have not been built yet. Whoever builds them should route their SELECT (and any other) policies through `is_project_visible_to`/`is_task_visible_to` directly from the start, rather than the old `is_task_workspace_member`/`is_project_workspace_member` pattern, so no further F132-style sweep is needed for them.
- **`active_timers`** (time-tracking) was not touched — it is not named in this feature's file scope ("projects/tasks/comments/attachments/time_entries"), but it does join through `is_task_workspace_member`-equivalent membership too. Not fixed here; flag for a future RLS-consistency pass if private-project timer leakage is later found to matter.
