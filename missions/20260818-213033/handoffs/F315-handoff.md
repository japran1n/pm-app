## Decisions made
- Fix 1 (AS-214): confirmed no existing "Supabase client construction might fail" guard pattern exists anywhere in the codebase (checked `use-comments-realtime.ts`, the sibling hook, and `lib/supabase/client.ts` — neither has one). Added a minimal try/catch guard directly in `use-reactions-realtime.ts`'s `useEffect`: if `createClient()` throws (missing env vars — happens only in jsdom unit tests that don't load `.env`, never in real browser/SSR contexts where these vars are always injected at build time), log a dev-only warning and skip the subscription non-fatally instead of crashing the render. Verified this is the actual root cause by reproducing the exact stack trace from `npx vitest run tests/unit/user-avatar.test.tsx` before the fix (unhandled `@supabase/ssr` throw originating in `use-reactions-realtime.ts:44`), and confirming the fix makes all 10 tests in that file pass.
- Fix 2 (AS-382): double-checked before assuming the positive proof was missing — grepped every `comment_reply` reference in `tests/`. Found only: (a) a pure-function unit test (`tests/unit/notification-fanout.test.ts`) proving `computeFanoutRecipients` computes the right recipient/kind pair, which doesn't touch the real DB or `addComment`'s actual fan-out wiring, and (b) the negative preference-gating integration test the scrutiny report already flagged. Neither is a positive end-to-end proof against the real project. Added the missing test to `tests/integration/notification-fanout.test.ts` (the file that already holds the equivalent positive proof for `mention`/`task_assigned`/`watcher_update`-adjacent kinds), following its exact existing pattern (real signed-in session client via the `sessionClientForMock` mock, real `adminClient` seed/verify). Added one new seeded workspace member (`watcherUserId`) reused by only this new test.
- Fix 3 (AS-369): investigated the real call graph — `useReactionsRealtime`/`subscribeToReactionsRealtime` has exactly one call site in the whole repo (`components/task/comment-list.tsx`, inside `task-detail-sheet.tsx`), and `taskId` there is always a prop threaded down from a task the current session already fetched through `getTaskDetail`'s RLS-gated query — never a URL param, search param, or form input inside this component's own render path. Concluded: (a) this app's *own* UI has no attacker-controllable route to pass an arbitrary `taskId` into this function, and (b) a client-side re-check inside this repo's code would not close the theoretical gap anyway, because an attacker exploiting the documented Supabase platform behavior (RLS not applied to postgres_changes DELETE) would construct their own Realtime subscription directly with a valid session token, never calling any function in this repo at all — so no code-level guard here is even reachable by that attack path; genuinely closing it requires a server-side authorization mechanism (e.g. Realtime Authorization on private channels), a materially larger migration out of scope for this fix. Given the only data exposed via this specific gap is reaction metadata (comment_id/user_id/emoji) for an un-react event — not comment content or any other sensitive field — chose option (b) from the spec: record this as an ACCEPTED, LOW-SEVERITY, DOCUMENTED RISK rather than either silently ignoring it or over-engineering a fix for a narrow, largely-theoretical exploit. Documented the full reasoning inline in `lib/tasks/subscribe-comments-realtime.ts` (right above `subscribeToReactionsRealtime`) and added `tests/unit/reactions-realtime-delete-payload-shape.test.ts`, which pins two things so the decision can't silently rot: (1) the DELETE handler forwards only the three documented, non-sensitive fields — breaks if a future change widens the leaked payload — and (2) there is still exactly one real call site with the RLS-already-checked-taskId property this decision's scope depends on — breaks (and forces re-review of the decision) if a second, more attacker-reachable call site is ever added.
