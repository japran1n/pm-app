## Decisions made
- Followed the run-time instructions' framing over the spec's generic "Clarified implementation" boilerplate: this feature's own Draft scope/Files list (`supabase/migrations/` only, "function + cron.schedule") is a pure-SQL/pg_cron feature with no `lib/` module and no application code, so the boilerplate's "pure module under lib/, unit-tested independently of Supabase" answer does not apply here — it is templated across every feature archetype in this mission's clarification round, not scoped to this feature's actual Draft scope. This is a considered deviation, not a silent one; recorded here per the run instructions.
- Kind used for the notification: `task_due_soon` (not a new `'task_overdue'` value). `notifications_kind_check` already has no such value, and F211's own migration explicitly documents `task_due_soon_in_app` as this feature's future fan-out gating column — adding a parallel kind would create a second concept for the same thing. Simplest option, no new dependency, no second source of truth.
- Idempotency: a unique partial index on `notifications (user_id, task_id) where kind = 'task_due_soon'`, plus a `NOT EXISTS` guard in the sweep function before calling `create_notification`. No new tracking table, no new column on `task_assignees` — reuses the table the notification already lives in.
- Timezone handling: per the clarified ambiguity-resolution default (simplest option, no new dependency, no second source of truth) and confirmed by grepping `lib/supabase/database.types.ts` — neither `profiles` nor `workspace_members` stores a per-user timezone anywhere in this schema today, and adding one (plus UI) is out of this feature's actual migrations-only scope. The sweep therefore treats every assignee as UTC: `due_date <= (now() at time zone 'utc')::date`. Real per-assignee timezone support is out-of-scope work (below).
- "Done-category" check: reused the exact literal `status = 'done'` that `lib/tasks/blocked-guard.ts`'s `isDoneStatus()` and `lib/queries/tasks.ts`'s `getProjectBoardTasks` already use, per F158's own sweep-note convention, rather than inventing a second "done category" concept in SQL.
- Archived project / trashed task: reused the existing conventions — `projects.deleted_at is not null` = archived (F142's convention, confirmed via that migration's own header comment explaining why a parallel `archived_at` column was deliberately rejected), `tasks.deleted_at is not null` = trashed (mission-1 soft-delete convention).
- `create extension if not exists pg_cron` + its grants were REMOVED from this migration after `supabase db push` failed with `ERROR: dependent privileges exist (SQLSTATE 2BP01)` — re-running those statements on this already-provisioned project re-triggers a managed post-create hook script that conflicts with grants F178's migration (20260822160000_recurrence_scheduled_generation.sql) already applied. Since pg_cron is already enabled and granted transitively by every migration after F178, this migration only adds objects specific to this feature. Documented in the migration's own comment.
- Verification path (per run instructions): this session's Supabase project had an active PostgREST outage (`PGRST002`) for the whole duration of this feature's implementation, so the usual supabase-js `.from()/.rpc()` path is unreachable. Used the Supabase Management API's `POST /v1/projects/{ref}/database/query` endpoint (authenticated with `SUPABASE_ACCESS_TOKEN`, already present in `.env`) to run raw SQL directly against the live linked database instead — confirmed with a `select 1` smoke test before writing the suite, then used for all seeding/assertion/cleanup in `tests/integration/overdue-notification-sweep.test.ts`. This bypasses PostgREST entirely and talks straight to Postgres, so it remains valid even if PostgREST recovers.
- MCP: the Supabase MCP registry entry says `Worker use: yes`, but this session's live-schema introspection needs (tables, columns, existing conventions) were satisfied by reading the actual migration files directly (faster and equally authoritative, since the repo's migrations ARE the live schema for a project kept in sync via `supabase db push`) rather than calling MCP schema-introspection tools; no MCP tool calls were made for this feature.
