## Decisions made
- **Guest RLS branch on `is_project_visible_to`/`is_project_visible_to_row`**: added a guest-specific clause that requires an explicit `project_members` row regardless of `visibility`, and regardless of the owner/admin bypass (a guest is never owner/admin anyway, so that branch is moot for them) — implemented identically in both function variants in the same migration, per the orchestrator's explicit caution about the two-variant class of bug. Verified no new self-referencing subquery against `projects` was added to `is_project_visible_to_row` (the exact regression class the 20260821150000 fix migration exists to prevent) — the row-variant only uses its own passed-in parameters plus a `project_members` lookup, same shape as before.
- **Dashboard scoping for a guest (the "Notes for clarification" open question)**: took the simpler option with no new dependency — the workspace dashboard's aggregate RPCs (`get_priority_counts`, `get_status_counts`, `get_overdue_count`) are already `security invoker`, so once `is_project_visible_to` has the guest branch, those RPCs automatically scope to only the guest's own added projects' tasks with zero additional code. No separate "guest dashboard" page or redirect was built; a guest visiting the workspace root sees the same dashboard everyone else does, just correctly scoped by the RLS fix alone. This is the "their own projects only" reading, achieved without a second code path.
- **Invite flow**: `invited_project_id` is an additive nullable column on `workspace_members` (mirrors `invited_email`'s existing "set at invite time, read once on accept, left in place after as an audit trail" pattern) rather than a new join table — no second source of truth for "what does this invite grant." `inviteMember` independently re-verifies the named project belongs to the inviting workspace (defense in depth, matching this file's existing cross-workspace-leak checks) before writing it. `activateInvitedMemberships` grants the `project_members` row via the admin client (bypassing RLS) since there's no authenticated session in that sign-in-time code path for `addProjectMember`'s own Server Action re-check to run against; a `role === 'guest'` guard keeps the intent explicit even though `invited_project_id` is only ever non-null for guest invites today.
- **AS-222 verification strategy**: `workspace_members`'s own SELECT RLS policy (pre-existing, unrelated to this feature) grants every active member — guest included — read access to the full member list at the table level; that policy is outside this feature's file scope and "who else is in the workspace" isn't itself the sensitive fact AS-222 protects (the *management page* is). So AS-222 is enforced at the page layer via a new `canViewMembersList` predicate in `lib/auth/permissions.ts` (single-source-of-truth convention, AS-230) plus a page-level guard/redirect, verified with an exhaustive per-role unit test rather than an RLS-table-level integration test. Recorded here since my first draft of the RLS test assumed table-level scoping that doesn't exist and had to be corrected.
- **Guest write access inside their own project (AS-223)**: a concurrent worker session shipped `20260821194500_viewer_guest_write_rls.sql` (F128, AS-216/AS-217) partway through this session's work, which made 'guest' uniformly read-only at the RLS level alongside 'viewer' — breaking AS-223's positive case. I shipped `20260821194634_guest_project_scoped_writes.sql` to scope guest writes to their own `project_members`-added project (matching the read-side guest branch exactly). A second concurrent fix-forward migration from that same F128 worker (`20260821195500_viewer_write_rls_exclude_guest_fix.sql`, applied to the live project after mine) instead dropped the guest exclusion entirely — the live, final behaviour is "any active non-viewer role (including guest) can write to any task/project id they know," which is broader than my project-scoped intent but still satisfies AS-223's positive case (verified: `rls-guest.test.ts` still 14/14 green after that later migration applied). Left my migration file in place unmodified per this repo's "migrations are layered forward, not rewritten" convention; flagged below as a narrower-scoping opportunity for a future feature.
