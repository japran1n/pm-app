## Decisions made
- **Backward-compatible `addComment` signature, not a breaking rewrite.** `addComment(taskId, text, bodyJson?)` — `bodyJson` is a new optional third parameter, so every existing caller (`tests/integration/rls-viewer.test.ts`, `tests/integration/watchers.test.ts`, `tests/integration/add-comment.test.ts`, all of which call `addComment(taskId, "plain string")`) keeps working completely unchanged. When `bodyJson` is omitted, the server wraps the plain text into the same single-paragraph Tiptap doc shape F170 already established (`docFromPlainText`, mirroring `public.tiptap_doc_from_text` from `20260822090000_task_description_json.sql`), so an un-formatted comment round-trips identically to before this feature. This is the "simpler option, no new dependency" per the clarified answer — avoided a second Server Action or a breaking signature change.
- **Composer's "compact toolbar" = reuse `RichTextEditor` exactly as-is, no new toolbar variant.** `components/editor/rich-text-editor.tsx`'s own doc comment already describes its `Toolbar` as "compact... built from existing shadcn `Button` primitives — no bespoke toolbar design system." Building a second, further-reduced toolbar subset for comments would require either adding a new prop to `rich-text-editor.tsx` (currently modified/owned by a concurrent worker, F172, this session — explicitly off-limits per instructions) or a parallel bespoke toolbar component (a second source of truth for formatting controls). Per the clarified "simpler option, no new dependency, no second source of truth" answer, the comment composer reuses `RichTextEditor` unmodified, toolbar included. **Flagged as follow-up** below in case a future feature wants comments to have a visually distinct, smaller formatting subset than descriptions.
- **`sanitiseDocument`'s XSS allow-list is not re-implemented server-side.** `lib/comments/rich-text.ts` deliberately does not import `components/editor/rich-text-editor.tsx` (a `"use client"` module pulling in `@tiptap/react`'s DOM-touching `useEditor`) into the server action's bundle. Server-side validation (`commentBodyJsonSchema` in `lib/validation/comments.ts`) only checks the payload is `{ type: "doc", content?: [...] }` — a shape guard, not a security boundary. The real security boundary remains `RichTextRenderer`'s `sanitiseDocument`, which re-sanitises on every render regardless of what's persisted (per that function's own doc comment: "never rendered as raw HTML, never trusted just because it came from our own database"), exactly matching how F171 already treats `description_json`. This keeps the allow-list defined in exactly one place across the whole app rather than a second, possibly-drifting copy in server code.
- **`body_text`/legacy `text` are server-recomputed, never trusted from the client.** The composer sends both a plain-text projection (`extractPlainText(draft)`, used only for the pre-flight non-empty check, matching `addCommentSchema`'s existing validation) and the real Tiptap document. The server independently recomputes the authoritative plain-text projection from the *validated* `bodyJson` (`extractPlainText`, defense in depth — a client could otherwise send mismatched `text`/`bodyJson`) and writes that same value into both the legacy `text` column (still required by the `comments_text_not_empty` CHECK constraint) and the new `body_text` column, so there is exactly one plain-text value per comment, not two independently-trusted ones.
- **No trigger-based derivation, unlike F170.** F170's `tasks.description_json` had to be derived FROM the legacy column by a DB trigger because no UI produced real Tiptap JSON yet at that point in the mission. This feature *does* wire the real editor into the write path (the comment composer), so `lib/actions/comments.ts`'s `addComment` writes `body_json`/`body_text` directly on every insert — the "right" direction from the start, no flip needed later (unlike F170's documented required flip).
- **Client-side lazy-load via a plain `useEffect` + dynamic `import()`, not `next/dynamic`.** Both the composer and each comment's rendered body lazy-load `RichTextEditor`/`RichTextRenderer` (client-only, per that module's own doc comment) through a small `useRichTextModule()` hook, falling back to plain-text rendering (a `<p>`/`<input>`) until the module resolves. This was chosen specifically so `tests/unit/comment-list.test.ts`'s existing `renderToStaticMarkup`-based SSR test (environment: node, no `window`, effects never run) keeps rendering the exact same plain-text output it always has — **zero change to AS-096/AS-097 behaviour**, verified by re-running that test unchanged and green. `next/dynamic({ ssr: false })` would likely have produced the same net effect (it also checks `typeof window === "undefined"`) but adds indirection this simpler, already-React-idiomatic pattern doesn't need.
- **Realtime reconciliation traced and updated, not just extended.** `lib/tasks/reconcile-realtime-comment.ts`'s `CommentRealtimeRow` gained an *optional* `body_json` field (so every pre-existing synthetic test payload without it still type-checks) and `toTaskComment` now sets `bodyJson: row.body_json ?? docFromPlainText(row.text)` — a live-delivered row (which, once the migration has run, always carries `body_json`) renders through `RichTextRenderer` with full formatting; a legacy/synthetic row without it falls back to the same single-paragraph wrap used everywhere else in this feature, so there is exactly one fallback shape across the codebase, not a second one invented for the realtime path specifically. Confirmed working end-to-end (not just unit-reasoned) by `tests/integration/comment-format-realtime.test.ts`'s second test, which subscribes a real independent Realtime client and feeds the exact wire payload through this exact reducer.
- **Migration is purely additive, reuses F170's SQL helper.** `comments.body_json`/`comments.body_text` are new nullable columns; the one-time backfill for existing rows calls `public.tiptap_doc_from_text` (already created and pushed by F170's `20260822090000_task_description_json.sql`) rather than redefining the same wrap shape in SQL a second time. Legacy `comments.text` is untouched (schema and values) beyond a `comment on column` marking it deprecated, per this mission's additive-first / F270-cleanup convention.

## Out-of-scope work needed
- **A visually distinct, more restrictive formatting subset for comments specifically** (e.g. no headings/lists, bold/italic/link/code only) was not built — see "compact toolbar" decision above. If a future clarification wants this, it needs either a new prop on `components/editor/rich-text-editor.tsx`'s `Toolbar` (e.g. `allowedMarks`/`allowedNodes`) or a genuinely separate compact toolbar component, and should be scoped as its own small feature so it doesn't collide with F172's concurrent paste-behavior work on that same file.
- **Comment editing** (changing a previously-posted comment's `body_json` after the fact) is not implemented — this feature only covers create (`addComment`) and existing delete (`deleteComment`, unmodified). If a future feature adds comment editing, it must also update `body_json`/`body_text`/`text` together, following the same "server recomputes the plain-text projection from the validated JSON" pattern established here.
- **F270 (already planned in this mission)** should also drop `comments.text` once every reader has migrated off it, alongside `tasks.description` (F170's same flagged item).
- **No full-text search over comment content** — `body_text` is populated but nothing indexes/searches it yet (comments have no search feature in this mission as scoped).
