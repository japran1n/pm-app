## Decisions made
- Guarded `moveAndReorderTask`'s new activity+fan-out block on an actual status change (`taskRow.status !== updated.status`), not just "the action ran" — a pure in-column reorder (drag within the same column) must not fabricate a "status changed" activity entry or a bogus watcher notification. Verified by `test_AS_353_AS_355_moveAndReorderTask_pure_reorder_within_the_same_column_writes_no_status_entry`.
- `bulkUpdateTasks`: batched the watcher-lookup query into ONE `task_watchers` select `.in("task_id", statusChangedIds)` covering the whole batch (not one query per task), matching this action's own existing "batch, don't loop network calls per row" convention for its before/after snapshot reads. `createNotification` itself is still called once per (task, recipient) pair — there is no bulk variant of `create_notification`/`filterRecipientsByInAppPreference` to route through instead, and this mirrors the acceptable "one RPC call per affected row" pattern the spec explicitly allows and that `bulkUpdateTasks`'s own pre-existing per-task `writeTaskFieldChanges` loop already established.
- `createTask`/`createTaskForUser`: added an optional `notifyClient` parameter (the caller's session-authenticated Supabase client) used ONLY for the new `task_assigned` fan-out. `createTask()` (the web Server Action) passes its own `supabase`. `app/api/extension/tasks/route.ts` (the other caller of `createTaskForUser`) was NOT touched — it authenticates via a bearer JWT validated one-off against a fresh anon-key client with no persisted session, which cannot authenticate a `create_notification` RPC call as that user without further plumbing. When `notifyClient` is omitted the fan-out is skipped with a logged (non-fatal) message rather than silently doing nothing unexplained. See "Out-of-scope work needed" below.
- `createTask`/`duplicateTask` initial-assignee notifications deliberately write NO `task_activity` entry — per `diffTaskFields`'s own documented "no prior value to diff against" rule, task creation is not a *change*, there is no "before" state to diff. Only the notification fires, matching AS-380's text ("a user receives a notification when a task is assigned to them") without inventing a "task created" activity kind that doesn't exist in F194's closed vocabulary.
- `restoreTask`: no dedicated "restored" kind exists in F194's closed `task_activity_kind` vocabulary (`field_changed`, `comment_added`, `comment_deleted`), and no migration is in this feature's scope. Followed the exact precedent `supabase/migrations/20260822231000_recurrence_scheduled_generation_activity.sql`'s own doc comment sets for this situation: reuse `field_changed` on the closest-fitting real field. Used `status` with `old_value := null` (no visible status while in trash) and `new_value := resolvedStatus`.
- `restoreTask` deliberately gets NO watcher/assignee notification fan-out, only the activity entry — per this task's own explicit scoping instruction ("restoring from trash is not really a watcher notification event per this mission's scope"). AS-294/AS-382's text is specifically about status changes on a live task; a restore isn't read as one.
- `setTaskAssigneesCore`: replaced the mirror-column-only diff (`mirrorBefore` vs `mirror`) with entries built directly from `toAdd`/`toRemove` — the real full-set diff already computed earlier in the function against `task_assignees`. One `assignee_id` `field_changed` entry per removed user (`oldValue: userId, newValue: null`) and per added user (`oldValue: null, newValue: userId`). This reads correctly through `formatTaskActivityEntry`'s existing per-id `assignee_id` rendering (single old/new id → "assigned to X" / "unassigned (was X)" / "reassigned from X to Y") without inventing a new field or kind, and now correctly records adding/removing a non-first assignee on an already-multi-assignee task (the scrutiny report's explicit finding), which the old mirror-only diff silently dropped. Removed the now-dead `taskBeforeRow`/`mirrorBefore` read that only fed the old diff.
- Test file follows the exact `sessionClientForMock`/`vi.mock("@/lib/supabase/server")` pattern `tests/integration/notification-fanout.test.ts` (F207) already established (a real signed-in publishable-key session client, not a bare stub), since these new tests need both `write_task_activity_entry` and `create_notification`'s SECURITY DEFINER `auth.uid()` pinning to resolve to a real actor.
