## Decisions made
- Verified the ordering in `lib/actions/attachments.ts`'s `uploadAttachmentForUser` before writing any code, per the task's explicit instruction: Zod validation (`uploadAttachmentSchema.safeParse`, which enforces `MAX_ATTACHMENT_SIZE_BYTES`/`ALLOWED_ATTACHMENT_MIME_TYPES`) runs and can early-return **before** any Storage or DB call. The Storage upload happens next, and the `attachments` row insert happens **last**, after Storage succeeds — so a rejected/failed file can never leave a partial row; this was already correct (no bug to fix), and is proven by two new integration tests (`test_AS_507_an_oversized_upload_explains_why_and_leaves_no_attachments_row`, `test_AS_507_a_disallowed_mime_type_upload_explains_why_and_leaves_no_attachments_row`) run against the real Supabase project, not just inferred from reading the code.
- Progress model chosen: **indeterminate per-file state**, not a fabricated byte percentage. The upload path is `lib/actions/attachments.ts`'s `uploadAttachment` Server Action, invoked as a plain `await` inside a React transition — Next.js Server Actions are POSTed through the framework's internal fetch with no exposed upload-progress event (no `XMLHttpRequest.upload.onprogress` equivalent, no direct-to-Storage signed-upload client in this codebase's upload path). Wiring a real percentage would require replacing the whole transport (e.g. a direct Supabase Storage resumable/TUS upload from the client), which F258 did not set up and which this feature's scope (`upload-progress.tsx`, `attachment-dropzone.tsx`, `attachment-list.tsx`, `lib/actions/attachments.ts`) does not call for rearchitecting. Per the clarification's explicit allowance ("if the storage client cannot report progress, an indeterminate per-file state is acceptable — say which one was implemented"), each row shows: spinner + file name + size while "uploading", settling to a checkmark ("success") or an error icon + reason ("error"/"rejected").
- Client-side validation (`lib/tasks/validate-attachment-file.ts`) reuses `MAX_ATTACHMENT_SIZE_BYTES`/`ALLOWED_ATTACHMENT_MIME_TYPES` imported directly from `lib/validation/attachments.ts` — the same constants the Zod schema enforces server-side — rather than a second, potentially-drifting copy of the limits, per the clarification's "no second source of truth" resolution rule. The client check never stands alone: `uploadAttachmentForUser`'s server-side Zod re-validation is untouched and still runs for every request regardless of what the client already checked.
- A file that fails client-side validation is never sent to the Server Action at all — it gets an immediate "rejected" progress row and a toast, and `uploadAttachmentMock`/the real action is never called for it (asserted in `test_AS_507_a_disallowed_file_is_rejected_before_upload_shows_a_reason_and_never_calls_the_action`). This makes it structurally impossible for a client-rejected file to produce a partial row, on top of the already-safe server-side ordering.
- "Cancel" for an in-flight ("uploading") row: the Server Action call itself has no `AbortController`/cancel hook (see `upload-progress.tsx`'s header comment for the full rationale) — no lower-level transport is exposed to cancel. Cancel is therefore implemented as "ignore this job's eventual result": the row is removed immediately, and a `cancelledJobIdsRef` set on `AttachmentList` causes `uploadOneFile` to no-op (no state update, no toast, no `appendAttachment`) when that job's result eventually arrives — the underlying network request still completes server-side (and, if it succeeds, a real attachment row is created that the user won't see reflected until they reopen/refresh the task, since the local list was never updated for a cancelled job). This is the simplest option that adds no new dependency (no AbortController plumbing through the Server Action boundary) and no second source of truth, per the clarification's ambiguity-resolution rule; documented here rather than silently assumed to mean "true network abort."
- `UploadProgress` is a presentational component only (`components/task/upload-progress.tsx`) — all job-list state (`uploadJobs`, `cancelledJobIdsRef`) lives in `AttachmentList`, matching this codebase's existing convention (state in the container, dumb rendering component below it, same as `AttachmentThumbnail`'s relationship to `AttachmentList`).
- Wired into the existing `AttachmentList`/`AttachmentDropzone` upload path exactly as instructed — `uploadFiles()` (called by both the file-picker `onChange` and `AttachmentDropzone`'s `onFilesDropped` via the F258 imperative handle) is the single place both validation and job-list population happen, so drag-drop and picker-driven uploads get identical progress/rejection UI with no parallel upload implementation.

## Out-of-scope work needed
- True per-byte upload progress would require switching the upload transport from a Server Action call to a client-side signed/direct-to-Storage upload (e.g. Supabase's resumable upload API) with a real progress callback, then having a Server Action only finalize the DB row. That is a meaningfully larger change touching `lib/actions/attachments.ts`'s contract and is out of this feature's scope (spec named `components/task/attachment-dropzone.tsx`, `components/task/upload-progress.tsx`, `lib/actions/attachments.ts` for verification only, not a transport rewrite). Flagged here rather than done silently; no follow-up filed since the clarification explicitly pre-authorized the indeterminate state as sufficient.
- True network-level cancellation (aborting the in-flight Server Action request) is not implemented, only "ignore the result" — see Decisions made above. If a future feature needs a real abort (e.g. for very large files on a slow connection), it would need the same transport change as the point above.
