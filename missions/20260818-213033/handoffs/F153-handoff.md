## Decisions made

- **A trailing "add an item" input, not free-text insertion anywhere in the list, is the one place Enter creates a NEW item.** `addChecklistItem` (F152, `lib/actions/checklist.ts`) only supports appending to the end of the list — there is no "insert at arbitrary position" Server Action. Pressing Enter on an EXISTING item therefore commits any pending rename and moves focus forward (to the next existing item, or to the trailing draft box if it's the last one) rather than trying to fabricate a mid-list insert via an extra add-then-reorder round trip. This is the simpler option per the clarification's ambiguity-resolution rule (no new Server Action, no second add+reorder round trip) and still delivers the literal "Enter adds the next item" flow: typing straight down through existing items and pressing Enter repeatedly always eventually lands you in the always-available "add the next one" box.
- **Backspace on the empty draft box (nothing typed yet) is not a delete** — there's no persisted row there to delete — it just walks focus up to the last real item, kept symmetric with Backspace's behaviour on an emptied real item, so "Backspace walks back up the list" is a single consistent gesture regardless of which input it's pressed in.
- **`knownGoodContentRef` tracks "last known good content" per item id in a `useRef` Map, seeded from the `items` prop and updated on every successful rename/add — deliberately NOT re-derived from the `items` prop at revert time.** That prop is this Sheet's one-time initial fetch and never changes for the life of an open Sheet; without this, a SECOND failed rename on the same item would revert all the way back to the original pre-Sheet-open text instead of the most recently persisted value.
- **All ref-based DOM focus management goes through a `pendingFocus` state + `useEffect`, not a direct `.current.focus()` call inside the render body or inside a still-pending `useTransition` callback.** This repo's `react-hooks/refs` eslint rule forbids reading/writing a ref's `.current` synchronously during render (only inside event handlers or effects) — an earlier draft used the same "adjust state during render" pattern this codebase already uses for `syncedTaskId` resyncs, but applied it to a ref, which the lint rule correctly rejects (refs are for effects/handlers, not render). Separately, `handleAddFromDraft`'s post-add focus call specifically needed the effect-deferred form rather than a same-tick `draftRef.current?.focus()`: that line still runs while `isAdding` (from `useTransition`) is `true`, so the draft `<input>`'s own `disabled={isAdding}` attribute is still in effect in the DOM at that exact moment, and calling `.focus()` on a currently-disabled form control is a silent browser no-op. The `pendingFocus` effect runs after the render that flips `disabled` back off, so the actual `.focus()` call lands on an enabled element. The focus-request state is tagged with a monotonically increasing `token` (not just the bare target id) so that requesting focus on the SAME target twice in a row (e.g. two consecutive Backspace-deletes that both resolve to "focus the new first item") still produces a distinct state value each time — otherwise React's bail-out-on-identical-state-value behaviour would silently skip the second `focus()` call.
- **Progress bar hidden at zero items, matching AS-273's "no completion percentage rather than 0%" principle applied locally** — this is this feature's OWN "checked of total for this task's checklist" summary, not the cross-checklist-and-subtasks task-level percentage (that's AS-272/AS-273, explicitly F154's job per the feature spec; not built here).
- **Checklist section placed between Subtasks and Comments in the Sheet**, reusing the existing `Separator`-delimited section layout `task-detail-sheet.tsx` already uses for every other section, per the instruction to reuse that file's conventions rather than introduce a new visual pattern.
- **No `lib/auth/permissions.ts` gating** — that module doesn't exist yet in this codebase (AS-230's own not-yet-built feature, lands in a later milestone than this mission's M13). Every control here is available to any active workspace member and re-verified server-side by each F152 Server Action (`requireActiveMembership`), matching the exact same documented decision `SubtaskList`/F150 already made for the identical reason.

## Out-of-scope work needed

- **Task-level completion percentage across checklist AND subtasks (AS-272, AS-273)** — this feature's progress bar is checklist-only by design; F154 is the feature that combines checklist + child-task completion into the task card's percentage. Not touched here.
- **A stray revalidation-driven focus-loss characteristic of this app's Server Action pattern**, discovered while writing the Playwright test, not introduced by this feature: every Server Action in this codebase calls `revalidatePath`, which triggers a Next.js router refresh of the current route. Empirically (observed via the `aria-describedby="DndDescribedBy-N"` id on `SortableTaskCard` incrementing after each checklist mutation, and via the draft input never regaining DOM focus after `addChecklistItem` resolves even though `requestFocus`'s effect does call `.focus()` on it), that refresh replaces enough of the client tree that a just-focused input's DOM node identity doesn't survive it. This is not specific to `Checklist`'s own code — it's a property of the shared Server-Action-triggered-revalidation pattern every mutating feature in this app already uses — but it does mean "Enter keeps focus in the draft box for continuous typing" doesn't hold up as a strict DOM-focus assertion end-to-end, even though the component's own `requestFocus` logic is correct in isolation. `tests/e2e/checklist-ui.spec.ts` documents this in a comment and asserts the FUNCTIONAL behaviour (you can keep adding items right after one succeeds) instead of raw focus. Worth a dedicated look by whoever next touches this app's revalidation strategy broadly — it likely affects every other Server-Action-triggered UI in the app identically, not just this feature.

- **Two real dnd-kit-with-Playwright gotchas hit while building the keyboard-reorder test, worth knowing before anyone else writes a keyboard-driven dnd-kit e2e test in this repo (none existed before this feature — `tests/e2e/board-reorder.spec.ts` only tests POINTER drag):**
  1. `@dnd-kit/core`'s `KeyboardSensor.attach()` registers its OWN keydown listener (for the move/drop keys) via `setTimeout(() => listeners.add(...))`, deferred by one tick from the very first pick-up keypress. Sending the next key (e.g. `ArrowDown`) in the same synchronous tick as the pick-up `Space` can race ahead of that registration and be silently dropped. A short `page.waitForTimeout(200)` between each key in the sequence, or polling `aria-pressed` (which dnd-kit sets to `"true"` on the drag handle's own `attributes` while `isDragging`) to confirm pick-up actually registered before continuing, fixed this reliably.
  2. dnd-kit's `useSortable` doesn't live-reorder the rendered array during a drag gesture (it only applies a visual CSS `transform` to the dragged row) — the actual array reorder happens once, in `onDragEnd`, on drop. A test that reads DOM order right after `ArrowDown` (before the drop `Space`) will see the ORIGINAL order, which is expected, not a bug.
- **Locator gotcha for anyone testing this Checklist component (or any component with per-item controlled `<input>`s) with Playwright:** an `<input>`'s `value` contributes NOTHING to Playwright's text-content-based `getByText()`/`:has-text()` matching (an input's value isn't a DOM text node) — `getByText(itemContent)` silently and permanently resolves to zero matches for checklist item text, which makes a `.toHaveCount(0)` "verify it's gone" assertion a false-positive PASS regardless of whether the item is actually still there. Every item-content presence/absence check in `tests/e2e/checklist-ui.spec.ts` instead goes through the CHECKBOX's accessible name (`itemCheckbox()` helper, anchored with `^Mark "<content>" as` to avoid one item's content ever ambiguously matching another's row). Relatedly: any locator built from an item's CURRENT content (via `rowFor`/`itemCheckbox`) stops resolving the instant that content changes (e.g. mid-rename) — for a sequence that edits an item's own text (the Backspace-delete flow), locate the row by POSITION (`itemTextInputs(sheet).nth(index)`, resolved once via `readItemValues()` before the edit) instead, since a content-based locator can't survive the very edit it's performing.
