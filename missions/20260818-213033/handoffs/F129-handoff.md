## Decisions made
- **Guest promotion (Notes for clarification — one action vs. two-step):** chose the simpler option — a single, always-visible "Admin" option in the picker that the server rejects with a specific error if the target is currently a guest, rather than building a two-step wizard/state machine in the UI. Reasoning: no new dependency, no second source of truth for "is a promotion in progress," and the rejection message tells the caller exactly what to do ("Change them to a member first, then to admin"). A caller who wants to promote a guest to admin makes two ordinary `changeMemberRole` calls (guest → member, then member → admin) — both already fully supported, no new code path.
- **AS-218 access line:** widened `changeMemberRole`'s server-side re-check from `requireWorkspaceOwner` to `requireWorkspaceAdmin`, and the members page's `canChangeRoles` gate from `ownMembership?.role === "owner"` to the shared `canManageMembers` predicate (same one `canInvite` effectively encodes) — per AS-218's explicit "an owner or admin can change any member's role," superseding mission-1's AS-014/AS-019 owner-only line.
- **`newRole` never includes "owner":** kept this restriction from mission-1 unchanged (schema enum is `admin | member | viewer | guest`) — granting ownership through a role-change action stays out of scope; this feature only widens who can perform the action and which non-owner roles are reachable.
- **An owner's row can now be a target, but the UI never shows the editable Select for it:** the page still renders an owner-role member as a plain `Badge`, never `<MemberRoleSelect>` (unchanged condition `canChangeRoles && member.role !== "owner"`). AS-219's negative sibling ("a non-sole owner CAN be demoted") is real, reachable, tested behaviour at the Server Action level — it's just not wired to a UI control in this feature's scope, since the spec's Draft scope only asked for "last-owner protection still holds," not a new UI affordance for demoting co-owners. Flagged below as out-of-scope UI work.
- **Sole-owner guard implementation — check-then-act, not the atomic RPC pattern:** originally implemented (and wrote a migration for) a `change_workspace_member_role` SECURITY DEFINER Postgres function mirroring the exact `SELECT ... FOR UPDATE` locking technique `remove_workspace_member` (F094) uses for AS-018, per the spec's "reuse the existing mission-1 sole-owner guard, don't reinvent it." **Could not deploy it**: `supabase db push` (both `--linked --yes`, which failed fast with `LegacyPlatformAuthRequiredError: Access token not provided` — no `SUPABASE_ACCESS_TOKEN` in this environment — and the plain linked-project form, which hung indefinitely with zero output on every attempt, consistent with a blocked outbound connection to the direct/pooled Postgres endpoint even though the REST API over HTTPS is reachable) never completed in this worker's sandbox. Reverted to a **check-then-act** guard in `changeMemberRole` itself: count active owners, reject if ≤ 1, otherwise update — the same class of guard mission-1's original (pre-F094-hardening) `removeMember` used, with a narrow, undeployed-assertion TOCTOU window (two concurrent role-change calls demoting different owners of the same 2-owner workspace). This satisfies AS-219 exactly as tested (serial calls); it is not exercised concurrently by any assigned assertion. See Out-of-scope below for the follow-up to finish the atomic version once migration-push access is restored.
- Deleted the unpushable migration file (`change_workspace_member_role_atomic_owner_guard.sql`) and the corresponding `database.types.ts` RPC entry rather than leaving dead code referencing a function that doesn't exist in the live database — application code no longer calls `admin.rpc("change_workspace_member_role", ...)`.

## Out-of-scope work needed

Low urgency — no assigned assertion requires concurrency-safety here, only `removeMember`'s AS-018 equivalent scenario ever got flagged by scrutiny.
- **UI affordance for demoting a non-sole owner:** currently only reachable by calling `changeMemberRole` directly (e.g. from another Server Action or a future admin console), not from `settings/members`, which still renders every owner row as a read-only `Badge`. If a future feature wants owners to demote co-owners through the UI, it needs to either (a) always show the Select for owner rows and rely on the server's sole-owner rejection, or (b) fetch the workspace's owner count server-side and conditionally hide the badge/show the select. Not attempted here — the spec's Draft scope named this only as "last-owner protection still holds," not a new UI surface.
- **`lib/queries/members.ts`'s `ActiveMember`/`PendingInvite.role` types are still `"owner" | "admin" | "member"`**, pre-dating F126/F134's `viewer`/`guest` additions — not touched here (not in this feature's Files list). At runtime this is harmless (the DB value is a plain string cast with `as`, so a real "viewer"/"guest" row's role string round-trips correctly through `ActiveMember`/badge rendering/`MemberRoleSelect` despite the stale type), but it's a latent type-accuracy gap a future worker touching that file should fix (widen both type aliases to the full `WorkspaceRole`).
