## Decisions made
- **`updateProjectVisibility` lives in `lib/actions/project-members.ts`, not `lib/actions/projects.ts`.** Checked `lib/actions/projects.ts` first per the task instructions — it has no existing visibility action to extend (F132 shipped only the schema/RLS/trigger, no Server Action). Per the clarified spec's ambiguity-resolution rule (simplest option, no new dependency, no second source of truth), I added it next to `addProjectMember`/`removeProjectMember` since it shares their exact conventions (`loadProjectContext`, `revalidateWorkspace`, discriminated-union result, admin-client checks + RLS-respecting-client write) rather than duplicating that scaffolding in `projects.ts`.
- **Removing yourself while you can still administer the project is allowed but warned about, not blocked** — implemented as an `AlertDialog` confirmation whose description branches on `isSelf && callerRetainsAccess` (you'll keep access, just lose your explicit membership scoping) vs `isSelf` alone (you'll lose access) vs removing someone else. The server-side action itself (`removeProjectMember`, unchanged from F131) never blocks self-removal for an authorized caller — this is a UI-only distinction, consistent with the clarified spec's stated resolution.
- **Added two new predicates to `lib/auth/permissions.ts`** (`canManageProjectMembers`, `canChangeProjectVisibility`) even though that file wasn't explicitly listed in this feature's "Files" section. The clarified spec's Access-control answer explicitly says controls are gated "through lib/auth/permissions.ts" (AS-230's single-source-of-truth convention), and no existing predicate there covered "lead-or-workspace-admin can manage project members" or "owner/admin can change visibility" — `canManageProjectMembers` mirrors the exact same rule `isProjectLeadOrWorkspaceAdmin` (the real server-side check in `lib/actions/project-members.ts`) already independently enforces, so this is the UI mirror, not a new authorization decision.
- **Add-member picker excludes people already in `project_members`** at the query layer (`getAddableWorkspaceMembers`), rather than letting the picker offer a guaranteed-to-fail choice and relying solely on the action's unique-constraint error message.
- **Visibility-loss warning only appears when switching workspace -> private and the computed loss list is non-empty**; switching private -> workspace never warns (that direction only grants access, never revokes it). Computed via `getVisibilityLossPreview`, which reads `is_project_visible_to`'s exact logic from the F132 migration: an active member loses access on the switch iff they are not owner/admin AND have no explicit `project_members` row.
- **Settings page does its own RLS-respecting visibility check** (`supabase.from("projects").select(...)` via the request-scoped client, not the admin client the parent layout uses) rather than relying on the parent layout, which deliberately bypasses RLS to always render archived projects. A caller who cannot see a private project gets the same `notFound()` the parent layout gives for a nonexistent/cross-workspace project id — same "don't distinguish doesn't-exist from no-access" convention as `app/.../projects/[projectId]/layout.tsx`'s AS-039/AS-040 handling.
