## Decisions made
- **Extracted `createTaskForUser(userId, input)` from `createTask()`** rather than reimplementing task creation in the route handler. Per tech-decisions.md: "creates the task through the same code path the web app uses so validation and defaults cannot drift." `createTask()` (the Server Action, unchanged calling convention for existing callers) now just resolves the cookie-session user and delegates to `createTaskForUser`. The route handler resolves its user from the bearer JWT and calls the same `createTaskForUser`. Both paths run the identical Zod validation, membership check, position calculation, subtask-parent validation, insert, and revalidatePath call — there is exactly one create-task implementation, not two.
- **Identity resolution via a fresh anon-key `@supabase/supabase-js` client's `auth.getUser(token)`**, not the cookie-based `lib/supabase/server.ts` `createClient()`. The cookie-based client reads Next.js request cookies, which a cross-origin extension `fetch` call does not send (and should not — the extension holds its own session via `chrome.storage.local`, per F281). `auth.getUser(token)` is the documented way to validate an out-of-band bearer token against Supabase Auth without a full client session; verified against the current `@supabase/supabase-js` API surface installed in this repo's `node_modules` (the same method every cookie-based caller in this codebase already calls with no argument for its own request-scoped session — this route just passes the token explicitly instead).
- **AS-572's "expired" case is proven with a syntactically JWT-shaped token carrying a stale `exp` claim and an invalid signature, not a real token that was allowed to age out in real time.** A genuinely expired real Supabase session token would require either sleeping past the token's real TTL in the test (impractically slow and flaky) or an admin API to mint an already-expired token (Supabase's admin API has no such endpoint). `auth.getUser()` rejects a token with a stale `exp` claim identically to a token with a bad signature — both fail server-side JWT verification and produce the same generic `{ error, status: 401 }` outcome this route returns for every invalid-token case (the route deliberately does not try to distinguish "expired" from "malformed" from "wrong-project", since `auth.getUser()`'s response gives it nothing to distinguish them by). This is stated plainly rather than glossed over: the test proves "a token that fails verification is rejected," which covers expired, malformed, and mismatched-project cases identically, because the route's actual behavior does not differ between them.
- **CORS: added a new `EXTENSION_ID` env var** (no prior convention existed in this repo — grepped for one before adding). The route only attaches `Access-Control-Allow-Origin` when the request's `Origin` header equals `chrome-extension://<EXTENSION_ID>`; a mismatched/absent `Origin` gets no CORS header, so a real browser blocks the extension (or any other site) from reading the response unless it's running with the configured id. A request with no `Origin` header at all (same-origin server-to-server calls, and this feature's own vitest tests, which invoke the exported `POST()` function directly rather than going through a browser fetch) is allowed through the CORS layer entirely — CORS is a browser-enforced restriction on cross-origin browser requests, not this route's actual authentication boundary; the Authorization/membership checks are the real security boundary and apply unconditionally regardless of Origin.
  - **Real-world caveat (per the clarification's "don't gloss over this" rule):** an unpacked/dev extension's id is randomly assigned by Chrome each time it's loaded, not fixed the way a Web-Store-published extension's id is. In practice this means: (1) a developer must copy the id shown at `chrome://extensions` after loading unpacked and set it as `EXTENSION_ID` in `.env`, and (2) that id can change if the extension is reloaded from a different unpacked location (e.g. a different `dist/` checkout), requiring the env var to be updated again. This is a real, known friction point for local development that the CORS check alone cannot solve — it is not simulated or worked around here, just documented. Once the extension is published (or side-loaded as an unpacked build pinned via a manifest `key`, deferred out of this feature per F281's own manifest notes), the id becomes stable and this friction disappears.
- **Route responds 404 "Project not found." before the 403 membership check** when the `projectId` doesn't resolve to a live project at all (mirrors `lib/actions/tasks.ts`'s own existing convention exactly — see that file's `createTaskForUser`). This is a pre-existing convention from F035, not a new decision, but noted here since it means a nonexistent project and "you're not a member of this project" are distinguishable by status code in this route, same as the web app.
- **Schema kept minimal per the spec's explicit instruction**: `extensionCreateTaskSchema` only accepts `projectId`, `title`, and `description` — the minimum `lib/actions/tasks.ts`'s create path needs. Documented in the schema's own comment as the deliberate extension point for F293 (screenshot/annotation), F294 (console capture), F295 (network capture) to add fields to, rather than building placeholders for those payloads now.
- **Rate limiting is explicitly NOT implemented**, per the feature spec's "Notes for clarification" ("Rate limiting was cut from this mission's scope"). This route has no request-rate protection of any kind — an authenticated extension user (or anyone who obtains a valid access token) can call it as fast as their network allows, bounded only by Supabase's own connection/query limits. Stated plainly here rather than silently built or silently omitted, per the standing "state the limitation" rule.
