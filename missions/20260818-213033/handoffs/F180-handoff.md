## Decisions made
- **Reused F176's `cloneTaskFields` verbatim, did not reimplement the copy-rules logic.** `duplicateTask` imports `cloneTaskFields` from `lib/recurrence/clone-fields.ts` and calls it with the source task's title/description/description_json/assigneeIds/priority/checklistItems/estimate_minutes — exactly the allow-list F176 established, per this feature's own spec. `cloneTaskFields`'s `status` output ("todo", recurrence's own reset rule) is deliberately NOT used for the new task's status — F180's status rule is different (same status as source, AS-327), so `targetStatus` is read straight from the source row instead, ignoring `cloned.status`.
- **`tags` is copied by `duplicateTask` itself, not by `cloneTaskFields`.** F176's allow-list intentionally does not include `tags` (a recurring occurrence does not inherit tags — confirmed by reading `clone-fields.ts`'s own `CloneableTaskSource`/`ClonedTaskFields` types, neither of which has a `tags` field). AS-325 for this feature explicitly requires tags to be copied, so `duplicateTask` reads `sourceRow.tags` and writes it straight onto the insert payload alongside the `cloneTaskFields` result — this does not touch or extend `clone-fields.ts`, so the single-source-of-truth allow-list for recurrence stays exactly as F176 left it.
- **Title marking convention: "Copy of <original title>"** — chosen per the clarification's "take the simpler option ... record the choice" instruction. Picked over "<original> (copy)" because it reads naturally as a sentence prefix and matches how most task-tracking tools (Jira, Linear, Trello) label duplicates by default; no dependency or second source of truth either way, so this was the arbitrary-but-consistent pick. Recorded here so a future project-duplication feature can reuse the identical convention rather than inventing a second one, per this feature's own "pick one and use it for project duplication too" note.
- **Key/number**: the insert into `tasks` never supplies `number` (or any key-shaped field) — F145's `assign_task_key` trigger fires on any insert without one and assigns the new row its own project-sequential number, exactly the same mechanism `createTaskForUser` (existing code, unmodified) already relies on. No manual computation anywhere in this feature.
- **Position**: computed via the existing `lib/board/position.ts` `calculatePosition(prev, next)` — same function board drag-and-drop reordering and `createTaskForUser`'s own append-to-end logic already use. `prev` is the source task's own current position; `next` is the source's current next sibling by position in the same `(project_id, status)` column (or `null` if the source is currently last), so the duplicate always lands strictly between the two (or right after the source with the standard boundary gap if there's no successor yet).
- **Same project/status**: both are read directly from the source row (`sourceRow.project_id`, `sourceRow.status`) and never accepted as input — `duplicateTaskSchema` takes only `taskId`, so there is no way for a caller to smuggle a different destination through this action.
- **Access control**: mirrors `createTask`'s own gate exactly — `requireActiveMembership` (defense-in-depth membership check) then `canWrite({ role })` (viewers/guests read-only, same AS-216/AS-217 convention as every other write action in this file), re-verified server-side even though RLS also covers the underlying inserts (admin client is used for the actual writes, same convention `tasks.ts`'s other actions already follow — see that file's own doc comments explaining why, distinct from `checklist.ts`'s RLS-exercising convention).
- **Assignee mirror**: after inserting the duplicate's `task_assignees` rows, `syncMirrorAssigneeId` (existing function, unmodified) is called so the duplicate's `tasks.assignee_id` mirror column stays consistent with the same convention every other multi-assignee write path in this file uses — not a new mechanism.
- **No UI wiring in this feature.** The clarification's "Files" section lists `components/task/task-card.tsx` only as an "approximate" file, and this feature's own "Dependencies on existing code" answer restricts scope to files named in the spec plus their direct validation schemas. Per the mission's Files guidance in the assignment prompt ("a duplicate/context-menu UI trigger if the spec calls for one ... may be action-only for this feature, with UI wiring deferred"), and since the spec's Draft scope UI mention was not carried into the Clarified implementation's Touches answer as a hard requirement, this worker implemented the Server Action + tests only and left the card/detail-sheet menu entry as explicit out-of-scope work below, rather than silently touching `task-card.tsx`/`task-detail-sheet.tsx` (files not confirmed in-scope by the clarified answers) under time pressure.
