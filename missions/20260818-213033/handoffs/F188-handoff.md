## Decisions made
- **`deleted_by` stamped INSIDE `cascade_delete_task` itself, not as a follow-up `.update()` from `lib/actions/tasks.ts` after the RPC returns.** The whole point of that RPC being one PL/pgSQL function body is atomicity (its own doc comment: "a single PL/pgSQL function body is atomic by construction"). A second UPDATE from the Server Action after the RPC returns would reintroduce exactly the "two statements, not one transaction" crash window that migration was written to avoid. Implemented as a NEW overload (`cascade_delete_task(p_task_id, p_deleted_by default null)`) via `create or replace function` with a different argument list — Postgres treats this as an additional overload, not a replacement of the original one-arg function, so the original signature is left in place (harmless, unused) rather than dropped, per this mission's "additive first, drops only in the dedicated cleanup feature (F270)" migration convention.
- **Cascaded children (deleted as a side effect of their parent, via either the single-task RPC or `bulkDeleteTasks`'s second UPDATE) are stamped with the SAME `deleted_by` as the parent**, not left null and not attributed to some other value. The child wasn't deleted by a separate actor — it was deleted by the same action the caller took on the parent — and this mirrors `deleted_via_task_id` already recording the parent as the cause. This differs from F187's own documented gap (`deleted_via_task_id` not stamped for bulk-cascaded children, per that handoff's "Out-of-scope work needed") — `deleted_by` for bulk-cascaded children WAS in scope and IS stamped here (a single extra column in the same `.update()` call, unlike `deleted_via_task_id` which per F187's handoff would require a per-row column-to-column assignment the Supabase JS builder can't express).
- **AS-352 / guest gate**: per this feature's own "Notes for clarification" question ("A guest should see only their own projects' trash — verify against F134's policies") and the clarification's ambiguity-resolution default (simplest option, no new dependency, no second source of truth), the trash page redirects a guest away entirely (`role === "guest"` redirect, mirroring F142's archive page verbatim) rather than building a guest-scoped "my projects' trash only" variant. This is consistent with the sidebar already hiding Archive/Members/Templates from guests for the identical "workspace-broad admin-adjacent view" reasoning — a guest never reaches this page at all, so there's no separate guest-scoped trash to build. If a future feature wants guests to see trash for the specific projects they're members of, that's a new, separately-scoped page/query, not a modification of this one.
- **The comments query's workspace scope is enforced by an explicit JS-side filter (`project.workspace_id === workspaceId`), not a two-level-nested PostgREST dot-path filter** (`"tasks.projects.workspace_id"`). The single-level nested filter (`"projects.workspace_id"`, used for the tasks query) is an established pattern in this codebase (`lib/queries/tasks.ts`'s dashboard query does the same thing), but PostgREST's support for filtering a SECOND level of embedded resource is not something this codebase has an existing precedent for, and getting AS-352 wrong here would be a real data leak — so rather than trust an unverified two-level filter, every comment row returned by the (RLS-scoped, so already bounded to visible rows) query is explicitly re-checked against `workspaceId` in JS before being included. Documented inline in `lib/queries/trash.ts`.
- **The trash view is read-only — no restore/undo action.** This feature's own Files list (`supabase/migrations/`, the page, the query file) never named a restore action, and building one would require deciding cascade-restore semantics for F187's bulk-deleted children (which per that feature's own handoff don't carry `deleted_via_task_id`) — explicitly out of scope, see below.
- **Comment "what was deleted" uses the comment's own text (truncated to 120 chars), not a reference to its parent task.** Comments have no title of their own; showing the raw text is the only way to satisfy AS-347's "what was deleted" for a comment row without a second query per row (which the performance-budget answer forbids). Truncation avoids one very long comment blowing out a trash row's height.

## Out-of-scope work needed
- **F189 (restore from trash)**: this feature is read-only by design (see Decisions Made above). A future restore feature needs to decide how to handle a task whose `deleted_via_task_id`/`deleted_by` chain is incomplete for bulk-cascaded children (F187's documented gap — those children have `deleted_via_task_id = null` even though they were cascade-deleted, though as of THIS feature they DO now correctly carry `deleted_by`). Flagged again here since F189 is the feature that will actually need to reason about it.
- **The original one-arg `cascade_delete_task(uuid)` overload is now dead code** (superseded by the two-arg overload `deleteTask` calls). Not dropped here per the additive-first convention; a cleanup feature (F270 per this mission's own established convention) could drop it once nothing else could plausibly still reference the one-arg form.
- **No UI affordance to view a single deleted task's full detail from the trash row** — the row shows title/project/deleter/time only, not the task's description, comments, or other fields. Not requested by this feature's spec ("a list of deleted tasks AND comments... with origin project, deleter, and time"); a future feature could make each row link to a read-only detail view if that's ever wanted.
- **Comment rows don't link back to their parent task** (see Decisions Made above) — a future polish feature could add a "PM-142" reference for a comment row if the product wants full provenance in the trash list, at the cost of one more embedded join per comment row.
