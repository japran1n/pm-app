## Decisions made
- Body limit set to `"3mb"` per the clarified spec's explicit instruction (multipart overhead means a 2MB file's raw request body can exceed 2MB).
- Magic-byte sniff implemented as three small local signature checks (JPEG `FF D8 FF`, PNG's 8-byte signature, WebP's `RIFF....WEBP`) in `lib/validation/profile.ts`, next to the existing `MAX_AVATAR_SIZE_BYTES`/`ALLOWED_AVATAR_MIME_TYPES` constants — no `file-type` dependency added, per the clarified spec.
- On mismatch, the upload is rejected outright with "Avatar must be a JPEG, PNG, or WebP image." — the sniffed type is never silently substituted for the declared one.
- `remove([objectPath])` cleanup added on `profiles` update failure in `uploadAvatar`, mirroring `uploadAttachment`'s post-Storage-success cleanup shape in `lib/actions/attachments.ts` (best-effort, logged, not surfaced to the caller).
- Client-side pre-flight in `profile-form.tsx` imports `MAX_AVATAR_SIZE_BYTES` directly from `lib/validation/profile.ts` (the same constant the server enforces) rather than duplicating the number, avoiding a second source of truth.
- `try/catch/finally` wraps the `uploadAvatar` call; `URL.revokeObjectURL` moved into `finally` so it always runs even if the promise rejects (e.g. an unexpected network error); the `catch` block reverts the preview and shows a generic toast, matching the existing `result.ok === false` branch's UX.
- Updated the two pre-existing AS-203 integration tests, which previously used arbitrary non-image bytes (`[1,2,3,4,5,6,7,8]`) declared as `image/png`/`image/webp` — that data no longer passes the new content-sniff check, so both were changed to use real PNG/WebP magic-byte-prefixed payloads. This is a direct, necessary consequence of closing AS-206's bypass (the M10 scrutiny report itself flagged "the feature's own AS-203 test demonstrates the bypass" as the reproduction case), not a scope expansion.
- New bucket-config-equals-TS-constants test queries the real linked Supabase project via `adminClient.storage.getBucket("avatars")` (integration test, real project) rather than reading the SQL migration file as text, so it catches actual drift in the deployed bucket rather than just the migration source.
- The oversize e2e test (AS-205) exercises the real running app in a real browser against the real `next dev` server started by `playwright.config.ts`'s `webServer` (same technique as the existing AS-202 test) rather than mocking `uploadAvatar` in-process — the specific gap M10 scrutiny called out ("never crossing the HTTP pipeline that owns the limit"). Because the client-side pre-flight check (added by this same feature) and the server-side validator both surface the identical "2MB or smaller" string, the e2e test asserts the message is shown and no unhandled rejection occurs — it does not force the client-side check to be bypassed. This is a reasonable reading of "crosses the real action pipeline": it is a real HTTP-capable browser session against the real, now-correctly-configured Next server, not the previous integration test's fully in-process `uploadAvatar(formData)` call. A follow-up could go further and directly POST a raw multipart Server Action request past the client entirely to independently exercise the exact byte-limit-vs-app-limit interaction at the HTTP layer — noted below as out-of-scope, not attempted here given the complexity of hand-constructing Next's Server Action wire protocol (Next-Action header, action id, RSC boundary encoding).
