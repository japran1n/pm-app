## Decisions made
- **AS-351 is satisfied by construction, not by a special-case check.** `restoreTask` never reads or writes any column on the `projects` table other than looking up `workspace_id` for the membership check — `projects.deleted_at` (the column F142 reuses for "archived", per that feature's own migration doc comment: a second parallel `archived_at` column would be a second source of truth) is never selected, referenced, or written anywhere in this function. A restored task simply becomes visible again inside whatever project it belongs to, archived or not — exactly like every other already-live task sitting in that same archived project (archiving a project doesn't itself hide the project's own tasks from that project's own board, only from cross-project aggregates, per the `p.deleted_at is null` exclusions in AS-129/AS-174's RPCs). Verified explicitly with a real archived-project fixture in the AS-351 test, not just inferred from the code path.
- **Position is always recomputed, never reused.** Per the worker brief's explicit instruction, the task's stale `position` value is discarded; `restoreTask` looks up the current last LIVE task in the resolved `(project_id, status)` column and calls `calculatePosition(lastPosition, null)` (`lib/board/position.ts`) to append to the end — the identical "append to the end" pattern `createTask` already uses for brand-new tasks. Verified with a test that deliberately creates a live task colliding with the restored task's old stale position, and asserts the restored position is strictly past it.
- **Cascade-restore scope boundary (per this feature's own instruction and F187/F188's documented gap):** only children whose `deleted_via_task_id` correctly points back to the task being restored are restored — this is exactly the F149 single-task `deleteTask` cascade path (`cascade_delete_task` RPC), which does stamp that column. Children soft-deleted as a side effect of `bulkDeleteTasks` (F187) never had `deleted_via_task_id` stamped in the first place (F187's own documented gap, restated again in F188's handoff) — this function has no way to distinguish those from an independently-deleted child that merely happens to be in trash at the same time, and deliberately does NOT attempt to restore them. Not a bug to fix here; restated in Out-of-scope below per the instruction not to fix F187's gap in this feature.
- **Cascaded-children restore is a bounded per-child loop, not a single RPC.** This feature's Files list (validation.tsx, tasks.ts, trash page) does not include `supabase/migrations/`, so no new RPC was written to make the parent+children restore atomic the way `cascade_delete_task` is. Each cascade-deleted child needs its OWN freshly-computed end-of-column position (a single multi-row `.update()` can't express distinct per-row values), so children are restored in a small loop — bounded by F148's one-level nesting limit (a task can have children, but children can't have their own children), so this is never an unbounded per-row loop over an arbitrary result set, unlike the "no per-row loop" prohibition this feature's inherited performance-budget answer is really guarding against (large N mutations). If a child's own restore update fails mid-loop, it's logged as non-fatal and the parent (already restored) is not rolled back — the same "best-effort cascade, parent restore is not lost to a child-row failure" tradeoff `bulkDeleteTasks`'s own non-atomic child cascade already accepts, restated here for the inverse operation. Documented inline in `restoreTask`'s doc comment.
- **A task that is not currently soft-deleted behaves as "not found" when restore is attempted**, mirroring every other action in this file's own "row doesn't match the expected pre-state" convention (e.g. `deleteTask`'s "already-deleted task looks like not found" idempotency-safety note) — inverted here to require `deleted_at IS NOT NULL` rather than `IS NULL`. This was chosen over a "no-op returns ok" branch (this feature's inherited empty-state convention from other actions in this mission) because restoring a task that was never in trash isn't a meaningful no-op the way, e.g., promoting an already-top-level task is — there's no sensible "success" data to return for a task that was never deleted.
- **Status-fallback branch is unreachable today, built anyway per the spec's explicit instruction.** `tasks.status` is a fixed, DB CHECK-constrained enum (`tasks_status_check`, `supabase/migrations/20260818013434_create_tasks.sql`) — every row's `status` is always one of `todo`/`in_progress`/`in_review`/`done`, so `statusWasReset` can never actually be `true` until F218 (caller-defined board columns) lands. The fallback logic (`KNOWN_STATUSES` membership check, falling back to `"todo"`) is implemented exactly as instructed and applies identically to both the parent task and every cascaded child, with `statusWasReset` surfaced in the action's return value so `TrashRestoreButton` can show a distinct toast message the day this branch becomes reachable. Not independently unit-tested as a "status was reset" scenario since the DB itself makes that state impossible to seed today (a direct insert of an invalid status value is rejected by the CHECK constraint) — this is a structural deferral, not a gap, consistent with `deleteTask`'s own AS-057 doc comment's precedent for a not-yet-reachable branch.
- **`TrashRestoreButton` (new Client Component) coexists with F191's concurrently-added `RestoreCommentButton`.** `components/trash/trash-list.tsx` changed on disk mid-session (F191, restore-comment, running concurrently in this mission's parallel-worker model) — rather than reverting that change, this feature's own restore control was added alongside it (`item.type === "task"` renders `TrashRestoreButton`, `item.type === "comment"` renders F191's `RestoreCommentButton`), each row type getting exactly one restore control wired to its own Server Action. No other part of F191's change was touched.

## Out-of-scope work needed
- **F187's bulk-delete cascade provenance gap remains unresolved** (restated per this feature's own instruction to flag it again, not fix it here): children soft-deleted as a side effect of `bulkDeleteTasks` never get `deleted_via_task_id` stamped, so restoring their parent through `restoreTask` will NOT bring them back — they'd need to be restored individually from the trash list, or a future feature would need to backfill `deleted_via_task_id` for `bulkDeleteTasks`'s cascade (which per F188's handoff would require a new RPC, since the Supabase JS `.update()` builder can't express a per-row column-to-column assignment).
- **No bulk-restore action.** This feature only restores one task at a time (mirrors `deleteTask`, not `bulkDeleteTasks`) — a future feature could add a `bulkRestoreTasks` sibling if multi-select restore from the trash view becomes a requirement; the current trash UI has no multi-select affordance to hang it off of anyway.
- **Restoring a task whose original assignee is no longer an active member of the workspace is not specially handled.** `restoreTask` never touches `task_assignees`/`tasks.assignee_id` at all — an assignee who left the workspace while the task sat in trash stays assigned to the restored task exactly as it was before deletion (no "unassign now-invalid assignees on restore" logic exists anywhere in this codebase, including on `editTask`/`setTaskAssignees`, for tasks that were never deleted). Flagging in case a future feature wants restore to also re-validate assignee visibility (AS-290's rule) the way `setTaskAssigneesCore` does for an explicit assignee change.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose "not found" (rather than a silent no-op `ok: true`) for a restore call against a task that isn't currently soft-deleted — no user input was available (ZERO_QUESTIONS run) and the spec/clarification didn't name this specific case; picked the option consistent with every sibling action's own "row must match the expected pre-state or it's not found" convention already established in this file, rather than inventing a new no-op branch for a case that has no meaningful "already done" state to report back.
AUTONOMOUS_DECISION: Implemented cascaded-children restore as a bounded per-child loop of ordinary `.update()` calls rather than writing a new `restore_task` RPC migration, because this feature's Files list didn't include `supabase/migrations/` and the loop is bounded by F148's one-level nesting limit (never unbounded), which reads as compliant with this feature's inherited "never a per-row loop of network calls" performance-budget answer (aimed at unbounded/large-N operations, not a small fixed-depth cascade). If a future feature wants full atomicity for the cascade-restore step, add a two-arg `restore_task(p_task_id)` RPC mirroring `cascade_delete_task`'s own pattern.
