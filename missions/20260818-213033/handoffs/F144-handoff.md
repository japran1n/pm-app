## Decisions made
- **Shared predicate (the "systematic" part of this feature's spec)**: created one Postgres view, `active_project_tasks` (`select t.*, p.workspace_id as project_workspace_id from tasks t join projects p on p.id = t.project_id where t.deleted_at is null and p.deleted_at is null`), `security_invoker = true` to match this codebase's `SECURITY INVOKER` RPC convention (see `get_priority_counts`'s own comment citing M6 scrutiny). Every existing dashboard aggregate RPC (`get_priority_counts`, `get_status_counts`, `get_overdue_count`) is rewired to select from this view instead of re-deriving `and p.deleted_at is null` inline — a future aggregate only has to `from active_project_tasks` (or join to it) and is structurally unable to forget the filter, rather than copy-pasting the same two-column exclusion at a new call site. This satisfies the spec's explicit "so a new aggregate added in the future can't forget the filter" requirement. `get_workspace_time_by_person` (the one genuine bug found) now joins through the same view.
- **Real gap found and fixed: `get_workspace_time_by_person` (F115)**. It joined `time_entries -> tasks -> projects` (to reach `workspace_id`) but only ever filtered `t.deleted_at is null`, never `p.deleted_at is null` — an archived project's logged time was still being summed into the workspace-wide per-person time report (`app/(workspace)/w/[workspaceSlug]/time/page.tsx`). Fixed by joining through `active_project_tasks` instead of raw `tasks`. Found by reading every RPC named/reachable from this feature's Files scope (`lib/queries/time-entries.ts`) against the assigned audit, not by assuming compliance — per the clarification's Q1 chosen implementation pattern.
- **`get_project_time_totals` (F114) and `get_project_board_tasks` (F279) intentionally NOT changed**: both are scoped by a single `p_project_id` — a project viewing its own data on its own page — not a cross-project workspace aggregate that an archived project's tasks could leak INTO. AS-254's wording ("excluded from the dashboard, search, and My Tasks") is about workspace-wide surfaces; whether an archived project's own detail page still shows its own historical time/board totals is a different, out-of-scope question. Flagged explicitly below rather than silently changed, per the clarification's scope-boundary default.
- **Ambiguity resolution (ombudsman default, "simpler option, no new dependency, no second source of truth")**: chose a plain SQL view over (a) a reusable PL/pgSQL predicate function called at each site, or (b) a client-side TypeScript constant — a view is the simplest single place Postgres itself enforces "this row counts toward a cross-project aggregate," with zero new dependency and no risk of app code and SQL disagreeing on the definition.
- **"Already compliant" is a valid, documented outcome (clarification Q6 default)**: dashboard (3 RPCs) and search were both already correct before this feature; said so explicitly above rather than inventing unnecessary changes to them beyond the view refactor (which is behaviour-preserving, not a fix).
