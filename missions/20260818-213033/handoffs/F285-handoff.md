## Decisions made
- **Where the CROPPED image lives, resolved:** per F284's flagged handoff note, the cropped result previously lived only in `Popup.tsx`'s local `captureState`, not in `store.ts`. This feature reads whichever image the user ended up with directly from `Popup.tsx`'s own state (`captureState.cropped?.dataUrl ?? captureState.capture.dataUrl`) when opening the editor — cropped takes precedence when both exist, since a crop is a deliberate narrowing of what the user wants attached. It does **not** add a second `store.ts` slot for the crop itself (that would be new, out-of-scope surface); instead it adds the one slot this feature's own assertion (AS-545) actually requires: `AnnotatedResult` in `store.ts`, holding the final flattened-with-annotations PNG. A later feature reads `getAnnotatedResult()` first, falling back to `getLastCapture()` only if the user skipped annotation entirely (not built here — out of scope, see below).
- **`AnnotatedResult` is a sibling slot in `store.ts`, not a reuse/overwrite of `CapturedScreenshot`/`setLastCapture`.** `CapturedScreenshot` is typed to exactly what `chrome.tabs.captureVisibleTab` returns (`devicePixelRatio`, `capturedAt`); an annotated result is a canvas-flatten output with neither of those fields and would be a type lie if forced into that shape. Kept the same in-module-singleton (not `chrome.storage`) pattern as `current`, for the same size/lifetime reasoning F283's original handoff already established.
- **Coordinate space: all annotation operations are stored in the base image's own natural pixel space**, not CSS display pixels. The interactive canvas's backing store (`canvas.width`/`canvas.height`) is sized to the base image's natural dimensions; its CSS display size can be scaled down to fit the popup. Every pointer event is mapped from screen pixels into backing-store pixel space before being recorded (`(clientX - rect.left) * (canvas.width / rect.width)`), so the exact same operations list, drawn through the exact same `drawAllOperations` function, produces pixel-identical output whether rendered live on the interactive canvas or flattened at full resolution in `flatten.ts` — this is what makes the AS-545 "what you saw is what gets attached" claim literally true rather than an approximation.
- **Undo/redo: a real stack of discrete operations, not a re-render-from-scratch-per-keystroke approach.** `ops: AnnotationOp[]` holds committed operations; `redoStack` holds operations popped by Undo and is cleared the instant a new operation commits (standard "new edit invalidates redo" behaviour). A freehand stroke accumulates points in a local `draft` during the drag and is pushed onto `ops` as exactly ONE entry on pointerup — so Undo removes a whole stroke at once. Chose this over point-by-point undo because a user drags one continuous gesture with one intent ("draw this squiggle"); undoing it one sampled point at a time would take dozens of clicks to reverse a single stroke and doesn't match how any real drawing tool (including the ClickUp extension's own markup tool referenced in tech-decisions.md) behaves.
- **Text tool keyboard operability (spec's explicit ask, in prep for AS-570):** text entry always goes through a real, focusable HTML `<input>` overlay — never a canvas-only click-to-type caret simulation. Two ways to open it: (1) clicking the canvas while the Text tool is selected, at the clicked point (mouse/pointer users); (2) a separate "Add text" `<button>` in the toolbar, reachable by Tab and activatable by Enter/Space, which opens the same input pre-positioned at the canvas centre — no pointer coordinate required at all. Confirmed with Enter or blur (if non-empty); Escape or a blur with empty text cancels without committing an op.
- **Font size for the text tool is derived from the shared stroke-width control** (`fontSizeForStrokeWidth`, `12 + strokeWidth * 4`) rather than adding a second, redundant size control — keeps the toolbar to exactly what the spec asked for (tool palette, colour picker, stroke-width control, undo/redo).
- **Pointer Events API** (`pointerdown`/`pointermove`/`pointerup` + `setPointerCapture`/`releasePointerCapture`) used on the canvas itself, per MDN's current guidance that this is the unified model superseding separate mouse/touch handlers for exactly this "drag to draw" case (verified https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture, 2026-08-20). `RegionSelect.tsx` (F284) used plain mouse events for its simpler single-rect-drag case; this feature has four distinct drag/tap tools and benefits from pointer capture's built-in "keep receiving move/up events even if the pointer leaves the element" guarantee.
- **No external drawing library was added for the editor itself** — canvas 2D context + Pointer Events cover arrow/rectangle/freehand/text exactly as the spec anticipated. `pngjs` was added only as a **test-only dev dependency**, to decode real PNG pixel bytes in `annotate.spec.ts` assertions (verifying actual pixel output changed, per the task's explicit testing instructions) — it is not part of the shipped extension bundle.

## Out-of-scope work needed
- **Attaching the annotated (or, if the user skips annotation, the plain/cropped) image to a task** — the actual upload to the attachments bucket / task-creation Route Handler is still a separate, later M19 feature per tech-decisions.md and F284's own handoff. This feature only gets the flattened PNG into `store.ts`'s `getAnnotatedResult()`; it does not upload anything.
- **A "skip annotation, attach as-is" fallback path for the next feature to read** — this feature does not itself decide what happens if the user never opens the annotation editor at all; that decision (read `getAnnotatedResult()` if present, else `getLastCapture()`/the crop) belongs to whichever feature builds the actual attach/upload flow, and is noted here so it isn't rediscovered from scratch.
- **AS-570 (full keyboard-operability testing of the text tool, e.g. arrow-key repositioning, full toolbar keyboard navigation audit)** — explicitly out of scope per the feature spec's own note; this feature only avoided architecting the text tool in a way that makes that later work structurally impossible (real focusable `<input>` for entry), it does not implement or test full keyboard operability of the whole editor.
- **Placing/repositioning existing annotation operations after they're committed** (e.g. dragging an already-drawn rectangle to move it, resizing an arrow after release) was not requested by the spec or clarification and was not built — only draw-once-and-undo/redo, matching AS-542/AS-543's literal wording.

## Autonomous decisions
AUTONOMOUS_DECISION: Resolved the F284-flagged "where does the cropped image live" question by reading it directly from `Popup.tsx`'s own render-tree state (`captureState.cropped`) at the point this feature's "Annotate…" button is clicked, rather than adding a new `store.ts` slot for the crop itself — the crop only needs to survive long enough to seed the annotation editor within the same popup mount, which local React state already does; per the clarification's "simpler, more private" tie-breaker, adding a second persistent slot for data that's about to be superseded by the annotated result one click later would be unnecessary surface. The one slot genuinely needed for the next feature to consume (`AnnotatedResult`) was added to `store.ts`, following the established pattern F283/F284 set for `CapturedScreenshot`.
AUTONOMOUS_DECISION: Freehand strokes undo as one whole stroke rather than per-sampled-point, per the spec's own explicit guidance ("undo as one whole stroke... unless you have a good reason to do otherwise") — no reason to deviate was found, so the guidance was followed directly.

## Notes for the next worker
- `extension/src/capture/store.ts` now exports `setAnnotatedResult`/`getAnnotatedResult`/`clearAnnotatedResult` alongside the existing `setLastCapture`/`getLastCapture`/`clearLastCapture`. The upload/attach feature should read `getAnnotatedResult()` first and only fall back to the plain capture/crop if the user never annotated — that fallback logic does not exist yet anywhere and needs to be built by whichever feature does the actual attach.
- `AnnotationEditor` (`extension/src/annotate/canvas.tsx`) is a self-contained component taking `baseImageDataUrl`, `onSubmit(FlattenResult)`, `onCancel()` — it doesn't know or care whether its base image came from a full capture or a crop, and doesn't touch `store.ts` itself (Popup.tsx does that in `handleAnnotationSubmit`, consistent with how F283/F284 kept capture-orchestration in the popup and left the sub-components purely presentational/functional).
- `drawOperation`/`drawAllOperations` in `extension/src/annotate/tools/draw.ts` are the single source of truth for how each op renders — both the live interactive canvas (`canvas.tsx`'s redraw effect) and the final flatten (`flatten.ts`) call the exact same functions, which is what makes the AS-545 pixel-identity test reliable rather than approximate.
- Real APIs used, verified 2026-08-20: `CanvasRenderingContext2D` 2D drawing (`strokeRect`, `beginPath`/`lineTo`/`stroke`, `fillText`, `arc`) — stable, no version concerns; `Element.setPointerCapture`/`releasePointerCapture` (https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture). No new runtime dependency was added to the shipped extension bundle — confirmed via `npm run build` + the existing AS-538 no-secret-key/bundle-content check, and by inspecting that `pngjs` only appears in `extension/tests/annotate.spec.ts` (a devDependency, excluded from `vite build`'s output).
