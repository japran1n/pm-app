## Decisions made
- Bulk updates collapse into ONE `task_activity` entry per changed field PER TASK, never one entry for the whole batch — resolved per this feature's explicit clarified ambiguity-resolution instruction ("the simpler option that adds no new dependency and no second source of truth"). `bulkUpdateTasks` now reads a single "before" snapshot for the whole allowed-id set in one query, diffs each updated row against its own before-snapshot in memory, and writes each task's changes via the existing per-change RPC loop — no new batch-shaped RPC or table was added, keeping the same `write_task_activity_entry` call this feature's spec assigns to every other mutation path.
- `diffTaskFields` is a genuinely pure function (no imports from `@supabase/supabase-js`, no React, no I/O) per the clarified "implementation pattern" answer — it lives in the same file as the RPC-calling wrappers (`writeTaskFieldChanges`, `writeTaskCommentEvent`) only because this feature's Files list names exactly one new file (`lib/activity/task-activity.ts`); splitting the I/O glue into a second, unnamed file would have been an out-of-scope expansion for no benefit, since the diff function itself has zero coupling to the wrappers and is independently unit-tested in isolation (`tests/unit/task-activity-diff.test.ts` never touches Supabase).
- Closed field vocabulary used is exactly the six names F194's migration header documents: `title`, `status`, `priority`, `due_date`, `estimate`, `assignee_id` — matching AS-355's exact list (title, status, assignee, priority, due date, estimate). No additional fields (description, tags) are diffed; the clarification file and F194 handoff both scope the vocabulary to these six, and AS-355's assertion text names only these six.
- Assignee changes are diffed against the `tasks.assignee_id` MIRROR column (F160's single-value projection of the possibly-multi-valued `task_assignees` set), not the raw `task_assignees` rows — consistent with every other reader in the codebase (notifications, board grouping) already treating that mirror as the canonical "current assignee" value, and avoiding a second, parallel multi-assignee diffing algorithm this feature's spec never asked for. `setTaskAssigneesCore` (the one real write path behind `assignTask`/`addTaskAssignee`/`removeTaskAssignee`/`setTaskAssignees`) now reads the mirror before recomputing it and diffs old vs. new mirror value once, so all four multi-assignee entry points get activity coverage for free from this one call site.
- AS-360's recurrence-job entry uses `kind: 'field_changed'`, `field: 'due_date'` (old value `null`, new value the computed due date) rather than inventing a new `kind` — F194's `kind` CHECK constraint is a closed, already-migrated vocabulary (`field_changed`/`comment_added`/`comment_deleted`) with no "task created" option, and adding a new enum value would require a new migration outside this feature's Files scope (`supabase/migrations/` is not listed as a file F195 may touch). `p_system: true` is passed explicitly so the RPC writes `actor_id = null` regardless of any session context the recurrence job happens to run under — this is the mechanism AS-360 actually tests, not the specific field name chosen to carry it.
- `requireAssignActionContext` (the shared preflight every multi-assignee action calls) now also returns the session-bound `supabase` client alongside the existing `admin` client, so `setTaskAssigneesCore` can call `write_task_activity_entry` through the same request-scoped session every other action's activity write already uses (the RPC requires `auth.uid()` to be set for a human-attributed write — the admin/service-role client has no session and would make every such call fail).
- Every activity write is wrapped in its own try/catch and logged via `console.error` on failure, never thrown — mirrors `writeAudit()`'s (F140) exact non-fatal rationale, per this feature's clarified failure-handling answer ("invalid input returns a typed error or null rather than throwing, and the caller decides how to surface it" — extended here to mean a failed *write*, not just invalid input, since the alternative would turn a best-effort audit trail into a hard dependency for every task mutation to succeed).

Wiring a `write_task_activity_entry` RPC call into that SQL function is out-of-scope for this feature (`supabase/migrations/` is not in F195's Files list, and doing so would require a new migration) — flagged here as a gap: a task auto-generated by the SQL-side scheduled job (as opposed to the TypeScript `moveTaskStatus`-triggered completion path this feature wires) will NOT currently get a system-attributed `task_activity` entry. Flagged for a follow-up.
