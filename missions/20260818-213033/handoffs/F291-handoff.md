## Decisions made
- **Orchestrator-resolved scope deviation, made explicit here per the task instructions.** The spec's draft scope said "Toggles in the report form" — no unified report form exists yet (F293, unbuilt). Following the exact precedent F289/F290 already established (their own independent, standalone popup UI sections rather than waiting on a form that didn't exist), this feature builds its own standalone toggle/preference module and popup UI now, wired to gate F289's and F290's existing "Start capturing" flows. `extension/src/capture/privacy-toggles.ts`'s file header documents that a future F293 should read/reuse `getCapturePreferences`/`setCapturePreferences` and the two gating functions rather than reimplementing capture on/off logic.
- **Both toggles default to OFF**, per the clarification's tie-breaker ("the simpler, more private option — less data captured, narrower permission — by default"). This is a real, load-bearing choice: it means F289's and F290's existing "Start capturing" buttons, which previously worked immediately on click, are now disabled until the reporter explicitly opts in via the toggle above them. **This broke F289/F290's own existing Playwright tests on the first full-suite run** (they clicked Start without first opting in) — fixed by updating those two spec files to check the relevant toggle before clicking Start, which is the correct fix: those tests should reflect the real (now-gated) reporter flow, not the pre-F291 ungated one. This is documented here rather than silently reverting to "on by default," which would have contradicted the clarification's private-by-default tie-breaker and the spec's own "nothing collected until off is explicitly turned on" framing.
- **The toggle genuinely gates the `chrome.scripting.executeScript` call itself, not just the UI.** `startConsoleCaptureIfEnabled`/`startNetworkCaptureIfEnabled` in `capture/privacy-toggles.ts` check the persisted preference first and return an `{ ok: false, reason }` early WITHOUT ever calling the injected starter function when the toggle is off — so the hook is never installed, not merely hidden from the popup once captured. Proved directly in tests by checking the real `window.__pmAppConsoleCapture__`/`__pmAppNetworkCapture__` marker the hooks themselves set, not just popup UI state. The Popup component also disables the Start buttons via a mirrored preference flag as a UX nicety (so a reporter isn't clicking a button that visibly does nothing), but that mirror is UI-only — the actual gate that matters is inside the two `*IfEnabled` functions, which re-check `chrome.storage.local` themselves rather than trusting the mirrored UI state.
- **Preference persisted under a single flat key `pmapp-capture-preferences`** holding `{ consoleCaptureEnabled, networkCaptureEnabled }` in `chrome.storage.local`, following this extension's established "no key prefixing needed, chrome.storage.local is already namespaced per-extension" convention from `lib/chrome-storage-adapter.ts`'s own header comment. Chose one JSON object over two separate boolean keys since both toggles are read/written together in the same popup section and a single round-trip keeps `getCapturePreferences`/`setCapturePreferences` simple; `setCapturePreferences` takes a `Partial<CapturePreferences>` patch and merges onto the current stored value (or defaults) so either toggle can be flipped independently without clobbering the other.
- **A malformed/partial stored preference falls back to `DEFAULT_CAPTURE_PREFERENCES` (both off), never to "on."** `isCapturePreferences` requires both fields to be real booleans; anything else (unset key, corrupted JSON-adjacent shape, one field missing) is treated as "no preference recorded yet" — a corrupted preference must never silently turn capture on.
- **Live counts are read from the popup's existing in-memory capture state** (`consoleCaptureState.entries.length` / `networkCaptureState.entries.length` from F289/F290's own state, passed down as props), not re-derived independently — per the task instructions' explicit guidance to reuse `getConsoleCaptureFromActiveTab`/`getNetworkCaptureFromActiveTab`'s existing consumers rather than re-deriving counts. A count only renders once that capture kind is `"active"` (i.e., has actually run at least once and been refreshed), matching the spec's own "12 console errors, 3 failed requests" example format — no count shows for a capture that's merely enabled but never started.
- **Log preview deferred**, per the clarification's explicit "decide whether preview lands here or is deferred" note and its tie-breaker toward the simpler/more private option. The live counts are themselves a form of summary; a full log-content preview modal is new UI surface AS-554's literal wording ("turned off per report") does not require. Documented in Out-of-scope below.
- **"Always visible and reversible before sending"** interpreted as: the toggle component is always rendered in the popup (not hidden behind another flow) and flipping it takes effect immediately via `chrome.storage.local`, with no reload and no effect on any already-captured buffer — there is no "send" action yet to attach a stricter "before sending" gate to (that's F293's job). Documented as an autonomous decision below.
- **Disabling the Start buttons is UI-only sugar layered on top of the real gate**, deliberately kept as a separate, simple boolean mirror (`consoleCaptureEnabled`/`networkCaptureEnabled` local state in `Popup.tsx`, updated via `CapturePrivacyToggles`'s `onChange` callback) rather than making `Popup.tsx` re-read `chrome.storage.local` on every render — this keeps `Popup.tsx`'s existing "local React state, not chrome.storage" pattern for the capture UI intact (per F289/F290's own established pattern) while still delegating the actual go/no-go decision to `privacy-toggles.ts`'s gating functions, which are the source of truth a future F293 should call directly.

## Out-of-scope work needed
- **No unified report form / send action exists yet (F293).** This feature's toggles gate F289's/F290's standalone "Start capturing" buttons; F293 should call `getCapturePreferences()`/`setCapturePreferences()` and `startConsoleCaptureIfEnabled`/`startNetworkCaptureIfEnabled` from `extension/src/capture/privacy-toggles.ts` directly rather than reimplementing on/off logic, and should render (or reuse) `CapturePrivacyToggles` in whatever assembled-report UI it builds, wiring `onChange` to whatever "before sending" gate F293 needs. `CapturePrivacyToggles` already accepts `consoleCount`/`networkCount` props for exactly this purpose.
- **Log-content preview is deferred** (not built here) — a reporter can see live counts next to each toggle and can already see full entries via F289's/F290's own "Refresh captured logs/requests" lists further down the popup, but there is no preview surfaced directly in/near the toggle section itself. If a future feature wants that, it can pass the already-fetched entries into `CapturePrivacyToggles` (or a sibling component) rather than re-fetching.
- **No explicit "clear captured data" affordance when a toggle is turned off after capturing** — per this feature's own "reversible... does not lose already-captured data when flipped back on" interpretation, turning a toggle off does NOT clear the popup's in-memory captured entries or stop hooks already installed on the page (F289/F290's own handoffs already document there's no "stop capturing" affordance either). A reporter who wants to discard already-captured data currently has no explicit way to do that short of closing the popup/tab. Flagging in case a future feature wants an explicit "clear" button.
- **No cross-tab/cross-session preference sync UI feedback** — `chrome.storage.local` preferences apply extension-wide (not per-tab), which is correct per "per-user" preference framing, but there's no popup affordance telling the reporter the preference is shared across all tabs/reports; not required by AS-554's wording, flagging for completeness.
