## Autonomous decisions
AUTONOMOUS_DECISION: assignee/tag cross-lane drag semantics resolved as "move" (remove the source lane's value, add the target's, leave every other existing value alone), not "add". Rationale (recorded in `board.tsx`'s own doc comment on `groupFieldPatch`): F224 already made "a task with N values for the grouped field appears in N lanes" the board's rendering contract. "Add" would leave the card permanently in the lane the user just visually dragged it out of (nothing would ever remove it), directly contradicting what the user watched happen on screen. "Move" keeps the board honest — after the drop, the task appears in exactly the lanes its real `task_assignees`/`tags` rows say it should, no more and no less. Dragging out of "None" (nothing to remove) or into "None" (nothing to add) both degrade correctly to a plain add/remove from the same single computation, with no special-cased branches needed for either direction — verified explicitly by `test_AS_420_assignee_drag_out_of_None_lane_adds_without_needing_a_removal` and `test_AS_420_assignee_drag_into_None_lane_removes_without_adding_a_replacement` (and the tag equivalents).
AUTONOMOUS_DECISION: `BoardColumn`'s pre-existing lane-scoped `dropId` (`${laneKey}::${column.id}`, F224's seam) meant a drop directly onto an EMPTY grouped column resolves to the column's real `id`, not its `name` — but every task's `status` field, and every existing validation/persistence call, is keyed on the column's `name`. Rather than changing `dropId`'s encoding (which would also require re-touching F224's `Swimlane`/`BoardColumn` id contract more invasively), `handleDragEnd` now looks the resolved id up against the board's real `columns` state (`columns.find((c) => c.id === overRealId)`) and falls back to using the id itself when no column matches — which is exactly what happens in the ungrouped view, where `dropId` already defaults to the column's `name`, so a single lookup correctly handles both paths without a groupBy-conditional branch.
