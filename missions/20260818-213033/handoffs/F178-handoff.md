## Decisions made
- **Verified pg_cron / Supabase Cron syntax** by fetching the CURRENT docs (not training-data memory, per this mission's version-freshness rule) on 2026-08-22 from https://supabase.com/docs/guides/cron/install (`create extension pg_cron with schema pg_catalog;` + `grant usage on schema cron to postgres;` + `grant all privileges on all tables in schema cron to postgres;`) and https://supabase.com/docs/guides/cron/quickstart (`select cron.schedule('job-name', '<schedule>', 'SELECT some_function()');`). Both are exactly what the migration uses. `tech-decisions.md` had already settled on this approach for this exact feature on 2026-08-18 ("Supabase Cron (pg_cron, enabled by default on all plans) calling a Postgres function directly") — this migration makes that decision reproducible rather than clicked into a dashboard, per the feature spec's explicit requirement.
- **SQL/TypeScript date-math parity** — `public.recurrence_next_due_date(rule jsonb, from_date date)` is a hand-written SQL port of `lib/recurrence/next-date.ts`'s `nextOccurrenceDate`, NOT a call out to the TypeScript module (Postgres can't run TS). Parity is proven, not assumed, by `tests/integration/recurrence-sql-parity.test.ts` running the same 14 representative cases plus 2 invalid-input cases through both implementations via `.rpc(...)` and asserting identical output — this is the feature spec's actual verification bar. Notable porting details: Postgres's own `date + interval 'N months'` does NOT clamp at month-end (it overflows into the next month), unlike date-fns's `addMonths` which does — the SQL function hand-rolls the clamp (`least(source_day, last_day_of_target_month)`) to match. The `timezone` parameter from the TypeScript signature is dropped in SQL: `next-date.ts`'s own comment documents that timezone only matters for a caller's "today" comparison layered on top, not the pure day-count arithmetic itself, which the SQL function performs identically (operating on plain `date` values, never timestamps).
- **Trigger condition (found and fixed mid-session against the real linked project)**: the correct semantics for "whose next date has arrived" (AS-322) is the task's OWN `due_date <= current_date` (the current occurrence is due/overdue), not the COMPUTED next date `<= current_date`. The first migration (20260822160000) got this backwards — gating on the computed next date meant every task with an interval longer than "already elapsed" (the common case: weekly, monthly, or any large `every_n_days`) was silently skipped forever, since its freshly-computed next date is itself in the future. Caught via a seeded `every_n_days: 20000` integration test that generated 0 occurrences where 1 was expected; fixed in a follow-up migration (20260822161000, `create or replace function`) within this same feature — additive/fix-forward per this mission's migration-safety convention, not a rewrite of migration history. This mirrors F177's own model exactly: F177 triggers on the CURRENT occurrence's completion and always writes a (possibly future) computed due_date onto the new row; F178 triggers on the CURRENT occurrence's due_date having arrived, and likewise always writes whatever `recurrence_next_due_date` computes onto the new row, future or not.
- **Idempotency**: reuses F177's exact DB-level guarantee — `ON CONFLICT (recurrence_parent_id, due_date) DO NOTHING` against the same `tasks_recurrence_occurrence_idempotency` unique constraint, `recurrence_parent_id` always the series ROOT (`coalesce(t.recurrence_parent_id, t.id)`), never the immediately-due task. This means F177's on-completion path and F178's date-driven path share one idempotency guard: whichever generates an occurrence for a given (series, due_date) pair first, the other is a safe no-op if it later tries the same pair.
- **Cascading behaviour is intentional, not a bug**: if a generated occurrence's own new `due_date` is itself already overdue (e.g. a long-untouched series), the NEXT scheduled run also picks it up and advances it one more step — each run advances every currently-overdue task by exactly one occurrence, so a series that's fallen many periods behind catches up incrementally across successive runs rather than in one unbounded burst per run. This is covered by an explicit test (`tests/integration/recurrence-scheduled-generation.test.ts`, the "cascades one step per run" case) so a future reader doesn't mistake it for a duplicate-generation bug.
- **SECURITY DEFINER + explicit grants**: `generate_due_recurring_occurrences` runs as SECURITY DEFINER (search_path pinned to `public`) since pg_cron's job runs as the `postgres` role with no human session/RLS context to authenticate as — the scheduled trigger IS the authorized caller, by design, matching this feature's Clarified implementation (auth/access-control answer: "no — it is pure; permission checks stay in the action layer that calls it"). `EXECUTE` is revoked from `PUBLIC` and granted only to `postgres`/`service_role` — least privilege for a function that writes tasks/checklist_items/task_assignees unconditionally once its date gate is satisfied.
- **Cron interval — hourly (`0 * * * *`)**: AUTONOMOUS_DECISION, no interval was pinned by the feature spec or its clarification round. Date-driven recurrence rules bottom out at day granularity (the shortest supported `freq` is "daily"), so there's no behavioural difference between a 5-minute and an hourly cadence — whichever run first sees an arrived `due_date` generates the occurrence, and a day has 24 hourly windows to catch it. Hourly is the simplest option adding no new dependency, stays well within Supabase Cron's "no more than 8 concurrent jobs, each under 10 minutes" guidance, and avoids needlessly re-scanning the whole recurring-task set every few minutes for a feature whose own precision floor is "once a day."
- **Field-copy allow-list, ported unchanged from F176/F177**: title, description, description_json, priority, estimate_minutes, checklist items (content + position only, always fresh/unchecked), assignees (user_id only). `status` always resets to `'todo'`. `assigned_by` on the new occurrence's `task_assignees` rows is the series' own `author_id` (there's no acting human user for a scheduled job to attribute the assignment event to).
- **Position**: appended to the end of the new occurrence's `(project_id, status='todo')` column via `coalesce(max(position), 0) + 1000` — same convention `calculatePosition`/`createTaskForUser`/F177's `generate-next-occurrence.ts` all use for a brand-new card at the bottom of a column.
