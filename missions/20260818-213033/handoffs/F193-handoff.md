## Decisions made
- **Full audit trail, per surface, per this feature's own "read every file in scope + repo-wide grep" instruction:**
  - **Board** (`getProjectBoardTasks` / `get_project_board_tasks` RPC, most recently amended by `20260822170000_rpc_project_board_tasks_recurrence.sql`) — already compliant: `where t.deleted_at is null` in the RPC's own WHERE clause. Its lateral joins for the newer join tables are also already correctly scoped: `child_agg` filters `c.deleted_at is null` (child tasks), `checklist_agg` reads `checklist_items` for the already-live outer task `t` (no leak vector — a checklist item can't outlive its own row's `task_id` FK, and the outer task is already filtered live), `blocker_agg` filters `blocking.deleted_at is null` (the blocking task), `assignee_agg` reads `task_assignees` for the already-live outer task `t`. No fix needed.
  - **Project List / Workspace List (dashboard table)** (`getProjectListTasks` / `getWorkspaceListTasks`, `lib/queries/tasks.ts`) — already compliant: both `.is("deleted_at", null)` directly in the query builder. The `task_assignees`-based assignee filter (`filterTaskIdsByAnyAssignee`) resolves candidate task ids from `task_assignees` without itself checking the task's `deleted_at`, but this is safe by construction — the resulting id list is only ever used as a further `.in("id", ...)` narrowing on top of the SAME query, which already filters `deleted_at is null` independently; a trashed task's id surviving the assignee-lookup step can never survive the outer filter. No fix needed.
  - **Search** (`searchWorkspaceTasks` / `search_tasks` RPC) — already compliant, same as F144 found: `search_tasks`'s own WHERE clause has `and deleted_at is null` (`20260818050300_fts_tasks_search_fn.sql`), and the exact-task-key lookup path added later by F147 (`lib/queries/search.ts`) independently adds its own `.is("deleted_at", null)` on that direct `tasks` select. No fix needed.
  - **Dashboard** (`get_priority_counts`, `get_status_counts`, `get_overdue_count`) — already compliant via F144's shared `active_project_tasks` view (`20260822010000_active_project_tasks_view_and_time_report_fix.sql`), whose definition is `where t.deleted_at is null and p.deleted_at is null` — this view is ALREADY the "one place is this row live" predicate the spec asks this feature to build/extend, and it already covers BOTH the trash exclusion (this feature's concern) and the archived-project exclusion (F144's concern) in a single definition. No new view/sibling helper was needed; extending it further would have duplicated what's already there.
  - **Newer join tables audited for their own leak potential** (per the spec's explicit call-out): `checklist_items` (F153), `task_dependencies` (F156), `task_assignees` (F159), `task_watchers` (F163) — none of these tables has its own `deleted_at` column (hard-delete convention per `20260819080358_checklist_items_update_delete_policies.sql`'s own comment: "checklist_items has no `deleted_at`"), so the only leak vector for any of them is a row surviving after its PARENT TASK is soft-deleted. Grepped every `.from("checklist_items"|"task_dependencies"|"task_assignees"|"task_watchers")` call site across `lib/`: every one is either (a) inside an aggregate lateral join already scoped to an already-live outer task (board RPC, covered above), (b) a single-task detail-page read/write reachable only after the caller has already loaded that specific task (out of AS-350's "board/list/search/dashboard/My Tasks" wording — a task detail page showing its own trashed task's own checklist is not one of the five named cross-project aggregate surfaces), or (c) a Server Action write path (`lib/actions/*.ts`) not a read surface at all. No leak found reachable from any of the five named aggregate surfaces.
  - **Realtime reconciliation** (`lib/board/reconcile-realtime-task.ts`, `lib/tasks/reconcile-realtime-comment.ts`) — both already explicitly strip a row the instant `row.deleted_at` is set (`if (row.deleted_at) return tasks.filter(...)`), independent of the initial-fetch-level `deleted_at is null` filters above. No fix needed; the initial load and the live-update path both independently enforce exclusion (defense in depth, not a single point of failure).
  - **"Already compliant" is a valid, documented outcome** (clarification Q6 default) — every named surface and every newer join table was already correct before this feature; this handoff documents that explicitly per-surface rather than inventing unnecessary changes.
- **Why no new migration/view change was made**: the spec's instruction ("extend F144's shared view... so it's the ONE place") is already satisfied — F144's `active_project_tasks` view's `where` clause already includes `t.deleted_at is null` (the trash predicate) alongside `p.deleted_at is null` (the archived-project predicate) in the SAME single definition. There is nothing to add; a second view or a sibling helper for the newer tables would have been a second source of truth for a predicate ("is this task itself live") that's already correctly expressed once, both in the shared view (for the three dashboard RPCs that select from it) and via the same one-line `.is("deleted_at", null)` TypeScript convention everywhere else (board RPC's own WHERE clause, list queries, search RPC) — per the clarification's ambiguity-resolution default ("the simpler option that adds no new dependency and no second source of truth").
- **Test file naming**: one new file per surface (`trash-exclusion-board/list/dashboard/search.test.ts`), each with its own AS-350-named test function(s), per this feature's own explicit "one integration test per surface" instruction — not consolidated into a single broader file, even though several existing test files (`search-tasks.test.ts`, `priority-counts-rpc.test.ts`, `list-view-render.test.ts`) already incidentally exercise trash exclusion as a side effect of an earlier feature's own assertion. Those pre-existing tests are left untouched; the new files give AS-350 its own explicit, independently-named, per-surface evidence.
