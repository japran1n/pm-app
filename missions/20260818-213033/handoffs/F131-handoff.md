## Decisions made
- Confirmed via direct file read (not the F132 handoff's description alone) that `project_members`, its indexes, RLS policies (`project_members_select_active_members`, `project_members_insert_leads_or_admins`, `project_members_delete_leads_or_admins`), and the `is_project_lead_or_workspace_admin` helper function already exist in `supabase/migrations/20260821140520_project_members.sql` and match what this feature needs — no new migration was written; the table/RLS were sufficient as-is.
- Server Action authorization re-check (`isProjectLeadOrWorkspaceAdmin` in `lib/actions/project-members.ts`) independently re-derives the exact same predicate as the `is_project_lead_or_workspace_admin` SQL helper (workspace owner/admin, OR an existing `project_role = 'lead'` row) using the admin client, rather than calling the SQL function via an RPC — kept the check as plain queries against `workspace_members`/`project_members` to match this codebase's established `lib/auth/require-membership.ts` pattern (queries via admin client, not RPC calls into SECURITY DEFINER functions) exactly, so there is one obvious place (this file) to look at the app-layer authorization logic without cross-referencing SQL.
- `addProjectMember` additionally requires the target user to already be an *active* member of the same workspace before creating a `project_members` row — the spec's "adding a member grants access" is scoped to granting **project**-level access to someone already in the workspace; onboarding a brand-new person to the workspace itself is `lib/actions/invites.ts`'s job, not this feature's. This is an explicit business-rule check in the action (not enforced by the DB FK, which only requires `user_id` to be *some* `auth.users` row), returning a specific `"That user is not an active member of this workspace."` error per the Clarified implementation's field-level-message failure-handling answer.
- Unique-constraint violation (`project_members_unique_project_user`, Postgres code `23505`) on `addProjectMember` maps to `"That user is already a member of this project."` rather than the generic fallback message, per the same failure-handling answer.
- Test file mocks `@/lib/supabase/server`'s `createClient` (module-level `vi.mock`, swapped per-call via a mutable `currentSessionClient` module variable) so the Server Actions under test — which read the caller's identity via the cookie-based, request-scoped `createClient()` — can be invoked directly from a Vitest integration test outside a real Next.js request, while still exercising real RLS/Postgres via a genuinely signed-in `supabase-js` client. This is the same integration-testing technique this mission's other action-layer tests use (spot-checked `checklist-actions.test.ts`'s structure before writing this).
