## Assertions covered
AS-280: PASS — moving a blocked task to a done status warns the user that a blocker is still open, and requires confirmation. `useBlockedDoneGuard` (new, `components/task/blocked-done-guard.tsx`) is called by every live path that can change a task's status: `board.tsx`'s `handleDragEnd` (drag-to-done column), `list-status-select.tsx`'s `handleChange` (inline Select), and `task-detail-sheet.tsx`'s new `handleStatusChange` (the status Select, previously permanently `disabled`, now enabled by this feature). Each calls `confirmIfMovingToDone(taskId, nextStatus)` BEFORE its own mutation; if the target is "done" and the task has ≥1 open blocker (`getOpenBlockers`, `lib/actions/tasks.ts`), an `AlertDialog` opens listing every open blocker by `formatTaskKey(projectKey, number)` (falling back to title) AND its title, and the mutation only proceeds if the user clicks "Mark as done anyway" — Cancel (or closing the dialog) leaves the status untouched. Covered by `tests/integration/open-blockers.test.ts` (`test_AS_280_returns_the_open_blocker_with_its_key_title_and_status`, `test_AS_280_a_task_with_several_blockers_reports_only_the_ones_that_are_not_done`) and, as the genuine live-interaction proof, `tests/e2e/blocked-done-guard.spec.ts`'s first test (real browser: dialog appears naming the blocker's title, Cancel leaves the DB row `status: "todo"`, confirming persists `status: "done"`).
AS-281: PASS — a task whose blockers are all complete shows no blocked warning. `getOpenBlockers` filters out any blocker whose own status is "done" (`isDoneStatus`, `lib/tasks/blocked-guard.ts`) or soft-deleted; `confirmIfMovingToDone` resolves `true` with **no dialog and no visible delay** whenever the returned list is empty — this includes both "no blockers were ever created" and "blockers exist but are all done", tested as two distinct cases per this feature's own explicit instruction not to conflate them. Covered by `tests/integration/open-blockers.test.ts` (`test_AS_281_a_task_whose_only_blocker_is_done_returns_an_empty_list`, `test_AS_281_a_task_with_no_dependency_rows_at_all_returns_an_empty_list`, plus a third soft-delete edge case) and `tests/e2e/blocked-done-guard.spec.ts`'s second test (real browser: a task with zero open blockers goes straight to "Done", `getByRole("alertdialog")` has count 0, DB row confirms `status: "done"`).

## Decisions made

- **One shared helper, three real callers today, F186-ready shape.** `useBlockedDoneGuard()` (`components/task/blocked-done-guard.tsx`) exposes exactly one entry point, `confirmIfMovingToDone(taskId: string, nextStatus: string): Promise<boolean>`. All three live done-paths (board drag, list Select, detail-sheet Select) call it identically, right before their own mutation. **For F186 (bulk update, not yet built):** this same single-task signature is directly reusable — bulk update can call `confirmIfMovingToDone` once per selected task (awaiting each in turn, skipping any task whose call resolves `false`) with zero changes to this hook's API. A batched "one dialog, N tasks, every blocker across all of them" variant was deliberately NOT built now — no current caller needs it, and building an unexercised second code path violates the clarification's "simpler option, no second source of truth" default. If F186's own UX genuinely wants one combined dialog instead of N sequential confirms, that's a small, additive follow-up to this same file, not a rewrite.

- **`getOpenBlockers` is a new, deliberately narrow Server Action, not a reuse of `getTaskDetail`.** `getTaskDetail` (F157) already returns `dependencies.blockedBy` with status/key/title, but it also fetches comments, attachments, checklist, subtasks, and both dependency directions in one big `Promise.all` — routing every status-change attempt through it would cost board.tsx/list-status-select.tsx (which need none of that) an unnecessary heavy fetch on every single attempt to complete a task. `getOpenBlockers(taskId)` mirrors `getTaskDetail`'s `blockedByQuery` shape (same FK-disambiguated embed, same soft-delete filter) but is a single small lookup, matching this feature's own performance-budget answer ("no per-item network call" — this is one call per actual completion attempt, not per row).

- **Data freshness over reusing already-loaded props.** `task-detail-sheet.tsx` already has `task.dependencies.blockedBy` loaded when the sheet opens, but `confirmIfMovingToDone` does NOT use it — it always calls `getOpenBlockers` fresh. That prop was fetched once, at sheet-open time; trusting it could produce a false negative (AS-281 says "no warning" only once blockers are *actually* all complete right now, not "were complete when the sheet opened"). This costs one extra round trip only at the exact moment of a real completion attempt, never per render.

- **Fail open, not fail closed, on a blocker-check error.** If `getOpenBlockers` itself errors, `confirmIfMovingToDone` resolves `true` (no dialog) rather than blocking the status change on a check that couldn't run. The actual mutation (`moveTaskStatus`/`moveAndReorderTask`) remains the authoritative success/failure path with its own toast — a failed *check* must never be confused with a failed *change*.

- **The "done" sweep point (F222) lives in exactly one place: `lib/tasks/blocked-guard.ts`'s `isDoneStatus`.** Both `getOpenBlockers` (server-side: which blockers count as "open") and `useBlockedDoneGuard` (client-side: does this status change even need a blocker check) call it — neither compares against the literal `"done"` string itself. When custom statuses land in M16, F222 only has to change this one function's body (e.g. to check a workspace-configured "done category" instead of a literal string); none of the four call sites (board, list, detail sheet, and whatever F186 becomes) need to change. This mirrors the exact same sweep-note convention `lib/tasks/subtask-progress.ts` and `lib/queries/tasks.ts`'s `getProjectBoardTasks` (AS-283) already established for this identical literal elsewhere — this feature does not touch those other pre-existing call sites (deliberately out of scope, see below), only its own new one.

- **The task detail sheet's status Select is enabled by this feature — a deliberate, bounded scope decision.** Before this feature, that Select was permanently `disabled`, with a comment noting "no Server Action currently persists task status changes... a future feature should add a changeTaskStatus action and enable this control." The critical context for this feature explicitly named the task detail sheet as one of the four paths the shared guard "must cover" — a guard cannot cover a path that doesn't exist. Enabling it was low-risk: `moveTaskStatus` (F045) already exists and is exactly what board.tsx/list-status-select.tsx already call, and `handleStatusChange` mirrors `handlePriorityChange`'s own already-established shape (direct `value`/`onValueChange` bound straight to the `task` prop, toast-only feedback, no local optimistic override) — no new mutation logic, no new pattern, just wiring an existing action to an existing (previously inert) control, gated by the new guard. This was NOT in the feature spec's own approximate Files list, but was explicit in this feature's assignment; the change is minimal and self-contained (one new handler, one Select's props, no other files affected by it).

- **Known, pre-existing, NOT-introduced-by-this-feature staleness note:** like the Priority and Assignee Selects it mirrors, the Status Select's `value` stays bound directly to the `task` prop with no local optimistic state and no re-fetch after a successful edit (`useTaskDetailSheet`'s `detail.task` is only ever set by `fetchDetail`/`retry`, never patched incrementally by `saveField`/`assignTask`/now `moveTaskStatus`). This means a successful status change from the detail sheet doesn't visually update that open sheet's own Select until it's closed and reopened — this is not a regression this feature introduces; it's the exact same limitation Priority/Assignee already have, and fixing it broadly is out of scope here (see below).

- **The `AlertDialog` primitive (`components/ui/alert-dialog.tsx`, installed by F119, unused until now) was used for the confirmation, not `window.confirm`.** AS-280 requires listing WHICH blockers are open, by key and title — a real list, not a single string `window.confirm` can format cleanly. `revoke-invite-button.tsx`'s own comment ("no alert-dialog component installed yet") no longer applies; F119 added one specifically for cases like this.

- **Board's `handleDragEnd` became `async`; the confirm check sits BEFORE the existing `setTasks(next)` optimistic update, inside the SAME `if (movedTask.status !== activeTask.status)` condition the existing action-dispatch `if`/`else` already uses** (checked twice — once to gate the confirm, once, unchanged, to choose `moveAndReorderTask` vs `reorderTask` — a small, deliberate duplication that keeps the diff minimal and leaves `tests/unit/board-move-status-wiring.test.ts`'s existing source-text regex assertions passing unmodified). A same-column reorder (the `else` branch) never changes status, so it never reaches the guard at all — `confirmIfMovingToDone` itself also short-circuits to `true` with zero network calls whenever the target isn't "done", so the added `await` is a genuine no-op for the overwhelming majority of drops.

- **`list-status-select.tsx`'s `handleChange` awaits the guard BEFORE applying its own local optimistic `setLocalStatus`** (unlike the mutation call, which still updates optimistically then reconciles/reverts on failure) — so a cancelled confirmation never has to visually flash "Done" and then revert; the Select simply never changes if the user cancels.
