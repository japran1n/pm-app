## Decisions made
- Grouping rows (the Draft scope's own open question, resolved per the ambiguity-resolution default): rows are grouped by PROJECT, not assignee. `getTimelineTasks` already returns `projectId`/`projectName` on every row with no second query; grouping by assignee would require deciding how a multi-assignee task appears in more than one row (a fan-out this feature doesn't need to solve) and a second lookup. `groupTimelineTasksByProject` in `page.tsx` is a small, isolated, pure step — swappable for an assignee-grouping variant later without touching the query or layout maths, per the spec's own "keep it swappable" instruction.
- Default visible window (no zoom switcher yet — F240's own seam, AS-456): a 3-calendar-month rolling window (month before, current, month after), anchored by the same `?month=YYYY-MM` URL convention `lib/calendar/month-grid.ts` already established, reusing its `parseMonthKey`/`currentMonthKey`/`toMonthKey`/`nextMonthKey`/`previousMonthKey` directly rather than a second parser — one shared URL contract across both date-scale views.
- Date-combination rendering rule (the spec's own flagged risk area, not fully named by AS-451/AS-452's text): both-dates-present renders a range bar (AS-451); due-only renders a marker on the due date (AS-452, named explicitly); start-only (the symmetric case AS-452 doesn't name) renders a marker on the start date, treated identically to due-only rather than inventing a second single-date rule; neither-date is excluded entirely from the query result and from the layout, with a footer count (`getUndatedTimelineTaskCount`, mirroring `getUndatedTaskCount`/AS-446's precedent) explaining the absence rather than a task silently vanishing.
- Query shape: `getTimelineTasks`'s interval-overlap filter is a single `.or(and(...), and(...), and(...))` PostgREST expression (three legs: due-in-range, start-in-range, spans-the-whole-range) rather than fetch-then-filter client-side, per the performance-budget answer ("one query for the visible range, no N+1"). Verified this returns the right rows for range bars, both marker cases, and correctly excludes the neither-date case via the real integration test (`f237-timeline-query.test.ts`), not just by reading the SQL.
- Visibility/soft-delete/archive posture is a direct structural copy of `getCalendarTasks` (`lib/queries/calendar.ts`, F232): plain RLS-scoped `createClient()`, never `createAdminClient()`; `projects!inner(..., deleted_at)` + `.is("projects.deleted_at", null)` for archived-project exclusion; `.is("deleted_at", null)` for trashed-task exclusion. No new visibility logic was written — reused the exact predicate the private-project/F322/F323 regression already covers via RLS, proven again here for the timeline's own query with its own private/archived/trashed seed rows.
- No sidebar nav entry was added for `/w/[workspaceSlug]/timeline`. Checked `components/nav/app-sidebar.tsx` first — the calendar page (F232-235, shipped and complete) also has NO sidebar entry; it's reachable by direct URL only. Followed that established precedent rather than unilaterally adding a nav item to a shared file not named in this feature's own Files list — flagged below as out-of-scope in case the mission wants both calendar and timeline linked from the sidebar together.
- No mutation/drag/resize logic was added (F238's own scope, AS-454) — `TimelineBar` is a plain `<Link>` to the task's existing board-detail deep link (`?taskId=`), the same "one real detail surface, many click-through entry points" pattern `components/calendar/agenda-list.tsx` established. This feature's own clarified "failure handling"/"validation"/"access control" answers (all about a mutation's optimistic-UI/rollback/Zod/permission path) don't apply here since there is no mutation in this feature's scope — left the seam for F238 to drop a "use client" wrapper around `TimelineBar` exactly the way F234 did for `MonthGrid`'s day cells, without restructuring this file.
