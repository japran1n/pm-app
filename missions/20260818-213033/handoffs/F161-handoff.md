## Decisions made
- **Picked up mid-feature after an interrupt** — read every already-modified/new file fresh before continuing (per the resume instructions), rather than assuming prior state. Found `UserAvatarGroup`, the board/list card wiring, the `assignee_ids` RPC migration, and `lib/queries/tasks.ts`'s three query functions already complete and correct; the only genuinely unfinished piece was `getTaskDetail` (as flagged) plus the multi-select pickers (task detail sheet + new-task dialog), which were still on the single-value `assignTask`/`Select` path.
- **`getTaskDetail` (`lib/actions/tasks.ts`) gets its own `task_assignees` query** (`assigneesQuery`, oldest-first), added to the existing `Promise.all` alongside comments/attachments/children/etc. — same "one query per section, no per-row round trip" convention every other section in that function already follows. `TaskDetailSheetTask.assigneeIds` is optional and defaults sensibly (falls back to the single legacy `assigneeId`) so an un-updated caller/test still renders.
- **Detail sheet and new-task dialog's assignee UI is a from-scratch Popover + checkable-row multi-select** (`components/ui/popover.tsx` + `components/ui/checkbox.tsx`, both already in the design system — no new dependency), replacing the old single-value `Select`. Each row is a real `<button role="menuitemcheckbox">`, keyboard-focusable and keyboard-activatable (Enter/Space), satisfying this feature's own clarified note ("tooltip/controls must be reachable by keyboard, not hover-only"). The trigger renders `UserAvatarGroup` once ≥1 assignee is selected, so the picker itself doubles as a live preview of the stacked-avatar rendering.
- **Detail sheet's write path**: replaced `handleAssigneeChange` (single value → `assignTask`) with `handleAssigneesToggle` (toggles one id in/out of the current set → `setTaskAssignees`, F160's shared multi-assignee write path). `assignTask` is still exported/used elsewhere (e.g. list/board quick-assign, out of this feature's Files scope) — only this Sheet's own control was migrated, per the clarified "Touches" scope.
- **`createTask` (F035) was NOT rewritten to accept multiple assignees** — out of this feature's Files scope (`lib/actions/tasks.ts`'s create path, not named in the clarified spec's Files list) and orthogonal to F160's own explicit out-of-scope note ("dropping `tasks.assignee_id`... out of scope"). Instead, `NewTaskDialog` passes the FIRST selected assignee to `createTask`'s existing single `assigneeId` param (so a brand-new task's legacy mirror is populated the moment it's created, matching `setTaskAssigneesCore`'s "always mirror the first assignee" rule from F160), then — only when more than one assignee was actually picked — makes one follow-up call to `setTaskAssignees(newTaskId, allSelectedIds)` to write the full set. A 0- or 1-assignee task creation never makes this second call. If the follow-up call fails, the toast surfaces a specific "created, but assignees couldn't be saved" message rather than silently losing the extra assignees or blocking the (already-succeeded) task creation.
- **Query-layer ordering fix**: `getProjectListTasks`/`getWorkspaceListTasks`'s embedded `task_assignees(user_id)` select has no guaranteed row order from PostgREST by default — the integration test caught this (assertion failed on order, not membership) before this handoff was written. Fixed by adding an explicit `.order("created_at", { ascending: true, referencedTable: "task_assignees" })` to both queries, so the returned `assigneeIds` array is oldest-first everywhere (matching the board RPC's own `assignee_ids` tie-break and `setTaskAssigneesCore`'s mirror rule) rather than only being correctly ordered on the board view.
- **Fixed a regression this feature caused in an unrelated pre-existing test** (`tests/unit/board-task-detail-sheet-wiring.test.ts`): its `SortableTaskCard forwards its onClick prop through to TaskCard` test asserted against the OLD single-line `<TaskCard task={task} onClick={onClick} ...>` source text; this feature's own `assignees` prop addition (from the prior worker's session, before the interrupt) reformatted that call onto multiple lines, breaking the regex. Fixed by matching `task={task}` and `onClick={onClick}` independently rather than as one contiguous single-line pattern — the test's actual intent (assert both props are forwarded) is unchanged, only the source-text matching strategy is more resilient to formatting.
