## Decisions made
- **Watcher lookup source**: `getTaskDetail` filters `task_watchers` on `is_watching = true` explicitly (not "row exists"), per F164's own durability rule — a row can exist with `is_watching: false` for a durable explicit opt-out, and that must never render as "watching" in the UI. Verified with a dedicated negative test (`task-detail-watchers.test.ts`'s fourth case) that calls the real `unwatchTask` action and confirms the resulting row is excluded from `watcherIds`.
- **`isWatching` is per-caller, not a count**: computed as `watcherIds.includes(currentUser.id)` inside `getTaskDetail`, server-side, from the same authenticated session already resolved for the rest of the function — never derived client-side from a generic watcher count, matching the clarified spec's explicit "for the SIGNED-IN caller specifically" instruction.
- **Watcher people resolved from the existing `members` prop, not a new query**: `TaskDetailSheet` already receives workspace members (for the assignee picker); `Watchers` reuses that same list to map `watcherIds` → name/email/avatar, avoiding a second per-render fetch. This mirrors the assignee picker's own `currentPeople` resolution pattern already in this file.
- **`UserAvatarGroup` extended with an optional `ariaLabelPrefix` prop** (default `"Assigned"`): the feature spec's "Files" list doesn't name `user-avatar-group.tsx`, but the clarified spec explicitly requires "names available to keyboard/screen-reader users... check the accessible-name convention `UserAvatarGroup` already established" — the existing convention hardcodes `"Assigned: ..."`, which would be a wrong/misleading accessible name for a watcher group. A one-line, backward-compatible prop addition (default preserves every existing caller's exact previous behavior, verified via full test suite + `git diff`) was judged the safest way to reuse the component correctly rather than duplicating it, per the clarified spec's own "reuse this... don't build a second stacked-avatar component" instruction. Recorded here rather than done silently.
- **Optimistic toggle with rollback**: `Watchers` keeps its own local `localWatcherIds`/`localIsWatching` state (re-synced on `taskId` change, same pattern as `CommentList`'s `syncedTaskId`), flips it immediately on click, calls `watchTask`/`unwatchTask`, and on failure restores the exact pre-click snapshot plus `toast.error(result.error)` — mirroring `TaskDetailSheet`'s own `handleAssigneesToggle` (toast on both outcomes) rather than `CommentList`'s silent-on-success append, since `handleAssigneesToggle` is the closer sibling (same header-area toggle-a-set-membership shape).
- **Toggle disabled without `currentUserId`**: if the caller hasn't wired `currentUserId` through (existing test/fixture callers), the button is disabled rather than guessing whose watcher state to show — same "safe default" convention as `CommentList`'s delete-affordance gating on `currentUserId`.
- **No `canWrite`/role gate on the toggle**: per F164's own precedent (`watchTask`/`unwatchTask` intentionally have no `canWrite` gate — watching is a personal notification preference available to any active member, including viewers), the UI toggle is likewise gated only on `currentUserId` being present, not on `canEdit`/`currentUserRole`.
