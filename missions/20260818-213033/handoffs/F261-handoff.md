## Decisions made
- **Resolved the spec's own flagged open question ("inline `<img>` vs attachment-row-only") by taking the simpler, no-new-sanitisation-surface option, per the clarification's explicit resolution rule.** Read F171's actual allow-list (`ALLOWED_NODE_TYPES` in `components/editor/rich-text-editor.tsx`) before deciding: it has no `image` entry (doc/paragraph/text/heading/bulletList/orderedList/listItem/codeBlock/blockquote/hardBreak/horizontalRule/taskList/taskItem/mention only). Adding one would mean extending the ONE shared security-boundary allow-list `sanitiseDocument` enforces for every comment/description ever rendered — exactly the "second source of truth" risk the clarification calls out, since an `<img src>` also needs its own trust/URL-scheme story (a raw Storage path isn't a browser-loadable URL; a signed URL would need re-minting per render and expires) that this feature's scope doesn't otherwise need to solve. Instead: the pasted image uploads as a REAL `attachments` row via the unmodified `uploadAttachment` Server Action (visible in the task's existing attachment list, exactly like a dropped/picked file per F258/F259/F260), and the comment body only gets a plain-text reference paragraph (`📎 <fileName>`) appended via the new `appendAttachmentReference` helper — no image node, no new allow-list entry, no new sanitisation surface.
- **`onImagePaste` is an opt-in prop on `RichTextEditor`, not a global behaviour change.** Every existing caller (task/project description editors) that doesn't pass it keeps F172's exact pre-existing behaviour: an image pasted there still degrades to its `alt` text via `transformPastedHtml`, unchanged. Only the comment composer (`comment-list.tsx`) passes `onImagePaste={handlePastedImages}`. The edit-mode (in-place comment editing) `RichTextEditor` instance in `comment-list.tsx` deliberately does NOT get this prop — flagged below under Out-of-scope, since the feature spec's Files/Notes only describe "the comment editor" in the singular composer sense and the clarification's scope-boundary answer says to stay in-scope and report the rest.
- **Interception happens inside `handlePaste`, before the plain-text-override check and before `transformPastedHTML` ever runs**, because a pasted image (e.g. an OS screenshot) typically carries no `text/html`/`text/plain` clipboard payload at all — only a `kind: "file"` `DataTransferItem` — so neither of those existing paths would ever see it anyway; this ordering is purely about correctness, not a behaviour trade-off. `event.preventDefault()` is called only when `imageFiles.length > 0`, so a normal HTML/plain-text paste with `onImagePaste` provided is completely unaffected (proven by `test_AS_508_non_image_paste_content_is_unaffected_when_onImagePaste_is_provided`).
- **No new upload path.** `handlePastedImages` in `comment-list.tsx` builds a `FormData` exactly the way `AttachmentList.uploadFiles` (F258) does and calls the same `uploadAttachment` Server Action (`lib/actions/attachments.ts`, completely unmodified by this feature) — proven by the integration test asserting `uploadAttachmentMock` receives a `FormData` with the real `taskId` and `file`.
- **Reused `validateAttachmentFile` (F259) for client-side pre-flight validation** (size/MIME) rather than re-deriving the limits, and reused `UploadProgress` (F259) for the inline progress UI rather than building a new indicator — both are the "existing attachment upload/progress/thumbnail machinery" the task instructions explicitly said to reuse.
- **Failure handling: a separate `useTransition` (`startPasteUploadTransition`) from the composer's own `isSubmitting`/`startSubmitTransition`.** An in-flight paste-upload must never disable the Post button or the editor (the user should be able to keep typing/posting while a screenshot uploads), and a failed paste-upload only updates the `UploadProgress` row's status + fires a `sonner` toast — `setDraft` is never called on the failure branch, so the already-typed draft is provably untouched (test: `test_AS_508_a_failed_upload_leaves_already_typed_comment_text_intact`).
- **Cancel semantics for an in-flight pasted-image upload mirror F259's `AttachmentList` exactly**: no `AbortController` hook exists on the Server Action transport (same documented limitation as F259's handoff), so "cancel" removes the row immediately and marks the job id in a ref so its eventual result is silently ignored (no toast, no draft mutation) when it resolves later.

## Out-of-scope work needed
- **Image paste is only wired into the add-comment composer, not the inline comment-edit `RichTextEditor` instance** (the one shown when a user clicks "Edit" on their own existing comment, `editingCommentId === comment.id` in `comment-list.tsx`). The feature spec's bullet list and Files section describe "the composer" specifically; wiring the same `onImagePaste={handlePastedImages}` (parameterised to append to `editDraft`/`setEditDraft` instead of `draft`/`setDraft`) into the edit-mode editor as well would be a small, mechanical follow-up if a future feature wants full parity there.
- **No inline image rendering was built anywhere** (see Decisions made) — if a future feature wants pasted/attached images to render inline in a comment, it needs to add an `image` node to `ALLOWED_NODE_TYPES`/`sanitiseDocument`/`sharedExtensions()` in `components/editor/rich-text-editor.tsx` AND solve signed-URL-in-a-persisted-document (a signed URL expires; a raw Storage path isn't directly loadable) — a meaningfully bigger change than this feature's scope, flagged rather than done silently, matching the clarification's explicit pre-resolution of this exact open question.
- **True per-byte upload progress** for a pasted image is not implemented — same architectural limitation as F259 (Server Action transport has no progress hook); the indeterminate `UploadProgress` state reused here inherits that same, already-accepted trade-off.

## Notes for the next worker
- `extractImageFilesFromClipboard` (lib/editor/paste-rules.ts) is pure and DOM-API-shaped (works against any `{ kind, type, getAsFile() }`-shaped item list, not just a real `DataTransferItemList`) — reusable anywhere else a clipboard/drop event needs the same "pull out the image files" logic.
- `appendAttachmentReference` (lib/comments/rich-text.ts) is pure JSONContent manipulation with no editor dependency — reusable for any future "append a system-generated reference paragraph to a draft" need (e.g. a future non-image attachment paste, if ever added, could call the same helper with a different label).
- `RichTextEditor`'s `onImagePaste` prop is intentionally generic (`(files: File[]) => void`, no upload logic baked into the shared editor component) — the editor component itself never uploads anything or knows about `attachments`; all of that lives in the caller (`comment-list.tsx`), matching this codebase's existing separation between the shared editor/renderer and its callers' own persistence logic.
