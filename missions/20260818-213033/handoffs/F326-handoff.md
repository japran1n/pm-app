## Decisions made
- **Blocker A fix — `key`-based remount, not a sync `useEffect`.** Read F234's handoff and `lib/calendar/reschedule.ts` first, per the assignment. `<CalendarDayGrid>`'s `byDate` mirror is a small "optimistic override on top of props" state, same shape as `board.tsx`'s own convention — a sync `useEffect(() => setByDate(tasksByDate), [tasksByDate])` would fire on EVERY re-render (the parent passes a brand-new `tasksByDate` object literal each render regardless of whether real navigation happened), silently wiping an in-flight optimistic drag/rollback the instant any unrelated re-render occurred elsewhere in the tree — an even worse bug than the one being fixed. Deriving `byDate` during render from a "sentinel" comparison was rejected for the same reason (it would need the exact same "did real navigation happen" signal a `key` already gives for free). `key` was chosen because it gives React an explicit, cheap, and correct identity boundary: it changes exactly when the SERVER data identity changes (month + active filters — `calendar/page.tsx`'s new `dataKey`, computed from the same `toMonthKey`/`filterQuery` values `hrefFor` already builds), and leaves the component instance (and its `byDate` state) completely untouched on any other re-render, which is exactly the guarantee F234's optimistic-update/rollback/single-toast contract needs. Verified both directions: `test_AS_443_...` (key change → fresh data wins) and `test_AS_442_an_incidental_rerender_with_an_unchanged_key_does_not_reset_in_flight_optimistic_state` (no key change → state survives) in `tests/unit/f326-calendar-day-grid-rerender.test.tsx`.
- **Timeline audit (per the assignment's explicit ask) — no fix needed.** `components/timeline/timeline-body.tsx`'s `overrides` state (`useState<DateOverrides>({})`) is NOT a full mirror of the `groups`/tasks prop — it is a small per-task `{startDate, dueDate}` override map, applied on top of the always-fresh `groups` prop inside `currentDatesFor(task)` (`override ?? {startDate: task.startDate, dueDate: task.dueDate}`), and `allTasks`/`barLayouts`/`rowPositions` are all recomputed from the live `groups` prop every render. A zoom change or range change (new `groups`) is therefore immediately reflected for any task with no in-flight override — there is no B1-shaped staleness bug here, because there was never a full-object mirror to go stale. This is in fact the SAME "small override map on top of fresh props" pattern this fix moves `CalendarDayGrid` toward being closer to in spirit (it already had this shape for the day-bucket case), so no code change was made to `timeline-body.tsx`. No sibling of B1 was found elsewhere in the M16 milestone's other client components (board.tsx's own `tasks` state is a genuine local copy too, but board.tsx is not in this feature's scope and was not part of M16's blocker list).
- **Blocker B fix — a new composing SQL helper, not a copy of the role predicate.** `is_project_workspace_admin(project_id)` only resolves `project_id -> projects.workspace_id` and then delegates the actual `role in ('owner','admin')` check to the EXISTING `public.is_workspace_admin(workspace_id)` helper (`supabase/migrations/20260817222822_rls_workspaces.sql`) — the same helper `enforce_project_visibility_change_role`, the `workspaces` UPDATE/DELETE policies, and `close_profiles_rls_gaps.sql` already reuse for "owner/admin only" gates. No `role in (...)` predicate was duplicated.
- **Scope of the role check — workspace owner/admin only, not "or project lead."** `canManageColumns` in application code also allows a project `lead` (a `project_members.project_role = 'lead'` row) who is not a workspace owner/admin. This migration deliberately does NOT extend the DB-level predicate to cover project leads, per the assignment's literal wording ("require the caller be an owner/admin of the project's workspace"). This is safe: I audited every real writer of `project_statuses` before making this call —
  - `lib/actions/statuses.ts` (`addColumn`/`updateColumn`/`deleteColumn`/`reassign_and_delete_project_status` caller) writes through `createAdminClient()` (service role), which **bypasses RLS entirely** — a project lead's Server Action edits are completely unaffected by this tightening.
  - `reassign_and_delete_project_status` (F220's RPC, `20260824040000_status_delete_reassign_rpc.sql`) is `security definer` — bypasses RLS, unaffected.
  - `seed_default_project_statuses_on_insert` (F218's `AFTER INSERT ON projects` trigger) is `security definer` — bypasses RLS, unaffected.
  - `sync_tasks_status_on_column_rename` (F325's rename-sync trigger, `20260828030000`) is `security definer` — bypasses RLS, unaffected.
  So the ONLY path narrowed by this migration is the direct-RLS browser path (publishable key + user JWT) that never had project-lead nuance to begin with — it wasn't checking role at all before this fix. `canManageColumns`'s own project-lead allowance continues to be enforced, correctly, at the Server Action layer.
- **AS-414 UPDATE test assertion — DB state, not `error`.** Postgres RLS convention for UPDATE: when the WITH CHECK (or, here, also USING) clause fails, some drivers/paths return a real PostgREST error and others silently affect zero rows depending on which clause fails and how the row is (or isn't) visible to the `USING` predicate first. Asserting on `error !== null` alone is not reliable across both failure shapes; the tests instead always assert real DB state via the admin client, which is the only ground truth that matters and is also what the assignment's "DB state asserted unchanged" requirement calls for directly.
- **saved_views DELETE policy left untouched.** A DELETE has no resulting row for a `WITH CHECK` to apply to, so `owner_id = auth.uid()` alone is already correct and complete — B5 is specifically about the UPDATE path's missing visibility check on the *new* row.
- **`saved_views_select_visible` and `project_statuses_select_visible` left untouched.** Neither blocker was about reads; every role (including viewer/guest) must still be able to read board columns/views to render the UI at all.
