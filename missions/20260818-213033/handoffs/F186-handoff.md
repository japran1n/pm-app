## Decisions made
- **List-length cap: 200 ids.** Per the feature's own "Notes for clarification" ("Decide the cap ... and what the UI does past it"), resolved by taking the simpler option per the clarification's default rule: 200 is large enough to cover a full page of the list view's select-all in any realistic project size this app supports today, small enough that a single `UPDATE ... WHERE id = ANY($1)` stays a cheap single-statement write. The UI never lets a selection exceed the tasks actually rendered on the current page (F185's select-all selects exactly the rendered `tasks` prop), so in practice the UI can never construct a request past the cap without a much larger page size than exists anywhere in this codebase today — no separate "past-the-cap" UI state was built, since there is no reachable path to trigger it. If a future feature adds true cross-page bulk selection, it will need its own chunking/UI messaging for the cap.
- **AS-341's crux — one forbidden task does NOT fail the whole batch.** Resolved from the assignment text itself ("confirm the permitted ones succeed and the forbidden ones are rejected/excluded, not that the whole call fails outright") and mirrored to match this codebase's own architecture: `bulkUpdateTasks` always returns `{ok: true, data: {succeededIds, failedIds}}` for any authenticated, well-formed call (even one where every single task is forbidden, e.g. an outsider's call — `succeededIds` is simply empty and every id lands in `failedIds` with a reason). `ok: false` is reserved for validation/auth failures at the whole-call boundary (unauthenticated caller, empty list, cap exceeded, no fields in `updates`) — never for "some or all individual tasks were forbidden." This is a deliberate asymmetry from `setTaskAssigneesCore` (F160), which DOES reject the whole call if any desired assignee id fails visibility — that action has no meaningful "partial" concept (one task's one field), whereas bulk update's whole reason for existing is applying one change across many independent tasks.
- **Per-task authorization re-implements AS-290's `is_project_visible_to` rule in application code**, exactly like `filterProjectVisibleUserIds`/`loadTaskAssignContext` (F160, already in this file) do for assignee-candidate visibility — same reasoning: every action in this file uses the admin client, which bypasses RLS by design, so the visibility check RLS would otherwise provide has to be re-run explicitly. One query for membership per distinct workspace touched, one extra query for private-project `project_members` rows covering every private project in the call — never a per-task round trip (AS-337/AS-338's own performance-budget answer, applied consistently to the auth check too).
- **`assigneeId` bulk-writes only the deprecated `tasks.assignee_id` mirror column**, not `task_assignees` (F160's multi-assignee table). Routing per task through `setTaskAssigneesCore`'s diff-and-write would be a per-row loop of network calls, which this feature's Clarified performance-budget answer explicitly forbids ("never a per-row loop of network calls"). This means a bulk assignee change replaces each task's single mirrored assignee but does not touch any OTHER existing multi-assignee rows a task might already have via `task_assignees` — flagged below in Out-of-scope, since fixing this without violating the performance budget would need either a Postgres RPC (one round trip, does the diff-and-write set-based) or an explicit product decision that bulk-assign always overwrites to a single assignee.
- **Blocked-done confirmation (F158) resolved client-side, once per selection, before the server call** — exactly as this feature's own draft scope specifies ("blocked-task confirmation (F158) is resolved before the call, not per row") and exactly as `useBlockedDoneGuard`'s own doc comment anticipated for a future bulk caller ("await each in turn, skipping any task whose confirm resolves false... without any change to this hook's own API"). `components/task/bulk-status-action.tsx` loops `confirmIfMovingToDone` over every selected id before calling `bulkUpdateTasks`, and only passes the confirmed subset through. The server action itself has zero knowledge of blockers — it is a pure field-update action, per this feature's Files scope.
- **UI wiring scope kept minimal**: only a bulk status Select was wired into `<BulkActionBar>` (AS-337's primary demonstrable UI path). Assignee/priority/due-date bulk-editing UI controls were NOT built — `bulkUpdateTasks` supports all four fields (proven by the integration tests), but building three more UI controls (assignee picker, priority Select, due-date picker) into the action bar was judged out of this feature's minimal-UI-wiring scope; see Out-of-scope below.

## Out-of-scope work needed
- **Bulk assignee/priority/due-date UI controls**: `bulkUpdateTasks` already supports all three (AS-338, proven server-side by integration tests), but `<BulkActionBar>` only got a status Select in this feature. A follow-up should add an assignee-picker button, priority Select, and due-date picker into the same children slot, calling `bulkUpdateTasks` the same way `<BulkStatusAction>` does.
- **Bulk assignee writes bypass `task_assignees` (F160 multi-assignee)**: a bulk assignee change only updates the `tasks.assignee_id` mirror column, so any task that already had MULTIPLE assignees via `task_assignees` keeps those other rows untouched while its mirror is overwritten. A future feature should either accept this as intended product behaviour (bulk-assign = "set the one assignee") or add a `bulk_set_single_task_assignee` Postgres RPC that also clears/replaces `task_assignees` in the same statement, to keep the mirror and the real table from drifting for tasks that go through the bulk path.
- **Cross-page bulk selection**: the 200-id cap has no reachable UI path today (F185's select-all only ever selects the currently-rendered page), so there is no "past the cap" UI state to build yet. If a future feature adds "select all N matching tasks across every page," it will need explicit UI messaging/chunking for the cap — flagged for whoever builds that.
