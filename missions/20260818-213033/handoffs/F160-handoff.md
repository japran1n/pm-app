## Decisions made
- **`assignTask` (F036) kept as the single-assignee entry point, unchanged signature/return shape.** Every existing caller — `components/task/task-detail-sheet.tsx`'s assign control, `createTask`'s `assigneeId` param, and `tests/integration/assign-task.test.ts` — calls it with `(taskId, assigneeId: string | null)` and expects `{ok:true, data:{id, assigneeId}}`. Rather than a parallel/duplicate write path, `assignTask` is now a thin wrapper around the same `setTaskAssigneesCore` the three new actions use (`assigneeId === null` → empty desired set, otherwise a one-element set) — there is exactly one real write path behind all four entry points, so `task_assignees` and the deprecated `tasks.assignee_id` mirror can never drift relative to each other regardless of which entry point a caller uses.
- **The deprecated-column mirror rule** (F160's own "Notes for clarification" open question): resolved per the ambiguity-resolution default (simpler option, no second source of truth) as **"always mirror the first assignee (earliest `task_assignees.created_at`, ties broken by `user_id`), never null while at least one assignee exists."** Rejected the alternative ("null once there are several assignees") because that would silently break every existing reader of `tasks.assignee_id` (board grouping, my-tasks, notifications) for a task that still very much has an assignee — a worse transition-period regression than a mirror that only ever names ONE of several assignees. Zero assignees still mirrors to `null` (AS-053's existing "unassign" meaning is unchanged). Verified live via `setTaskAssignees keeps tasks.assignee_id ... in sync with the first assignee` in the new test file — asserts the DB column equals the action's returned `mirrorAssigneeId`, both when non-null (2 assignees) and when cleared to `null` (0 assignees). **This is the fact other code should rely on**: `tasks.assignee_id` is never null-because-of-multiple-assignees; it's null only when the task has zero assignees.
- **AS-290 assignability check is a from-scratch application-code reimplementation of `public.is_project_visible_to`'s exact rule** (`supabase/migrations/20260821140526_project_visibility_rls_sweep.sql`), not a call to RLS — every action in `lib/actions/tasks.ts` uses `createAdminClient()`, which bypasses RLS entirely by this file's own established convention (see `createTask`'s doc comment), so the visibility gate RLS would otherwise provide has to be re-run explicitly server-side. Implemented in `filterProjectVisibleUserIds`: a candidate is assignable only if they are an ACTIVE workspace member of the task's workspace AND (the project is `'workspace'`-visible, OR they're a workspace owner/admin, OR they have an explicit `project_members` row for this project) — bounded query cost (one `workspace_members` query + one conditional `project_members` query, both `.in()`-scoped to the caller-supplied candidate ids), never a per-candidate loop of network calls.
- **`addTaskAssignee`/`removeTaskAssignee` are implemented as read-current-set + delegate to `setTaskAssigneesCore`**, not direct single-row INSERT/DELETE, so they get AS-290 validation, the zero-state no-op, and mirror-sync for free from the one shared write path rather than duplicating that logic three times. Trade-off: each of these two actions does its own `requireAssignActionContext` preflight (auth/membership/permission) AND `setTaskAssigneesCore` repeats an equivalent preflight — two round trips of small queries instead of one. Accepted as the simpler, more maintainable option (no dependency, no second source of truth) per the ambiguity-resolution default; the performance budget's actual concern (no per-row loop over existing assignees) is still met.
- **Permission predicate: `canEditTask`, not `canWrite`** (which the old `assignTask` used). Per the Clarified implementation's explicit instruction ("permission-checked (`canEditTask` or similar from `lib/auth/permissions.ts`)"). This is a deliberate, spec-directed behavior change from the old `assignTask`: `canEditTask` additionally excludes guests (`canWrite` does not), so a guest can no longer change a task's assignees at all, even on a project they belong to. This is a narrower guest capability than F134's AS-223 ("a guest can comment on and be assigned tasks") literally covers — AS-223 is about a guest being *assigned to* a task, not a guest *assigning others* — so this doesn't regress AS-223 (a guest can still be added as an assignee by anyone else with edit rights; they just can't call the assignee actions themselves). Flagged here since it's the one place this feature's behavior diverges from the pre-existing `assignTask`'s permission gate rather than purely extending it.
- **`setTaskAssigneesCore` rejects the whole call if ANY desired id fails AS-290** (not a partial "assign who's valid, skip the rest"), matching this feature's "validation as the final gate before any write" convention (Zod → permission → DB-derived business rule → write) — no assignment is ever partially applied.
