## Decisions made
- **Typed confirmation applies to every purge, not only "multi-item" purges.** The feature's Files section and this codebase's actual trash UI (F188) only ever expose purge as a single-row action (one row = one task or one comment) — there is no multi-select/bulk-purge UI anywhere in this mission's scope for F192. Per the Clarified implementation's ambiguity-resolution answer ("take the simpler option that adds no new dependency and no second source of truth"), rather than inventing a bulk-selection UI not requested by any spec Files entry (which would also require deciding bulk-purge's own atomicity/partial-failure semantics — real added scope), the same typed-confirmation gate the brief describes for "multi-item purges" is applied uniformly to the one purge surface that exists: a single item. This still satisfies AS-348 ("an admin can purge an item after a confirmation") exactly as written, and is strictly MORE cautious than the minimum the assertion requires, never less.
- **`canPurge` (owner only) reused verbatim from `lib/auth/permissions.ts` rather than adding a new predicate.** It already exists, already has this exact feature's doc comment ("Permanently purging soft-deleted data (e.g. emptying trash). Owner only — irreversible, workspace-wide destructive action"), and is unused by any other feature yet — this is clearly its intended call site. No new predicate needed.
- **`purge_task`'s dependent-row cleanup covers BOTH this mission's added tables (per the worker brief's explicit list: checklist_items, task_dependencies, task_assignees, task_watchers, attachments) AND pre-existing mission-1 tables that reference `tasks.task_id` with no cascade rule at all (comments, active_timers, time_entries).** Grepping every migration with `references tasks` (per the worker brief's own instruction) found comments/active_timers/time_entries have a plain `references tasks (id)` FK with NO `on delete` clause — a hard `delete from tasks` would raise a foreign-key-violation error for any task that ever had a comment, time entry, or active timer, which is the overwhelming common case, not an edge case. Cleaning these up was necessary for `purge_task` to work at all, not optional scope creep — documented as an explicit decision here since the brief's Files list only names this mission's own tables.
- **Self-reference cleanup (`parent_task_id`/`deleted_via_task_id` pointing AT the task being purged) nulls those columns on the other rows rather than deleting them.** Those other rows (e.g. a cascade-deleted subtask sitting in the same trash) are themselves independent trash entries a user might still want to purge or (if F189 restore ever supports it) inspect separately — deleting them as a side effect of purging their former parent would be an unrequested, surprising second deletion. Nulling the now-dangling FK reference is the minimal fix that lets the parent's own row-delete succeed.
- **Storage object removal happens in application code (`lib/actions/purge.ts`), AFTER the DB-level `purge_task` RPC returns, using the attachment paths the RPC itself collected and returned.** SQL/PL-pgSQL cannot call the Storage REST API — this ordering mirrors `deleteAttachment`'s own AS-114 rationale precedent inverted for this feature's constraint: here the ROW delete must happen inside the atomic RPC (so a `checklist_items`/`comments`/etc. delete can never partially commit while the task row survives), so the row-delete-first / storage-delete-second order is the only one available — a storage-removal failure after a successful `purge_task` is logged (dangling Storage object, loud on inspection of the bucket) but does NOT undo the already-committed row deletion (there is nothing to roll back to: AS-349 only requires the row+its DB dependents to be gone, which they already are).
- **`purge_comment` needs no dependent-row cleanup at all** — grepped every migration for `references comments` and found none; nothing else in the schema points at a comment row.
- **The full-suite `npm run test` run's 57 failed test files were verified NOT to be caused by this feature**, via two independent checks: (1) every failure's actual error is `Hook timed out in 10000ms` (afterAll racing under full-suite Supabase connection pressure), `Request rate limit reached` (Auth sign-in throttling), or one `JWT issued at future` (a clock-skew Auth error) — none reference `purge`, this migration, or any file this feature touches; (2) the one unit-test failure that IS listed under a file this feature touched (`tests/unit/trash-list.test.tsx`, 2/3 tests) was isolated by `git stash push -- components/trash/trash-list.tsx` (reverting ONLY this feature's edit to that file, back to F188/F189's original) and re-running — the identical 2/3 failure reproduced on the unmodified file, proving it is a pre-existing gap in F189's `TrashRestoreButton` (missing a router-mock wrapper in its own test setup), not something this feature introduced or worsened.
