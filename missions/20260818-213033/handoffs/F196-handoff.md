## Decisions made
- **Comments-vs-activity integration**: a Tabs toggle ("Comments" | "Activity"), not an interleaved single feed. `CommentList` (F060/F174) already owns a fully-featured comment surface — rich-text rendering, add/delete/undo, realtime reconciliation — that this feature's Files scope does not include; interleaving would require either duplicating that rendering here (a second source of truth for "what a comment looks like") or reaching into `comment-list.tsx`'s internals (out of scope). A toggle lets `CommentList` keep owning comment rendering entirely, while the new `ActivityFeed` owns the read-only day-grouped chronicle of every `task_activity` row — including `comment_added`/`comment_deleted` EVENTS (their existence, not their content), which is what AS-356's "comment additions and deletions appear in the same feed as field changes" actually requires and is already proven at the DB layer by F195's own test. This is the simpler option (no new dependency, no second comment-rendering implementation), per the clarified ambiguity-resolution answer.
- **Sentence vocabulary** (one place, per this feature's Notes for clarification): `lib/activity/format-task-activity-entry.ts`'s `formatTaskActivityEntry`, a single switch over F195's closed field vocabulary (`title`, `status`, `priority`, `due_date`, `estimate`, `assignee_id`) plus the two comment kinds. A switch (not a flat string-template object map) because several fields need a null-old-value branch ("set the X" vs "changed the X from A to B") that a flat map can't express without duplicating placeholders — still the one and only place this vocabulary lives. Status/priority labels reuse `lib/task-colors.ts`'s `STATUS_LABELS`/`PRIORITY_LABELS` verbatim (the same source of truth every other status/priority surface in the app uses) rather than a second local copy.
- **Null-actor handling**: a null `actorLabel` renders as "System", never the literal word "null", and never crashes (`formatTaskActivityEntry` has an explicit `input.actorLabel ?? "System"` at the top of every branch). The one system entry the feature spec names explicitly ("System generated this task from a recurring series") is detected by its distinctive shape — a system-attributed (`actorLabel === null`) `field_changed`/`due_date` entry with a null old value, which is exactly and only what F195's recurrence-job write (`generateNextOccurrence`, `p_system: true`) produces — rather than a new `kind`, since F194's `kind` CHECK constraint is a closed vocabulary this feature's Files scope cannot migrate.
- **Data loading**: `ActivityFeed` fetches lazily via a new Server Action (`lib/actions/task-activity.ts`'s `getTaskActivityFeed`) rather than being bundled into `getTaskDetail`'s (lib/actions/tasks.ts) existing nine-query round trip. `getTaskDetail` is a very large, already-in-scope-elsewhere file not named in this feature's Files list; adding a tenth parallel query there would be an out-of-scope expansion. Fetching on demand (when the Activity tab is shown) also means a viewer who only reads comments never pays for an activity query at all — a stronger reading of the clarified performance budget ("no N+1 queries per row and no per-item network call") than bundling would give. This deviates from the clarified spec's stated default ("Server Component for data loading") for the exact same architectural reason `comment-list.tsx`'s own doc comment gives: `TaskDetailSheet` is already, unavoidably, a Client Component (the caller fetches the task and passes it down; there is no Server Component wrapper to put data-fetching in without a second network round trip) — this is a pre-existing, already-established deviation in this codebase, not a new one introduced by this feature.
- **Read access**: `getTaskActivityPage` uses the caller's session-bound client (`lib/supabase/server`'s `createClient`), never the admin client — relies entirely on F194's `task_activity_select_visible` RLS policy (reusing `is_task_visible_to`) to enforce AS-359, matching `lib/queries/audit.ts`'s (F141) own "this function does not widen visibility" convention. Verified end-to-end against the live DB: a real signed-in outsider with zero workspace membership gets `rows: []` from both the raw query and the Server Action, never an error.
- **Estimate formatting**: no shared "format estimate minutes" helper existed anywhere in the codebase (grepped `lib/tasks`, `lib/queries`, `lib/activity` before adding one) — a small local `formatEstimateMinutes` (`"45m"` / `"2h"` / `"2h 30m"`) was added inside `format-task-activity-entry.ts` rather than a new shared file, since this is the only current caller.
- **Assignee display**: `assignee_id` old/new values are raw uuids in `task_activity`; `formatTaskActivityEntry` accepts an optional `resolveAssigneeLabel` callback rather than performing its own lookup (keeping the function pure/I/O-free). The current `ActivityFeed` component does not yet wire this callback to a real name lookup (see Out-of-scope below) — assignee-change entries currently render "assigned this to someone" rather than a resolved name; the sentence is still accurate and never crashes, just less specific than status/priority/title/due-date/estimate entries.

## Out-of-scope work needed

Left out because doing it well (avoiding a second per-row lookup) would touch the query's return shape further than this feature's scope review time allowed; assignee-change entries currently render "assigned this to someone" / "reassigned this from someone to someone" — accurate in kind, not in specific name.
