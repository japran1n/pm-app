## Decisions made
- **Moved `isProjectVisibleToCaller` to a new shared module** `lib/actions/project-visibility.ts` (exported, with its doc comment carried over and extended to name every new call site) rather than exporting it from tasks.ts and importing it back — this repo's existing convention for a helper shared across multiple `lib/actions/*.ts` files (e.g. `lib/auth/require-membership.ts`, `lib/auth/permissions.ts`) is a small standalone module under `lib/actions/` or `lib/auth/`, not a re-export from one sibling action file into another. `tasks.ts` now imports from this new module; all its call sites are unchanged.
- **Audited every exported Server Action in all eight named files** (checklist.ts, comments.ts, dependencies.ts, attachments.ts, watchers.ts, time-entries.ts, comment-reactions.ts, purge.ts) rather than assuming the spec's characterization ("every one mutates through createAdminClient() after checking only requireActiveMembership") held uniformly. It did NOT hold uniformly — four of the eight files turned out to be already safe for a structural reason not visible from a name-only grep:
  - **checklist.ts**: every mutation (`addChecklistItem`/`toggleChecklistItem`/`renameChecklistItem`/`reorderChecklistItem`/`deleteChecklistItem`) performs its ACTUAL insert/update/delete through the request-scoped RLS-respecting `supabase` client, not the admin client (this file's own header comment explains why — RLS is the deliberately-kept enforcement boundary for `checklist_items` per F152's original design). `checklist_items`' RLS was fully swept for project visibility (SELECT/INSERT/UPDATE/DELETE) in `supabase/migrations/20260821140526_project_visibility_rls_sweep.sql` via `is_task_visible_to`. The admin client is used ONLY for read-only lookups in this file. Not vulnerable — no fix needed.
  - **watchers.ts**: same pattern — the actual watch/unwatch row write goes through the caller's own session, and `task_watchers`' RLS (`supabase/migrations/20260822040000_task_watchers.sql`) already enforces `is_task_visible_to` on INSERT. Not vulnerable.
  - **comment-reactions.ts**: same pattern — `toggleReaction`'s insert/delete on `comment_reactions` goes through the caller's own session, and `comment_reactions`' RLS (`supabase/migrations/20260823010000_create_comment_reactions.sql`, refined in `20260823080000_fix_comment_reactions_soft_delete_and_scoping.sql`) already enforces `is_task_visible_to` via the underlying comment's task. Not vulnerable.
  - **dependencies.ts**: `createDependency`'s insert and `deleteDependency`'s delete both go through the caller's own session, and `task_dependencies`' RLS was fully swept in the same migration as checklist_items. NOT vulnerable for those two mutations. **However**, `getDependencyCandidates` (a read, using the admin client for its whole body) fetches every non-deleted project in the task's workspace — including a private one the caller cannot see — to build the candidate-task search space, with no visibility filter at all. This IS the same bug class (a read-path leak, matching this feature's part (b) scope), and is fixed here by filtering the fetched project list through `isProjectVisibleToCaller` before any task is ever queried from it.
  - **purge.ts**: `purgeTrashItem` is restricted to workspace OWNER ONLY via `canPurge` — no admin, no member. Per `isProjectVisibleToCaller`'s own rule, an owner is ALWAYS visible to every project regardless of its visibility flag. A structural analysis shows this action can never actually reach the vulnerable case (an owner-gated caller can never be denied by the visibility check), so no functional fix was needed here. Documented rather than silently skipped, and NOT covered by a regression test in the new test file (there is no negative case to test — any caller who can pass `canPurge` already passes `isProjectVisibleToCaller` by construction).
  - **comments.ts, attachments.ts, time-entries.ts** matched the spec's characterization exactly: every mutation writes through the admin client after checking only `requireActiveMembership` (+ role/author checks), never project visibility. All fixed here.
- **Fixed two additional read-path leaks in `lib/actions/tasks.ts` itself** (`getTaskDetail`, `getOpenBlockers`) exactly as instructed in part (b) of the spec — both now return the function's pre-existing `"Task not found."` string on a visibility failure, never a distinct permission-denied message, per the explicit "must not even confirm the task exists" instruction.
- **Failure messages**: every mutation fix reuses the exact string the same action already returns for its role/membership failure immediately above (or, where the visibility check runs after an author-or-admin branch with two different failure strings — deleteComment, restoreComment, deleteAttachment, deleteTimeEntry — the ONE generic string common to that function's own failure paths, e.g. "You don't have permission to delete this comment.").
- **`callerRole` capture pattern**: in the four files with an author-or-admin branch (deleteComment, restoreComment, deleteAttachment, deleteTimeEntry), the resolved `WorkspaceRole` from whichever branch (admin-check or author-membership-check) succeeded is captured into an outer-scoped `let ...CallerRole: WorkspaceRole` variable so the visibility check — which needs the role — can run once, after both branches, rather than being duplicated inside each branch.
- **getDependencyCandidates**: filtered the project list (not the final task list) so an invisible project's tasks are excluded before they're ever fetched at all — smaller query, and matches this feature's "filter first" convention rather than fetching-then-discarding.
