## Decisions made
- `getMyTasks`'s `includeWatched` merge is a SECOND bounded round trip (task_watchers lookup, then a second `tasks` select filtered by `.in("id", watchedTaskIds)`), never a per-row query — the same "one statement/RPC, never a per-row loop" performance budget F230 already established, extended by exactly one more query only when the toggle is on.
- Per-row status options are resolved with ONE batched `project_statuses` query across every distinct `projectId` present in the result (not `getProjectColumns` called per row), then threaded down as a `projectId -> options` map — avoids the N+1 the spec explicitly warns against.
- Reused `moveTaskStatus` (`lib/actions/tasks.ts`) unchanged — it already re-verifies workspace membership, `canWrite` role, and (post-F322/F323) `isProjectVisibleToCaller` against the task's OWN project server-side, and already resolves the target status against `project_statuses` scoped to `project_id = project.id` (the task's own project, never a fixed list). No parallel status-change action was written.
- The watched-tasks toggle is a plain server-rendered `<Link>` flipping `?watched=1` in the URL (no client component for the toggle itself) — matches the "state in URL params for anything shareable" convention F230's handoff pointed to for this exact follow-up, and needs no client-side interactivity beyond navigation.
- Watched-only rows get a "Watching" badge (visually distinguishable from assigned rows) per the clarified answer; a task that is both assigned and watched shows only the assigned styling, since assignment is the primary reason it's on the page and the row already appears exactly once (deduped by task id, `isAssigned && isWatched` both true on that single row).
- Empty state's primary action links to `/w/{slug}/projects` (a "browse your projects" CTA) — the simplest option satisfying AS-440 without inventing a new empty-state component, following `components/board/board-empty-state.tsx`'s existing "purposeful, not a dead end" convention rather than duplicating it.
- `MyTaskStatusCell` imports `MyTaskStatusOption` as a type-only import from the page module (`app/(workspace)/w/[workspaceSlug]/my-tasks/page.tsx`) — erased entirely at compile time (`import type`), so this does not pull the Server Component or its data-fetching code into the client bundle.

## Autonomous decisions
AUTONOMOUS_DECISION: The status-change control's write-permission gate reuses `<ListStatusSelect>`'s existing `useMembership()`-based `canWrite` check (workspace-level role), not a new per-project permission read. `moveTaskStatus`'s own private-project visibility re-check (`isProjectVisibleToCaller`) only differs from workspace role by PROJECT VISIBILITY, and `getMyTasks` already only returns rows for projects the caller can see — so no row on this page can hit that specific rejection path from a UI affordance that looked enabled; the viewer-role negative test (`test_AS_438_negative_...`) proves the write-permission axis (role), which is the one that can actually vary row-to-row for an otherwise-visible task.
