## Decisions made
- **Orchestrator-resolved scope deviation from the spec's literal draft wording, made explicit here per the task instructions.** The spec's draft scope said "content script injected at `document_start` in the MAIN world" across arbitrary pages. That requires a statically-declared `content_scripts.matches` entry (or `<all_urls>`) covering every page in advance — exactly what `tech-decisions.md`'s locked "`activeTab` only — no `<all_urls>`... keeps the store review and the privacy story simple" decision rules out, and which is not gesture-scoped the way `activeTab` is. Implemented instead by following F287's established pattern exactly: the hook is injected via `chrome.scripting.executeScript` (with `world: "MAIN"` so it patches the page's real `console`/`window`, not an isolated-world copy — verified against the current `chrome.scripting` API reference, the `world` option on `ScriptInjection` accepts `"MAIN" | "ISOLATED"`, default `ISOLATED`), triggered by a popup button click. Consequence: the hook genuinely can only ever see console activity from **after** that click — nothing from page load. This is a real, intentional design decision, not a workaround failure: a gesture-triggered hook has an unambiguous, easy-to-state start point ("logs from before you clicked to start capturing are not included"), which is arguably a *more honest* AS-552 statement than the draft's `document_start` framing — even a real `document_start` content script can race very-early synchronous errors on some pages, whereas this hook's boundary is exactly "the click," full stop.
- **Only `error` and `warn` console levels are captured**, not `log`/`info`/`debug`. AS-550's literal wording is "console errors and warnings"; the clarification's tie-breaker for open questions is "the simpler, more private option (less data captured...)". Combining both, `log`/`info`/`debug` are deliberately excluded — a bug reporter's console noise floor is dominated by non-error `console.log` calls in most real apps, and capturing only error/warn plus uncaught errors/rejections keeps the payload meaningfully smaller and more private by default. Documented in the popup's captured-entry list (each entry shows its `level`) and tested explicitly (`AS_550_real_console_error_and_warn_calls_made_after_injection...` logs a `console.log` alongside error/warn and asserts only 2, not 3, entries are captured).
- **`window.onerror`/`unhandledrejection` are captured as `level: "error"`** with a `source` field (`"console" | "onerror" | "unhandledrejection"`) distinguishing them from direct `console.error` calls — they're a different signal (uncaught exceptions vs. deliberate logging) and the spec explicitly calls out both as worth capturing.
- **Ring buffer capacity: 200 entries** (`MAX_CONSOLE_ENTRIES` in `console-hook.ts`), matching the spec's own suggested figure — large enough to cover a real debugging window's worth of error/warn activity, small enough (combined with the 2000-char per-entry truncation) to bound the eventual report payload hard regardless of how chatty a broken page gets.
- **Serializer never throws, by construction and by test.** `serializeLogArgument` (canonical, in `console-hook.ts`) and its duplicated in-page copy (`serializeInPage`, inside the injected `installConsoleHookInPage` function — required because `chrome.scripting.executeScript({ func })` serializes `func` with no closure over this module, the same tradeoff F287's `element-picker.ts` documents) both wrap their entire body in try/catch with a final `"[unserializable value]"` fallback, and detect DOM nodes via duck-typing (`"nodeType" in value`) rather than `instanceof Node`, so it also works correctly when the value crosses realms. Verified directly: `AS_550_serialization_never_throws_on_circular_objects_DOM_nodes_Errors_undefined_or_functions` logs a circular object, a real DOM node, a real `Error`, `undefined`, `null`, a named function, and a `Symbol` through the real function and asserts none of the 7 calls throw and each produces a non-empty readable string.
- **Console capture defaults to off, started by an explicit popup button** ("Start capturing console output"), per the clarification's "default it deliberately... simpler, more private" instruction — not always-on/silent hooking. There is no F291 toggle yet to gate behind (see Out-of-scope below); this button *is* the deliberate default this feature owns on its own.
- **Popup state for captured entries stays in local React state**, refreshed on demand via a "Refresh captured logs" button rather than a live-updating stream, matching F283/F287's precedent (`store.ts` not touched) and keeping the injection surface to two simple one-shot `chrome.scripting.executeScript` calls (start, and read-back) rather than a persistent message-passing channel.
- **Idempotent install:** `installConsoleHookInPage` checks a `window.__pmAppConsoleCapture__` marker before wrapping anything, so clicking "Start capturing console output" a second time (e.g. after switching tabs and back) never double-wraps `console.error`/`console.warn` or resets the existing buffer.

## Out-of-scope work needed
- **F291's on/off toggle** (referenced in this feature's own clarification notes but not yet built in this milestone) should wrap around `startConsoleCaptureOnActiveTab`/`getConsoleCaptureFromActiveTab` as exported here — this feature's own popup button is a reasonable default trigger on its own and needs no changes to work standalone, but a future toggle-driven UX (e.g. auto-start capture when the reporter opens the popup, if the user has opted in) should call these same two functions rather than reimplementing hook installation.
- **No `store.ts` slot / persistence for captured console entries beyond local popup React state** — same reasoning as F287's picked-element result: no downstream feature yet assembles the final bug-report payload. Whichever feature does that (attaching screenshot + picked element + console log + environment metadata into one submitted report) should read `getConsoleCaptureFromActiveTab()`'s result the same way it will read the other capture modules' in-popup state.
- No UI affordance yet to explicitly "stop" capturing (the hook simply keeps running on that tab until the tab navigates/closes, since removing `console.error`/`console.warn` wrapping cleanly would need a stored reference to the *current* wrapped function across separate `executeScript` calls, which isn't worth the complexity for a capture that's already bounded and page-lifetime-scoped). Flagging in case a future feature wants an explicit "stop and discard" affordance.

## Notes for the next worker
- **`world: "MAIN"` vs. the default `world: "ISOLATED"` for `chrome.scripting.executeScript` matters here specifically** (unlike F287's picker, which works fine in the default isolated world since it only reads DOM state and adds its own listeners): patching `console.error`/`console.warn` needs to replace the property the *page's own* code calls into, which requires running in the page's own JS realm (`world: "MAIN"`), not the extension's isolated one. Verified empirically via the real `AS_550_real_console_error_and_warn_calls_made_after_injection...` test, which calls `console.error`/`console.warn` from `contentPage.evaluate()` (i.e. genuinely from the page's own context, not the injected script's).
- Same Playwright harness caveats as F287's `element-picker-selector.spec.ts` apply here (documented in that file's header and F287's handoff): `chrome.scripting.executeScript` succeeds in this test harness without a real toolbar-click `activeTab` gesture specifically because the target origin (`http://localhost:3000`) is already covered by the manifest's `host_permissions` entry — real usage still relies on the `activeTab` gesture chain (popup opened via toolbar click → button clicked in that same popup) exactly like the element picker.
