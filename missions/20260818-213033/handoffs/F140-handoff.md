  - `workspace.deleted` — `deleteWorkspace` (lib/actions/workspaces.ts)
  - `workspace.renamed` — `renameWorkspace` (lib/actions/workspaces.ts), metadata `{ name }`
  - `invite.accepted` — `activateInvitedMemberships` (lib/actions/invites.ts), metadata `{ role }`
  - `project.created` — `createProject` (lib/actions/projects.ts)
  - `project.updated` — `editProject` (lib/actions/projects.ts), metadata `{ fields: [...changed field names] }` — added even though not named verbatim in the spec's example list, because AS-245 explicitly covers "project ... mutations" and edit is one; used the simpler existing verb pattern (`updated`) rather than inventing a qualifier per field.
  - `project.archived` — `archiveProject` (lib/actions/projects.ts)
  - `project_member.added` — `addProjectMember` (lib/actions/project-members.ts), metadata `{ project_id, user_id, project_role }`
  - `project_member.removed` — `removeProjectMember` (lib/actions/project-members.ts), metadata `{ project_id, user_id }`
  - `project.visibility_changed` — `updateProjectVisibility` (lib/actions/project-members.ts), metadata `{ visibility }` — added for the same "project mutation" coverage reason as `project.updated`.
  - `workspace.slug_changed` — `changeWorkspaceSlug` (lib/actions/workspaces.ts) — added independently by the concurrent F137 worker following this feature's `writeAudit` convention once it existed on disk; not something I wrote, noted here for completeness since it lives in a file this feature also touches.
- `writeAudit(supabase, params)` takes the caller's already-in-scope **session-bound** client (the one from `lib/supabase/server`'s `createClient()`), never the admin client — the `write_audit_log_entry` RPC pins `actor_id` to `auth.uid()` and re-checks active membership, both of which require a real session. Documented prominently in `lib/activity/audit.ts`'s header comment so no future caller accidentally passes the admin client.
- Failure handling: `writeAudit()` never throws and never returns an error — a failed RPC call (returned `error`) and an unexpected throw (e.g. network failure) are both caught internally and `console.error`-logged, exactly matching this codebase's established non-fatal `revalidatePath`-failure convention (see any `try { revalidatePath(...) } catch { console.error(...) }` block in `lib/actions/*.ts`). No caller has to check a return value.
- `activateInvitedMemberships` (lib/actions/invites.ts) is the one caller with no natural session client already in scope (it only ever used the admin client before). Rather than changing its signature to require the caller to pass one (which would mean touching `app/(auth)/auth/callback/route.ts`, outside this feature's file scope), it calls `createClient()` itself — safe in production since it only ever runs after `exchangeCodeForSession` has already set the request's session cookies. Wrapped in try/catch: `next/headers`' `cookies()` throws when called outside an active request/render context (e.g. a test harness invoking the function directly), and per this feature's own failure-handling convention, that must never fail the real invite-activation logic — it only skips the audit write for that call and logs it. This was caught and fixed after the first `npm run test` run broke `tests/integration/invite-accept-on-signin.test.ts` (3 failures), which does not mock `next/headers`.
- `project.updated` and `project.visibility_changed` were added beyond the feature spec's literal example list (`workspace.renamed`, `workspace.deleted`, `member.role_changed`, `member.removed`, `member.invited`, `project.created`, `project.archived`, `project_member.added`, `project_member.removed`) because AS-245's actual wording covers "project ... mutations" generically, and `editProject`/`updateProjectVisibility` are real project mutations already in this feature's file scope (`lib/actions/projects.ts`, `lib/actions/project-members.ts`). Per the clarification's "simpler option, no second source of truth" default, this was resolved by extending the same one enumeration rather than leaving those two mutations silently unaudited.
- `lib/activity/audit.ts`'s RPC args use two narrow, explicitly-commented type casts (`p_target_id` and `p_metadata`) to bridge a mismatch between the generated `write_audit_log_entry` RPC `Args` type (which incorrectly makes `p_target_id` a required non-nullable `string` even though the underlying SQL function's `target_id uuid` parameter is nullable) and this helper's public `targetId?: string | null` shape — rather than either widening `WriteAuditParams` to hide the nullability from every caller, or regenerating `database.types.ts` (out of scope; no migration or schema change happened in this feature).
