## Decisions made
- Read `mention-extension.ts` and confirmed `Suggestion.items` is called lazily per-keystroke (`items: ({ query }) => filterMentionItems(getItems(), query)`), so in principle the candidate SOURCE does not need the whole `Editor` instance destroyed/recreated to stay current — this is exactly what the follow-up spec asked me to confirm and implement.
- **Attempted the spec's prescribed fix first**: replaced `pristineRef`/`focusedRef`/`justConstructedRef`/state-key machinery with a plain always-live mutable box (`useState(() => ({ items: [...] }))`, updated unconditionally via `useEffect`), with `getMentionItems: () => box.items`. This is functionally correct (verified: typecheck passes, and the mechanism itself is standard) but **fails lint categorically** in this codebase: `eslint-plugin-react-hooks@7.1.1` (React Compiler's rule set) rejects `getMentionItems: () => box.current`/`box.items` wherever that closure flows into `useEditor()` during render, via two different rules depending on the box's shape:
  - A literal `useRef` box → `react-hooks/refs`: "Cannot access refs during render" / "Passing a ref to a function may read its value during render".
  - A `useState`-boxed plain object with any field name → `react-hooks/immutability`: "Modifying a value returned from `useState()`, which should not be modified directly."
  There is no object shape that is both (a) stable-identity and mutable across renders, and (b) passable into `getMentionItems` inside the render-time `useEditor()` call, that satisfies both rules simultaneously in this codebase. This is a hard project-wide lint constraint (React Compiler is enabled), not a style disagreement — confirmed by trying three variants (`useRef` with `.current`, `useState` with `.current`-named field, `useState` with `.items`-named field), all rejected.
- **Fell back to the next-best fix** (per this feature's own instructions: "if you find a reason it doesn't work cleanly this way, explain in the handoff and pick the next-best fix"): kept F310's `deps`-array-driven destroy/recreate mechanism (the only mechanism in this codebase that can hand the Mention extension a genuinely fresh `getItems` closure without fighting the lint rules above), but **removed F314's "only while pristine" gate entirely** — `computedMentionSuggestionsKey` now always drives a recreation the instant the candidate set changes, with zero focus/edit-based blocking. This eliminates every code path that could freeze the picker (the actual regression this feature exists to fix).
- Added a best-effort selection-preservation mitigation to reduce (not eliminate) the UX cost of recreation-while-focused: `onSelectionUpdate` continuously records the current ProseMirror selection into a ref; `onCreate` on the newly (re)created instance restores that selection (and refocuses if the previous instance was focused) via `editor.commands.setTextSelection` + `editor.commands.focus()`. The controlled `content` prop is passed fresh to the new instance regardless, so no typed text is lost. The one accepted remaining cost, documented in the file: a recreation starts a brand-new ProseMirror undo-history stack, so a recreation that happens exactly mid-edit loses undo entries prior to that point. This is explicitly smaller than the fixed bug (a picker that never works again for the session).
- `RichTextRenderer` (read-only): confirmed the reasoning in the spec holds — it has no cursor/focus/undo-history to protect, so F310/F314's `deps`-keyed recreation (on `id:label` pairs) is left completely unchanged. Its existing rename-repaint test still passes unmodified.
- `resolveMentionLabel`'s/`renderHTML`'s call sites in `mention-extension.ts`: confirmed no changes needed — they already call `getItems()` fresh on every Tiptap render pass (never store a resolved label), so once a fresh editor instance exists (post-recreation, or on initial mount), a mention chip's displayed name is always correct as of that instance's construction. No live-ref treatment was needed there independent of the composer's construction mechanism.
- Fixed the two tests flagged by the scrutiny pass (previously at ~616/642 in `tests/unit/mention-extension.test.tsx`) that asserted the broken "focus-before-candidates freezes forever" behaviour as correct — rewrote them (now inside `describe("F317: focusing the editor before candidates arrive no longer freezes the picker")`) to assert the opposite: focusing early must NOT block the later rebuild. Added a new regression test (`test_AS_371_regression_focus_before_candidates_then_populate_then_at_shows_real_candidates`) that drives the exact scenario end-to-end through a real Tiptap `useEditor`/`EditorContent` tree (mirroring `RichTextEditor`'s actual recreation mechanism: `deps`-keyed on `id:label`, `getItems` closing over the current prop) and asserts the real picker DOM shows real candidates, not "No matching members", after mount-empty → focus → populate → type "@".
- Also updated the pre-existing rename test for `RichTextEditor` (previously named `test_AS_373_editor_side_rename_also_recreates_when_pristine`) since its old name/assumption ("only recreates while pristine") no longer applies — recreation on rename is now unconditional; renamed and kept the same assertion (a rename still produces a fresh `.ProseMirror` node).
