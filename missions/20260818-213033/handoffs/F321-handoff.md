## Decisions made
- Matched the exact "is this user an active member of this workspace" predicate shape already used by `public.create_notification`'s own recipient check (`20260823110000_create_notification_task_workspace_check.sql`) and `public.is_active_workspace_member` (`20260817222822_rls_workspaces.sql`): `wm.workspace_id = <workspace> and wm.user_id = <user> and wm.status = 'active'`. Implemented as an inner `join workspace_members wm on ...` in the sweep's driving SELECT (per the spec's half (a)) rather than a `not exists`/anti-join — an inner join is the natural "must be an active member" shape and reads identically to the existing membership-check call sites this migration explicitly cites.
- Per-row exception handling (spec half (b)): wrapped only the `perform public.create_notification(...)` call (plus the counter increment) in `begin ... exception when others then raise warning ...; end;` inside the loop, not the whole loop body — keeps the `for ... loop`'s row-fetching/iteration outside the exception scope so a single row's failure can't corrupt cursor state, and matches the spec's explicit instruction to wrap only the `create_notification` call.
- Used `raise warning` (not `raise notice` or silently swallowing) exactly as the spec specified — visible in Postgres logs for CI/ops visibility without aborting the transaction, and includes `sqlerrm`/`sqlstate` plus the row's user/task/workspace ids for triage.
- Did not add a `when unique_violation then null` special case separate from the general `when others` handler — per the spec's own instruction, a unique_violation against `notifications_overdue_once_idx` is "the expected, harmless already-notified case" and is adequately handled (logged-and-continue, no re-raise, no double-notify) by the general handler; no special-casing needed since the desired behavior (log-and-continue) is identical for both the expected race case and any genuinely unexpected error.
- Test used the SAME hard-delete-only-workspace_members-row pattern `remove_workspace_member` itself uses (confirmed by reading `20260817234900_remove_member_atomic_owner_guard.sql`), issued directly via the Management API SQL path this file already uses, rather than calling the `remove_workspace_member` RPC itself — keeps the test focused on reproducing the exact orphaned-row DB state (the bug's actual precondition) rather than also exercising the owner-guard RPC's unrelated logic.
- New regression test creates two fresh users (one to be removed, one to stay valid) scoped to the existing suite's `workspaceId`/`projectId` fixtures and cleans up its own extra rows explicitly at the end of the test body (the suite's `afterAll` only tracks the original `assigneeUserId`/`optedOutUserId` users) — avoids leaking test data into other tests in the same file while not needing to restructure the existing `beforeAll`/`afterAll` fixture scope.
