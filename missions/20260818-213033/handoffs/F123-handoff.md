## Decisions made
- **The fallback chain lives in `lib/queries/people.ts`'s `resolvePeople`, not a new "name resolution helper."** F122 already built the single shared resolver every avatar/label call site reads through (`personLabel`, `resolveAssigneeNames`, `getWorkspaceMembers`, the dashboard table, etc. all ultimately read `resolvePeople`'s `name` field). The Draft scope's "Name resolution helper... replaces `lib/queries/assignee-names.ts` usage" predates F122 landing; per this feature's explicit instruction ("do not build a second name-resolution path"), I fixed the one existing resolver instead of adding a parallel implementation. `lib/queries/assignee-names.ts` itself needed no code change — its `person.name ?? person.email` already benefits automatically once `resolvePeople`'s `name` field is correct.
- **Added the missing "email local part" step.** Before this feature, a user with no `display_name` was rendered by their *full* email address everywhere (`personLabel`: `person.name || person.email`) — which doesn't read as "the email was replaced by anything nicer," even though AS-201/AS-202 don't literally forbid it. Added `emailLocalPart(email)` (new export, `lib/queries/people.ts`) and inserted it into the chain: `display_name -> user_metadata.full_name (pre-existing F122 fallback) -> email local part -> full email`. The full email is still returned unchanged on the `email` field of `PersonSummary` for callers that want it verbatim (e.g. a mailto link) — only the `name` field's fallback shortens.
- **Found and fixed a real bug while verifying the fallback chain against real data: `Intl.supportedValuesOf("timeZone")` does NOT include the literal string `"UTC"`** (verified: `node -e "console.log(Intl.supportedValuesOf('timeZone').includes('UTC'))"` prints `false`; only `"Etc/UTC"` is listed). F120's `profiles.timezone` column defaults every existing row to exactly `'UTC'`. A naive `Set(Intl.supportedValuesOf('timeZone')).has(value)` validation would have rejected every user's own unchanged default the first time they saved this form, and the Select's initial value wouldn't have matched any rendered option (would show blank instead of "UTC" selected). Fixed two places: (1) `lib/validation/profile.ts`'s timezone check now constructs `Intl.DateTimeFormat(undefined, { timeZone: value })` and catches the `RangeError` instead of doing Set membership — accepts "UTC" (and any other alias the runtime legitimately resolves) while still rejecting garbage; (2) `app/.../settings/profile/page.tsx` prepends `"UTC"` to the list passed to `<ProfileForm>` so it's actually selectable and shows correctly as the current value for every user who hasn't changed it yet. Both are documented in-line with the exact `node -e` repro. This satisfies "the timezone select must be populated from `Intl.supportedValuesOf('timeZone')`" while not silently breaking on the one value the DB actually stores by default.
- **Updated one pre-existing mission-1 assertion** (`tests/integration/list-view-render.test.ts`, `"AS-085: resolveAssigneeNames resolves a display name for an assigned task's assignee"`) whose hard-coded expectation encoded the *old* fallback behavior ("falls back to the full email"). AS-085's actual contract text ("shows... assignee... columns") doesn't pin down the exact fallback string shape; the test's specific expected value was a regression guard for whatever `resolveAssigneeNames` happened to return pre-F123, and fixing the fallback chain (this feature's explicit assignment) necessarily changes that value from the full email to its local part. Reverting my fix to keep an outdated implementation-detail assertion green would have contradicted the assignment's own instruction, so I updated the one `expect(...)` line and its comment to describe *why* it changed, rather than leaving the suite red or silently reverting the chain fix. No other test in the repo asserted the old full-email fallback (checked every caller of `resolvePeople`/`resolveAssigneeNames`/`resolveAssignees`/`getWorkspaceMembers` across `tests/`).
- **`updateProfile` takes plain arguments** `(displayName: string, timezone: string)`, not FormData — same convention as `inviteMember`/`changeMemberRole` in `lib/actions/workspaces.ts` (neither field here is a file upload, unlike `uploadAvatar`).
- **AS-208 ("cannot edit another user's profile, including via a direct API call") is out of my assigned assertion list** (it's F120's, already covered by `tests/integration/rls-profiles.test.ts`'s RLS-level tests) but the assignment explicitly asked me to prove "a user cannot update someone else's profile through this action" for AS-202's own action. `updateProfile` never accepts a target user id at all — every write is `.eq("id", user.id)` from the caller's server-verified session — so there's no argument a caller could pass to make it touch anyone else's row. Tested directly: calling it as user A while user B has a pre-existing display name leaves B's row completely untouched.
- **Avatar upload reuses `uploadAvatar` unmodified** (F121) — the form's file input calls it directly with a fresh `FormData`, live-previews via `URL.createObjectURL` before the upload resolves, and reverts to the previous `avatarUrl` on failure (revoking the temporary object URL either way). No second upload path was written.
- **Timezone select uses the existing shadcn `<Select>` primitive** (already used elsewhere, e.g. `MemberRoleSelect`), not a new searchable combobox built on `cmdk`/`Command` (also available in `components/ui/`). ~400 entries is more than the app's other selects hold, but building a combobox was more engineering than this assertion needs and would be a second selection-UI pattern; per the clarification's ambiguity-resolution default (simpler option, no new dependency), I used the plain `<Select>`. If AS-207's own worker (or a UX pass) finds the flat list hard to use, swapping in a `Command`-based combobox is a self-contained follow-up — the `timezones: string[]` prop shape wouldn't need to change.
- **No theme-preference link was built.** The Draft scope's file list mentions one, but AS-211–213 (the actual theme toggle) are not in my assigned assertions and `next-themes` is "currently unused in the UI" per tech-decisions.md — nothing exists yet for a link to point at. Building a dead link, or a full toggle out of scope, seemed worse than omitting it; noted below.
- **No page-level membership gate beyond the workspace layout guard**, matching the members settings page's existing convention — a profile is the same row regardless of which workspace's settings URL it's reached through, so there's nothing workspace-scoped to re-check here.
