## Decisions made
- **Strip, not reject the whole comment.** The clarified spec's Notes left "reject (or strip)" open. Per the clarified "simpler option, no new dependency, no second source of truth" default: a mention node referencing a user invisible to the commenter is replaced with a plain text node (`{ type: "text", text: "@Former member" }`) rather than failing the entire addComment/editComment call. This means a comment with nine valid mentions and one hostile/invalid one still posts, with only the bad mention neutralised — consistent with `sanitiseDocument`'s own existing "degrade gracefully, never throw the whole document away" philosophy in rich-text-editor.tsx.
- **Generalised `is_project_visible_to()` rather than calling it via RPC.** The SQL function (`supabase/migrations/20260821140526_project_visibility_rls_sweep.sql`) is hardcoded to `auth.uid()` — it answers "is this project visible to the CALLER", not "is this project visible to an arbitrary mentioned user id". Re-implementing the same three-way rule (active workspace member AND (workspace-visible OR owner/admin OR explicit project_members row)) with the admin client, batched over all mentioned ids in one `workspace_members` query + one `project_members` query, follows the exact precedent `lib/actions/project-members.ts`'s `isProjectLeadOrWorkspaceAdmin` already set for "re-derive an RLS helper's predicate for a specific target user with the admin client" — no new SQL function, no new dependency.
- **`resolveMentionLabel` (AS-373, F203) is left untouched**, still falling back to the raw id — that's the *insert*-path contract (a comment currently being composed shouldn't silently blank out a mention while typing). A new, separate function `resolveMentionDisplay` was added specifically for the *render* path, returning `{ label, known }` so renderHTML/renderText can render plain text (not a chip, no `data-id`) for an unresolved mention — this is what AS-377 actually asks for ("renders as plain text"), and keeps AS-373's existing test/contract from F203 unbroken rather than repurposing the same function for two different failure-mode expectations.
- **The raw user id never reaches the DOM for an unresolved mention.** Previously `resolveMentionLabel`'s id fallback meant an unresolvable mention rendered as `@<uuid>` in the chip. That's a straightforward "leak identity" reading of the spec's explicit warning, so `resolveMentionDisplay` returns `"Former member"` instead, and `renderHTML` drops the `data-id`/`data-type="mention"` attributes entirely for the unknown case.
- **Where "not visible to this reader" is decided at render time**: unchanged from F203 — `mentionSuggestions` passed into `RichTextRenderer` is whatever the caller (`comment-list.tsx`) already scopes per-reader. This feature only changed what happens when a mention's id isn't found in that list; it did not change how that list itself is scoped (see Out-of-scope below).

## Out-of-scope work needed
- **The client-side suggestion picker (`comment-list.tsx`'s `mentionSuggestions`) is still scoped to all active *workspace* members, not narrowed to users with actual visibility into the specific (possibly private) project.** AS-376's "not offered" half is therefore only partially satisfied by this feature: a commenter on a private project can still see (and select) a workspace member who lacks project access in the picker itself — but per this feature's own instructions, "F203's picker only filters the suggestion UI, it doesn't stop a hand-crafted payload" is explicitly *not* the real security boundary, and that boundary (server-side reject/strip) is fully implemented and tested here. Narrowing the picker itself would require a new project-scoped member query (there isn't one yet that includes workspace owners/admins + explicit project_members + visibility, batched, no N+1) and threading a `projectId`/`projectVisibility` prop from `task-detail-sheet.tsx` down into `comment-list.tsx` — real scope expansion beyond this feature's named files (`lib/actions/comments.ts`, `components/editor/mention-extension.ts`/renderer). Suggested follow-up: a small feature that adds a `getVisibleProjectMentionCandidates(projectId, workspaceId)` query (reusing `resolveVisibleMentionIds`'s exact rule from `lib/comments/mentions.ts`, inverted to "list who's visible" rather than "check if this id is visible") and passes it into `comment-list.tsx`'s `mentionSuggestions` computation instead of the raw workspace `members` list, whenever the task's project is private.
- Notification-on-mention (sending an actual notification when someone is mentioned) remains out of scope, as F203's handoff already flagged — nothing in this feature touches notification delivery.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose "strip the offending mention node, keep the rest of the comment" over "reject the whole submission" for AS-376 enforcement — the clarified spec explicitly left this open ("reject (or strip)") and delegated the choice to the simpler-option default. Stripping avoids a confusing user-facing failure mode (a comment with 9 valid mentions failing entirely because of 1 hostile one crafted outside the picker) and matches the existing `sanitiseDocument` precedent of degrading hostile/invalid input rather than rejecting the whole document.
AUTONOMOUS_DECISION: Left the client-side mention-suggestion source (`comment-list.tsx`) unchanged (still all active workspace members) rather than expanding scope to also narrow the picker to project-visible members — documented above as Out-of-scope work needed, since the feature's own instructions were explicit that the server-side reject/strip is the real, required security boundary and the picker was called out only as inadequate on its own, not as something this feature must also fix.
