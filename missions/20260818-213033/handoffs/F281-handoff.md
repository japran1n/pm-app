## Decisions made
- **One-time token, not `externally_connectable`.** Per the clarification's tie-breaker ("take the simpler, more private option"), chose a short-lived encrypted one-time token over `externally_connectable`. `externally_connectable` requires the web app to call `chrome.runtime.sendMessage(extensionId, ...)`, which means either publishing the extension to get a stable id or pinning one via a generated signing `key` in the manifest just for local/dev use — more moving parts — and it means the extension keeps an open listening surface for any tab matching the declared origin pattern. The token approach never opens a listening surface at all: a content script scoped to only `/extension-connect*` on the app's own origin (declared narrowly in `manifest.json`'s `content_scripts.matches`, not `externally_connectable`) reads a DOM node that page renders only for an authenticated request, and relays it via `chrome.runtime.sendMessage` to the extension's *own* background worker (internal messaging, not cross-extension). An arbitrary site cannot trigger this: the content script only ever runs on the declared origin+path.
- **Token shape:** AES-256-GCM encrypted blob containing `{accessToken, refreshToken, userId, email, expiresAt}`, base64url-encoded, keyed by a new server-only `EXTENSION_HANDOFF_SECRET` env var (not reused from `SUPABASE_SECRET_KEY`, to avoid key-purpose reuse). TTL 60s.
- **"One-time" enforcement is best-effort:** a 60s TTL is the primary defense; a same-process in-memory `Set` of consumed token digests blocks replay within one server instance but does not survive a process restart or span multiple serverless instances. A persistent single-use store (e.g. a Postgres table with a unique constraint) would close this gap fully but needs a migration, which is out of this feature's 45-minute budget — documented as a known limitation, not silently glossed over.
- **AS-538 check matches on a pattern, not a bare substring.** An initial version matching the bare string `sb_secret_` false-positived on `@supabase/supabase-js`'s own library code, which legitimately contains that prefix as a string literal (to classify a key's format internally) without ever containing real key material after it. The check now requires the prefix followed by 16+ key-shaped characters (`/sb_secret_[A-Za-z0-9_-]{16,}/`), which the library's bare prefix constant never matches, and a test (`AS_538_the_check_actually_detects_a_leaked_secret_key`) proves the pattern still catches an actual fabricated secret.
- **`manifest.json`'s `content_scripts.matches` / `host_permissions` are hardcoded to `http://localhost:3000/*`** (dev-only), driven by `extension/.env`'s `VITE_APP_URL` for the app-facing runtime code but not for the manifest itself (crx's vite plugin imports `manifest.json` as static JSON, not templated). Deploying to a real hosted app origin needs this updated — see Out-of-scope below.
- **`chrome.storage.local` adapter and `createClient({ auth: { storage } })`** shape verified against the current `@supabase/supabase-js@2.112.3` `SupportedStorage` interface in `node_modules/@supabase/auth-js/dist/module/lib/types.d.ts` (getItem/setItem/removeItem, sync or async) rather than assumed from memory, per the spec's explicit instruction.
- **`sign-in?next=/extension-connect`** link is rendered but the sign-in flow itself does not yet honor a `next` redirect param (out of scope — see below); the user currently has to manually reopen `/extension-connect` after signing in via the link. This does not break AS-533 (which only requires being told to sign in and given a link), but it is a rough edge worth closing.
