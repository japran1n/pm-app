## Decisions made
- **Restore uses Realtime Broadcast (`comment_restored`), not `postgres_changes`, even though a restore's NEW row (deleted_at now null) would actually PASS `comments_select_active_members`'s SELECT policy** (unlike delete's NEW row, which fails it — that asymmetry is real and I checked it before deciding). The reason broadcast is still required: `lib/tasks/subscribe-comments-realtime.ts`'s `postgres_changes` subscription is filtered to `event: "INSERT"` only (not `"*"`, not `"UPDATE"`) — this restriction was F104's own fix and predates this feature; a restore is an UPDATE under the hood, so it would never reach `postgres_changes` subscribers at all regardless of whether its NEW row passes RLS. Widening the subscription back to include UPDATE to catch restores would also re-widen it to catch delete's UPDATE (whose NEW row still fails RLS), reintroducing exactly the class of bug F104 fixed for every OTHER UPDATE-shaped soft-delete transition on this table. Broadcast avoids this entirely and keeps the channel's event set symmetrical (`comment_deleted` / `comment_restored`), which is the "mirror the same mechanism" instruction from this feature's own brief and clarification file.
- **The broadcast payload carries the full comment row** (id, task_id, user_id, text, body_json, created_at), not just an id (unlike `comment_deleted`, which only needs an id to remove a row). A restore needs to *reconstruct* the comment for a viewer whose local state no longer has it at all — an id alone wouldn't let `reconcileComment`'s existing INSERT-append branch do anything. Translating the broadcast into an INSERT-shaped `CommentRealtimeEvent` reuses that existing branch verbatim (no new reducer code needed in `reconcile-realtime-comment.ts`), the same "no second source of truth" simplicity default this feature's clarification calls for.
- **No-op on restoring an already-active comment** (deleted_at already null): per the clarification's inherited "empty/zero state" default (a no-op returns ok without writing, no error toast), rather than treating "not currently deleted" as an error. Implemented as an explicit early return after the permission check (permission is still checked first, so the no-op path can't be used to probe whether a comment is currently deleted for someone without restore rights).
- **Permission rule copied verbatim from `deleteComment`** (author, active + `canWrite`; or workspace admin/owner via `requireWorkspaceAdmin`) rather than inventing a separate restore-specific rule — this is the exact "same class of problem, same pattern" mirroring both AS-346's own wording ("restored ... by its author or an admin") and the clarification's ambiguity-resolution default point to.
- **`deleted_by` is cleared to `null` on restore** (not left pointing at whoever deleted it, and not set to the restorer). Once a comment is active again, `deleted_by` has no meaning — F188's trash view only reads it for deleted rows — and leaving a stale value would misrepresent a currently-active comment as still carrying deletion metadata.
