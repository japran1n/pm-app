## Decisions made
- **Idempotency mechanism (the clarified spec's explicit requirement)**: a real DB-level UNIQUE constraint `tasks_recurrence_occurrence_idempotency` on `tasks (recurrence_parent_id, due_date)`, enforced via `.upsert(row, { onConflict: 'recurrence_parent_id,due_date', ignoreDuplicates: true })` in `generateNextOccurrence` — i.e. `INSERT ... ON CONFLICT (recurrence_parent_id, due_date) DO NOTHING`, not an app-level "check if it exists, then insert" (which races under concurrent requests). First attempt used a PARTIAL unique index (`where recurrence_parent_id is not null and deleted_at is null`), but PostgREST's upsert `onConflict` issues a plain `ON CONFLICT (columns)` with no WHERE clause, which Postgres can only resolve against a non-partial index/constraint (confirmed against the real linked project: `42P10: no unique or exclusion constraint matching ON CONFLICT`). Fixed in a follow-up migration (`20260822151000`) by dropping the partial index and adding a full UNIQUE constraint instead — safe because NULL <> NULL under a standard unique constraint, so every non-recurring task (recurrence_parent_id IS NULL) is entirely unaffected; the constraint only fires for two rows sharing the same non-null `recurrence_parent_id` AND the same `due_date`.
- **`recurrence_parent_id` always points at the SERIES ROOT**, never the immediately-completing task: `source.recurrence_parent_id ?? source.id`. This means completing occurrence N, N+1, N+2... of the same series all write against ONE `recurrence_parent_id` value, so the single unique constraint enforces "at most one occurrence per due date across the whole series," not just per-immediate-parent (which would let a chain of completions bypass the guard by always differing in `recurrence_parent_id`).
- **Generation is purely additive/non-fatal**: `generateNextOccurrence` is called from `moveTaskStatus` AFTER the status-change write already succeeded, wrapped in try/catch — a failure to generate the next occurrence (network blip, unexpected error) never turns the user's "mark done" action into a failure. This matches AS-321's framing ("archived project generates nothing... completing the task still succeeds") generalized to every skip/failure reason, not just the archived-project case.
- **Skip conditions** (all silent, all documented in `generate-next-occurrence.ts`'s own comments): no `recurrence` rule (not a recurring task), no `due_date` on the source task (nothing to advance from — autonomous decision, see below), the owning project is archived (`projects.deleted_at is not null`, AS-321), `nextOccurrenceDate` returns null (invalid rule or past `until`, per F176), or the unique constraint absorbs a duplicate (AS-320).
- **New occurrence fields**: reused `cloneTaskFields` (F176) verbatim for title/description/description_json/assignees/priority/checklist/estimate + the `status: 'todo'` reset, exactly the same pattern F180's `duplicateTask` already established for inserting the cloned checklist items and assignee rows — no new parallel insert logic invented. `due_date` is the newly computed date; `recurrence` is carried forward unchanged so the series continues; `recurrence_parent_id` is the series root (see above); position is appended to the end of the target project's `todo` column via the same `calculatePosition` convention `createTaskForUser` uses for brand-new tasks.
- **Timezone source**: reused `getCurrentUserTimezone(supabase)` (F124, `lib/queries/profile.ts`) — the acting user's own `profiles.timezone` — passed to `nextOccurrenceDate`, rather than inventing a workspace-level timezone concept that doesn't exist in this schema.
- **Hooked into `moveTaskStatus` only**, not `moveAndReorderTask` (the combined drag+reorder action) — the feature spec explicitly named `moveTaskStatus` as the hook point ("Hook into the task status-change path (`moveTaskStatus`...)"). See Out-of-scope below.

## Out-of-scope work needed
- **`moveAndReorderTask`** (lib/actions/tasks.ts) is a second code path that can also transition a task into a done-category status (a drag-and-drop cross-column move with reposition, combined into one call). It does NOT currently trigger recurrence generation — the spec named `moveTaskStatus` specifically as the hook point, and `moveAndReorderTask` wasn't in scope for this feature. A future feature (or a follow-up to F177) should decide whether drag-to-done on the board should also generate the next occurrence, and if so, factor the generation call into a shared helper both actions call, rather than duplicating the hook.
- **F178 (scheduled job)** is unaffected by this feature — it's a separate generation trigger (time-based, not completion-based) that will need the SAME idempotency guarantee this feature's unique constraint already provides; F178's worker can and should reuse `generateNextOccurrence` from `lib/recurrence/generate-next-occurrence.ts` directly rather than re-implementing the insert logic.
- **F179 (recurrence UI)** — setting/editing a task's `recurrence` rule from the UI remains out of scope here, unchanged from F175/F176's notes; this feature only consumes an already-set `recurrence` value.

## Autonomous decisions
AUTONOMOUS_DECISION: A recurring task with no `due_date` set generates nothing on completion (silent skip), since there is no calendar anchor to compute a next date from and the spec doesn't cover this edge case explicitly. Chosen over falling back to "today" as the anchor, because that would make the next occurrence's schedule depend on WHEN the task happens to be completed rather than the series' own due-date cadence — the simpler, no-second-source-of-truth option per this feature's ambiguity-resolution answer.
