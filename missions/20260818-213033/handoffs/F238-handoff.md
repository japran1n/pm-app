## Decisions made
- Inversion handling for a resize (this feature's own explicitly-flagged open decision, "clamp? refuse?"): CLAMP, not refuse. Dragging the start handle past the due date clamps the new start to the existing due date (collapsing to a one-day bar, never inverted); dragging the due handle before the start date clamps symmetrically. This guarantees `planTimelineBarResize` never returns a pair that could violate `tasks_start_date_not_after_due_date` (F236's DB CHECK, `supabase/migrations/20260828010000_tasks_start_date.sql`) — the UI never even attempts a write the database would reject, satisfying the spec's own "the UI must not be able to produce a rejected write" line. "Refuse" (a silent no-op past the boundary) was rejected as worse UX (the user's drag would appear to do nothing at all with no feedback) for no correctness benefit over clamping. Verified with a real integration test (`test_AS_454_a_resize_that_would_invert_the_bar_clamps_instead_of_producing_a_db_check_violation`) that the clamped write succeeds against the real DB.
- Whole-bar move can never invert by construction (both dates shift by the identical `deltaDays`, so duration — their difference — is invariant), so no clamping logic exists in `planTimelineBarMove` at all; only resize needed the clamp.
- Single-day marker tasks (F237's own AUTONOMOUS_DECISION: exactly one of start/due present, AS-452): dragging moves the one known date it has; there is no second edge to resize, so `planTimelineBarResize` returns `null` for a marker task rather than inventing a second-date behaviour. Verified with both a unit test and a real-DB integration test (`test_AS_454_a_marker_task_with_only_a_due_date_drags_its_one_date_and_leaves_start_date_null`).
- Both writes (move and resize) always send BOTH `startDate` and `dueDate` to `editTask` in one call (never a single-field partial update for a range bar), even though `editTask`'s Zod cross-field refine only enforces order when both fields are present in the same call. This means the DB CHECK's "only one field touched" fallback path (the `tasks_start_date_not_after_due_date` error-message mapping `editTask` already has, per F236's own doc comment) is never actually exercised by this feature's own writes — the clamp logic in `reschedule.ts` makes it structurally unreachable from this UI. That mapped error path remains defense-in-depth for any other future caller that DOES send a single field.
- Pixel-to-date conversion (the spec's own flagged "Notes for clarification" risk — "must round consistently at zoom boundaries or bars will drift by a day"): `pixelDeltaToDayDelta` uses `Math.round(deltaPx / pixelsPerDay)`, the simplest option with no new dependency — round-to-nearest rather than floor/ceil, so a drag slightly short of a full day-width still snaps to that day. Since this feature ships against F237's single fixed `DEFAULT_PIXELS_PER_DAY` (F240's own zoom-level seam, not yet built), there is no live "zoom boundary" to round inconsistently across yet; the function takes `pixelsPerDay` as an explicit parameter so F240 can vary it without this module changing.
- Interaction implementation: `@dnd-kit/core`'s `useDraggable` with a single shared `DndContext` (`TimelineBody`), delta-based (no droppable targets) — the timeline is a continuous pixel axis, not calendar's discrete per-day drop cells, so there's nothing to make droppable; the plan is derived purely from `event.delta.x` on drag end. Three separate draggable ids per range bar (`timeline-move:{id}`, `timeline-resize-start:{id}`, `timeline-resize-end:{id}`), one (`timeline-move:{id}` only) for a marker. Nested resize-handle `onPointerDown` calls `event.stopPropagation()` before invoking dnd-kit's own listener, so a pointer press on a resize handle activates only that handle's draggable, never both it and the enclosing whole-bar move draggable simultaneously.
- Keyboard alternative (Draft scope's own line): satisfied by dnd-kit's existing `KeyboardSensor` (the same sensor `CalendarDayGrid`/`board.tsx` already register) — no new code needed; any focused `useDraggable` region is keyboard-operable by dnd-kit's own default coordinate getter. No bespoke keyboard-shortcut UI was built beyond this, per "reuse existing primitives, not new parallel implementations."
- Access control: `canDrag` gates on the caller's WORKSPACE role only, via `canEditTask` (the exact predicate `editTask` itself re-checks server-side — AS-230's "one predicate backs both UI gating and the server-side re-check"), never a per-project precomputation — directly following `CalendarDayGrid`'s own established precedent for this identical "workspace-wide surface, permission varies per task's project" shape (F234's own doc comment was reused almost verbatim). A member who can edit tasks generally but lacks visibility into one specific task's private project still sees the bar as draggable; the drop is rejected by `editTask`'s own `isProjectVisibleToCaller` re-check (F322/F323's fix, reused unmodified) and rolled back with one toast — proven by the real-DB `test_AS_454_negative_...` integration test.
- Optimistic state + rollback: a small `Record<taskId, {startDate, dueDate}>` override map in `TimelineBody`, applied on top of the server-fetched `TimelineTask[]` props and recomputed through the SAME `computeBarLayout` (F237's pure layout function) every render — never a second layout computation. Exactly one `toast.error` fires on either an `ok:false` result or a thrown/rejected promise (`rolledBack` guard flag), matching `CalendarDayGrid`'s own convention precisely.
