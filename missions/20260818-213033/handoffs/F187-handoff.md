## Decisions made
- **Reused F186's exact per-task authorization pattern wholesale** (`loadBulkTaskAuthContexts`, one membership check per distinct workspace touched, one extra `project_members` query covering every private project in the call, `ok: true` with per-id `failedIds` for any forbidden/not-found task rather than `ok: false` for the whole call). This is explicitly what the feature spec and clarification instructed ("mirror F186's exact per-task auth pattern") — no independent design decision was made here, this is intentional parity, not a shortcut.
- **`canWrite`, not `canEditTask`, gates delete permission** — matches `deleteTask`'s own existing single-task permission gate exactly (see that function's doc comment: "any active role may delete, no per-task ownership check... `canEditTask` would additionally scope plain members to their own creations, which would regress AS-055"). `bulkDeleteTasks` had to make the same choice as `bulkUpdateTasks` did for `canEditTask` — picked `canWrite` specifically to stay consistent with the existing single-task delete's permission model rather than introducing a new one for the bulk path.
- **Cascade-to-children (AS-267/F149 parity) is a second batch UPDATE, not the single-task `cascade_delete_task` RPC, and does NOT stamp `deleted_via_task_id`.** Calling the RPC once per selected task would be a per-row loop of network calls, which this feature's Clarified performance-budget answer explicitly forbids. A single `UPDATE tasks SET deleted_at = :ts WHERE parent_task_id = ANY(:allowedIds) AND deleted_at IS NULL` covers every affected child of every deleted parent in the call in one statement, using the SAME `deletedAt` timestamp value as the parent UPDATE (computed once in JS, not two separate `now()` calls) so parent and child rows end up with an identical `deleted_at`. It deliberately does not set `deleted_via_task_id` (the future F189 restore feature's cascade-provenance marker) — the Supabase JS `.update()` builder can't express a per-row "set this column to that row's own `parent_task_id`" assignment without a new RPC/migration, which is outside this feature's Files scope (`lib/actions/tasks.ts`, `components/task/bulk-action-bar.tsx` only). Documented as a known partial-parity gap in the function's own doc comment and in Out-of-scope below, verified by `tests/integration/bulk-delete-tasks.test.ts`'s "cascades to a deleted task's live children in the same call" test (proves the child ends up soft-deleted; does not assert `deleted_via_task_id`, since this implementation intentionally doesn't set it).
- **Two independent UPDATE statements (parent batch, then child batch), not one transaction.** Same reasoning as the point above — a shared-transaction RPC is out of this feature's Files scope. This narrows, but does not eliminate, the crash-window risk `cascade_delete_task`'s own migration doc comment describes for the single-task path (a crash between the two UPDATEs could leave a deleted parent with a still-live child momentarily). Recorded as an explicit, deliberate scope trade-off rather than silently built to look fully atomic.
- **Confirmation dialog uses `AlertDialog` (components/ui/alert-dialog.tsx), not the plain `Dialog` `ArchiveProjectDialog` uses**, since `AlertDialog`'s existing `AlertDialogCancel`/`AlertDialogAction` split maps directly onto "Cancel" vs. the explicit destructive confirm action this feature needs, and the codebase already has this exact primitive wired up (no new dependency).
- **Wording: "Move N tasks to trash?" / "will be moved to trash, not permanently deleted"** — chosen directly from this feature's own Clarified implementation text ("Move 14 tasks to trash?" not "Delete 14 tasks?" — the wording matters), not left to interpretation.
- **`AlertDialogAction`'s `onClick` calls `event.preventDefault()` before running the mutation** — `AlertDialogAction` (unlike `AlertDialogCancel`) is a plain `Button`, not wrapped in `AlertDialogPrimitive.Close`, so it does not auto-close the dialog on click; `handleConfirm` closes it explicitly via `setOpen(false)` once the mutation settles (success, partial failure, or whole-call error), keeping the dialog open (with its `disabled`/spinner state) for the duration of the pending mutation — an intentional UX choice so the user sees "Moving to trash..." rather than the dialog vanishing before the toast appears.
- **Client-side failure-to-key resolution lives in `bulk-delete-action.tsx`, not the server action** — `bulkDeleteTasks` returns raw `failedIds: {id, reason}[]` (same shape as `bulkUpdateTasks`'s `failedIds`, a deliberate sibling-consistency choice), and the component resolves each failed id to a "PROJECTKEY-number" string via `formatTaskKey` (`lib/tasks/task-key.ts`, the one formatter for this) using the `selectedTasks` prop it already has in hand (the same rows the selection was made from) — no second server round trip needed to look up keys for the failures.

## Out-of-scope work needed
- **Cascade provenance (`deleted_via_task_id`) is not stamped for children cascaded via the bulk path** (see Decisions Made above). A future feature adding a `bulk_cascade_delete_tasks` Postgres RPC (mirroring `cascade_delete_task`'s SECURITY DEFINER pattern, but accepting an array of parent ids and doing the parent+child updates plus provenance stamping in one atomic transaction) would close this gap and also remove the two-statements-not-one-transaction risk noted above. Not done here because it requires a new migration, outside this feature's Files scope (`lib/actions/tasks.ts`, `components/task/bulk-action-bar.tsx`).
- **F189 (task restore from trash)**, when built, needs to be aware that a task cascade-deleted via THIS bulk path has `deleted_via_task_id = null` even though it was in fact deleted as a side effect of its parent — restoring such a parent will not auto-restore its cascaded children the way it would for a single-task `deleteTask` cascade. Flagged for whoever builds F189.
- **No UI surfaces the `failedIds` reasons themselves** (e.g. "you don't have access to this task's project" vs. "you don't have permission to delete this task") — the toast only names which tasks failed by key, not why. This mirrors F186's `<BulkStatusAction>` precedent exactly (that component's toast also only reports a count, not per-task reasons), so it is treated as consistent existing UX, not a new gap introduced here — but a future polish feature could surface per-task reasons in a richer failure summary (e.g. a small expandable list) if that's ever prioritized.
