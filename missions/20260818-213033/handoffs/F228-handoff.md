## Decisions made
- AUTONOMOUS_DECISION (F227 integrity gap, per the mission spec's "Known gap you must close"): `createSavedView` resolves the target project's REAL `workspace_id` via the admin client and REJECTS the write outright when the caller-supplied `workspaceId` disagrees (`WORKSPACE_MISMATCH_ERROR`), rather than silently deriving/overwriting it. Chose "reject" over "derive" because the spec explicitly asks for a test that "a forged mismatched pair is rejected" — an explicit, loud failure is also simply safer for an integrity bug like this (a caller who got the pair wrong should see an error, not have their input silently rewritten).
- AUTONOMOUS_DECISION: added `canManageSavedView` to `lib/auth/permissions.ts`, mirroring `canManageTemplate` exactly (creator-or-workspace-admin/owner). This is technically outside this feature's named "Files (approximate)" list, but the spec's own house-style instructions require reusing the single permissions module rather than re-deriving the same "creator or admin" rule a second time (this repo already has that exact rule for templates) — adding one predicate function to the existing single-source module is a much smaller deviation than duplicating the rule inline in lib/actions/views.ts.
- AUTONOMOUS_DECISION: "the user's default" (AS-431) is scoped to the VIEW'S OWNER, not the caller viewing a shared view. F227's unique index is `(owner_id, project_id) where is_default`, so `is_default` is intrinsically "is this the owner's chosen default view", not "is this the caller's chosen shared-view-to-treat-as-default". `setDefaultSavedView` therefore requires `view.ownerId === callerId` even for an admin who is otherwise allowed to edit/delete that same shared view (AS-430's admin exception does not extend to AS-431's default flag) — tested explicitly (`test_AS_431_only_a_shared_views_owner_can_set_it_as_their_own_default_not_an_admin`).
- AUTONOMOUS_DECISION: default-swap atomicity uses a new `set_saved_view_default(p_view_id)` SECURITY DEFINER RPC (supabase/migrations/20260827010000_saved_views_set_default_rpc.sql), granted only to `service_role`, called from the admin client AFTER the action has already re-verified ownership — same idiom as `reassign_and_delete_project_status` (F220). Two UPDATE statements (clear old default, set new one) inside one PL/pgSQL function is the only way to guarantee no window where either zero or two rows are `is_default = true` for the same (owner, project) pair, and to never surface a raw `23505` unique-violation to the app layer.
- AUTONOMOUS_DECISION (Clarified implementation's Notes: "URL params as the canonical state... do not introduce a parallel client store"): `lib/views/apply-view.ts` maps a saved view's config onto the SAME query-string keys the project list page's filter machinery already reads (`status`, `priority`, `assigneeId`, `sort`) rather than a serialized JSON blob param, so applying a view needs no new parsing machinery on the read side (F229's job) beyond calling `parseViewSearchParams`. Only `operator: "eq"` filters on the three known filterable fields, and the two existing `due_date_asc`/`due_date_desc` sort values, round-trip through the URL; anything outside that (not needed by any current assertion) is dropped rather than corrupting the URL. `groupBy` has no existing URL-backed reader yet (F226's board grouping is server-persisted per-user, not URL-driven) so it round-trips through its own `groupBy` param for F229 to consume.
- Chose the session-scoped, RLS-respecting client (`createClient()`) for every write where the caller is the view's own owner (create; owner-path update/delete), matching F227's documented RLS floor exactly and this repo's board-prefs.ts precedent — only the AS-430 "admin editing someone else's shared view" path uses `createAdminClient()`, and only after `canManageSavedView` has already been re-checked server-side, per the mission's "anything mutating through createAdminClient() bypasses RLS and MUST re-check authorization in application code" rule.
- No-op update (Clarified implementation #6): calling `updateSavedView` with no changed fields and no default-flag change returns `{ok: true, data: <current row>}` without issuing a write or an error, matching "a no-op returns ok without writing."
