## Decisions made
- **Verified end-to-end query wiring (the explicit ask in this feature's brief):** `getTaskDetail`'s task select previously did NOT include `description_json` (confirmed by reading the live select string before editing — only `description` was there). Added `description_json` to the select and mapped it to `task.descriptionJson` in the returned payload. `useTaskDetailSheet` (`components/task/use-task-detail-sheet.ts`) passes `detail.task` straight through with no field allowlisting, so `descriptionJson` reaches `TaskDetailSheet` with zero additional plumbing. This closes the exact "UI built but query never fed it real data" gap called out in F167's handoff for this same mission.
- **Sanitisation lives in `RichTextRenderer`'s module, not a separate file**, per the clarified spec's "the allow-list ... must be defined once and shared by editor, renderer, and any server-side projection" note and the "simpler option, no second source of truth" ambiguity-resolution rule — `sanitiseDocument`, `ALLOWED_NODE_TYPES`, `ALLOWED_MARK_TYPES`, and the link-protocol allow-list are all exported from `components/editor/rich-text-editor.tsx` so a future server-side projection (if one is ever added) can `import` the exact same constants rather than re-deriving them.
- **Two-layer defence, not just relying on `@tiptap/extension-link`'s own `isAllowedUri`:** the installed `@tiptap/extension-link` (bundled via `StarterKit.configure({ link })`, per F169) already strips disallowed-scheme hrefs at `renderHTML` time, but its DEFAULT allowed-protocol list includes `ftp`, `ftps`, `tel`, `callto`, `sms`, `cid`, `xmpp` — broader than the clarified spec's explicit "http/https/mailto only." Rather than trying to reconfigure Tiptap's `protocols`/`isAllowedUri` options (which only ADD to or narrowly override its allowlist, and don't get a chance to run before an unknown node type's `Node.fromJSON` could throw), `sanitiseDocument` rewrites the ENTIRE document — every node's `attrs` are rebuilt from an explicit per-type allowlist (only `heading.level` is copied through; nothing else) and every mark's `attrs` are rebuilt the same way (`link.href` only, re-validated against `/^(https?|mailto):/i` after stripping whitespace/control characters to defeat `java\tscript:`-style obfuscation). This also means an unknown node type like a fabricated `"script"` node is dropped BEFORE it ever reaches `editor.commands.setContent`/`useEditor({ content })` — ProseMirror's `Node.fromJSON` throws on unknown types, so sanitising first is also what keeps the renderer from crashing on hostile input instead of just failing to escape it.
- **Link `rel` is force-set to exactly `"noopener noreferrer"`** on every surviving link (not inherited from stored attrs), matching the clarified spec's literal wording. `target="_blank"` is also force-set (previously undefined) since an allow-listed http/https/mailto link opening in the current tab vs. a new tab isn't a security boundary — recorded here as the one attribute value chosen without an explicit spec answer.
- **UI placement for the rendered view:** the existing plain-text `Textarea` (backed by `EditTaskUpdates.description: string`) is left untouched as the ONLY edit control — wiring `RichTextEditor` into the actual write path is explicitly out of scope per F170's own handoff ("Wiring `RichTextEditor` into the task create/edit UI ... is F171's job for rendering [only]; a companion write-path feature ... needs to [[accept/validate/write JSON]]"). A read-only "Preview" block using `RichTextRenderer` was added directly below the Textarea, shown only when `descriptionJson` has non-empty `content`, so the plain edit surface remains the single empty-state UI and nothing duplicates or fights with it. This is the simplest option that satisfies "wire the task detail sheet to fetch and render description_json via this renderer" without redesigning the edit UX (which is a separate, not-yet-planned write-path feature per F170's Out-of-scope section).
- **`dynamic(..., { ssr: false })`** used for `RichTextRenderer` in `task-detail-sheet.tsx`, per F169's own doc comment on how any consumer must import it (Tiptap's `useEditor` touches the DOM; `TaskDetailSheet` is a Client Component but is still SSR-eligible for its initial HTML unless the Tiptap-backed piece is explicitly opted out).

## Notes for the next worker
- `sanitiseDocument(content: JSONContent | null | undefined): JSONContent` is exported from `components/editor/rich-text-editor.tsx` — import it, don't re-derive the allow-list, for any future server-side rendering/export of task descriptions.
- `ALLOWED_NODE_TYPES` currently covers everything `sharedExtensions()` (StarterKit) actually supports: doc, paragraph, text, heading, bulletList, orderedList, listItem, codeBlock, blockquote, hardBreak, horizontalRule. `ALLOWED_MARK_TYPES`: bold, italic, code, link, strike. If a future feature adds a new extension (e.g. Mention, TaskList — already installed per F169's Out-of-scope notes but not wired in), its node/mark type name must be added to these sets here or it will be silently dropped by the renderer even though the editor could otherwise interpret it.
- The "Preview" block only shows when `descriptionJson.content` is a non-empty array — a task whose only description is via the legacy plain `description` column but hasn't been touched since F170's migration will still show a single-paragraph `description_json` (F170's DB trigger backfills/derives it on every read of the row via the trigger's write-time derivation), so this should already cover virtually all existing tasks, not just newly-created ones.
- No MCP tools were needed for this feature (pure client-side rendering + one additional column in an existing select); `mcp-registry.md` confirms none required for a UI-only feature like this.
