## Decisions made
- **"Check what the mission-1 archive action actually writes before adding columns"** (the spec's own explicit ambiguity note): read `archiveProject` (lib/actions/projects.ts) and `lib/supabase/database.types.ts` directly. Confirmed `projects` has only `deleted_at` (set by `archiveProject`) — no `archived_at`, no actor-tracking column at all. Decision: do NOT add a duplicate `archived_at` — `deleted_at` already is the archive timestamp per this codebase's one soft-delete convention (tech-decisions.md), and a parallel `archived_at` would be exactly the "second source of truth" the clarification's ambiguity-resolution default forbids. Only `archived_by` was added, since nothing existing tracks "by whom."
- **Why not source "by whom" from `audit_log` instead of a new column**: `audit_log` (F139/F140) does record the actor for the `project.archived` action, but `writeAudit()`'s own header comment states writes are best-effort/non-fatal ("a failed audit write is logged via console.error and otherwise swallowed... not a precondition for it"). Relying on it as the sole source for AS-251 would make "by whom" silently absent on any RPC hiccup — not an acceptable reliability bar for an assertion this view must satisfy. `archived_by` is instead set atomically in the same `UPDATE` statement `archiveProject` uses to set `deleted_at`, guaranteeing it's present whenever the row exists and the migration is live.
- **Migration additive, not backfilled** (clarification Round B Q4, "additive first"): `archived_by` is nullable, no backfill attempted for projects archived before this column existed — there's no way to know who archived them. The archive page and query both handle a `null` `archivedByName` explicitly (renders "Archived <date>" with no "by ..." clause), not a fabricated value.
- **Sidebar access gate**: "gated to non-guests" was implemented by reusing the `isGuest` boolean already computed once in the workspace layout (`app/(workspace)/w/[workspaceSlug]/layout.tsx`, F135) and already threaded into `AppSidebar` — the exact same value and pattern that already gates the "Members" nav item. No new membership/role plumbing was added.
- **Page-level access gate**: the archive page itself independently redirects a guest who navigates to `/w/[workspaceSlug]/archive` directly (not just hides the sidebar link), mirroring the audit log page's (F141) `canViewAudit`-style "redirect away, not just hide UI" convention rather than inventing a new pattern. Any active non-guest role (member/admin/owner/viewer) can view the archive — the spec's access-control question doesn't distinguish further, and the clarified spec's default ("controls hidden/disabled via lib/auth/permissions.ts... the server still rejects the call") is about mutating controls; this page has none (read-only history, no "unarchive" action — see Out-of-scope).
- **Empty state**: this codebase has no single generic, reusable `<EmptyState>` component (`components/board/board-empty-state.tsx`, `components/nav`... — checked via `find -iname "*empty*"`); each view builds its own following one shared structural pattern (muted-circle icon, heading, one-line explanation). The archive page's empty state follows that same established pattern inline rather than inventing a new visual language or extracting a premature new shared component (which would be out of this feature's file scope).
- **Task counts**: the spec's "listing archived projects with task counts" is satisfied via one batched `tasks` query (`.in("project_id", projectIds).is("deleted_at", null)`) reduced in JS to per-project counts — not one query per row, per this feature's inherited "no N+1 queries" performance budget. Verified by `tests/integration/archive-view.test.ts`'s "(definition-of-done: performance)" test, which counts actual `fetch` calls made by `getArchivedWorkspaceProjects` and asserts it stays small regardless of archived-project count.
- **`archived_by` write/read resilience**: both the write side (`archiveProject`) and read side (`getArchivedWorkspaceProjects`) feature-detect the column's existence and fall back to a column-free query on failure, rather than assuming the migration is live. Initially checked only Postgres error code `42703` ("column does not exist"); the real error observed from a live `UPDATE`/`SELECT` against the actual schema cache was PostgREST's `PGRST204` ("Could not find the 'archived_by' column... in the schema cache") — caught by running the existing `tests/integration/archive-project.test.ts` suite, which regressed on the first version of this fallback and was fixed by also checking `PGRST204`. Both codes are now checked everywhere the column is touched.
