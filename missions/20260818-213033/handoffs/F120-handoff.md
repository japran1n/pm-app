## Decisions made
- **Shared-workspace visibility predicate as a reusable SQL helper** (per the feature's explicit note): added `public.shares_workspace_with(target_user_id uuid) returns boolean`, `SECURITY DEFINER`, mirroring the shape/grants of F012's `public.is_active_workspace_member` and F034's `public.is_project_workspace_member`. It self-joins `workspace_members` (caller side vs. target side) and returns true iff both have an *active* membership row in the same workspace. Future features (F203 mentions, members lists) should call this directly rather than re-deriving the join.
- **Predicate does not special-case self.** `shares_workspace_with` answers "do these two distinct users share a workspace" — it is not true for a user with zero workspaces checking themselves. The RLS SELECT policy instead ORs it with a separate `id = auth.uid()` clause (`profiles_select_self_or_shared_workspace`), so a brand-new user with no workspace yet can still read their own profile, and the helper stays a clean, reusable "shared workspace" check for callers (like F203) that don't want an implicit self-true case baked in.
- **`on_auth_user_created` trigger on `auth.users`** (`AFTER INSERT`, `SECURITY DEFINER`) is the standard Supabase pattern for AS-201's "no manual step" requirement — it fires regardless of how the user was created (password signup, magic link, OAuth, or `admin.createUser` as used in tests). Used `on conflict (id) do nothing` in the insert for idempotency safety, and a one-time backfill `insert ... select ... on conflict do nothing` for any auth.users rows that predate this migration.
- **Only `id`/`timezone` are populated by this feature; `display_name`/`avatar_url`/`color` stay nullable and empty.** F120's assigned assertions (AS-201, AS-208, AS-209, AS-210) only require the row to exist and be correctly access-controlled — populating those columns is explicitly owned by later features (F121 avatar-storage-bucket, F122 avatar-component, and whatever feature adds the "set display name" action for AS-202, none of which are in this feature's scope). Per the clarified spec's ambiguity rule, took the simpler option (no Server Action, no Zod schema in this feature) rather than speculatively building a profile-update action nothing yet calls — there is no client-writable path to those columns in this feature (RLS UPDATE policy exists and is tested, but nothing in `lib/actions/` invokes it yet), so a Zod schema would have no action layer to mirror.
- **No CHECK constraint on `timezone` or `display_name`.** The Draft scope only specifies `timezone text default 'UTC'` with no validity constraint; enforcing "valid IANA timezone string" belongs with whichever feature (AS-207) builds the timezone-setting Server Action, where a Zod schema with an IANA-name check is the natural place per the DB+Zod convention — adding a CHECK here without the corresponding Zod layer would be enforcement without the "mirrored in Zod" half of the same clarified answer.
- **RLS UPDATE test asserts "filtered, not errored"** rather than expecting a thrown error, matching the established pattern from `rls-tasks.test.ts`/`rls-comments.test.ts`: a Postgres UPDATE whose `USING`/`WITH CHECK` clause excludes the target row simply matches zero rows and returns `{ data: [], error: null }`, it does not raise. Verified the value was actually unchanged via a separate admin-client read, since "the API call succeeded with 0 rows" alone doesn't prove the row wasn't mutated by a different path.
- **No MCP Supabase tool calls were made** — `ToolSearch` for `mcp__supabase__list_tables`/`mcp__supabase__execute_sql` returned no matches (registry's "Pending approval" status held for this session), so schema application/verification went entirely through the Supabase CLI (`supabase db push --linked`, `supabase migration list --linked`, `supabase gen types typescript`) per `mcp-registry.md`'s "Never block a feature on MCP approval."

Followed the `create_comments.sql`/`rls_comments_delete_update.sql` precedent's own stated rationale ("both the schema and policies are small and this feature is scoped as one unit") — F120 is one feature covering all four pieces, unlike F011/F012 or F033/F034 which were split across two separate features in the plan.
AUTONOMOUS_DECISION: Named the helper `public.shares_workspace_with(target_user_id uuid)` rather than something profiles-specific (e.g. `can_view_profile`), since the spec explicitly says F203 (mentions) and members lists will reuse it — a generic "do these two users share a workspace" name keeps it usable outside the profiles-RLS context it was first written for.
AUTONOMOUS_DECISION: Did not add a CHECK constraint enforcing non-blank `display_name` (unlike `tasks.title`/`comments.text`/`projects.name` elsewhere in this schema) because no feature in scope here ever writes a non-null value to it — there is nothing yet to validate. The next feature that adds the display-name Server Action should add that CHECK alongside its own migration, per the "DB is the last line" convention, at the point where a write path actually exists.

## Notes for the next worker

Call it directly (`public.shares_workspace_with(some_user_id)`) rather than re-deriving the `workspace_members` self-join — this is exactly the function F203 (mentions) and any members-list feature should join through.
- The profiles RLS SELECT policy is `id = auth.uid() OR public.shares_workspace_with(id)` — remember the self-clause is separate from the helper; the helper alone returns false for a user with zero workspaces checking their own profile.
