## Decisions made
- **Reporter identity is an input parameter, not a global read.** Checked every existing capture module (`visible-tab.ts`, `crop.ts`, `store.ts`) — none of them read auth/session state; `Popup.tsx` already resolves the session itself via `createExtensionSupabaseClient().auth.getSession()` (F281/F282). `collectEnvironmentMetadata(reporter: ReporterIdentity)` follows the same split: it reads real `navigator`/`window`/`Intl` globals directly (matching how `visible-tab.ts` reads `window.devicePixelRatio`/`Date.now()` directly), but takes the already-known `{ id, email }` as a parameter rather than creating its own Supabase client or touching `chrome.storage`. A later feature that wires this into the popup capture flow passes the session it already has in React state.
- **Timestamp shape follows F124's literal convention**, read from `lib/time/user-timezone.ts` directly: never a pre-formatted local string, always an instant plus an explicit, identically-named `timeZone: string` field (not `timezone`, not a combined type) — same field name every function in `user-timezone.ts` uses. The instant itself (`capturedAt`) is `new Date().toISOString()` (ISO 8601 UTC string) rather than epoch ms, since that's the "instant" representation `lib/time/user-timezone.ts` accepts/returns elsewhere at its `Date`-typed boundaries (`startOfDayInTimeZone`/`endOfDayInTimeZone` return `Date`, which round-trips to ISO string). Note F283's own `capturedAt` field in `visible-tab.ts` is epoch-ms, not ISO — that field predates this feature and captures a different concept (a raw client-side sequencing timestamp, no timezone attached, not user-facing); this feature's `capturedAt` is deliberately the ISO+timeZone pair per F124's convention since it's meant to be read back and rendered later, which is exactly F124's stated reason for the convention.
- **`Intl.DateTimeFormat().resolvedOptions().timeZone` is read directly inside this module**, not passed in as an argument — unlike `lib/time/user-timezone.ts`'s pure functions (which always take `timeZone` as an explicit argument because some *other* layer already resolved it). This collector's whole job is to be the layer that resolves "what timezone is the reporter in right now" for the very first time; there's no earlier caller who could supply it.
- **Low-entropy, synchronous `navigator.userAgentData` fields only** (`brands`, `platform`) — not the async `getHighEntropyValues()` (which would be needed for a full dotted browser version or full OS version string). Per the clarification's "resolve open questions by taking the simpler, more private option, less data captured" instruction: `brands[].version` (a major/significant version) and `platform` (an OS name) satisfy AS-548's "browser and version, OS" wording without the extra async round trip or extra entropy `getHighEntropyValues()` exposes. Verified against MDN's `Navigator: userAgentData` page (low-entropy fields synchronous; high-entropy requires `getHighEntropyValues()`) and Chrome's User-Agent Reduction docs, both checked 2026-08-20.
- **Confirmed `navigator.userAgentData` is genuinely present in the Chromium extension popup context** — not assumed. `AS_548_reports_real_page_url_browser_os_viewport_and_device_pixel_ratio` asserts `hasUserAgentData === true` on the real, unstubbed popup page before asserting `source === "userAgentData"`, so the test would fail (not silently pass) if that assumption were wrong in a future Chromium version.
- **`source` field records which path was actually used** (`"userAgentData" | "userAgentParse" | "unknown"`) per the clarification's explicit instruction not to silently pick one and hide it.
- **"Unknown" convention: the literal string `"unknown"` everywhere**, not `null` — every field this module returns is naturally a `string` (browser name, OS name, version, IDs, email), so a single string sentinel keeps every field's type plain `string` rather than `string | null` on some and not others. `UNKNOWN` is exported as a named constant so a later caller can compare against it without a magic string.
- **Test harness for a not-yet-UI-wired module**: this feature's scope is exactly one file with no popup wiring (a later feature attaches it to the capture flow), so there's no `data-testid` button to drive. Rather than write a mocked-DOM unit test (this workspace has no vitest setup for the extension workspace at all — only Playwright), the test transpiles the real source file with the TypeScript compiler (already a devDependency) and loads the compiled module as a real `<script type="module">` inside the real, built, unpacked extension's popup page (same `launchExtension` harness every other spec uses) — so every assertion is against genuine, unstubbed `navigator`/`window`/`Intl` state in the actual Chromium extension context, not a simulation. The compiled file is written into `dist/` (not injected as an inline `<script>`) because the extension's own manifest CSP is `script-src 'self'`, which blocks inline script execution but permits scripts served from the extension's own origin; the test file is deleted in `afterAll`.
