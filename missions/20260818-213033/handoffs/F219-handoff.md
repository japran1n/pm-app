## Decisions made
- **Post-verification blocker fix (orchestrator-reported): project hard-delete cascade tripped the AS-415 guard.** The `project_statuses_prevent_last_delete` `BEFORE DELETE` trigger added by `20260824020000_project_statuses_management.sql` guards a genuine standalone column delete, but it also fired during `ON DELETE CASCADE` from `projects`: a project's `project_statuses` rows are deleted one at a time by the cascade, and on the LAST row `v_remaining` correctly computed 0 for the (now-being-destroyed) project — which is exactly what the guard was designed to reject, just for the wrong reason. The orchestrator reproduced this directly against the linked DB with the service-role client: seeding the default four columns then hard-deleting the project raised `{"code":"P0001","message":"A project must have at least one board column."}`, making project hard-delete impossible for every project (every project has >=1 column by construction). Fixed with an additive `create or replace function` migration (`20260824030000_project_statuses_cascade_delete_fix.sql`, the already-applied `20260824020000` file left untouched) that checks, at the top of the trigger function, whether the parent `projects` row still exists — if it doesn't, the delete arrived via the project's own `ON DELETE CASCADE` (Postgres removes the parent row before firing cascaded child deletes) and the trigger returns immediately without guarding; if the project row still exists, it's a genuine standalone column delete and the original zero-columns guard still applies. Proven by two new tests in `tests/integration/f219-status-management.test.ts`: a hard-delete-succeeds-and-cascades-columns-away regression test, and a standalone-last-column-delete-still-rejected regression test confirming the fix didn't weaken the real guard. Verified against a broad slice of every test file in the repo whose teardown hard-deletes a project (14 files, 155 tests, all passing) — see Commands run.
- **Critical known issue (tasks.status CHECK vs. custom column names)**: relaxed `tasks_status_check` (limited to the fixed four) to `tasks_status_not_empty` (`btrim(status) <> ''`) in the new migration. `tasks.status` stays live and populated (F223/F270 still own dropping it later) — this is the minimal additive fix that lets F218's `sync_task_status_and_status_id` trigger write a custom column's name into `tasks.status` without the old CHECK rejecting it. Proven end-to-end by this test file's "critical known issue" test: rename/add a custom-named column, insert a task with `status: <custom name>`, assert no error and that `status_id` was correctly derived by the trigger.
- **Consequence for a mission-1 test (AS-048)**: `tests/integration/tasks-schema.test.ts`'s `AS-048` test ("the database CHECK constraint rejects a status value outside the fixed set") asserted exactly the constraint this feature is required to relax — it is a mission-1 (`missions/20260817-230717`) assertion structurally superseded by mission-16's per-project custom columns. - **Reorder UI**: move-up/move-down buttons computing the new fractional-index position via the existing `lib/board/position.ts` `calculatePosition` (same function board card drag-and-drop uses), rather than adding a drag-and-drop library dependency for this one settings-page list — the "simpler option that adds no new dependency" resolution this feature's Clarified implementation specifies for open questions.
- **Colour palette (AS-526 open question)**: constrained the colour picker to `lib/board/column-colors.ts`'s `COLUMN_COLOR_PALETTE`, which reuses the exact hex values from `lib/task-colors.ts` (already contrast-checked >=3:1 on light backgrounds by F087/AS-154) rather than introducing a new colour space or a free colour input — no new contrast computation, no second source of truth.
- **Rename + colour/category as one action (`updateColumn`)** rather than three separate Server Actions, since the UI always submits all three fields together from one inline row and a single Zod-validated action is simpler with no loss of granularity.

## Notes for the next worker
