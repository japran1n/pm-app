## Decisions made
- **Optimistic placeholder shape**: `onOptimisticAdd` (new, optional prop on `QuickAdd`) is called synchronously, before `createTask` is awaited, with a `TaskCardTask` whose `id` is a client-generated `optimistic-<uuid>` string (via `crypto.randomUUID()`, the same primitive already used elsewhere in this codebase, e.g. `tests/integration/subtask-actions.test.ts`) and whose `position` comes from a module-level, always-decreasing counter (`nextOptimisticPosition`) so it always sorts to the bottom of the column and two rapid quick-adds never collide on position, without needing to know the column's real current max position.
- **Reconciliation on success** (`onCreated(task, tempId)`): `board.tsx`'s `handleTaskCreated` checks whether the real row is *already* present locally (`hasReal`) before deciding whether to append it or just drop the placeholder — this makes the merge correct regardless of whether the local `createTask()` promise or the Realtime INSERT echo resolves first.
- **Realtime-echo dedup (the spec's own "single most likely bug")**: rather than only relying on the eventual `hasReal` check in `handleTaskCreated` (which still allowed a *transient* duplicate card to render for a render pass or two if the Realtime INSERT arrived first — caught by my own test, not by chasing a hypothetical), `board.tsx` now keeps a `pendingOptimisticCreatesRef` (a ref, not state — pure bookkeeping for the Realtime callback, not something that should itself drive a render) of `{tempId, title, status}` for every still-unresolved optimistic placeholder. The `useBoardRealtime` callback checks this list on every INSERT event; a match (by title+status, first-match/FIFO) is spliced out of the pending list and the placeholder is removed from `tasks` *before* handing the event to `reconcileTask`, so the real row is inserted exactly once, synchronously, in the same `setTasks` pass — no transient duplicate at all, in either resolution order. `handleTaskCreated`/`handleCreateError` also remove the pending entry on their own paths, so a placeholder is never matched twice.
- **Failure handling**: kept F248's existing "clear + refocus happens right after the optimistic add, not after the network round trip" ordering for the happy path (AS-480 unchanged), but on failure the title is restored into the input (`setTitle((current) => current === "" ? trimmed : current)`) only if the user hasn't already started typing something new in the meantime — preserves F248's existing "actionable retry" contract (verified via the updated `tests/unit/f248-quick-add.test.tsx` failure-path test) without clobbering a second, unrelated in-flight quick-add's own typed text.
- **`QuickAdd`'s contract change**: `onCreated`/`onError` now take a second `tempId` argument. This is a breaking signature change from F248, but F248's own handoff explicitly flagged this exact seam ("F249 owns AS-481... left as a clean seam without any rework") — updated `board-column.tsx`/`swimlane.tsx`'s pass-through types and the one existing test (`f248-quick-add.test.tsx`) that asserted the old one-argument shape, rather than inventing a parallel/duplicate callback pair.
- **AUTONOMOUS_DECISION**: `onOptimisticAdd` is optional (not required) on `QuickAdd`, so a caller that hasn't been updated (none exist besides `board.tsx`, but this preserves the "no forced rewrite of every caller" convention the codebase already uses for every other optional prop on this component) falls back to F248's pre-existing non-optimistic behaviour rather than crashing.
- **AUTONOMOUS_DECISION**: title+status matching (not a stronger key) for the pending-placeholder-to-Realtime-event correlation, per the "simpler option, no second source of truth" clarification default — a truly robust idempotency-token approach would require plumbing a client-generated id through `createTask`'s own signature into the DB row itself, which is out of scope here and unnecessary: this board's own INSERT filter is already scoped to one project (`project_id=eq.<projectId>`), and within one project a title+status collision between two *simultaneously* in-flight optimistic creates is an edge case, not the common path this assertion is actually testing.

## Out-of-scope work needed
- The title+status matching heuristic above has a known theoretical gap: two genuinely simultaneous quick-adds with the *identical* title into the *same* column could have their Realtime INSERT echoes matched to the wrong placeholder (FIFO order, not per-request correlation). This never produces a duplicate or a lost card — worst case, the wrong-but-equally-valid placeholder gets replaced first, and the eventual `handleTaskCreated` `hasReal` check still converges to the correct final set of rows — but a truly airtight fix would need a client-generated idempotency token threaded through `createTask`'s params into the `tasks` row itself, which is a schema/action-signature change out of this feature's scope. Not fixed here; flagged for a future feature if it's ever observed as a real issue.
- Nothing else identified as out-of-scope — the spec's Files list (`quick-add.tsx`, `board.tsx`, `lib/board/reconcile-realtime-task.ts`) undersold the real wiring surface once F248's `board-column.tsx`/`swimlane.tsx` pass-through was accounted for (both needed their `onTaskCreated`/`onCreateError` types widened and a new `onTaskOptimisticAdd` prop threaded through); `lib/board/reconcile-realtime-task.ts` itself was NOT touched — the dedup logic lives entirely in `board.tsx`'s own Realtime callback (the pending-placeholder list), so `reconcileTask`'s existing pure, well-tested INSERT/UPDATE/DELETE behaviour for every OTHER caller (drag, another viewer's own creates) is completely unchanged.
