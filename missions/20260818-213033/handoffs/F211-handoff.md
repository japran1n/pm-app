## Decisions made
- **No SECURITY DEFINER RPC for writes** (unlike F206's `create_notification`): a preferences row is data a user directly owns and writes about themselves, so plain self-scoped RLS (`user_id = auth.uid()` on SELECT/INSERT/UPDATE, mirroring `profiles_update_self`) is enough — per the clarified "ambiguity resolution" answer (simpler option, no new dependency).
- **Defaults ("not spammy on day one", this feature's own Notes, the worker's call to make)**: `mention` and `task_assigned` (kinds that name/target the recipient specifically) default to `true` for both in-app and email. `comment_reply`, `watcher_update`, and `task_due_soon` (broader activity-stream kinds on something the user is already watching) default to `true` for in-app but `false` for email — watching is itself opt-in, so an in-app update is expected, but a new user's inbox shouldn't fill with email for every comment on every watched task. `email_enabled` (the master switch) defaults `true` — a user must explicitly opt out, matching AS-396's "turn email off" framing (an off switch to flip, not an on switch to seek out).
- **`task_due_soon_*` columns included now** even though F212 (the only producer of that kind) hasn't landed yet, so F212 has something to consult without a second migration — the feature spec's own "Files (approximate)" note plus F206's precedent of including `task_due_soon` in the `notifications.kind` CHECK constraint before any producer existed.
- **Digest boolean/digest_hour columns from the draft scope were deliberately NOT built.** No feature in this mission's currently-active plan consumes a digest schedule (F217, the digest scheduler, is `[SKIPPED]` along with the rest of the email chain), so adding those columns now would be speculative scope with no consumer — out-of-scope work, noted below, not built.
- **`filterRecipientsByInAppPreference` lives in a new `lib/notifications/preferences.ts`, not inside `fanout.ts`.** `fanout.ts`'s own doc comment explicitly declares it pure/no-I/O/no-Supabase-client; a real DB read to check a specific recipient's stored preference is a different concern (matching the split fanout.ts's comment already draws between "who qualifies" and "the actual write").
- **Fail-open on both "no preferences row" and "preferences read error."** A missing row should not normally happen (trigger + backfill), and a transient read failure degrading fan-out to "notify everyone" is safer than silently dropping legitimate recipients — mirrors every other non-fatal side-effect convention already established in these three call sites (comments.ts/tasks.ts/mentions.ts all wrap their fan-out in try/catch and log-don't-throw).
- **The settings form sends a partial per-toggle patch, not the whole row**, so two tabs open to the same settings page never clobber each other's unrelated toggle — `updateNotificationPreferencesSchema` is `.partial()` and the Server Action only builds an `upsert` payload from the keys actually present.
- **`upsert` (not `update`) on write**, defensively covering the edge case where a row somehow doesn't exist yet for the caller (RLS's `notification_preferences_insert_own` policy already allows a user to create their own row).
