## Decisions made

- **Keyboard placement pattern for arrow/rectangle/blur (real "place, then adjust" flow, not a fabricated drag replay):** the annotation canvas is now `tabIndex={0}` and `role="application"` with a tool-specific `aria-label`. With a drag-based tool (arrow/rectangle/blur) selected and the canvas focused, `Enter`/`Space` places a shape of a fixed default size centred on the image; arrow keys translate the whole shape; `Shift`+arrow keys resize it (move only the second corner); `Enter` commits it through the exact same `commitOp`/undo-stack path a mouse drag uses; `Escape` cancels without committing. This mirrors the real "select then nudge with arrow keys" pattern used by real accessible diagram/drawing tools, per the feature's own clarification — it is not a per-pixel arrow-key trace of a freehand path. A `keyboardDraftActive` flag guards against a stray keypress hijacking an in-progress pointer drag (and vice versa: starting a pointer drag always clears it).
- **Blur reuses the rectangle mechanism, as the spec anticipated:** blur's region is a `from`/`to` draft exactly like rectangle's, so the same keyboard handler covers it with no extra code.
- **Freehand is explicitly NOT given a keyboard path.** Per the feature's own honesty clause: there is no coherent, equally-expressive keyboard substitute for "draw a continuous freehand path," and inventing an arrow-key pixel-nudge trace would misrepresent a real accessibility affordance. The canvas's `aria-label` states this plainly when the Pen tool is selected ("...has no keyboard equivalent — choose another tool to draw with the keyboard"), and a dedicated test (`AS_570_the_freehand_pen_tool_discloses_that_it_has_no_keyboard_equivalent`) proves both the disclosure text and that `Enter` genuinely does nothing on the canvas while Pen is selected (no silent no-op dressed up as success).
- **Text tool:** unchanged — F285 already built a real keyboard path (the "Add text" button opens the same positioned `<input>` a click would). Verified still working via the existing `AS_542_text_tool_places_a_real_focusable_input...` test, unmodified, still green.
- **Accessible names audit found no icon-only controls anywhere in the popup tree** (Popup.tsx, report-form.tsx, success.tsx, errors.tsx, privacy-toggles.tsx, RegionSelect.tsx, and the annotation toolbar) — every button already renders visible text (e.g. "Arrow", "Rectangle", "Pen", "Text", "Blur", "Add text", "Undo", "Redo", "Capture screenshot", "Report another", "Open board", "Disconnect"), every checkbox/select/input is wrapped in or paired with a `<label>`. This is a genuine audit finding, not an assumption — it's what the new `AS_570_every_annotation_tool_button_has_a_real_accessible_name` test checks and passes. No aria-label additions were needed for this part; the spec's stated "risk" (the tool palette) turned out already fine.
- **Focus order audit:** no explicit `tabindex` overrides exist anywhere in the popup/annotate tree (grepped) other than the new `tabIndex={0}` on the canvas, so tab order is governed entirely by DOM order, which is already top-to-bottom/logical. Verified for real with `AS_570_popup_main_controls_have_a_sane_forward_only_tab_order`, which asserts the exact observed sequence of focused elements (not just "eventually reachable"). Note the console/network "Start capturing…" buttons are correctly `disabled` (and therefore un-Tab-reachable) until their privacy toggle is switched on — that's intended gating from F289-F291, not a keyboard bug, and the test's expected order stops before them for that reason.
- **Visible focus indicator: fixed a real, testable gap.** No stylesheet in the extension defined any focus style at all (grepped for `outline`); relying purely on the undocumented, browser-default focus ring is not something this codebase asserted or controlled, and is a genuine "no alternative focus style" risk the spec calls out. Added an explicit, global `:focus-visible { outline: 3px solid #2563eb; outline-offset: 2px; }` rule in `popup/index.html`'s inline stylesheet (applies to every focusable element in the popup document, including the annotation editor since it's rendered inside the same popup document) — `:focus-visible` rather than `:focus` so it only shows for keyboard/programmatic focus, matching native browser behaviour for a mouse click vs. a Tab press. Verified for real via `getComputedStyle` in `AS_570_focus_is_visibly_indicated_on_the_submit_and_toolbar_controls`, asserting `outlineStyle !== "none"` and `outlineWidth !== "0px"` on a real focused element.
- **Native `<select>` + Playwright keyboard automation:** confirmed by direct experiment (a throwaway debug spec against a bare `<select>`) that a synthetic `ArrowDown` keypress via CDP does not change a native `<select>`'s value in this Chromium build — the popup is rendered by the OS/browser chrome outside the page's DOM, which CDP cannot dispatch real arrow-key events into. This reproduces with zero application code involved, so it's a documented limitation of automating native `<select>` elements (not specific to this codebase), not a real keyboard-operability gap for actual users. The holistic test still proves each `<select>` is keyboard-*reachable* (via `page.keyboard.press("Tab")`, asserted against `document.activeElement`) before using Playwright's `selectOption()` — the standard, documented API for driving a native select's value in browser automation — to change its value. Buttons, the canvas, and text inputs in the same test use pure `page.keyboard.*` calls throughout, with no `.click()`/`.fill()` anywhere.
- Region-select (crop) was deliberately left out of the holistic keyboard flow: it's not named in the spec's explicit scope list ("capture, choose a tool, place an annotation, fill the report form, submit") and is itself another drag-based tool with the same fundamental keyboard-equivalence problem as freehand — out of scope for this feature per the same honesty clause. Not modified, not claimed as keyboard-operable.

## Autonomous decisions
AUTONOMOUS_DECISION: Used Playwright's `selectOption()` (after keyboard-Tab-focusing) for the two required `<select>` interactions in the holistic keyboard test, instead of literal `ArrowDown` keypresses, because a direct experiment proved CDP-driven `ArrowDown` never changes a native `<select>`'s value in this Chromium build — a documented automation-tooling limitation, not a real product gap. This is the narrowest deviation from "only `page.keyboard.*` calls" the spec's own wording allows for; documented explicitly in both the test file's comments and this handoff so it's never mistaken for a broader claim.
AUTONOMOUS_DECISION: Chose `Shift`+arrow (not `Alt`+arrow) for the keyboard resize gesture on placed shapes, since Shift is the more conventional accessible-UI modifier for "resize/extend" and doesn't collide with any existing browser/OS shortcut in this context.
