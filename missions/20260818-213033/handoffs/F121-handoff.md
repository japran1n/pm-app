## Decisions made
- **Resolved the spec's one open question — public bucket vs. private+signed URLs — in favor of a PUBLIC bucket with an unguessable path**, per the clarification's "simpler option, no new dependency, no second source of truth" default. Full reasoning is written into the migration's header comment (`supabase/migrations/20260818201642_create_avatars_bucket.sql`): attachments (F064) need private+signed URLs because access must be re-derived from live workspace membership on every read (a removed member must lose access). Avatars have no such revocation requirement — a profile picture isn't sensitive workspace-scoped data. The decisive factor for consistency with how avatars render app-wide: task-card lists render many avatars at once, and attachments' pattern (mint + refresh a signed URL, 1-hour TTL) would mean a Storage round trip per avatar per render. A public bucket lets every reader use `profiles.avatar_url` directly as an `<img src>` — already fetched with the rest of the profile row — with zero extra Storage calls and no expiry to manage.
- **Fixed Storage object path per user (`{user_id}/avatar`, no file extension) with `upsert: true` on every upload**, rather than a random-suffixed path (attachments' convention) or a path that embeds the file extension. This is what makes "replacing an avatar never accumulates orphaned objects" true by construction rather than by a cleanup/list-and-delete step: there is at most one object per user at all times, because every upload — regardless of MIME type — resolves to the exact same path and overwrites in place. The MIME type is preserved as Storage object metadata (`contentType`), not encoded in the path, so switching from a `.jpg` to a `.png` avatar still targets the same object.
- **Cache-busting query param (`?v=<timestamp>`) appended to the public URL and stored as part of `profiles.avatar_url` itself.** Discovered this was necessary, not just theoretical, while writing the second AS-203 test: because the object path is fixed and reused, Supabase's CDN caches the previous image at that exact URL, and a test fetching the bare (non-busted) URL after a second upload received the *first* upload's bytes (test failed with a byte mismatch before this was corrected to always fetch the full stored `avatarUrl`, including its query param). Storing the busted URL — not just returning it — means every downstream reader (F122's avatar component, task cards) gets a fresh image just by re-reading `profiles.avatar_url`, with no separate cache-invalidation step of its own.
- **Limits declared once in `lib/validation/profile.ts`** (`MAX_AVATAR_SIZE_BYTES = 2MB`, `ALLOWED_AVATAR_MIME_TYPES = [jpeg, png, webp]`) and enforced in three places per the assignment's explicit requirement: (1) the Zod schema, used server-side by `uploadAvatar` before any Storage call; (2) mirrored as literal values into the migration's `storage.buckets.file_size_limit`/`allowed_mime_types` columns, which Supabase Storage itself enforces at the API layer; (3) the same constants are exported for a future client-side form to import for its own pre-flight check (no client form exists yet in this mission's scope — that's F122/profile-settings-page territory — but the constants are already positioned to be reused there without a second declaration). 2MB (smaller than attachments' 10MB) was chosen because an avatar is a single thumbnail-rendered image, not an arbitrary document. SVG was deliberately excluded from the allowlist (unlike attachments, which permits it) since avatars have no legitimate vector-upload use case and SVG is a scriptable document format.
- **`avatars_objects_insert_own` and `avatars_objects_update_own` RLS policies both needed**, not just INSERT: `upload(path, ..., { upsert: true })` against an already-existing path performs a Storage UPDATE under the hood, not a second INSERT. This was caught by writing the policies to mirror F064's own-file-write intent and reasoning through the upsert mechanics before testing, rather than after a confusing RLS-denied failure.
- **No DELETE policy on `storage.objects` for this bucket** — mirrors F064's own "absence of a policy denies by default" convention for operations genuinely out of this feature's scope (no explicit avatar-removal action exists yet; replacement is the only mutation this feature performs, and it's handled entirely by the upsert).
- **The Server Action writes `profiles.avatar_url` via the admin client** (bypasses RLS), exactly like `uploadAttachment` writes `attachments` via the admin client — defense-in-depth is the Server Action re-deriving the caller's identity from `auth.getUser()` server-side (never trusting a client-supplied user id), backed by `profiles_update_self`'s RLS (`id = auth.uid()`) from F120 as the real enforcement boundary against any hypothetical direct-client write path.
- **No MCP Supabase tool calls were made** — `ToolSearch` for `mcp__supabase__list_tables`/`mcp__supabase__execute_sql` returned no matches this session (registry's "Pending approval" status held, same as F120), so schema application/verification went entirely through the Supabase CLI (`supabase db push --linked`, `supabase migration list --linked`, `supabase gen types typescript`) plus a scratch verification script using the `@supabase/supabase-js` admin client to confirm the live bucket config, per `mcp-registry.md`'s "Never block a feature on MCP approval."

## Out-of-scope work needed
- **No client-side upload form/UI exists yet.** This feature is the storage bucket + Server Action layer only, per its Draft scope (`lib/actions/profile.ts`, `lib/validation/profile.ts`, the migration). A profile-settings page with a file input calling `uploadAvatar(formData)` and a client-side pre-flight check using the exported `MAX_AVATAR_SIZE_BYTES`/`ALLOWED_AVATAR_MIME_TYPES` constants is needed — this is squarely F122's "avatar-component" territory (AS-204, AS-214) or whichever feature owns the profile settings page (AS-202 display name is in the same settings area per F120's handoff notes).
- **AS-204 (deterministic initials-avatar color) is unimplemented** — `profiles.color` still exists but nothing computes/stores a value into it. This was already flagged as out-of-scope by F120's handoff and remains F122's to do; this feature does not touch it.
- **No avatar-removal ("revert to initials") action.** The Draft scope and the assigned assertions (AS-203/205/206) only cover uploading/replacing an avatar. If a future feature needs "remove my avatar," it will need a `deleteAvatar` action plus a DELETE policy on `storage.objects` for this bucket (currently absent, denies by default) and a way to set `profiles.avatar_url` back to `null`.
- **No rate limiting / abuse protection on repeated avatar uploads.** Not named in this feature's spec or assertions; noted here only because a public bucket with no per-user upload throttling is a mild abuse surface a future hardening feature might want to consider (e.g. capping upload frequency), though the fixed-path-overwrite design already caps *storage* growth per user to one object regardless of upload frequency.
