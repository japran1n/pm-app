## Decisions made
- Overlay is one `<svg>` per timeline (not one per connector), per the Draft scope's explicit instruction and the clarified "simpler option, no second source of truth" default.
- Row/connector positions are computed with PURE maths (`computeTimelineRowPositions`/`computeDependencyConnectors`), not DOM measurement (`getBoundingClientRect`/`ResizeObserver`). `TimelineBody`'s render loop already computes each task's real `TimelineBarLayout` on every render (including mid-drag optimistic updates); this feature reuses that exact same computation (never a parallel one) and adds the one missing piece — vertical row position — as an equally pure function keyed off the same `groups` array the rows themselves render from. This keeps `DependencyOverlay` a Server Component (no client boundary needed at all for F239's own assertion) and means connectors recompute automatically whenever the page's own props change (scroll is pure CSS and doesn't move row order; a real layout change — reschedule, month nav — re-renders `TimelineBody` with fresh `groups`/`overrides` anyway).
- Made this possible by fixing the project-header row to a deterministic `h-10` (40px, matching `TimelineScale`'s own header height) instead of its previous `py-2`-sized variable height — a small, justified edit to `timeline-body.tsx` since without a fixed header height, connector vertical positions could not be computed purely.
- Query-layer leak fix (the feature's flagged sharp edge): `task_dependencies_select_active_members`'s current RLS policy (after the F322/F323-era `20260821140526_project_visibility_rls_sweep.sql`) only re-checks `is_task_visible_to(blocking_task_id)` — it does NOT check the blocked side. On its own, a caller could `SELECT` a `task_dependencies` row naming a `blocked_task_id` in a private project they cannot see. `getTimelineDependencyEdges` closes this at the application layer (the same "RLS + app-level re-check" posture F322/F323 themselves established): it takes `visibleTaskIds` — the caller's own already-visibility-filtered set (in practice, exactly what `getTimelineTasks` just returned) — and constrains BOTH `blocking_task_id` and `blocked_task_id` to that set via `.in()` twice. An edge whose other endpoint isn't in that set never leaves the database.
- AUTONOMOUS_DECISION: an invisible/off-screen/date-less dependency endpoint is rendered as **nothing** — omitted entirely, not an anonymous stub/arrow-into-nowhere. The spec's own Draft-scope notes floated "degrade to edge marker" for off-screen partners, but given a single query already constrains both endpoints to the caller's fully-visible set, there is no case where the code KNOWS an edge exists but only one endpoint is drawable without ALSO knowing something about the other side that the leak-safety design intentionally never learns. Adding a distinct "stub marker" rendering path would require either (a) a second, less-safe query that fetches edges with only one constrained endpoint (reopening exactly the leak this feature's own leak test proves closed), or (b) a marker drawn from no real data at all (decorative noise). The simpler, zero-new-dependency, zero-second-source-of-truth choice — per the clarified ambiguity-resolution default — is: an edge with an unknown endpoint is invisible, full stop. This is documented behaviour for the DoD's "endpoint outside the visible range / filtered out / date-less" requirement: all three cases collapse to the identical "connector omitted" rule, proven by `test_AS_455_negative_a_date_less_endpoint_with_no_bar_layout_is_omitted` and `test_AS_455_negative_an_endpoint_with_no_known_row_position_is_omitted_not_drawn_toward_nowhere`.
- `page.tsx` passes `tasks.map(t => t.id)` (the full RLS+visibility-filtered result, before the `placeable` date filter) as `visibleTaskIds`, not just the rendered `placeable` subset — costs nothing extra (same array, no second query) and stays correct: a date-less task's edge is still correctly omitted downstream in `TimelineBody`/`computeDependencyConnectors` because it has no row position, never because it was pre-filtered out of the query's own safety boundary.

- **DB-level fix (post-review, same family as F322/F323):** `task_dependencies_select_active_members` and `task_dependencies_delete_active_members` (both from `20260821140526_project_visibility_rls_sweep.sql`) only ever re-checked `is_task_visible_to(blocking_task_id)` — the SAME migration's own INSERT policy already required BOTH sides (`is_task_visible_to(blocking_task_id) and is_task_visible_to(blocked_task_id)`), which is the proof this was an oversight, not a deliberate asymmetry. Consequences: (1) a read leak my original app-level `.in()` fix in `getTimelineDependencyEdges` only protected for the timeline's own call site, and (2) a WRITE-side privilege escalation via the DELETE policy — a caller who can see only the blocking task could actually DELETE a dependency row whose blocked task sits in a private project they cannot see. (2) was NOT caught or reported in my original handoff; the orchestrator's review caught it. Fixed with a new migration (`supabase/migrations/20260828020000_task_dependencies_two_sided_visibility.sql`, applied via `npx supabase db push --linked`) that recreates both policies with the two-sided check, matching INSERT exactly. `is_task_visible_to()` itself is unchanged — no new predicate function, only the two policies' `using` clauses widened.
- **Fallout audit (every real reader/writer of `task_dependencies`), performed after the migration:**
  - `lib/actions/dependencies.ts`'s `createDependency`/`deleteDependency`: both already independently re-check membership via `requireActiveMembership` and resolve both tasks through the ADMIN client for their own lookups/error messages BEFORE the real RLS-scoped insert/delete. Neither function's own success path changes for a caller who could already see both tasks (the only case either action's own UI ever offers a dependency for). A caller who could see only the blocking side and somehow attempted a DELETE against a row with an invisible blocked side now correctly gets 0 rows affected instead of a silent delete — `deleteDependency`'s existing "not found"-style handling already covers a 0-row delete gracefully (confirmed by `tests/integration/dependency-ui-actions.test.ts` and `tests/integration/dependency-cycle.test.ts` passing unchanged, 0 regressions).
  - `getDependencyCandidates` (same file): calls `get_dependency_ancestors`/`get_dependency_descendants` (both `language sql stable`, explicitly NOT `security definer` per their own migration's header comment) and reads `task_dependencies` THROUGH THE ADMIN CLIENT, which bypasses RLS by design (the admin/service-role client bypasses RLS regardless of the called function's own security context) — unrelated to and unaffected by this policy fix. Flagged as a separate, pre-existing, out-of-scope condition below (not touched by this feature — F323 already independently filters this function's own RETURNED candidates by `isProjectVisibleToCaller` before they reach the client, so the admin-client read itself doesn't currently leak anything to the end user; it's a defense-in-depth gap, not a live leak).
  - `lib/actions/tasks.ts`'s `getOpenBlockers` / the board's open-blocker-count path: reads `task_dependencies` through the ADMIN CLIENT (confirmed by reading the function directly — `const admin = createAdminClient();` then `admin.from("task_dependencies")...`), with its own explicit `isProjectVisibleToCaller` re-check before returning data. Unaffected by an RLS policy that only the plain session client is ever subject to. `tests/integration/open-blockers.test.ts` passes unchanged.
  - The board RPC (`get_project_board_tasks` and its column-adding siblings): confirmed by grep that no board RPC migration selects from `task_dependencies` at all — open-blocker counting happens in TypeScript via `getOpenBlockers`, not inside the board RPC. `tests/integration/f224-board-swimlane-grouping.test.ts`, `board-reload-persistence.test.ts`, `trash-exclusion-board.test.ts`, and `board-tasks-completion.test.ts` all pass unchanged, standing in as the closest real board-surface coverage.
  - `lib/queries/timeline.ts`'s `getTimelineDependencyEdges` (this feature's own): already ran through the plain RLS-scoped session client and already independently constrained both endpoints via `.in()` — this DB-level fix makes that app-level constraint strictly redundant for this one call site, kept deliberately as defense in depth per the orchestrator's explicit instruction.
