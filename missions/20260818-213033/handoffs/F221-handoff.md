## Decisions made
- **Backward-compatible `columns` prop, not a breaking retype**: `Board` gained an optional `columns?: BoardColumnDef[]` prop; when omitted it falls back to `DEFAULT_COLUMNS` (the original fixed four, built from `STATUS_COLORS`/the enum). The real board page (`.../board/page.tsx`) always passes real `project_statuses` rows via the new `getProjectColumns` query. This means every existing test that renders `<Board>` without a `columns` prop keeps rendering exactly as before F221 (zero of the 8 pre-existing board test files needed a rewrite for this), while a real viewer always sees the project's actual columns — matches the Clarified implementation's "no second source of truth" resolution: one rendering code path, real data layered on top via an optional prop rather than a parallel component.
- **`BoardColumn` gained optional `label`/`color` props, `status` stayed the match/droppable key**: a real column's `name` doubles as both the value written into `tasks.status` (matching F218/F219's own `(project_id, name)` convention — a column's name and its `tasks.status` value are the same string by design) AND, via the new `label` prop, its own display text. `label`/`color` default to the existing `STATUS_LABELS`/`STATUS_COLORS` lookups when omitted, so a column literally named `"todo"` (every unrenamed default column, per `20260824010000_project_statuses.sql`'s seed data) still displays "To Do" — satisfying AS-407 ("a new project starts with the default four columns, matching the previous behaviour") without a second label table.
- **`over.id as TaskCardTask["status"]` cast for a real column name**, `lib/queries/tasks.ts`'s own `status: task.status as TaskCardTask["status"]` cast — TaskCardTask's `status` field stays narrowly typed as the original 4-value union (widening it app-wide is F223's job, per F218/F219's own stated boundary; it's read in ~17 files outside this feature's scope: list view, dashboard chart, filters, activity feed, etc.). This feature only widens what the BOARD write path (`moveTaskStatus`/`moveAndReorderTask`) accepts and validates — every other reader of `TaskCardTask.status` is untouched, matching the Draft scope's file list.
- **Zod schemas relaxed from `z.enum([...4 values])` to `z.string().trim().min(1).max(100)`**, mirroring F219's `tasks_status_not_empty` DB relaxation (100-char cap matches the column-name length already enforced by `lib/validation/statuses.ts`'s `addColumnSchema`). The REAL guard against a forged/stale column name isn't the Zod schema (which can't know a project's columns) — it's a new `project_statuses` lookup added to both `moveTaskStatus` and `moveAndReorderTask`, keyed on `(project_id, name)`, the same pair F218's `sync_task_status_and_status_id` trigger already keys off. Without this check, an unmatched name would silently leave `status_id` null (the trigger's `select into` finds no row and doesn't raise) — this app-layer check turns that into a clean, actionable "That column no longer exists. Refresh the board and try again." error instead.
- **Realtime**: new dedicated `board-columns:<projectId>` channel/table/reconciler, deliberately separate from the existing `board:<projectId>` tasks channel (a column-only reconnect never has to resubscribe to task events and vice versa) — same "plain function + thin hook wrapper" split as F049's `subscribe-board-realtime.ts`/`use-board-realtime.ts`. `project_statuses` needed `REPLICA IDENTITY FULL` added (new migration) for the same reason `comment_reactions` did (F305/AS-369's fix, `20260823080000_...sql`): its primary key is just `id`, so a DELETE payload's OLD row wouldn't otherwise carry `project_id`, and the `filter: project_id=eq.<projectId>` server-side row filter — which does NOT go through RLS for DELETE payloads — is the real, only, anti-leak boundary for a column-removal event. Documented at length in the migration's own comment.
- **`DEFAULT_COLUMNS`' `position` values use the same 1000-step convention** every other seeded/computed position in this codebase uses (F218's seed data, `create_project_from_template`'s `v_position`).

AUTONOMOUS_DECISION: `BoardColumn`'s `label`/`color` props are optional with a fallback to the existing fixed lookups (rather than required), and `Board`'s `columns` prop is optional with a `DEFAULT_COLUMNS` fallback (rather than required) — chosen specifically so the 8 pre-existing board unit test files needed zero changes (only 1, `board-column-counts.test.ts`, needed updating, and only because it does a source-level regex match against board.tsx's literal render-loop text, which legitimately changed).
