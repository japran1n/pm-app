## Decisions made
- AUTONOMOUS_DECISION: this feature wires saved views into the **List** view only (`view_type: "list"`), not Board. `lib/views/apply-view.ts` (F228) already documented that Board's grouping is server-persisted per-user (F226's `board-prefs.ts`), not URL-driven, so there is no existing "apply a config to the board via the URL" seam to hook into without inventing one — and the assigned assertions (AS-429/432/433) don't require a specific `view_type`. Wiring Board is flagged below as Out-of-scope rather than done partially/inconsistently.
- AUTONOMOUS_DECISION: the shareable URL contract is `?viewId=<uuid>` on the List page itself, NOT the filter-param encoding (`?status=...&sort=...`) `apply-view.ts`'s `buildViewSearchParams` produces. Rationale: `buildViewSearchParams`'s encoding is lossy by design (drops anything outside 3 filter fields/1 sort field) and re-decoding a URL's OWN params can't distinguish "this filter was never set" from "this filter was dropped for AS-433 reasons" — whereas resolving from the SAVED CONFIG (via `getSavedView` + `resolveListViewFilters`) gets the real row, re-enforces AS-429/AS-434 via `saved_views`' own SELECT RLS on every open (not just at save time), and lets the page compute and show a per-open drop count. `apply-view.ts`'s `parseViewSearchParams` is still reused as-is by `save-view-dialog.tsx` to capture the CURRENT url's filters into a new view's `config` at save time — that's the direction it was built for.
- AUTONOMOUS_DECISION: dangling-reference classes enumerated for AS-433, and how each is handled — this is the answer the spec explicitly asked to be spelled out in the handoff:
  1. **Deleted `project_statuses` row** (e.g. via F220's reassign-and-delete): a `status` filter naming a column name no longer in the project's CURRENT `project_statuses` set is dropped by `resolveListViewFilters`, validated against the same `validStatusNames` set the page already builds for its own `<ListFilters>` dropdown — no second source of truth. Proven against a real DB row deleted mid-test (`test_AS_433_a_view_referencing_a_since_deleted_status_still_opens_and_returns_tasks`).
  2. **Removed workspace member**: an `assigneeId` filter naming a user no longer in `workspaceMembers.active` (this codebase's real `removeMember` action hard-deletes the `workspace_members` row via the `remove_workspace_member` RPC — verified by reading `lib/actions/workspaces.ts`) is dropped the same way, validated against `validAssigneeIds`. Proven against a real deleted membership row (`test_AS_433_a_view_referencing_a_removed_workspace_member_still_opens_and_returns_tasks`).
  3. **Unrecognised sort field/direction**: dropped by `resolveListViewFilters`, falling back to the page's existing default order — same "tampered/stale param = ignored" posture the List page's own `sort` handling already uses for URL params (F055). Proven in `tests/unit/resolve-view.test.ts`.
  4. **The view's own project deleted, or the view no longer visible to its owner/the project turned private and the caller lost access**: NOT this module's concern — caught upstream by `getSavedView`'s RLS-scoped read (F227's SELECT policy), which resolves to a plain `ok:false` / "View not found." never a thrown error. The List page treats that exactly like "no viewId at all," which is itself "degrading gracefully instead of erroring" for that dangling-reference class. A deleted *tag* class does not apply here since the List page has no tag filter today (only Board's swimlane grouping reads tags, and Board is out of scope per the decision above).
- AUTONOMOUS_DECISION: AS-431's "auto-apply the user's default view on project open" is implemented as a server-side `redirect()` inside the List page's Server Component, guarded by "no `viewId` AND no filter/sort param present at all" (not just "no `viewId`") — this both prevents ever overriding an explicit bookmarked/shared filtered URL with the default, and makes the redirect provably non-looping (the redirect target always carries `viewId`, which fails the guard on the next render). Proven at the `getMyDefaultSavedView` read-path level (`test_AS_431_getMyDefaultSavedView_resolves_the_callers_own_default_for_this_project`); the redirect wiring itself is a thin, un-mockable `redirect()` call in a Server Component, consistent with this repo's existing untested-Server-Component-redirect pattern elsewhere (no vitest DOM harness exercises real Next.js redirects in this codebase).
- AUTONOMOUS_DECISION: the View Switcher's delete/set-default controls are only rendered for the caller's OWN views (`view.isMine`), even though `deleteSavedView`/`updateSavedView` (F228) support an admin managing someone else's SHARED view (AS-430). This is a UI-gating choice, not a security one — AS-430's real enforcement is server-side in `lib/actions/views.ts` (F228, unmodified) and is exercised by F228's own tests; adding an admin-override affordance to this dropdown was out of this feature's assigned assertions (AS-429/432/433) and is flagged below as optional follow-up UI polish, not a gap in AS-430's own coverage.
