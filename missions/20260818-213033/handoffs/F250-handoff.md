## Decisions made
- Extended, did not fork: `ListStatusSelect` (F057) is untouched. The three new fields each got their own small Client Component cell, matching this file's existing "one Client Component cell per editable field" convention (ListStatusSelect itself) rather than one large combined inline-cell component.
- AUTONOMOUS_DECISION (per this feature's "Notes for clarification" — simpler option, no new dependency): "one inline-cell abstraction shared by all four field types" is satisfied by factoring the optimistic-commit/rollback/toast logic (not the rendered markup, which differs — Select vs. native date input vs. popover — by design) into `lib/hooks/use-inline-field-edit.ts`, used by the new priority and due-date cells. Status keeps its own pre-existing, independently-tested copy of the same shape rather than being retrofitted onto the hook (retrofitting it risked regressing F106/F223's passing tests for zero behavioural gain); assignee is a *set* mutation (add/remove), not a scalar commit, so it hand-writes the same optimistic/rollback/toast shape directly (mirroring TagsEditor's `persist`) rather than being forced through a scalar-typed hook. This is recorded rather than silently deviating from the spec's literal wording.
- Priority: reuses `editTask({ priority })`, exactly the same call the task detail sheet's own Priority Select already makes.
- Due date: reuses `editTask({ dueDate })`, exactly the same call the task detail sheet's own due-date `<input type="date">` already makes. Kept the existing overdue icon/`sr-only` text alongside the input (derived from `task.status`, not something the date field itself owns).
- Assignee: reuses `setTaskAssignees(taskId, nextIds)`, the same Server Action + full-next-set convention `addTaskAssignee`/`removeTaskAssignee`/the detail sheet's own multi-select already use. The popover markup/keyboard shape (focusable trigger button + focusable, checkable member rows) is copied from the task detail sheet's existing Assignees control rather than invented fresh, per the clarification's "reuse existing primitives" answer. Uses the `members` prop `TaskListTable` already threads through for the detail sheet — no new query, no N+1 (perf budget honoured).
- Escape (AS-487): the due-date input does NOT handle Escape with a local `stopPropagation`/`preventDefault` — it registers itself as an F244 escape layer (`useEscapeLayer`) ONLY while the field is dirty (`localValue !== committedValue`), so pressing Escape while mid-edit reverts exactly that field via the SAME `popTopEscapeLayer()` mechanism the global shortcut provider already calls, and the field never occupies the stack (and therefore never swallows an unrelated Escape, e.g. for a genuinely open dialog) once it's clean. `Select`/`Popover`-based cells (priority, status, assignee) rely on Base UI's own built-in Escape-closes-popup behavior, same as the pre-existing status cell — no new escape-layer registration needed there.
- Duplicate-commit guard: `useInlineFieldEdit`'s `commit()` is called from both an Enter keydown (which then `.blur()`s the field, itself firing `onBlur`, which also calls `commit()`) and from a plain blur alone. A pending-value ref inside the hook makes the second call for the same in-flight value a no-op rather than firing the Server Action twice — caught and fixed during implementation by inspection, not by a failing test (a race-condition regression here wouldn't reliably repro in jsdom's synchronous event dispatch, so this is a code-review-level guarantee, not a test-covered one; flagged for anyone auditing this file).
- `committedValue`/`isSaving` etc. are tracked as component **state**, not refs, inside `useInlineFieldEdit` — an initial ref-based draft tripped the `react-hooks/refs` "cannot access refs during render" ESLint rule (the hook's return statement reads the value during render). Refs are still used, but only for the commit-in-flight de-dupe guard, which is read/written exclusively inside the async `commit()` callback, never during render.
