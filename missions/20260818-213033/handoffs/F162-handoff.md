## Decisions made
- **Dedup strategy: filter `tasks.id IN (task ids matching any selected assignee)`, computed via a separate `task_assignees` query, not an embedded/inner join between `tasks` and `task_assignees`.** An embedded join (`tasks.select("...,task_assignees!inner(...)")` with `.in("task_assignees.user_id", ids)`) would fan out one row per matching assignee — a task assigned to both selected people would come back twice, which is exactly the bug AS-291 forbids. The two-step approach (`task_assignees.select("task_id").in("user_id", ids)` → dedupe with `Set` → `tasks.in("id", taskIds)`) guarantees exactly one row per matching task by construction, since the outer query filters by primary-key membership, not by a join that can multiply rows. No new dependency, no RPC/migration needed — reuses the existing RLS-scoped `task_assignees` table and the existing `.in()` builder method already used elsewhere in this file.
- **`assigneeId` filter type widened from `string` to `string | string[]`, not renamed/split into a new field.** Keeps `<ListFilters>` (still single-select at the UI layer today — see Out-of-scope below) and every existing caller (`app/.../list/page.tsx`, `components/dashboard/dashboard-task-table.tsx`) working unchanged with a bare string, while `getProjectListTasks`/`getWorkspaceListTasks` and their tests can now also pass an array. Simpler option per the ambiguity-resolution default: no second filter field, no second source of truth for "which assignee(s)."
- **Board view: no filter change made.** Grepped `components/board/*.tsx` and found no `<ListFilters>` usage and no `assigneeId` filter parameter anywhere in the board's data path (`getProjectBoardTasks` takes only a `projectId`, no `filters` argument) — the board view has no assignee-filter UI or query parameter to begin with, only per-card assignee *display* (avatars). The feature spec's "board filters" line is therefore a no-op for this codebase's current state; documented here rather than inventing new board-filter UI/query plumbing that isn't named as this feature's own scope.
- **Existing `AS-088`/`AS-134` single-assignee-filter test fixtures updated to also seed a matching `task_assignees` row**, not just the legacy `assignee_id` column. Necessary because those pre-existing tests seed tasks via a raw `adminClient.from("tasks").insert({ assignee_id: ... })`, which — unlike the real app's `setTaskAssigneesCore` write path (F160) — does NOT also write a `task_assignees` row (there is no DB trigger keeping them in sync; F159/F160's mirror guarantee is application-code-only, inside the Server Action layer). Since the filter now reads exclusively from `task_assignees` (per this feature's own "nothing reads `tasks.assignee_id`" resolution below), the raw-insert fixtures needed the same `task_assignees` row a real assignment would produce, or the pre-existing single-assignee-filter assertions would have started failing for a reason unrelated to their own behaviour.
- **"After this feature, nothing reads `tasks.assignee_id`" (spec's open question) — confirmed true for the three filter query functions.** `getProjectListTasks`/`getWorkspaceListTasks`'s filter logic (this feature's scope) no longer references `assignee_id` at all. Note this is scoped to *filtering* specifically — both functions still *select and return* `assignee_id` (`assigneeId: task.assignee_id` in the mapped output) for other unrelated purposes (the deprecated single-assignee display fallback F161 is wiring into `assigneeIds`'s empty-array case elsewhere) — that display-layer read is F161's concern, not this feature's, and out of this feature's Files scope.

## Out-of-scope work needed
- **Board view has no assignee-filter UI or query parameter at all** (see Decisions made above) — if/when a board filter bar is added, it should reuse `getProjectBoardTasks` + a `filters` argument following the same `filterTaskIdsByAnyAssignee`-style dedup this feature established for list/dashboard, but that's a new UI feature (a board filter bar doesn't exist to wire into), not something this feature's spec's "Files" list actually names in the board's code path.
- **`<ListFilters>` (`components/task/list-filters.tsx`) is still a single-select assignee `<Select>`, not a multi-select.** The query layer now supports an array (this feature's actual deliverable, which is what AS-291's "match any" and "no duplicates" behaviour concretely requires and is what's tested), but no UI currently constructs an array — `?assigneeId=` in the URL is still one value. A future feature that wants a genuine multi-select assignee filter chip/combobox in the UI can pass `searchParams.getAll("assigneeId")` or similar straight into the now-array-capable `filters.assigneeId` with no further query-layer changes needed.
- **Dropping `tasks.assignee_id` entirely** remains explicitly out of scope per this mission's migration-safety convention (additive first, drop only in the dedicated cleanup feature F270) and per F160's own prior handoff note — unchanged by this feature.
