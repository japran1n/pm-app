## Decisions made

- **Closed the known gap first, exactly as instructed, with a dedicated migration.** Added `checklist_items_update_active_members` (UPDATE) and `checklist_items_delete_active_members` (DELETE) in `supabase/migrations/20260819080358_checklist_items_update_delete_policies.sql`, scoped through the SAME `public.is_task_workspace_member(task_id)` helper F151's SELECT/INSERT policies already use — no new RLS function. Shape mirrors `tasks_update_active_members` (`20260818013805_rls_tasks.sql`): any active workspace member, no per-item author/ownership restriction, per F151's own handoff calling this out as the expected shape ("checklist items are task-owned state, not user-authored content like a comment").

- **Deliberately did NOT use `createAdminClient()` for the actual checklist_items mutations, diverging from every other action file in this codebase (comments.ts, tasks.ts, attachments.ts, projects.ts, time-entries.ts, profile.ts all use the admin client for their real writes).** This was an explicit instruction for this feature specifically: the admin client bypasses RLS, so using it for the write would have made the newly-added UPDATE/DELETE policies untested by construction (an admin-client write would succeed regardless of whether the policies were correct, present, or even `using (true)`). Every mutation in `lib/actions/checklist.ts` (insert/update/delete) goes through the request-scoped, RLS-respecting client from `lib/supabase/server.ts` — whose own header comment already says "the client used by application logic; RLS is the authorization boundary". `createAdminClient()` is still used in this file, but ONLY for read-only lookups (resolving a task's or item's real owning workspace, for accurate "not found" vs "permission denied" messaging) and for `requireActiveMembership`'s own check — never for the mutation itself. `requireActiveMembership` (`lib/auth/require-membership.ts`, the pre-F127 membership-guard convention `comments.ts` already established) remains the second line of defense-in-depth on top of RLS, per the Clarified implementation's Access control answer.

- **`toggleChecklistItem`'s `isChecked` parameter is the explicit TARGET state, not "flip the current value."** This makes repeated calls with the same value idempotent-safe (the no-op branch: "a no-op returns ok without writing" per the Clarified implementation's empty/zero-state answer) and keeps the client's optimistic guess and the server's write always talking about the same value rather than racing on "what is it right now."

- **`checked_by`/`checked_at` are set/cleared from server-verified data only.** Checking an item stamps the caller's own `user.id` (from `auth.getUser()`) and the current server time; unchecking clears both to `null`. Neither is ever accepted from client input — this wasn't explicitly required by the assigned assertions, but it's the only sensible interpretation of what those two columns (added by F151, unused until now) are for, and leaving them silently unset while flipping `is_checked` seemed more likely to be a future bug report than a scope violation.

- **Reorder does not call `calculatePosition` itself — the caller does, same split as `reorderTask`/`createTask` in `lib/actions/tasks.ts`.** `reorderChecklistItem` only validates and persists an already-computed fractional-index value; `addChecklistItem` (append-to-end) is the one place in this file that calls `calculatePosition` server-side, mirroring `createTask`'s "look up the last item, hand it to calculatePosition with `nextPosition: null`" convention exactly. No fractional-index maths is reimplemented anywhere in this feature.

- **Content max length: 500 characters** for add/rename, not comments' 10000. A checklist item is a short todo line (title-like), not a paragraph — this is the simpler option per the ambiguity-resolution rule (no new constant/config, just reused the same order of magnitude as `tasks.title`'s limit in `lib/validation/tasks.ts`).

- **Delete is a real hard DELETE**, not a soft-delete flag flip — `checklist_items` has no `deleted_at` column (F151's migration deliberately omitted one; not in this feature's file scope to add one). `deleteChecklistItem` calls `.select("id")` after the DELETE and treats an empty result as a failure, so a silently-affected-zero-rows outcome (a bug in the RLS policy, or a race with a concurrent delete) surfaces as `{ ok: false }` rather than a false `{ ok: true }`.

- **A `SUGGESTED FOLLOWUP`-style test-infra note, not a blocker:** `tests/integration/checklist-actions.test.ts` mocks `@/lib/supabase/server`'s `createClient()` to a REAL signed-in Supabase client (publishable key + `signInWithPassword`), not the usual bare `auth.getUser()` stub every other action test file in this repo uses — this was necessary because this feature's actions genuinely run their mutations through that client (see the RLS decision above), so the mock has to be capable of running real RLS-checked Postgrest queries as the current test user. This is new to the test suite; future workers writing tests for actions that also route real writes through the RLS-respecting client should reuse this pattern rather than reinventing it.
