## Decisions made
- Selection state (`selectedIds: Set<string>`) lives inside `<TaskListTable>` itself as local component state, not lifted to the page or a shared store — matches the clarified spec's "local component state for ephemeral UI only" answer, and both callers (project List page, dashboard table) already pass their filtered `tasks` array as a prop, so the component has everything it needs without new plumbing.
- AS-335 is satisfied structurally rather than by re-deriving "the active filters" inside this component: `tasks` IS already the filtered/sorted result the caller fetched server-side (`getProjectListTasks(projectId, filters, sort)` in list/page.tsx, `getWorkspaceListTasks` in dashboard-task-table.tsx) — select-all (`toggleSelectAll`) simply selects `tasks.map(t => t.id)`, so it structurally cannot select anything the active filters excluded. Recorded per the clarification's "take the simpler option, no new dependency, no second source of truth" instruction — this avoids introducing a second "all matching task ids" concept.
- Shift-click range selection reads `event.shiftKey` off the raw DOM click event inside the Checkbox's `onClick` handler rather than `onCheckedChange`, because Base UI's `Checkbox.Root` `onCheckedChange` signature only forwards `(checked, eventDetails)` and doesn't reliably expose the triggering native event's modifier keys the same way a raw click handler does; `onCheckedChange` itself is a no-op and all toggling logic lives in `toggleRow`, keeping the checkbox fully controlled via the `checked` prop.
- Range selection (shift-click) always ADDS the range rather than toggling it — the common file-manager convention and avoids surprising partial-deselection when the range overlaps existing selection.
- The header checkbox uses Base UI's `indeterminate` prop for the "some but not all selected" state (not a full tri-state library) — no new dependency, `@base-ui/react`'s Checkbox already supports it natively (components/ui/checkbox.tsx already wraps `@base-ui/react/checkbox`).
- `<BulkActionBar>` is a standalone, presentational component (`selectedCount`, `onClear`, optional `children` slot) rather than owning any selection state itself, so F186/F187 can render their actual bulk-action buttons into the `children` slot without needing to touch task-list-table.tsx's selection logic.
- Selection is enabled unconditionally in `<TaskListTable>` (no new opt-in prop) since both existing callers (project List page and the dashboard's `dashboard-task-table.tsx`) render the same shared component and the spec is about "the list view's table" broadly; this also means the workspace dashboard table now gets row selection + the action bar for free — flagged below as a possible scope question for the orchestrator, though it does not violate the spec's file list (dashboard-task-table.tsx itself was not touched).

## Out-of-scope work needed
- AS-342's full proof (selection clears specifically AFTER a bulk action's mutation completes, not just after a manual "Clear selection" click) needs F186/F187 to exist first. This feature only provides the mechanism: `<BulkActionBar onClear={...}>` and `<TaskListTable>`'s internal `clearSelection()` function are both already wired and ready to be called by a future bulk-action Server Action's success handler (e.g. `onSuccess: () => clearSelection()` after a bulk status-change/delete mutation resolves). No code change should be needed in this file for F186/F187 to call it — they'll need `clearSelection` (or an equivalent handler) threaded out of `<TaskListTable>`, which currently keeps it as purely-internal state. SUGGESTED FOLLOWUP for F186/F187: when building the first real bulk action, either (a) lift `selectedIds`/`clearSelection` out of `<TaskListTable>` into a small shared hook (e.g. `useBulkSelection`) both the table and the new bulk-action component can consume, or (b) pass a `selectedTaskIds: string[]` + `onActionComplete: () => void` prop pair down from a wrapping Client Component that owns the action's mutation call, so the action's success handler can call back into the table's `clearSelection`.
- Access-control gating (per the clarified spec's "controls hidden/disabled via lib/auth/permissions.ts") was not applied to the checkboxes/action bar themselves in this feature, since there is no bulk action yet to gate — a viewer-role user can currently select rows and see the count/clear bar, they just have nothing to act on. F186/F187 should gate their own action buttons (rendered into `<BulkActionBar>`'s `children` slot) through `lib/auth/permissions.ts`/`useProjectRole` from `components/auth/membership-provider.tsx` (F135), exactly as instructed by AS-334..342's parent spec — selection itself is not a mutating action so it did not need gating for this feature.
- `components/task/list-filters.tsx` was listed as an approximate file in the feature spec but was not touched — no changes to filter UI were needed since AS-335 is satisfied entirely by the existing prop flow (see Decisions made). If a future feature wants filters to visibly announce "select-all will act on N tasks" inline within the filter bar itself (rather than only in the floating action bar after selecting), that would touch list-filters.tsx and is out of this feature's scope.
