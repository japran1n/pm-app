## Decisions made
- Reused `searchPalette` (`lib/actions/palette-search.ts`) verbatim — the exact same Server Action the command palette (F242) already calls — per this feature's own clarification note: "Two search entry points must not become two search implementations — one query module, two surfaces." No second ranking/visibility query was written. Debounce (200ms) + "only the latest in-flight request's response is applied" stale-response guard is copied verbatim from `command-palette.tsx`'s `handleQueryChange`, for the same reason that file gives (no server-side cancellation primitive for Server Actions in this codebase).
- AS-520's assertion text says "matching tasks and projects" specifically (not people) — the header dropdown renders only the `projects`/`tasks` groups from `searchPalette`'s result and omits the `members` group. Cmd+K (F242's "People" group) remains the one surface for finding people; this keeps the two surfaces distinct in purpose rather than fully duplicating the palette's UI.
- Navigation targets for project/task results are identical to the ones `command-palette.tsx` already uses (`/w/[slug]/projects/[projectId]/board` for both) — there is no other query-param-driven task/project detail route in this codebase (same reasoning F242's own handoff already documented), so this is not a second, invented destination.
- AS-522's Enter target reads the exact `?q=` contract `app/(workspace)/w/[workspaceSlug]/search/page.tsx`'s own `searchParams: Promise<{ q?: string }>` prop expects — verified by reading that file directly rather than assuming a param name.
- Escape (clear input + close dropdown) is wired through F244's shared escape-layer stack (`useEscapeLayer`/`popTopEscapeLayer` in `lib/hooks/use-shortcut.ts`) rather than a second `keydown` listener — `ShortcutProvider`'s existing document-level Escape handler (already mounted once in the workspace layout) is what actually calls `popTopEscapeLayer()`; this component only registers/unregisters itself as the topmost layer while its dropdown has something to close.
- "/" (F244's `SHORTCUT_EVENTS.openSearch`) also focuses this header input, in addition to the command palette opening (its existing, already-tested behaviour, untouched). Both are valid "search" entry points per this feature's own clarification wording ("...two surfaces"); the palette's own dialog, once open, ends up holding focus on top of this input, which is harmless — no assigned assertion for this feature covers the "/" shortcut specifically (AS-467/468/470/471 belong to F244, already shipped and untouched here).
- AUTONOMOUS_DECISION (clarification's "simpler option, no new dependency, no second source of truth" default): did NOT relocate the notification bell (F208) or the user menu/sign-out (F273/F256) into the new header, even though the feature spec's draft scope mentions them. Both already live, work, and are independently tested inside `components/nav/app-sidebar.tsx`. Relocating them touches F208/F253/F256/F273's already-tested layout for no benefit to this feature's assigned assertions (AS-519..AS-522, all specifically about the search input) and risks regressing tour anchors / bell tests that don't belong to this feature's Files scope. Documented as Out-of-scope work below instead of silently expanding this feature.
- `AppHeader` is a plain Server Component (no data of its own beyond the two ids it already receives from the layout) that renders the Client Component `HeaderSearch` — matches the mission's "Server Component for data loading, Client Component only for interaction" convention; there is no new data-fetch here since `searchPalette` is called client-side, identically to how the command palette already calls it.
- Header height (`h-12`) matches the sidebar's own top-bar row (`h-12 border-b`) for visual consistency at both the desktop `<aside>` header row and the `md:hidden` mobile top bar.
