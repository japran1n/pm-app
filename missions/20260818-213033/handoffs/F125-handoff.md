## Decisions made
- Built the toggle as a `ToggleGroup` (three simultaneously-visible icon buttons: Sun/Moon/Monitor) rather than a dropdown menu. AS-211 says "a visible toggle offers light, dark, and system" — a segmented control keeps all three states visible and one click/keypress away, which is the more literal reading than hiding two of the three behind an extra menu-open interaction. `components/ui/toggle-group.tsx` (added by F119, unused until now) was the natural fit; no new dependency needed.
- Read Base UI's `ToggleGroup` source (`node_modules/@base-ui/react/toggle-group/ToggleGroup.js`) before wiring it up: its accessible role defaults to `role="group"`, not `role="toolbar"` — the file-header comment in an early draft of `components/theme-toggle.tsx` said "toolbar" from assumption rather than verification; corrected before committing, and the Playwright test queries `getByRole("group", { name: "Theme" })` to match what's actually rendered.
- Used `React.useSyncExternalStore` (not a `useState` + `useEffect(() => setMounted(true))` "mounted" guard) to gate the toggle's controlled `value` on whether the client has hydrated. next-themes' own `theme` state reads `localStorage` synchronously in its state initializer, which already differs between the server render (`undefined`) and the client's first render (the real stored value) — using it directly in this component's JSX would be a genuine hydration mismatch (different `aria-pressed` in server-rendered markup vs. what the client computes while hydrating). The `useEffect` + `setState` version of this guard is the pattern most similar libraries document, but it's flagged by this repo's `react-hooks/set-state-in-effect` ESLint rule (`eslint .` failed on it); `useSyncExternalStore` with a `getServerSnapshot` that differs from `getSnapshot` is the React-documented alternative for exactly "is this the client, post-hydration, yet," and it isn't caught by that rule. This mismatch is scoped to the toggle control's own pressed-state rendering only — it has no bearing on AS-213, which is resolved before this component ever mounts.
- Ambiguity in the feature spec's Notes ("MCP at run: none") — no MCP was used; there's no external service this feature talks to (next-themes is a pure client-side library, no Supabase/DB involvement).
- Dark-mode token audit (per the assignment's explicit instruction) covered the surfaces this mission added — `app/(workspace)/w/[workspaceSlug]/settings/profile/page.tsx`, `components/profile/profile-form.tsx`, `components/user-avatar.tsx`, `components/ui/avatar.tsx` — by computing real WCAG contrast ratios from `app/globals.css`'s `.dark` OKLCH values (OKLCH → linear sRGB → relative luminance → contrast ratio, scripted, not eyeballed): foreground-on-background 18.96:1, muted-foreground-on-background 7.63:1, muted-foreground-on-card 6.91:1, destructive-on-background 6.84:1, destructive-on-card 6.19:1, primary-foreground-on-primary 14.22:1 — every pairing those four files actually use clears WCAG AA (4.5:1) with margin. No token changes were made; nothing on those surfaces was unreadable in dark mode. `lib/user-color.ts`'s `AVATAR_PALETTE` was left untouched (fixed background/foreground hex pairs, deliberately theme-independent per that file's own header comment and this feature's explicit instruction not to "fix" it).
- Wiring `<ThemeProvider>` into `app/layout.tsx` also activates `components/ui/sonner.tsx`'s existing (previously dead) `useTheme()` call — that file already called `useTheme()` and passed the result to `<Sonner theme={...}>` before this feature, it just always got the library's ungated default (`"system"`) because no provider existed yet. Not a file this feature edited; noting it because it's a real, if small, behavioural side effect of this change (toasts now actually track the chosen theme instead of only ever using the OS default).
