## Decisions made
- **Fixed four-status list, not per-project custom statuses.** Grepped the codebase for `custom_statuses`/`project_statuses` and found neither table nor feature — M16 has not landed. Per the spec's own explicit fallback, `extensionCreateTaskSchema`'s `status` field is `z.enum(["todo", "in_progress", "in_review", "done"])`, matching `lib/actions/tasks.ts`'s own status type exactly. When M16 lands, this schema (and the form's `STATUS_OPTIONS` constant) are the two places to update to source the list from the project instead.
- **Context endpoint auth duplicated from F292's route, not factored into a shared helper.** For exactly two routes, the ~25-line "resolve identity from a bearer JWT via a fresh anon-key client" block is duplicated verbatim (with a comment in the new route pointing at its twin) rather than extracted into a shared module. Two call sites duplicating a well-understood, well-commented block is simpler to read/audit here than an extra file both routes would need to import and keep in sync; if a third extension route is ever added, that's the natural point to factor it out for real. This was an explicit either/or choice offered by the spec ("your call, document the choice").
- **Context endpoint shape: no query param returns the caller's workspaces; `?workspaceId=<id>` (re-verified server-side via `requireActiveMembership`) returns that workspace's non-deleted projects and active members.** Two round trips (one on popup mount, one when a workspace is picked) rather than one nested payload — this mirrors how the web app itself splits "workspaces I'm a member of" (`lib/queries/workspaces.ts`) from "a given workspace's projects" (`lib/queries/projects.ts`) and "members" (`lib/queries/members.ts`) as three separate concerns, and means a compromised/buggy caller can never even receive a second workspace's project/member list bundled alongside the first — AS-557's server-side scoping is enforced per-request, not just per top-level response.
- **Reused, not reinvented, the app's existing "workspaces I'm an active member of" and "workspace's live projects/members" filtering.** The workspace list query mirrors `lib/queries/workspaces.ts`'s `getDefaultWorkspaceSlug` (`workspace_members` filtered to `user_id` + `status = "active"`). The per-workspace query mirrors `lib/queries/projects.ts`'s `getWorkspaceProjects` (`deleted_at IS NULL`) and `lib/queries/members.ts`'s `getWorkspaceMembers` (`status = "active"`) + `lib/queries/people.ts`'s `resolvePeople` for a display name. No new filtering logic was invented.
- **Sensible defaults for the form's optional fields (per the clarification's "everything else optional"):** status defaults to `"todo"` (mirrors the DB column's own default and `createTaskSchema`'s default, so the value shown if left untouched matches what the server would persist anyway), no assignee (`""` maps to `undefined`, i.e. unassigned), no priority (`""` maps to `undefined`), no due date. Documented in `report-form.tsx`'s own doc comment.
- **Screenshot/annotation/console-log/network-log payloads deliberately NOT attached to the submitted task.** `extensionCreateTaskSchema` doesn't accept those fields yet (F292's own handoff already documented this as F294/F295's extension point). `report-form.tsx`'s doc comment states this explicitly as a handoff point rather than half-building ahead of those features' own scope.
- **`Popup.tsx`'s `Status.connected` variant now carries `accessToken`**, sourced from the exact same `getSession()`/`onAuthStateChange` session objects that already determine "connected" — never re-derived, cached, or read from storage a second time. This is the "wiring the extension's fetch call" F292's handoff explicitly left out of scope for that feature to do.
- **Playwright test needed a REAL running Next server with a REAL matching `EXTENSION_ID`, not a stub.** The report form makes genuine cross-origin `fetch()` calls from the popup document to `app/api/extension/context` and `app/api/extension/tasks`, both CORS-restricted to `chrome-extension://<EXTENSION_ID>` (F292's convention). An unpacked extension's id is randomly assigned by Chrome per load (documented in F292's own handoff caveat) and the placeholder in root `.env` doesn't match any real load. `extension/tests/report-form.spec.ts` therefore: (1) launches the extension first to learn its real id, (2) spawns `npm run dev` (root app) on port 3100 with `EXTENSION_ID` set to that real id, (3) intercepts the popup's `http://localhost:3000/**` requests via Playwright's `page.route` and rewrites them to port 3100 (so the built extension, which embeds `VITE_APP_URL=http://localhost:3000` at build time, doesn't need to be rebuilt per test run), (4) waits for the server to be ready, (5) drives the real form interactions, (6) tears the spawned server down in `afterAll`. This is slower (~6s) than this suite's other tests but proves the CORS allowlist, the bearer-token auth, and the real database write all work together for real — not mocked at any layer.
- **The seeded "connected" session for this test is a REAL `signInWithPassword()` result** (not the "fake-access-token" placeholder F281-F283's own tests use for their simpler assertions, which never make a real authenticated network call) — because the report form's fetch calls need a token that actually verifies against Supabase Auth.

## Out-of-scope work needed
- **F294 (screenshot/annotation attachment upload)** and **F295 (console/network-log metadata into the task)**: `extensionCreateTaskSchema` and `createTaskForUser` do not accept attachment ids or log blobs yet — both features need to extend the schema (documented in its own comment as their extension point) and the route, and `report-form.tsx` needs a call site added for whatever payload each produces. Neither is guessed at or half-built here.
- **`EXTENSION_ID`/CORS friction for real (non-test) local development** — still exactly the gap F292's handoff already documented (an unpacked extension's id is random per load; a developer must copy it from `chrome://extensions` into `.env` by hand). This feature's own Playwright test works around the same friction programmatically (see Decisions made) but does not close the gap for a human developer running the popup against a normally-started `npm run dev`. A small `extension/scripts` helper that prints the id after `npm run build`, or pinning the id via a fixed `key` in `manifest.json` (F281's own deferred note), would close this — not part of this feature's declared file scope.
- **No rate limiting on the new context endpoint**, matching F292's own explicit "cut from this mission's scope" decision for the sibling tasks endpoint — same rationale applies here, not re-litigated.
