## Decisions made
- Item 1 (AS-376): added `stripAllMentions` as a new exported function in `lib/comments/mentions.ts` (reuses the existing private `stripInvisibleMentions` with an empty `visibleIds` set) rather than inlining a second stripping implementation in `templates.ts` — keeps "the one place the stripping rule is defined" convention this module's own doc comment already establishes. `createProjectFromTemplate`'s catch block now: (a) retries the real check once (transient DB errors are often momentary), (b) if that also throws, falls back to `stripAllMentions` and writes that back — never falls through to "leave the original as-is." This preserves F316's own reasoning for NOT aborting the whole batch (the RPC already committed atomically; there's nothing to roll back) while closing the specific "unsanitised document left in place" gap the scrutiny report flagged.
- Item 2 (AS-358): read the actual function and determined this is a UI-truthfulness bug, not a cursor-correctness bug — `getTaskActivityPage` has no cursor at all (it's a growing-window "load more", not offset-based pagination), so there's no row-skip/repeat risk at the boundary; the bug is that `hasMore` stayed `true` forever once the 200-row cap was hit, because `hasMore` was computed from "does more data exist" rather than "can requesting more actually return something new." Split this into two signals (`hasMore`: is another `Load more` click useful; `cappedAtMax`: is there more data that's permanently unreachable) rather than overloading one boolean, so the UI can be honest about both facts independently.
- Item 3 (AS-389): the p_task_id/workspace check runs first, before the p_system/auth branch, so it applies uniformly to every caller (system and human-attributed alike) — a mismatched task_id is a data-integrity problem regardless of who's calling. Used `create or replace function` (signature unchanged) matching the two prior fix migrations' own convention for this function. Left `p_kind`'s own validation entirely to the existing `notifications_kind_check` CHECK constraint (already enforced at insert time) — the scrutiny report's phrasing said the RPC's error handling "may be poor" for that case, but on inspection an invalid `p_kind` already raises a clear Postgres constraint-violation error from the `insert`, which is a legitimate DB-level validation failure, not a silent/swallowed one; no code-level pre-check was needed there and I didn't add a duplicate one.
- Item 4 (AS-369): confirmed via code reading (not just observation) that the test's ordering is already race-free — `subscribe((status) => { if (status === "SUBSCRIBED") toggleReaction(...) })` guarantees the toggle physically cannot fire before the subscriber is live. Chose to widen timeouts rather than add retry/polling logic (which would risk toggling the reaction an even number of times and flipping the row back to absent, silently invalidating the very thing being asserted) or switching to a DB-poll fallback (which would stop actually proving live Realtime delivery, defeating this test's stated purpose per its own header comment).
