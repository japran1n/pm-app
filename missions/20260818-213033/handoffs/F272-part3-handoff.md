## Decisions made
- **Root cause of the tour reappearing mid-test (both `blocked-done-guard.spec.ts` and `templates-ui.spec.ts`)**: every affected spec's own tour-dismissal helper had the SAME logic bug — `if (!visible) return;` (or an equivalent single check) treats "the tour is not visible RIGHT NOW" as "already dismissed, nothing to do." But called immediately after `page.goto()`/`waitForURL()`, the tour genuinely isn't in the DOM yet (the client hasn't hydrated / hasn't flipped its `mounted` `useSyncExternalStore` gate yet — see `components/onboarding/tour.tsx`'s own doc comment on why that gate exists). That first `isVisible()` check reads false, the helper returns immediately WITHOUT EVER CLICKING SKIP, and the tour then genuinely renders a second or two later, fully undismissed, and sits there for the rest of the test — only surfacing as a failure much later when it happens to intercept an unrelated click (`blocked-done-guard.spec.ts`'s very first status-select click; `templates-ui.spec.ts`'s "New from template" picker click). Confirmed by instrumenting `getTourStatus`/`OnboardingTour` with temporary `console.error` calls (removed before commit) and observing zero `writeTourCompletedAt` server-action invocations across an entire failing run — the Skip click was never even attempted. Fixed by changing every affected helper to a `while` loop that keeps polling for the FULL deadline unless it has actually SEEN the tour appear and then disappear (`lastSeenVisible` flag) — correctly handles "never shows up," "shows up immediately," and "shows up late," where the old logic only handled the first two by accident and the third not at all.
- **Verified this was NOT a dnd-kit hydration-mismatch-driven remount** (my first hypothesis, since the WebServer logs for `templates-ui.spec.ts`'s failures repeatedly showed a genuine `aria-describedby="DndDescribedBy-N"` SSR/CSR mismatch on the board page): fixed that mismatch too (see below, it's real and worth fixing regardless), but re-ran the repro with debug instrumentation and a clean `.next` cache and still saw the SAME tour-dismissal failure with ZERO hydration-mismatch log lines present in that specific run — proving the two are separate, independently-real bugs, not one causing the other. Both are fixed now.
- **Fixed the dnd-kit `aria-describedby` SSR hydration mismatch anyway**, since it's a real, reproducible, low-risk, one-line-per-instance fix (`id="..."` on every `DndContext` in the codebase — board, checklist, timeline, calendar) and dnd-kit's own documented remedy for exactly this class of issue (a module-scope id counter that starts fresh on the server per-request but can already be non-zero on the client). Confirmed via `node_modules/@dnd-kit/core`'s own source (`useUniqueId("DndDescribedBy", id)` — passing an explicit `id` makes it return that value directly instead of generating a counter-based one) that this is the correct, complete fix, not a workaround.
- **Reduced `checklist-ui.spec.ts`'s `dismissTourIfPresent` deadline from 10s to 4s** (and used 4s for the new copies of this helper elsewhere) after the corrected (non-early-return) version of the loop caused one run's `AS-271` (renamed/deleted/Backspace/Enter) test to blow its own 30s test-level timeout — the loop was correctly polling out the FULL 10s deadline on a call where the tour genuinely never appeared (a false-negative-safe design, but wasteful), and combined with the rest of that test's own real work it exceeded budget. 4s is still comfortably longer than the tour's typical hydration/mount delay (well under 1s in every observed run) while leaving much more headroom for the rest of each test.
- **`templates-ui.spec.ts`'s AS-330 click** additionally wraps the actual template-name click in a short retry loop (re-dismiss, then attempt the click with a 3s per-attempt timeout, up to a 20s overall budget) rather than relying on a single dismiss-then-click, since — even with the dismissal bug fixed — the tour can in principle still race a fresh remount exactly at click time; this is belt-and-suspenders test robustness, not a sign the underlying bug wasn't actually fixed (all 6 repeated runs after the fix landed clean on the FIRST click attempt, no retries needed).
- **Did not attempt to fix the residual full-suite flakiness in `dependency-ui.spec.ts`, `subtask-ui.spec.ts`, or `notifications.spec.ts`'s live-badge test**, since (a) none of these were in this session's assigned scope, (b) all of them pass individually/in isolation every time I re-ran them, and (c) they match part 2's handoff's own already-diagnosed, explicitly-deferred issues: item 1 (the other four `subscribe*Realtime` hooks likely share the exact realtime-auth race already fixed for notifications, but fixing it requires updating several existing unit tests' synchronous-subscribe assertions — a bigger, riskier change than this session's budget), and item 4 (this suite's tests all hit the SAME real, shared, linked Supabase project, and load-dependent timing varies run to run in ways that aren't simple worker-contention). Re-investigating these from scratch would have meant re-doing part 2's own diagnostic work rather than building on it.
