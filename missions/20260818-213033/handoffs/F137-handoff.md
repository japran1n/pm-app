## Decisions made
- **Slug validation is a new, separate regex-based schema** (`changeWorkspaceSlugSchema`), not a reuse of `slugify()`. `slugify()` silently normalizes arbitrary input (lowercasing, collapsing non-alphanumerics to hyphens) — reusing it for user-typed slug-change input would let someone type `"My Workspace!!"` and have it silently become `my-workspace` with no feedback about what actually got saved. The new schema instead rejects anything that isn't already `lowercase-alnum-with-single-hyphens` with a specific validation message, matching the clarified spec's "client-side for immediate feedback, re-validated by the action's Zod schema server-side" pattern used elsewhere in this file.
- **Uniqueness check order**: live-slug collision (`workspaces.slug`, excluding soft-deleted) checked first, then history collision (`workspace_slug_history.old_slug`). Both return distinct, specific field-level error strings ("This URL is already in use." vs "This URL was used before and can't be reused.") rather than one generic "slug taken" message — closer to what AS-242's "specific error" wording asks for, and it also tells the caller *why* (still live vs. retired) which matters for deciding what to try next.
- **A workspace's own retired slugs are also rejected on reuse** (not just other workspaces'), including by the SAME workspace trying to reclaim its own old slug back. This follows directly from `old_slug` being a hard unique constraint at the DB level (any row already existing there blocks the insert regardless of which `workspace_id` it's associated with) and from the clarified spec's "no expiry, slugs are cheap" answer — a retired slug is retired permanently, full stop, which is also what keeps the redirect chain from ever pointing at the wrong destination if a slug were allowed to bounce between owners.
- **`permanentRedirect()` instead of `redirect()` with a `RedirectType`** — checked the installed Next.js 16.3.1 API surface directly (`node_modules/next/dist/client/components/redirect.d.ts`) rather than relying on training-data memory: `redirect()`'s second parameter is `RedirectType.push | RedirectType.replace` (a client-navigation hint, not an HTTP status), while `permanentRedirect()` is the dedicated function that serves a 308 in a Route Handler / carries permanent semantics elsewhere — matching what the feature spec explicitly asked for ("301, or Next.js's `redirect()` with the appropriate type").
- **Redirect logic lives in the workspace layout** (`app/(workspace)/w/[workspaceSlug]/layout.tsx`), not `proxy.ts`. Read `proxy.ts` first: it only handles the auth-required-for-`/w/*`-redirect-to-sign-in concern (AS-001) and has no Supabase table access or per-route-segment param resolution — `[workspaceSlug]` is resolved exactly once, in the layout, which already runs the "does this slug map to a workspace" query and is the single place `notFound()` is called from. Putting the redirect check there means it reuses the exact same request-scoped Supabase client and runs as one more query in the existing miss-path, rather than duplicating slug-resolution logic in proxy middleware (which would also need its own Supabase query per request just to check history, on every single `/w/*` request, including ones for slugs that already resolve fine).
- **The redirect lookup runs before the membership/RLS-scoped active-workspace check on the failure path, not instead of it**: `workspace_slug_history` grants a SELECT-to-authenticated RLS policy with no membership scoping (any signed-in user can resolve "old slug X now belongs to workspace Y"), but the actual workspace access decision is unchanged — a non-member who follows the redirect to the workspace's new slug hits the exact same `workspaces_select_active_members`-scoped query on the next request and gets the same generic `notFound()` AS-144 already guarantees. No new information is leaked beyond "this old slug used to point somewhere, and now points at a specific new slug" — the same non-secret shape a slug itself already has.
- **Slug field made editable in `WorkspaceGeneralForm`**, superseding F136's read-only slug field (F136's own comment there said "The URL slug can't be changed once a workspace is created" — that was accurate only until this feature). Saved through its own form/`useTransition`/error-state trio, entirely separate from the name field's, per the clarified spec's optimistic-revert-on-failure pattern applied independently to each field (a slug-change failure must not also revert an in-progress, unrelated name edit, and vice versa).
- **`workspace.slug` regenerated via `supabase gen types typescript --linked`** rather than hand-editing `database.types.ts` — diffed the full output against the existing file first (only the new `workspace_slug_history` table entry differs) before overwriting, so no unrelated/stale drift from other concurrent workers' un-pushed local migrations could sneak in.
- Added a `writeAudit(..., "workspace.slug_changed", ...)` call inside `changeWorkspaceSlug`, matching the F140 (concurrent worker) convention already present on every other mutating action in this same file (`renameWorkspace`, `deleteWorkspace`, etc.) by the time I got to writing this action — not an assigned assertion of this feature, but leaving it out would have made this one action inconsistent with a pattern every sibling action in the file now follows.

## Out-of-scope work needed
- No UI surfaces a workspace's slug history to end users (e.g. "past URLs" list on the settings page) — the clarified spec only calls for the redirect mechanism, not a management UI for it. `workspace_slug_history` has a `workspace_id` index specifically anticipating this as a future, separate feature.
- The settings page's browser URL does not update to the new slug's path after a successful `changeWorkspaceSlug` (unlike, say, `createWorkspace`'s `redirect()` on creation) — the form updates in place and a subsequent navigation naturally lands on the new slug via the redirect chain this feature adds, but there's no `router.replace()`/`router.push()` call wiring the address bar to follow immediately. Not required by AS-241/AS-242 (both are about server-side behaviour, not client URL-bar state), flagging in case a future UX pass wants it.
