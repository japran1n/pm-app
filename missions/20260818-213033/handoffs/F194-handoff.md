## Decisions made
- `kind` vocabulary for `task_activity` (F195/F196 must follow it exactly, per the mission's instruction): a closed set enforced by a CHECK constraint (`'field_changed'`, `'comment_added'`, `'comment_deleted'`) — unlike `audit_log.action` (open free text), because F196's activity feed renders from a small, fixed set of UI templates, so a closed vocabulary costs nothing and catches typos at the DB layer. `field_changed` entries carry `field` (e.g. `'status'`, `'assignee_id'`, `'priority'`, `'due_date'`, `'estimate'`, `'title'`) plus `old_value`/`new_value` jsonb. `comment_added`/`comment_deleted` entries leave `field` null and carry the comment id in `new_value`/`old_value` respectively (e.g. `{"comment_id": "..."}`). A `task_activity_field_presence_check` CHECK enforces `field` is present iff `kind = 'field_changed'`, so a comment-kind row can never be mistaken for a mis-tagged field change. This is documented in full in the migration's header comment.
- Writes go exclusively through a new SECURITY DEFINER function `public.write_task_activity_entry(p_task_id, p_kind, p_field, p_old_value, p_new_value, p_system)`. There is deliberately **no INSERT RLS policy at all** on `task_activity`, mirroring F139's `audit_log` design exactly, per the spec's explicit instruction. The function itself still enforces visibility for non-system calls (`is_task_visible_to(p_task_id)`) and pins `actor_id := auth.uid()` server-side, never trusting a client-supplied actor.
- `p_system boolean default false` parameter (not named in the spec's column list, but necessary to satisfy AS-360's requirement that "recurrence-job-driven changes" be attributable to the system without an authenticated session): when `true`, the function skips the `auth.uid()` requirement and always writes `actor_id = null`, for the recurrence job's own service-role/cron context. This is additive surface on the write path, not a schema change, and keeps the human-attributed path (the common case, used by F195 for user-driven edits) fully auth-gated. Documented in the migration header and exercised by a dedicated AS-360 test (system entry has null actor_id) even though AS-360 itself is assigned to F195 — I verified the DB-layer mechanism this feature owns works, since F195 will build directly on top of it.
- SELECT policy reuses `public.is_task_visible_to(task_id)` verbatim (F132's shared helper), per this feature's explicit instruction not to invent a parallel visibility check — a single `using (public.is_task_visible_to(task_id))` clause, no copy-pasted join.
- No UPDATE or DELETE policy exists for `task_activity`, for any role, permanently — the entire mechanism behind AS-357. Confirmed via negative tests using the member's real session (not the admin client), per the assertion's exact wording and F139's precedent.
- Indexes: `(task_id, created_at desc)` for the single named read path ("activity feed for task X, most recent first"). No secondary actor index was added — unlike `audit_log`'s "everything actor Y did" index — because no read path in this feature's spec or F195/F196's drafts names a per-actor activity query; adding one now would be speculative index surface not justified by a named query.
- Regenerated `lib/supabase/database.types.ts` after applying the migration, per the clarification's "must be regenerated" answer.
