## Decisions made
- AS-486's real boundary was already in place (F250/F127's server-side `canEditTask`/`canWrite` checks) — this feature's job for AS-486 was to PROVE it with a test that drives the real action as a viewer and checks DB state, not to add new server-side code. Four new integration test cases were added to the existing `tests/integration/edit-task.test.ts` (reusing its existing `viewerUserId`/`makeTask()` fixtures) rather than a new file, since it already has the exact fixture this needed.
- AS-489's literal wording ("not rendered") is stricter than F250's own "disabled + tooltip" rendering (which was correct for F250's assigned assertions — AS-489 wasn't among them). Resolved per this feature's own draft scope ("render plain text for viewers and guests without rights") by adding a `!canEdit` early-return branch to all four cells (including `list-status-select.tsx`, touched here for the first time) that renders a plain `<span>`/`<div>` with the current value, no focusable/interactive element at all — not merely a disabled one. `list-status-select.tsx` was in scope to touch despite not being named in F250's file list, because AS-489 says "inline controls" (plural, all four) and is assigned to F251, not F250.
- AUTONOMOUS_DECISION (F251's clarified "simpler option, no new dependency" + the spec's explicit callout: "An incoming realtime update must not clobber a cell the user is actively editing"): the no-clobber rule is — (1) while a field is CLEAN (`localValue === committedValue`), a fresh server value (Realtime-reconciled or otherwise) is adopted immediately into both `localValue` and `committedValue` — this is what makes AS-488 "appear live." (2) while a field is DIRTY (an uncommitted local edit in progress), the fresh value updates `committedValue` only, never `localValue` — the user's in-progress edit is preserved, but the revert/no-op-comparison baseline stays current so a later Escape reverts to the actual latest server value, not a stale one. (3) while THIS client has its own commit in flight (`isSaving`), incoming remote values are ignored entirely, left to that commit's own server-echoed resolution — this prevents a same-tick Realtime echo of the client's own write from racing the optimistic path. No lock/merge UI, no new dependency — same last-write-wins semantics every other mutation in this app already has once a value IS committed.
- The assignee cell (a set, not a scalar — doesn't use `useInlineFieldEdit`) gets the equivalent rule hand-written: while `isSaving` (a toggle's own request in flight), remote `assigneeIds` prop changes are ignored; otherwise the local set is fully re-synced to the incoming prop. Simpler than field-level diffing for a set, and consistent with this cell's existing "toggle == eager commit, no separate dirty-draft state" design (there's no multi-checkbox draft to preserve — each click is already its own commit).
- `reconcileListTask` (new) is a SEPARATE function from the board's existing `reconcileTask`, not a reuse — documented in its own header comment: `reconcileTask` fully REPLACES a matched row with only the columns a bare `tasks`-table event can carry, which is correct for the board (it only ever renders those columns) but would silently drop List-view-only fields (`assigneeIds` plural, `statusCategory`, `totalMinutes`, `estimateMinutes`, `projectKey`) that a bare `tasks` row event never carries and the initial server fetch already resolved via joins/aggregates. `reconcileListTask` instead merges (`{ ...existing, ...changedColumns }`) so those already-loaded fields survive a Realtime UPDATE for the same row. Same ordering guard (`updated_at` comparison) and soft-delete/DELETE handling as the board's version, by design.
- `TaskListTable`'s Realtime subscription is scoped to the single-project List view only (`projectId` prop, wired from `list/page.tsx`). The workspace-wide dashboard table (`components/dashboard/dashboard-task-table.tsx`) spans every project in the workspace and has no single topic to subscribe to — it simply omits `projectId`, and `useListRealtime`/`useBoardRealtime` are documented no-ops when it's absent (`if (!projectId) return;`, pre-existing in `useBoardRealtime`). See Out-of-scope below.
- Per-project permission variance (the spec's "check whether the list view is ever multi-project and handle it" instruction): confirmed `canWrite`/`canEditTask` (lib/auth/permissions.ts) key off the caller's WORKSPACE role only, never `projectRole`, for the viewer/guest exclusion this feature cares about — a workspace member has exactly one workspace role across every project in that workspace, so there is no per-project permission variance for AS-486/AS-489 to handle on the dashboard's multi-project surface. (`projectRole` only ever ADDS extra rights, e.g. "lead," never removes the baseline write access a workspace role already grants.) No code change was needed for this concern.
- DELETE-payload leak concern (spec's explicit callout that Realtime DELETE payloads aren't RLS-filtered): followed the exact same posture `useBoardRealtime`/`subscribe-board-realtime.ts` already established and accepted for the Board view — the Postgres-level row filter (`project_id=eq.<projectId>`) already scopes every event (DELETE included) to one project regardless of RLS, and this hook is only ever mounted from a route (`list/page.tsx`) the caller already had server-side access to render (same "project detail layout's guard one level up" the List page's own doc comment already documents, including F322's private-project rule). No new logic was added here since none is needed beyond what Board already relies on and this mission has already accepted.
- Duplicate-guard interaction: `useInlineFieldEdit`'s existing `isPendingRef`/`pendingValueRef` de-dupe (read/written only inside `commit()`, never during render) was left untouched; the new `lastSeenValue` re-sync uses real React state (not a ref) specifically so it's safe to read during render, matching this file's own established convention (see its "Tracked as state (not a ref)" comment on `committedValue`).

## Out-of-scope work needed
- The workspace-wide dashboard table (`components/dashboard/dashboard-task-table.tsx`) gets NO Realtime subscription from this feature (AS-488 is satisfied for the per-project List view, which is what this feature's scope named) — a future worker wanting live updates on that multi-project surface would need either N per-project subscriptions (one per project the workspace's tasks span, expensive/wasteful for a large workspace) or a new workspace-scoped Realtime topic/filter (`workspace_id=eq.<id>` isn't a `tasks` column today — would need a migration or a view). This is a real gap, not an oversight; flagging for a follow-up feature if the mission wants dashboard-level live updates.
- `reconcileListTask`'s plural `assigneeIds` field is NOT updated from a bare Realtime `tasks` event (that array is resolved via a join to `task_assignees`, which never arrives in a `tasks`-table `postgres_changes` payload) — only the legacy scalar `assigneeId` (mirror-synced by `setTaskAssigneesCore`, per that function's own doc comment) is. A multi-assignee task edited by another user while this client's List tab stays open will show a briefly-stale avatar group for that one task until the next full navigation/reload. Documented in `reconcile-list-realtime-task.ts`'s own header comment; same class of tradeoff the board's existing `reconcileTask` already accepts for its own set of un-carriable fields.
- A brand-new task INSERTed by another user (visible on Realtime because it matches this project) is appended to the List view's local row list even if it wouldn't match the CURRENT status/priority/assignee filter or sort order the page's URL params encode — `reconcileListTask`, like the board's `reconcileTask`, has no way to know the active filter/sort criteria. Same pre-existing tradeoff class the board accepts; would need `TaskListTable` to be handed the active filter set to fully close.
