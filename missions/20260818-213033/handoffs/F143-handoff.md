## Decisions made
- **Restore never touches the `tasks` table** (the spec's own explicit ambiguity note: "Restoring must not resurrect tasks that were independently soft-deleted before archiving"): read `archiveProject`'s exact update statement and its own doc comment before writing `restoreProject` — confirmed archiving *only* sets `projects.deleted_at`, never writes to `tasks` at all (F029's AS-032 already proves this: "an archived project's row remains fully readable... with its data intact", and nothing about individual task rows is ever mutated). Since tasks were never touched by archiving, they don't need to be touched by restoring either — `restoreProject` clears only `projects.deleted_at` (and `archived_by`, see below). A task independently soft-deleted before the project was archived retains its own `deleted_at` through the entire archive→restore cycle simply because nothing in either action ever writes to `tasks.deleted_at`. This is the simpler option (no new dependency, no second source of truth, per the clarification's ambiguity-resolution default) — it relies on the existing invariant rather than adding a new "was this task deleted before or after archiving" tracking mechanism.
- **Gated by `requireWorkspaceAdmin` (owner/admin), same as `archiveProject`**: the spec's Draft scope says "gated by F127" without naming a specific role; the clarified spec's access-control answer ("re-verified server-side against the caller's membership and role via lib/auth/permissions.ts") doesn't name the exact role either. Chose owner/admin — mirroring `archiveProject`'s exact gate — because restoring is the direct inverse of an admin/owner-only action; there's no reason the reverse operation should be open to a lower role than the forward one, and this avoids introducing an asymmetric, unexplained permission model. AS-253's assertion text ("restore is rejected without admin rights") directly confirms admin is the right bar.
- **`archived_by` cleared alongside `deleted_at`, with the same `42703`/`PGRST204` feature-detection fallback `archiveProject`'s write already uses**: since this worker's sandbox (like F142's) has no confirmed live status for the `projects.archived_by` migration, the restore write mirrors the exact same tolerant-of-column-absence pattern, rather than assuming the column exists. Clearing it (not leaving a stale value) keeps the column meaningful — a restored, currently-active project has no "archived by" in the same way a never-archived project doesn't.
- **No-op restore (already-active project) returns `ok: true` without writing**, per the clarified spec's Round A Q6 default ("a no-op returns ok without writing, and the UI shows no error toast for an intentional no-op") — same pattern this codebase already establishes elsewhere (e.g. `editProject`'s "No changes to save" is the negative case, but the no-op-success shape here matches the definition-of-done's own stated convention for this archetype).
- **Revalidation mirrors `archiveProject`'s exact scope**: `revalidatePath(\`/w/${slug}\`, "layout")` — the same single call `archiveProject` makes. Checked: the project list, dashboard (F073's tiles), and search all render under that one `/w/[workspaceSlug]` layout segment (no separate top-level route for any of them), so this one revalidation call covers all three paths the spec names, exactly as `archiveProject` already relies on for the reverse direction — no wider revalidation surface was needed.
- **No confirmation dialog on the restore button** (UI decision, not in the clarified spec's explicit answers): archiving warrants a confirm step because it's the action that hides a project; restoring is the corrective, non-destructive action undoing that, and remains trivially reversible (archive again) if clicked by mistake. A lighter single-button-with-loading-state affordance was chosen over reusing `ArchiveProjectDialog`'s dialog pattern for this asymmetry-appropriate reason.
