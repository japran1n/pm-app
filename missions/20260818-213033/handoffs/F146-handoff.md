## Decisions made

- **The key follows the project's CURRENT key, not one frozen at task creation** (the feature spec's one explicitly-open question, clarification Round B Q2: "take the simpler option that adds no new dependency and no second source of truth"). `formatTaskKey(projectKey, taskNumber)` takes the project key as a plain argument — there is no `tasks.key_at_creation` snapshot column, no backfill, and no migration for this feature. This is simpler (nothing new to keep in sync) and matches Jira/Linear's own behavior: if a project's key is ever edited later (F145's handoff: the DB already allows it via `projects.key`'s UPDATE-time constraints; no editing UI exists yet), every task under that project immediately displays the new key on next render, with no second source of truth that could drift.

- **One formatter, no duplication.** `lib/tasks/task-key.ts`'s `formatTaskKey` is the only place in the codebase that concatenates `${key}-${number}`. Every surface (task card, detail header, list row, dashboard table, search result) imports it — none re-implements the concatenation locally. This was the explicit anti-pattern called out in the brief (referencing F275's date-formatter cleanup), so it was treated as a hard constraint, not a nice-to-have.

- **Extended the three existing task-list queries instead of adding per-row fetches** (`lib/queries/tasks.ts`'s `getProjectBoardTasks`, `getProjectListTasks`, `getWorkspaceListTasks`) — each now selects `number` (a plain `tasks` column, F145) and joins `projects(key)` (already joining `projects!inner(...)` for `getWorkspaceListTasks`; added a plain `projects(key)` embed to the other two, which previously had no project join at all). No N+1: this is one extra selected column/join on an existing single query, not a new query per row. A small `firstRelated<T>` helper was added at the top of the file to normalize PostgREST's object-or-array embedded-relation shape, mirroring the exact `Array.isArray(...) ? x[0] : x` pattern already used inline at several call sites in `lib/actions/tasks.ts` (assignTask, editTask, etc.) — factored into one named helper here since this file needed it three times.

- **`getTaskDetail` (lib/actions/tasks.ts) extended its existing task+project fetch** the same way — added `number` to the `tasks` select and `key` to the already-present `projects!inner(workspace_id)` join — rather than a second query for the detail sheet's header badge.

- **`searchWorkspaceTasks` (lib/queries/search.ts) needed no RPC/migration change.** `search_tasks` is declared `returns setof tasks`, and F145 already added `tasks.number` to that table, so the RPC's return rows already carried `number` for free — confirmed by reading the RPC's SQL definition before assuming a migration was needed. Only the project key needed adding, and the function already fetches the workspace's `projects` rows (for `projectNameById`) — extended that same select to include `key` and built a second `Map` (`projectKeyById`) from the same already-fetched rows, no second query.

- **Board Realtime reconciliation (`lib/board/reconcile-realtime-task.ts`) needed an explicit fix, not just a type change.** `tasks.number` is a plain column, so it already arrives in every Realtime `postgres_changes` payload — trivial to read off `row.number`. A task's **project key** is not a `tasks` column and therefore never arrives in a Realtime payload for that table. Left unaddressed, every board-realtime UPDATE/INSERT event would have silently reset a card's `projectKey` to `undefined`, making the key badge flicker away on every drag/drop or status change until the next full page load — a real, user-visible regression on the one surface (the board) that has live Realtime reconciliation. Fixed by resolving the board's (single, invariant) project key once per event — from the matched existing row on an UPDATE, or from any other task already on the board for an INSERT, since `useBoardRealtime`'s subscription filter (`project_id=eq.<projectId>`) guarantees every task on a given board instance belongs to the same project — and threading it into `toTaskCardTask` as an explicit parameter rather than expecting it in the row. This kept the fix inside the one file already responsible for Realtime merge semantics; `board.tsx`/`board-column.tsx`/`sortable-task-card.tsx` needed no changes since they only ever forward the `task` object through unchanged prop signatures. `BoardRealtimeTaskRow`'s type (`lib/board/subscribe-board-realtime.ts`) gained a `number: number` field to match.

- **New fields (`projectKey`, `number`) are optional on `TaskCardTask`/`TaskDetailSheetTask`, never a required prop with a dangerous silent default.** This is a deliberate contrast with F275's `timezone` hardening (required, no default, because a silently-wrong timezone renders every date wrong with no visual cue). A missing task key is not dangerous in the same way — `formatTaskKey` returns `null` and the badge simply doesn't render, which is a safe, visible "nothing to show" rather than a silently-wrong value. Optional also matches this codebase's existing convention for every other per-row enrichment field in these two types (`updatedAt`, `totalMinutes`, `avatarUrl`, etc.).

- **Click-to-copy is a plain native `<button>`, no new dependency.** Keyboard-operable for free (Tab to focus, Enter/Space to activate — no custom key handling needed), calls `navigator.clipboard.writeText` (no clipboard library existed or was needed), and reports success/failure via `sonner`'s `toast`, matching every other mutation in `task-detail-sheet.tsx` (`saveField`, `handleDelete`) for its "what does the user see when something fails" convention.

- **Added a "Key" column to `<TaskListTable>`** (before Title) rather than inlining the key into the Title cell — this table is shared by the project List view and (via `dashboard-task-table.tsx`, unmodified) the workspace dashboard table, so this one change covers both of the brief's "list row" and "dashboard table" surfaces at once, per the brief's explicit instruction to reuse rather than duplicate.
