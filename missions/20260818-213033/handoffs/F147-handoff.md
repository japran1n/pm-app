## Decisions made
- **Parser location and export shape**: added `parseTaskKeyQuery(query: string): { projectKey: string; taskNumber: number } | null` to `lib/tasks/task-key.ts`, alongside F146's `formatTaskKey`. This is the file's natural home (already the single source of truth for task-key concatenation/parsing) and satisfies the explicit instruction that F242 (command palette) must reuse this exact function rather than a second copy of the regex — `formatTaskKey` turns `(projectKey, taskNumber)` into a display string; `parseTaskKeyQuery` is its pure inverse, turning a free-typed query back into a candidate pair, with zero DB access.
- **Regex shape** (Decisions Made per the clarification's "simpler option, no new dependency, no second source of truth"): `/^([A-Za-z]{1,6})[-\s]?(\d{1,9})$/` on the trimmed, case-normalized-on-output query. Letters-only prefix, optional single dash or space, digits suffix. This covers every example in the spec ("pm142", "PM-142", "pm 142") and every key F145's `derive_project_key_base` produces for a **fresh** key (always pure ASCII letters). **Known limitation**, documented in the code comment: a key that itself ends in a digit after F145's collision-suffix step (e.g. a workspace's second "Marketing" project keyed `MARKET2`) is ambiguous in the no-dash form (`MARKET2142` could mean key `MARKET2` task `142`, or key `MARKET` task `2142`) — this parser does not attempt to disambiguate that case; it's still findable via the dashed form (`MARKET2-142`, which the FTS index also covers) and via ordinary full-text search on title/description. Flagged as a documented limitation, not a blocker, since it only affects a minority key shape and every findability path except the exact no-dash parse still works.
- **FTS migration approach — generated column → trigger-maintained column**: the existing `tasks.search_vector` (`20260818050200_fts_tasks.sql`) is a `generated always as (...) stored` column computed only from `tasks.title`/`tasks.description` — same-row columns only, which Postgres generated columns require. A task's key needs `projects.key` (a **different** table), so a generated column literally cannot express it. `20260819064522_task_key_search_fts.sql` converts `search_vector` into an ordinary stored column (drop index → drop column → re-add as plain `tsvector`), adds a `BEFORE INSERT OR UPDATE OF title, description, number, project_id` trigger (`tasks_update_search_vector`, `security definer` so the cross-table `projects` lookup doesn't depend on the caller's own RLS visibility of that row — same rationale as F145's `assign_task_number()`) that recomputes title (weight A) + description (weight B) + `"KEY-NUMBER"` (weight A, `to_tsvector('simple', ...)` since it's an identifier, not prose), then **backfills every existing row** with one `UPDATE ... FROM projects` in the same migration (per the critical-context instruction: a change that doesn't backfill existing rows leaves old tasks unfindable by key), then recreates the GIN index.
- **Known limitation, documented in the migration's own header comment**: the trigger fires on writes to `tasks`, not on writes to `projects` — if a project's key is ever renamed (no such UI exists yet, per F146's handoff), already-written tasks' *indexed* search_vector would lag behind the *displayed* key (which `formatTaskKey` always resolves live, per F146's decision) until that task is next updated. Not fixed here: there is no caller today that can rename a project's key, so a companion trigger on `projects` would be unverifiable dead code. Flagged for whichever future feature adds key-rename.
- **Ranking — exact match above full-text hits**: `searchWorkspaceTasks` (`lib/queries/search.ts`) runs `parseTaskKeyQuery` on the trimmed query; if it parses, resolves the candidate against the **same already-workspace-scoped `projects` array** the full-text loop already uses (never a second, wider query), looks up the task by `project_id` + `number` + `deleted_at is null` via the ordinary RLS-bound client, and — if found — prepends it to the final results, de-duplicating it out of the full-text set if it also appears there (it legitimately can now, since the key is part of `search_vector` too).
- **Cross-workspace isolation (AS-262's explicit negative case)**: the exact-match project lookup only ever searches within the `projects` array already fetched with `.eq("workspace_id", workspaceId)` under RLS — a project belonging to another workspace's identical key can never be found this way, because it never appears in that array. Verified explicitly in the integration test using two workspaces with **deliberately distinct, explicitly-set** project keys (`FKEYA` / `FKEYB` — inserted directly rather than relying on the F145 name-derivation trigger) specifically to rule out a coincidental key collision between the two randomly-named test workspaces silently making the isolation test pass for the wrong reason.
- **Query-error handling**: the exact-key task lookup swallows a Postgres error the same way "no row found" is swallowed (`maybeSingle()` + `if (!keyTaskError && keyTask)`) rather than throwing, so a transient issue on the (supplementary) exact-key path never breaks the (primary) full-text path for the same query.
- Left the one pre-existing ESLint warning in `lib/queries/search.ts` (`'_titleMatches' is defined but never used`) exactly as found — the destructuring line it comes from is unchanged; it was only moved (unmodified) from the old inline `return` into the new `fullTextResults` intermediate variable.

## Out-of-scope work needed
- **Project-key rename propagation to FTS**: if/when a "rename project key" feature ships, it needs a companion trigger (or explicit re-index step) on `projects` so already-indexed tasks' `search_vector` picks up the new key — see the migration's own comment. No such feature/UI exists yet, so nothing to wire up today.
- **Ambiguous no-dash keys ending in a digit** (e.g. `MARKET2142`): out of scope per the parser's documented limitation above — would need a caller-side DB lookup trying multiple digit-boundary splits, which conflicts with keeping the parser itself pure/DB-free. A future worker could add this as an enhancement to the exact-match resolution in `lib/queries/search.ts` (try each valid split against the known project keys in the workspace) without touching the pure parser's contract.
- F242 (command palette) itself is not implemented here — this feature only guarantees `parseTaskKeyQuery` exists, is exported, and is the single copy of the regex for F242 to import.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose the letters-only-prefix regex (`[A-Za-z]{1,6}`) over a more permissive alphanumeric-prefix regex, because a fully general parser would need workspace-specific knowledge (which keys actually exist) to disambiguate alphanumeric prefixes from trailing digits, and this parser is required to stay pure/DB-free for F242 reuse. Documented as a known limitation rather than silently guessing; every finding path except this one specific no-dash edge case still works for such keys.

AUTONOMOUS_DECISION: Converted `tasks.search_vector` from a generated column to a trigger-maintained one (rather than leaving it generated and denormalizing a copy of the project key onto `tasks`) because a trigger with a live subquery has no second source of truth to drift, whereas a cached `tasks.project_key_snapshot`-style column would need its own propagation-on-project-rename logic anyway — same problem, plus an extra always-present column. This matches the mission's stated additive-migration convention (index dropped/recreated, but no data-losing operation: the column drop+re-add is followed by an in-migration backfill in the same transaction, so no row is ever left with a stale/empty search_vector after the migration commits).
