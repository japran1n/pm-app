## Decisions made
- **`max-md:` (not `max-sm:`) for the sidebar's own hamburger trigger and nav Link rows** — the sidebar toggles between its desktop `<aside>` and its hamburger-triggered mobile `Sheet` at the `md` breakpoint (`hidden ... md:flex` / `... md:hidden`, pre-existing, unrelated to this feature), not `sm`. Using `max-sm:` there would leave 640–767px (tablet-portrait) widths — where the mobile Sheet nav is still what's actually shown — under the 44px floor. `max-sm:` was kept for everything that's actually gated by the `sm` breakpoint elsewhere in this codebase (the task-detail Sheet's own full-screen switch, per F264's established convention, and the collapsible-section triggers, which live inside that same Sheet).
- **The Sheet's close button fix lives in the shared `components/ui/sheet.tsx`, not duplicated per-caller** — this codebase has exactly one `SheetContent` close-button implementation, reused by every Sheet (task detail, the mobile sidebar nav, every dialog-as-sheet). Fixing it once there means every Sheet's close control meets the 44px floor on phone widths, not just this feature's own task-detail Sheet — matches the spec's own "Audit sidebar/sheet/menu trigger buttons" instruction, which named `sheet.tsx` explicitly as a file this feature may touch.
- **Sections are collapsible, not collapsed-by-default** — the clarified spec says sections "become collapsible... so the screen stays navigable", not "start collapsed". `MobileCollapsibleSection` defaults `open` to `true` everywhere; the mobile-only trigger only gives the ABILITY to collapse a section the user isn't using right now. This is the simpler/safer default per the clarification's ambiguity-resolution rule: a user who wants everything expanded (today's actual desktop-first, everything-visible behaviour) sees no change on first open.
- **`isMobile` is tracked with a real `matchMedia` hook (`lib/hooks/use-media-query.ts`, new), not left as a pure CSS `hidden max-sm:flex` on the trigger alone** — a pure-CSS approach would leave a section a user collapsed on a phone STAYING collapsed if the window is later resized to desktop width (Collapsible's content-hiding is JS/`data-state`-driven, not itself a CSS media query — a `max-sm:hidden` class on the panel would only hide/show the outer wrapper, not un-collapse the actual Collapsible state). `MobileCollapsibleSection` computes `effectiveOpen = isMobile ? open : true`, so at desktop width the section is always rendered open regardless of stale local state — the exact "looks right in one viewport, silently wrong after a resize" bug class this feature's brief specifically warned to be alert to (one level removed from F264's flex-basis bug, same root cause: a Tailwind class alone isn't always what's actually gating something). No new dependency — a ~25-line hook, no `usehooks-ts`/similar package added, per the clarification's "simpler option, no new dependency" rule.
- **`useMediaQuery` is defensive against a missing `window.matchMedia`** (returns the safe `false`/desktop default rather than throwing) because this codebase's jsdom test environment doesn't implement it by default. The new test file stubs `window.matchMedia` itself (an "always matches" stub simulating a phone viewport) to exercise the real mobile collapse-toggle behaviour, rather than adding a global jsdom polyfill/setup file the rest of the suite didn't already have.
- **Only 5 sections wrapped in `MobileCollapsibleSection`**: Description, Subtasks, Checklist, "Comments & activity" (the existing Tabs block, both tabs share one collapse control since they're already mutually exclusive), Time tracking — exactly the sections the clarified spec names ("description, checklist, subtasks, comments, activity, time"). Tags/Recurrence/Dependencies/Attachments were left unwrapped — not named by the spec, and wrapping them would be scope creep beyond the clarified list (flagged in Out-of-scope below in case a future feature wants full coverage).
- **Back-button / F247 intercepted-route interaction — verified by reasoning, not re-tested from scratch**: F247's own handoff documents that `useTaskDetailSheet`'s `router.back()`/`router.replace()` fallback logic is driven entirely by `onOpenChange(false)` and `window.history`/a `pushedTaskIdRef` — none of which this feature touched or could affect. This feature only changed the Sheet's own CSS presentation (full-screen at mobile widths) and added collapsible sections; `onOpenChange`, the `Sheet`/`SheetPrimitive.Root`'s `open`/`onOpenChange` wiring, and every one of F247's close-path branches are byte-for-byte unchanged. The existing `f247-task-modal-routing.test.tsx` suite (7/7) was re-run as part of the full suite above and still passes unmodified, confirming no regression.

## Notes for the next worker
- The core CSS technique this whole feature rests on is: the base `Sheet` (`components/ui/sheet.tsx`) sets `data-[side=right]:w-3/4`/`data-[side=left]:w-3/4` with NO responsive qualifier — a plain `w-full`/`max-sm:w-full` class on a caller's own `className` LOSES that cascade tie (equal specificity: one class + one attribute selector on each side; the unconditional rule has no media-query wrapper so it sorts before any responsive-variant rule in Tailwind v4's generated stylesheet). The pre-existing `data-[side=right]:sm:max-w-2xl` override already in this file (predating this feature) proves the fix pattern: qualify the override with the SAME `data-[side=...]` attribute selector so it wins on specificity AND lands inside a media-query block that sorts after the base rule. This feature's `max-sm:data-[side=right]:w-full`/`max-sm:data-[side=left]:w-full` follows that exact same proven pattern — NOT Tailwind's `!important` escape hatch, and NOT a bare unconditional class. Any future Sheet-presentation change in this file should keep using this pattern, not a plain `w-*`/`max-w-*` class, or it will silently be a no-op the way F264's `flex-1`/`w-[88vw]` interaction was.
- `MobileCollapsibleSection` is a small local component defined in `task-detail-sheet.tsx` itself (not exported/shared) — if a future feature wants the identical collapsible-with-resize-safety behaviour elsewhere, it's a candidate to extract into its own file, but wasn't extracted here to stay inside this feature's named file scope.
- `useMediaQuery`/`MOBILE_BREAKPOINT_QUERY` in `lib/hooks/use-media-query.ts` use `(max-width: 639.98px)`, matching Tailwind v4's default `sm` breakpoint (`40rem`/640px) exactly — if this codebase's Tailwind config is ever customized to change that breakpoint, this constant needs to move in lockstep or the JS-driven "force open on desktop" logic will disagree with the CSS-driven `max-sm:` trigger visibility at the boundary.
- No MCP tools used — this is a pure UI/CSS feature per `worker-mcp-usage`'s decision tree, and the feature spec's own Notes say "MCP at run: none."
