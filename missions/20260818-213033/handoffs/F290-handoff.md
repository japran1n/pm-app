## Decisions made
- **`world: "MAIN"` injection via `chrome.scripting.executeScript`, gesture-triggered by a popup button**, following F287/F289's exact established pattern (see those handoffs for the full "why not a `document_start` content script" reasoning — the same `activeTab`-only / no-`<all_urls>` constraint from `tech-decisions.md` applies here unchanged). Patching `window.fetch`/`XMLHttpRequest.prototype` needs the page's own JS realm, not the extension's isolated one.
- **"Reuse the same bounded buffer as F289" — interpreted as the same bounding strategy/shape, not literal shared storage.** This is genuinely ambiguous in the spec's wording, so documenting the reasoning explicitly: network-hook.ts keeps its OWN window-scoped buffer (`__pmAppNetworkCapture__`, separate from console-hook.ts's `__pmAppConsoleCapture__`), built with the exact same shape F289 established — a plain array capped at 200 entries (`MAX_NETWORK_ENTRIES`, matching F289's `MAX_CONSOLE_ENTRIES`), oldest-entry eviction on overflow, and an idempotent "already installed" marker under a `window` key, injected/read via the same two-call (`start`/`get`) pattern. Considered and rejected literal single-shared-array: `chrome.scripting.executeScript({ func })` gives each injected function no closure over any other injection's state, so a truly shared buffer would require either (a) console-hook's injection reaching into a global object network-hook also writes to (fragile ordering/definition coupling across two files that are otherwise fully independent features a reporter may start independently, in either order, or not at all) or (b) a third shared "capture-buffer" module both import and duplicate identically inline anyway — same duplication cost, more coupling, no functional benefit, since nothing downstream currently reads console and network entries as one merged timeline (F289's own handoff already says a future report-assembly feature should read each capture module's state independently and merge as needed). Two independent 200-cap buffers, same shape/strategy, is the interpretation this handoff commits to.
- **Both `fetch` and `XMLHttpRequest.prototype.open`/`send` are patched**, not just `fetch` — per the spec's explicit callout that library/older code still uses XHR. A failure is either (a) the call itself rejects/errors (network failure, CORS block, aborted mid-flight — surfaced for XHR as `xhr.status === 0` on `loadend`, for fetch as the returned promise rejecting) OR (b) it completes with `status >= 400`. Successful (< 400) requests are never recorded — verified explicitly with a dedicated negative-case test.
- **Request and response bodies are never captured**, per the spec. Only `method`, `url` (redacted), `status` (`number | null` — `null` means a pure network failure with no HTTP status ever received), and `duration` (via `performance.now()` deltas) are recorded.
- **URL redaction is unconditional, not opt-in**, per the clarification's tie-breaker ("defaulting to redaction is the safer choice"). Redacted query-param key names (case-insensitive substring match via regex, not an exhaustive allowlist): `token`, `key`, `signature`, `secret`, `password`, `passwd`, `auth`, `credential`, `session`, and `api[-_]?key` (covers `apiKey`, `api_key`, `api-key`). These substring-matching patterns intentionally also catch reasonable variants (`access_token`, `refresh_token`, `client_secret`, `sessionId`, `Authorization` as a query param, etc.) without needing an exhaustive enumeration. Only the matched param's VALUE is replaced with `[REDACTED]` — the path, all other query params, and the redacted key's own name remain visible, so the report stays useful for reproducing the bug. Applied via a canonical, unit-tested `redactUrl()` (uses the real `URL`/`URLSearchParams` API, falls back to a coarse regex replace if the string genuinely isn't parseable as a URL) and a duplicated in-page copy inside the injected function, for the same "no closure across `executeScript` calls" reason F289/F287 document.
- **`XMLHttpRequest.prototype.send`'s `loadend` listener** covers both a genuine network error and a normal (possibly failing-status) completion in one place — `xhr.status === 0` on `loadend` reliably distinguishes "never got an HTTP response at all" (connection refused, DNS failure, CORS block, or abort) from a real received status, matching how browsers report XHR failures (there is no separate low-level "network error" callback with structured status the way `fetch`'s rejected promise gives one).
- **Popup UI section for network capture is a new, independent block** (own start/refresh buttons, own state, own `data-testid`s: `network-capture-start-button`, `network-capture-limitation`, `network-capture-refresh-button`, `network-capture-count`, `network-capture-list`, `network-capture-entry`, `network-capture-error`), mirroring F289's console-capture section exactly but not sharing any React state with it — a reporter can start console capture, network capture, both, or neither, independently, matching the "two independent hooks, two independent buffers" interpretation above.

## Out-of-scope work needed
- **No `store.ts` slot / persistence for captured network entries beyond local popup React state** — same reasoning as F287/F289's picked-element/console-log results: no downstream feature yet assembles the final bug-report payload. Whichever feature does that should read `getNetworkCaptureFromActiveTab()`'s result the same way it will read `getConsoleCaptureFromActiveTab()`'s, `pickElementOnActiveTab()`'s, and the environment-metadata collector's (F288) in-popup state — and, if that future feature wants a single merged timeline of console + network events, it can trivially merge both arrays by `timestamp` at that point (see "Decisions made" above for why that merge isn't done here).
- **No F291 on/off toggle exists yet** (same gap F289's handoff already flags) — this feature's own popup button is a reasonable standalone default trigger and needs no changes to keep working once that toggle exists; a future toggle should call `startNetworkCaptureOnActiveTab`/`getNetworkCaptureFromActiveTab` rather than reimplementing hook installation, exactly as F289's handoff already recommends for its own two functions.
- **No explicit "stop capturing" UI**, same reasoning/scope decision F289's handoff documents for console capture (the hook runs for the tab's lifetime; removing the patch cleanly across separate `executeScript` calls isn't worth the complexity for an already-bounded, page-lifetime-scoped capture). Flagging in case a future feature wants an explicit stop/discard affordance for either hook.
