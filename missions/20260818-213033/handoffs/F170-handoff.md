## Decisions made
- **Exact backfill JSON shape (F171 needs this):** for non-empty text, `{ "type": "doc", "content": [{ "type": "paragraph", "content": [{ "type": "text", "text": "<original text>" }] }] }`. For null/empty description, `{ "type": "doc", "content": [] }` (an empty doc with no paragraph child) — this is Tiptap's own canonical empty-document shape, verified against F169's editor code (an empty `RichTextEditor`/`RichTextRenderer` renders from a doc with no content array entries). Implemented as a SQL helper function `public.tiptap_doc_from_text(text) returns jsonb`, immutable, reused by both the trigger and the one-time backfill `UPDATE`, so there is exactly one place this shape is defined.
- **Trigger derives description_json/description_text FROM description, not the other way round, for now.** The clarified answer says "the plain projection must be produced server-side from the JSON on every write, so search never drifts from what is displayed" — but the rich-text editor (F169) is not yet wired into any create/edit UI or into `lib/actions/tasks.ts` (explicitly out of scope per this feature's own framing: "just the DB shape and backfill"). The only writer of descriptions today is still the plain `description` column via the existing Server Action. Modifying `lib/actions/tasks.ts` to also write `description_json` would be scope creep on a feature explicitly scoped to storage, and there is no page anywhere in the app yet that could produce a real Tiptap document to write. So `tasks_update_search_vector()` (the existing trigger from `20260819064522_task_key_search_fts.sql`, extended in place rather than duplicated) derives BOTH new columns from `description` on every insert/update, using the exact same `tiptap_doc_from_text()` wrap the backfill uses — this keeps `description_json`/`description_text` always in sync with whatever gets written today, with zero drift, and needs zero application-code changes. **This direction must be flipped by whichever future feature wires the rich-text editor into the write path**: that feature should change the trigger (or move the derivation into the Server Action, per the clarified answer's original intent) to extract `description_text` FROM `description_json` instead, once `description_json` becomes the real source of truth. Flagged again below under Out-of-scope.
- **FTS trigger widened, not touched at the call site.** Rather than adding a new trigger, extended the existing `tasks_update_search_vector()` function (from F147/`20260819064522_task_key_search_fts.sql`) in place — one function, one trigger, same "single source of truth" convention that migration already established for `search_vector`. The trigger's column list (`before insert or update of title, description, description_json, number, project_id`) now also fires on direct writes to `description_json`, future-proofing for when that becomes the real write path.
- **Legacy `description` column left completely untouched** (schema and values) — only a `comment on column` marks it deprecated, per the "additive, drop later" clarified answer and this mission's F159/F270 convention. Verified explicitly in a test (`legacy description column is left unchanged by the migration/trigger`).
- **No RLS changes** — these are new columns on the existing `tasks` table; existing RLS policies (workspace/project-member scoped) already govern row visibility and were not touched, so no new policy work was needed for AS-310 (a storage/backfill assertion, not an access-control one).
- **No new index** on `description_json`/`description_text` — the existing GIN index on `search_vector` already serves the read path this feature enables; nothing yet queries `description_text` directly.

## Out-of-scope work needed
- **Wiring `RichTextEditor` (F169) into the task create/edit UI and `lib/actions/tasks.ts`**, so `description_json` becomes an actual write target instead of a value derived from the legacy column. This is F171's job for rendering; a companion write-path feature (not yet in `plan.md` under this exact name, may already be covered by a later M14 feature — check `plan.md`) needs to: (a) have the Server Action accept/validate a Tiptap `JSONContent` payload (Zod schema mirroring the DB shape), (b) write `description_json` directly, (c) flip `tasks_update_search_vector()`'s derivation direction described above so `description_text` is extracted FROM `description_json` (via a new `tiptap_extract_text(jsonb) returns text` SQL function walking the full Tiptap node tree — general paragraph/heading/list/code-block support, not just the single-paragraph case this migration's helper handles) rather than the description column.
- **F270 (already planned in this mission)** — the actual drop of the legacy `description` column, once every reader (this migration's trigger included) has moved off it.
- Rendering `description_json` anywhere in the UI — explicitly F171, not touched here.
