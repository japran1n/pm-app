## Decisions made
- **Root cause is NOT what the scrutiny report's hypothesis said, and I verified this by live reproduction rather than trusting the write-up.** The hypothesis was "a client-side function reference (`extractPlainText`'s `resolveLabel` parameter) crosses the Server Action boundary." I checked every call site: `lib/actions/comments.ts` (server-side) NEVER passes `resolveLabel` to `extractPlainText` — it was already correctly recomputing the plain-text projection from validated JSON alone, exactly as the "FIX" instructions asked for. That half of the bug was already fixed (by F308, which shipped before F272 even wrote the e2e test that documented this bug).
- **Actual root cause, confirmed by live reproduction against a running dev server + real browser + real "Post" click:** the crash is `Error: Cannot access id on the server. You cannot dot into a temporary client reference from a server component`, thrown inside `extractPlainText`'s `collect()` on `node.attrs?.id` — meaning the mention node's `attrs` object arrives at the server as an unreadable React Flight "temporary reference" placeholder, not plain data. I confirmed via instrumentation that the client-side `draft` object (the exact value handed to `addComment`) is, at the moment of submit, 100% plain JSON with no functions, no non-`Object.prototype` prototypes, and no cycles anywhere in the tree (a recursive walker over the whole document found nothing). The corruption therefore happens during React's Server-Action argument *encoding* itself — most likely because ProseMirror/Tiptap structurally shares/interns `node.attrs` object references across the live editor's own document/decoration state, and passing that still-referenced-elsewhere object as a Server Action argument causes Next's Flight client to encode it via the "temporary reference" mechanism (normally reserved for functions/refs) instead of a plain clone.
- **The fix is therefore at the client-to-server boundary, not inside `addComment`/`extractPlainText` at all** (there was nothing left to fix there). Added `toPlainJson()` to `lib/comments/rich-text.ts` — a `JSON.parse(JSON.stringify(...))` round-trip — and call it on `draft`/`editDraft` immediately before both `addComment` and `editComment` in `components/task/comment-list.tsx`. This severs any lingering reference identity to the live ProseMirror document, guaranteeing every value crossing the wire is fresh, plain JSON with no possible temporary-reference encoding. Verified live: the exact same repro that reliably 500s with raw `editor.getJSON()` succeeds (200, comment persisted with correct `body_json`, `mention` notification created) once `toPlainJson(draft)` is sent instead.
- Applied the same fix to `editComment`'s call site too (`saveEdit`/`editDraft`) even though BLOCKER-4 only names `addComment` — an edited comment can just as easily introduce/keep a real mention node and would hit the identical crash; leaving it unfixed would just be the same bug filed again next scrutiny pass. This is a two-line, same-file, same-pattern change well within "fix the serialisation boundary."
- Did **not** touch `lib/actions/comments.ts` or `lib/notifications/mentions.ts` — neither needed a change once the real root cause was identified, and the feature's own instructions say not to guess at server-side changes if the actual mechanism turns out different from the hypothesis (it did).
- Rewrote the e2e mention test's submission step to use the real composer `pressSequentially` + real "Post" button click, replacing the admin-client `insert` + `create_notification` RPC stand-in, per the instructions and per M18-scrutiny.md's own recommended follow-up text. Ran it twice in the same session to rule out one-off luck.
- Added `tests/integration/f339-add-comment-mention-regression.test.ts` (real Supabase project, same `describe.skipIf(!haveAdminCreds)` convention as every sibling integration test in this repo) rather than a mocked unit test — `addComment` is a Server Action with heavy DB-dependent authorization/fan-out logic (membership checks, mention-visibility stripping, notification RPC, watcher upserts), and every existing test for it in this codebase (`tests/integration/add-comment.test.ts`, `tests/integration/notification-fanout.test.ts`) uses this same real-DB pattern rather than mocking Supabase — matching that convention was the safer choice over inventing a new mocking strategy. The test uses a REAL signed-in session client (via `signInWithPassword`, mirroring `notification-fanout.test.ts`'s own doc-commented rationale) rather than a bare `getUser()`-only stub, because `createNotification`'s `create_notification` RPC and the broadcast channel both need a real PostgREST/Realtime session to run through — a fake client without `.rpc()` throws inside `addComment`'s own non-fatal fan-out `try/catch`, silently producing zero notifications and a false green.
- The mention-bearing `bodyJson` in both the new integration test and the regression comment above uses the REAL shape `editor.getJSON()` produces (`{ id, label: null, mentionSuggestionChar: "@" }`), not a hand-trimmed `{ id }`-only object — confirmed via live instrumentation what the real attrs shape actually is, so the regression test exercises the real data shape, not an idealised one.
- AUTONOMOUS_DECISION: left the pre-existing "Encountered two children with the same key" React console warning (visible during the live repro and the e2e run) uninvestigated — it did not affect correctness (exactly one comment row was created per submission, verified by direct DB query) and is outside this feature's scope (a rendering/key concern in the comment list, unrelated to the Server Action boundary this feature fixes). Flagged below under Out-of-scope work needed.
