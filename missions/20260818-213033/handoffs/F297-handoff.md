## Decisions made
- **Storage quota, verified rather than assumed (per this task's explicit instruction):** fetched the current Chrome extension docs (https://developer.chrome.com/docs/extensions/reference/api/storage, checked 2026-08-20) and confirmed `chrome.storage.local`'s real, current `QUOTA_BYTES` is **10,485,760 bytes (10MB)**, measured as "the JSON stringification of every value plus every key's length," ignored only with the `unlimitedStorage` permission — which this extension deliberately does not have (tech-decisions.md's narrow-permission stance; not silently added). Critically: `extension/src/submit/upload.ts`'s `MAX_ATTACHMENT_SIZE_BYTES` (10MB decoded) means a maximum-allowed screenshot's base64 data URL (~13.3MB of text, since base64 inflates by ~4/3) would **already exceed the entire 10MB quota by itself**, with zero room left for anything else this extension ever writes to `chrome.storage.local` (session tokens, F291's privacy toggles, F296's remembered workspace/project).
- **Resolved the spec's own flagged open question ("decide the cap and what happens past it") via the clarification's "less data, simpler, more private" tie-breaker: graceful degradation, never a silent drop.** `draft.ts`'s `saveDraft()` ALWAYS persists the form's text fields (tiny — a few KB), and persists the screenshot's data URL alongside them only when it's under `DRAFT_IMAGE_MAX_DATA_URL_LENGTH` (6MB of base64 text — chosen with deliberate headroom under the real 10MB total, not "as much as technically fits"; corresponds to ~4.5MB of real decoded PNG bytes, well under the 10MB upload cap). When the image doesn't fit, `imageOmitted: true` is set on the draft and `report-form.tsx` shows a plain, explicit notice ("...the screenshot was too large to save for retry — please recapture it...") rather than silently discarding it with no explanation. A belt-and-suspenders retry (drop the image, keep text-only) also guards the theoretical edge case where even the capped write still overflows because other data already occupies most of the quota.
- **Draft write timing: on submit-attempt, not on every keystroke and not only after a failure.** Per the spec's own explicit "pragmatic middle ground" framing and AS-565's literal wording ("an offline SUBMISSION"), `saveDraft()` is called as the very first thing inside `handleSubmit` — before the size check, before building the description, before the fetch — so the draft is safely on disk even if the extension/browser is killed mid-network-call, without paying the cost of writing chrome.storage.local on every character typed.
- **Draft takes priority over F296's "last used workspace/project" remembered context**, not merged with it. An active unsent draft means the reporter is mid-way through a specific, already-typed report — more specific and more urgent than "the workspace/project they happened to use last time." Implemented by gating both of F296's existing remembered-context-application `useEffect`s on `draftState.kind === "loaded" && !draftState.draft` (i.e. only apply remembered context once a draft has been positively confirmed absent), avoiding any render-order race between the two preselection paths.
- **Offline detection: primarily "the fetch call itself threw" (no HTTP response ever received), not `navigator.onLine` alone.** Verified this is the current recommended approach (an extension/page can have `navigator.onLine === true` while genuinely unable to reach a specific host — e.g. a captive portal or a broken upstream — so it's a real but imperfect signal on its own). `report-form.tsx`'s `try { await fetch(...) } catch { ... }` block is exactly where a real network failure surfaces (this is also precisely what `page.route(...).abort(...)` produces in the test, and what an unreachable host produces in production), so `classifySubmitError({ networkFailure: true })` is called from that catch block specifically — not from a separate `navigator.onLine` poll that could disagree with what actually happened on the wire.
- **Five genuinely distinct messages, each with its own `data-error-kind` attribute** (`offline`, `expired-session`, `permission-denied`, `too-large`, `server-error`) so tests assert on the specific classification, not just "some red text appeared." `expired-session` and `too-large` reuse the real server-side message strings verbatim (F292's exact 401 body, F294's exact AS-566 "...MB or smaller." message) rather than re-wording them, per the task's explicit "reuse, don't duplicate" instruction — verified by rereading both routes' actual current source rather than trusting the handoffs' prose alone.
- **Screenshot resolution's third fallback tier.** `report-form.tsx`'s existing priority (F294's `getAnnotatedResult()` first, then `getLastCapture()`) now falls back a third time to a restored draft's `imageDataUrl` — only when this popup mount itself never captured/annotated anything (a fresh mount's in-module singletons are empty by construction), so a restored draft's image is genuinely usable for a real retry without recapturing.
- **Clear-on-success uses `.catch(() => {})`, not an awaited call inside the same try/catch that classifies submit failures.** A hypothetical failure in `clearDraft()` itself (e.g. a genuine extension-runtime error) must never be misclassified as an "offline" submit failure on a task that was already, genuinely, successfully created — mirrors the same reasoning F296's handoff already documented for `setLastReportContext`'s defensive `.catch`.
