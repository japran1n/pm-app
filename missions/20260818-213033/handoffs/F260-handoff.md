## Decisions made
- **Thumbnail-size open question, resolved per the clarification's ambiguity rule (simpler option, no new dependency, no second source of truth):** did NOT add a server-side image resize/transform pipeline. The full-size image is used directly as both the inline thumbnail source (pre-existing, `object-cover` in an 80x80 box) and the lightbox's displayed image (`max-h-[80vh] max-w-full object-contain`, added this session). A real transform pipeline (Supabase Storage image transformations, which needs a paid-tier project feature, or a `sharp`/`next/image`-loader setup) is a genuinely new dependency/infra requirement out of scope for a 45-minute UI pass. Pure CSS sizing satisfies "thumbnail" (visually constrained) without it. Recorded here per the spec's explicit instruction.
- **Overlay pattern, not the shadcn/ui `Dialog` primitive:** `components/ui/dialog.tsx` wraps `@base-ui/react/dialog`, which owns its own portal, focus trap, and independent Escape handling. Layering the shared escape-layer stack (`lib/hooks/use-shortcut.ts`, used by every other Escape-closeable overlay in this codebase — F244's `useEscapeLayer`) on top of a second, competing Escape handler risks double-handling and is harder to prove correct in jsdom. Followed `components/onboarding/tour.tsx`'s (F253) established pattern instead: a plain `role="dialog" aria-modal="true"` fixed overlay + `useEscapeLayer`. This is the same convention this codebase already uses everywhere Escape needs to close exactly one thing, per the task instructions' explicit pointer to F244/F253/F250/F251.
- **Signed-URL refresh:** the lightbox never reuses the thumbnail's already-minted signed URL (which could be close to `SIGNED_URL_TTL_SECONDS` = 1 hour old) or a URL cached at initial page load. Each displayed image — on open, and on every next/previous navigation — mints its own fresh URL via the existing `getAttachmentSignedUrl` Server Action (`lib/actions/attachments.ts`, unmodified). Implemented as `LightboxImageBody`, a small subcomponent remounted via `key={attachmentId}` for each navigated-to image, mirroring `AttachmentThumbnail`'s existing "own signed URL, minted on mount" convention in the same file, rather than resetting shared state inside a `useEffect` (which an eslint `react-hooks/set-state-in-effect` rule in this repo's config specifically flags as an error — the remount-via-key approach was chosen over a lint-suppression to actually avoid the anti-pattern, not just silence the linter).
- **Click target for opening the lightbox:** `AttachmentList`'s existing `handleOpen(attachmentId)` (already called by both the thumbnail button and the filename-link button) now branches on `mimeType?.startsWith("image/")`: image attachments open the in-app lightbox; everything else keeps the pre-existing "mint a signed URL, `window.open` in a new tab" behaviour unchanged. No new click handler was added — the existing single entry point for "open" was extended, not duplicated.
- **Focus restore:** captured via `document.activeElement` at the moment the lightbox opens (a ref, not React state, since it never needs to trigger a render) and restored with `.focus()` when it closes (Escape, the explicit close button, or a backdrop click all funnel through the same `onClose`). Verified in jsdom by explicitly calling `trigger.focus()` before `fireEvent.click(trigger)` in the tests — jsdom's `fireEvent.click` does not move real focus the way a browser click does, so the test simulates the realistic pre-condition rather than relying on an environment quirk.
- **Next/previous scope:** `imageAttachments` in `AttachmentList` is derived by filtering `localAttachments` to `image/*` mime types, in the same order they're rendered in the list — navigation never includes non-image attachments, matching "the task's other image attachments" in the feature spec.
