## Decisions made
- Reused board.tsx's exact optimistic-update/rollback/single-toast shape (`snapshot` captured before `setByDate`, a `rollback(message)` closure guarded by a `rolledBack` flag, `toast.error` from sonner) rather than inventing a second convention, per the spec's explicit instruction.
- Extracted the drop-target date math into a new pure `lib/calendar/reschedule.ts` (`planReschedule`) rather than inlining it in the client component — matches the clarified spec's "pure, side-effect-free module under lib/, unit-tested independently of React and Supabase" answer, and gives the off-by-one/adjacent-month guarantees their own fast, deterministic unit tests instead of only being provable via a slow real-DB integration test.
- `planReschedule` never constructs a `Date` object anywhere — `targetDate` (the dropped-on cell's own `day.date`, already computed correctly for leading/trailing days by F232's month-grid.ts) flows through as an opaque string into both the returned bucket and the `dueDate` field sent to `editTask`. This is what makes the off-by-one/timezone guard hold.
- `canDrag` is gated on workspace-level `canWrite` (same predicate + `useMembership` null-fallback as board.tsx), NOT on a per-project precomputation — the calendar is workspace-wide and has no per-task project-role data available client-side to hide with. Per-project visibility variance (AS spec's "permission varies per task across projects") is left entirely to `editTask`'s own `isProjectVisibleToCaller` re-check, which rejects the specific rejected drop with a rollback + toast rather than ever silently succeeding or crashing. This matches the spec's explicit "Enforce in the ACTION, not by hiding UI" instruction.
- Did not add a keyboard-drag-shortcut UI (the draft scope's "Keyboard alternative: focus a chip and use a date shortcut" note, AS-523) — AS-523 is not among this feature's assigned assertion IDs (only AS-445 is), and the clarified spec's assigned scope is silent on it beyond that draft note. The KeyboardSensor IS wired (dnd-kit's built-in keyboard-driven dragging, same as board.tsx), so a focused chip is still keyboard-draggable via dnd-kit's own arrow-key gesture — just not via a separate one-key "shortcut" UI. Flagged below as out-of-scope in case AS-523 is assigned to a future feature.
- DayOverflow's popover chips (tasks beyond the first 3 visible per cell) are NOT made draggable — dragging out of a closed popover is not a reasonable interaction, and the spec's file list didn't include day-overflow.tsx. Left untouched.
- Converted `day-cell.tsx` from a Server Component to a Client Component (required — dnd-kit hooks are client-only). It has no data-fetching of its own either way, so this doesn't change what it renders when `canDrag` isn't in play (defaults to `true`, matching every pre-F234 caller/test).
