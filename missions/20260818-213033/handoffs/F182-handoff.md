## Decisions made
- **Dropped-assignee handling (the spec's explicit, easy-to-miss instruction)**: `createTaskFromTemplate` re-checks EVERY assignee id saved in the template's payload against active membership of the TARGET workspace at apply-time (not save-time — a template can be saved once and reused indefinitely, and membership drifts in between). Any id that fails `requireActiveMembership` is silently excluded from the `task_assignees` insert; the create never fails because of a stale assignee. The dropped ids ARE still returned in the result (`droppedAssigneeIds`) alongside the ids actually applied (`assigneeIds`), so a future UI caller can optionally surface a non-blocking notice — but this is purely informational, never a blocking error. Proven by the "createTaskFromTemplate silently drops assignees who are no longer members of the target workspace" test: a template payload with one valid + one nonexistent assignee id still creates successfully with only the valid one applied.
- **`payload` shape validated by a shared Zod schema (`taskTemplatePayloadSchema` in `lib/validation/templates.ts`)**, used by BOTH the producer (`saveTaskAsTemplate`, which builds the payload) and the consumer (`createTaskFromTemplate`, which re-parses the stored jsonb before using it) — the single source of truth the clarified spec's "no second source of truth" rule calls for, and defense against a hand-edited or pre-F182 row with an unexpected shape (mapped to a specific user-facing error, not a raw crash, if parsing fails).
- **Reused F176's `cloneTaskFields` (not a re-derivation of the allow-list)** in `saveTaskAsTemplate`, exactly like F180's `duplicateTask` does — title/description/description_json/priority/checklistItems/estimate_minutes are produced by `cloneTaskFields`, and `tags` is added separately (same convention F180 established: tags are a plain column copy, not part of the recurrence allow-list).
- **The new task's key/number is never computed by this feature** — `createTaskFromTemplate`'s insert omits `number` entirely, letting F145's `assign_task_key` DB trigger assign it, identical to `createTaskForUser`/`duplicateTask` in `lib/actions/tasks.ts`. No new key-generation code was written.
- **A template must be applied within its own workspace**: `createTaskFromTemplate` re-checks `templateRow.workspace_id === projectRow.workspace_id` server-side and returns "Template not found" (not a permission-specific message) if they differ, so a template id from a different workspace can never be probed/distinguished from a nonexistent one by an unauthorized caller (same "not found, not forbidden" convention the codebase uses elsewhere for cross-tenant lookups).
- **AS-331's permission rule was re-implemented in the Server Action layer** (`isCreator || isAdminOrOwner`, checked explicitly before the mutation) rather than relying solely on RLS, per the clarified "access control re-verified server-side ... even though RLS also enforces it" answer — this matters concretely here because both actions use the ADMIN client (which bypasses RLS entirely), so the app-level check is the ONLY enforcement these two actions perform; RLS from F181 remains the backstop for any other caller of the table (e.g. a direct client-side query).
- **No new "notes for clarification" open question needed resolving** beyond the one already pre-resolved in the spec itself ("templates are snapshots, not live links") — nothing else in the spec was ambiguous enough to require a default.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose to return both `assigneeIds` (applied) and `droppedAssigneeIds` (silently excluded) from `createTaskFromTemplate`'s result rather than only the applied list — the spec only requires the create to succeed despite the stale assignee, not that the caller be told which ones were dropped, but returning both costs nothing and lets a future UI show a "some assignees were removed" notice without a second round trip. This does not change the "drop, never fail" behavior the spec requires.
AUTONOMOUS_DECISION: `createTaskFromTemplate` accepts an optional `status` parameter (defaulting to `"todo"`) not explicitly named in the spec's function signature sketch (`createTaskFromTemplate(templateId, projectId, ...)` — the `...` was left open). Chose this because a template payload has no saved status of its own (status isn't part of `taskTemplatePayloadSchema`, matching `cloneTaskFields`'s convention that every fresh creation starts at "todo" unless the caller says otherwise) and every other create path in this codebase (`createTaskForUser`) already accepts an optional status override — this keeps the new action consistent with that existing pattern rather than inventing a new one.
