## Decisions made
- **Reused `resolveVisibleMentionIds` directly rather than writing a second "list visible members" query**, per this follow-up's own instructions and F204's own handoff Notes recommendation — exported the existing function instead of duplicating the (active workspace member AND (workspace-visible OR owner/admin OR explicit project_members row)) rule a second time.
- **Returns only ids from the new Server Action, not full member records.** `comment-list.tsx` already has full member display data (name/email/avatar) in its own `members` prop; the action only needs to narrow which of those ids are offered, so it doesn't duplicate a second member-record fetch (no `resolvePeople` call, no second N+1 risk).
- **On mount / while resolving / on fetch failure, `mentionSuggestions` is empty, not "fall back to all members."** This is the safer default for a "not offered" requirement — AS-376 says a user without access must not be offered; a transient loading or error state defaulting to the wider list would violate that, even if only briefly. This means there's a short window after opening a task where the picker offers nothing before the candidate list resolves (typically one client-server round trip) — acceptable per the "simpler option, no new dependency" default, and per this feature's own explicit "no second source of truth" instruction: the composer/editor's own text editing is fully usable during that window, only the mention picker's candidate list is temporarily empty.
- **State reset on `taskId` change uses the "adjust state during render" pattern**, not a synchronous `setState` inside the effect body — the latter tripped the `react-hooks/set-state-in-effect` ESLint rule (`Calling setState synchronously within an effect can trigger cascading renders`). Matches `comment-list.tsx`'s own pre-existing `syncedTaskId` convention exactly (a second `syncedMentionTaskId` mirror), so this file now has two parallel "reset on taskId change" state pairs rather than one function handling both — kept separate rather than merged into the existing `syncedTaskId` reset block, since that block already has its own unrelated set of resets (draft/editingCommentId) and folding an unrelated concern in would make it harder to reason about.
- **Found and fixed a real regression during full-suite verification**: `tests/unit/undo-toast.test.tsx` mocks `@/lib/actions/comments` and renders the real `CommentList`; it did not include `getMentionCandidates` in its mock, so CommentList's new mount-time effect threw synchronously inside `commitHookPassiveMountEffects` and failed that test. Fixed by adding `editComment` and `getMentionCandidates` (resolving to `{ ok: true, data: { userIds: [] } }`, irrelevant to that test's delete/undo assertions) to its existing mock object — this is exactly the kind of "Files changed" ripple this follow-up's own instructions anticipated ("Read components/task/comment-list.tsx... first to see exactly how members/mentionSuggestions currently flow") and is in scope as a direct consequence of narrowing the picker, not a separate feature.
- **Verified `tests/unit/user-avatar.test.tsx`'s one failure is pre-existing, not caused by this change**: `git stash`-ed this feature's diff and re-ran that file alone — it fails identically (missing Supabase env creds for `use-reactions-realtime.ts`'s real browser client, a real Supabase URL/key is not present in the test env) with or without this feature's changes. Left un-mocked/untouched since fixing it is out of this follow-up's scope (it isn't in the "Touches" list and isn't caused by this change).
