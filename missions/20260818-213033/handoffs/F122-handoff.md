## Decisions made
- **Colour is computed, never stored.** `profiles.color` (added by F120, still unpopulated) is deliberately left untouched. AS-204 asks for a colour "derived deterministically from the user id" — computing it on the fly from `person.id` via `lib/user-color.ts` is simpler, has no write path to maintain, and is the only way to guarantee "the same person always gets the same colour" everywhere without a migration backfilling every existing user. Per the clarification's ambiguity-resolution default (simpler option, no second source of truth), this is the one I took.
- **Fixed, theme-independent hex palette (8 colours), not derived from `app/globals.css`'s `--background`/`--foreground`/`--chart-*` tokens.** Checked `app/globals.css` first, per this feature's explicit instruction: the existing token system's chart colours (`--chart-1`..`--chart-5`) are grayscale, not a categorical hue palette, so there was nothing color-coded to extend. Instead this follows the precedent `lib/task-colors.ts` (F073/F087, AS-154) already set for STATUS_COLORS/PRIORITY_COLORS: plain hardcoded hex pairs, chosen and contrast-checked once, used identically as inline `style` values regardless of the light/dark toggle. Each of the 8 background/foreground pairs was verified ≥4.5:1 (WCAG AA, normal-size text — the initials are small text, so the 4.5:1 threshold applies, not the 3:1 large-text/graphical-object threshold `task-colors.ts` uses for its non-text dots) via a Node contrast-ratio script during design, then locked in by `tests/unit/user-color.test.ts`'s `test_AS_526_user_color_palette_meets_wcag_aa_text_contrast` suite. Because the pairs never change with the app's theme, "meets WCAG AA in both light and dark themes" (this feature's explicit instruction, and AS-526 which re-checks this at the end of the mission) holds unconditionally rather than needing a separate light-mode/dark-mode check.
- **djb2 string hash, `>>> 0` then `% palette.length`.** Small, pure, dependency-free, deterministic across Node/browser — no crypto API, no external package. Not collision-resistant in a cryptographic sense, which is fine: it only needs to pick a display bucket, not protect anything.
- **`lib/user-color.ts` has zero React import**, per this feature's explicit instruction, so F224's swimlane/grouping colours can import `AVATAR_PALETTE`/`userColorIndex`/`getUserColor` directly without pulling in `components/user-avatar.tsx` or any UI dependency.
- **Accessible name via `role="img"` + `aria-label` on the `<Avatar>` root, with both the `<img>` and the initials `<span>` marked `aria-hidden`.** Base UI's `Avatar.Fallback` (`components/ui/avatar.tsx`) is documented as "rendered when the image fails to load or when no image is provided" — i.e. it swaps automatically based on internal image-load state. Putting the accessible name on the root instead of on whichever child happens to be visible means the name is correct and constant regardless of that internal timing (an `alt` on the image alone would announce nothing while the image is still loading).
- **New shared module `lib/queries/people.ts`** (not in the Draft scope's approximate file list) factors out the "batch-fetch `profiles.display_name`/`avatar_url`, fall back to the Auth Admin API only when `display_name` is null" logic that both `lib/queries/assignee-names.ts` and `lib/queries/members.ts` needed. Added because the alternative — copy-pasting the same ~25-line Admin API loop into both files a second time — would create the exact "second source of truth" the clarification's ambiguity-resolution rule says to avoid, and because AS-214's own assignment explicitly says to "extend the existing query rather than adding a second per-row fetch": this resolves `display_name`/`avatar_url` with ONE batched `.in("id", ids)` query per call site, not one query per id.
- **`resolveAssigneeNames`'s signature and return shape (`Map<string, string>`) are unchanged**, specifically to keep `tests/integration/list-view-render.test.ts`'s pre-existing `"AS-085: resolveAssigneeNames resolves a display name..."` test (mission-1, not owned by this feature) passing untouched. It's now implemented on top of the shared `resolvePeople` resolver instead of its own Admin API loop, but for a member with no `display_name` set (true of the test's seeded member, since F120 creates profile rows with `display_name = null`), the observable result is identical to before: the auth email. A new sibling export, `resolveAssignees`, returns the richer `{ name, email, avatarUrl }` shape for future callers.
- **Board/list/dashboard-table avatar maps are built directly from `getWorkspaceMembers`'s result, not from a separate `resolveAssignees()` call.** `assignTask` (`lib/actions/tasks.ts`) only ever accepts an active workspace member's id as `assigneeId`, so every task's assignee is, by construction, already present in the `workspaceMembers.active`/`members.active` array these three pages fetch anyway (for the assignee filter/creation pickers). Building `Map<string, UserAvatarPerson>` from that existing array costs zero extra queries — this is actually a net *reduction* in query count versus the pre-F122 code, which had `list/page.tsx` and `dashboard-task-table.tsx` each separately call `resolveAssigneeNames()` (its own Admin-API-backed resolution) AND `getWorkspaceMembers()` (a second, largely-overlapping resolution) for the same set of people. Documented as a deliberate perf improvement, not just incidental.
- **Trade-off accepted, documented in-code:** a task whose assignee changes via a Realtime event from another viewer (`components/board/use-board-realtime.ts`) keeps showing its previous assignee's avatar (or none) until the next full page load, because `assignees`/`assigneeOptions` are resolved once server-side and not re-resolved on every Realtime reconcile. This is the same pre-existing limitation `assigneeNames`/`resolveAssigneeNames` already had before this feature (a Realtime-introduced new assignee id was never in that Map either) — not a regression, and out of scope for AS-204/AS-214 to fix.
- **`task-list-table.tsx`'s prop was renamed from `assigneeNames: Map<string, string>` to `assignees: Map<string, UserAvatarPerson>`**, rather than adding a second parallel prop, since the Assignee column now needs the full person shape (avatar + name), not just a display string. Both existing callers (`list/page.tsx`, `dashboard-task-table.tsx`) and two pre-existing unit tests (`tests/unit/list-table-status-priority-colors.test.ts`, `tests/unit/list-view-empty-state.test.ts`) that passed `assigneeNames: new Map()` were updated to `assignees: new Map()` — a mechanical rename with no assertion/behaviour change (both tests already passed an empty Map; neither test's Map contents were ever inspected).
- **Files touched beyond the Draft scope's "approximate" list** (`components/board/*`, `app/.../board/page.tsx`, `app/.../list/page.tsx`, `lib/queries/people.ts`, `lib/queries/members.ts`): all are necessary plumbing to get resolved assignee data (id/name/email/avatarUrl) from the server-side query down to `components/task/task-card.tsx` — the one AS-214-named surface (task cards) that had zero existing person-rendering to "replace," so there was no pre-existing call site to edit in place; the data path had to be built. Reported here per this feature's own instruction to enumerate every call site touched, rather than silently expanding scope.

## Out-of-scope work needed
- **Pending invites (members settings page) still show a plain initials span, not `<UserAvatar>`.** An invite row has no `auth.users`/`profiles` id yet (it's keyed by `invited_email` only), so AS-204's user-id colour hash has nothing to key on. If a future feature wants visual consistency here too, it would need either a placeholder non-personal colour or to wait until the invite is accepted.
- **`profiles.color` (F120's column) remains permanently unpopulated by design** — this feature computes colour on the fly instead of storing it. If a future feature wants to persist per-user colour overrides (e.g. a user picks their own avatar colour), it would read/write that column instead of always calling `getUserColor`, and `UserAvatar` would need a way to prefer a stored override over the hash.
- **A task's avatar can go stale for one Realtime event** if another viewer changes its assignee to someone not already in the page's resolved members set (see Decisions made) — self-heals on the next full page load/navigation. Not observed as a practical issue since assignees are always drawn from the same workspace's member list, which is small and already fully resolved per page load.
- **No client-side avatar-colour preview anywhere** (e.g. showing a user their own colour before they've set a display name) — not requested by AS-204/AS-214, not built.
