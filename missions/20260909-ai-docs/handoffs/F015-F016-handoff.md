## Decisions made
- Registered `propose_doc_edit` into `buildDocsAgentTools()` in `lib/ai/docs-agent.ts` as part of this feature (not left for a separate wiring step) — F014's own handoff flagged this explicitly as the next worker's job when the UI existed to render the resulting `proposal` event, which is exactly what F015 builds. Updated `lib/ai/__tests__/docs-agent.test.ts`'s `test_AS_004_tool_array_contains_exactly_the_three_existing_docs_tools` (now "...four registered docs tools") to match — this is the one pre-existing test this feature's own scope required touching, and it was a mechanical count/name update, not a behaviour change.
- The route handler (`app/api/ai/docs/route.ts`) needed NO changes — F014 had already built its `PROPOSAL_TOOL_NAMES` whitelist and `asProposal()` parser to include `"propose_doc_edit"` in anticipation of this feature, and the NDJSON `proposal` event shape it emits already matches what `useDocAssistant` (F008) parses into `ProposalView`. Confirmed via `tests/integration/f007-docs-agent-route.test.ts` passing unmodified.
- `acceptProposal`/`rejectProposal` were added to `useDocAssistant` (they did not exist before this feature — F008's hook only had `messages`/`toolCalls`/`proposals`/`send`/`stop`/`reset`). Both are pure `setProposals` transitions with a `status !== "pending"` guard — no network, no knowledge of `updateDoc` or Supabase. This keeps the "one-time" invariant (AS-065/066: a settled proposal can never move again) enforced in exactly one place, reusable regardless of what UI calls it.
- **The editor-bridge approach (`lib/ai/doc-editor-bridge.ts`)**: `MarkdownEditor` and `AssistantSidebar` are SIBLING components under the workspace layout (the sidebar mounts in `layout.tsx`; the editor mounts in the page it wraps — confirmed by reading both files), not ancestor/descendant, so there's no React context tree that naturally spans both without hoisting a provider absurdly high for one narrow need. Used the SAME "leaf announces itself upward" shape `components/docs/markdown-editor.tsx` already uses for its breadcrumb title (`useSetBreadcrumb`), but as a plain module-level `Map<docId, handle>` registry instead of a context, since the consumer (`ProposalCard`) needs an imperative pull-on-click lookup keyed by a specific `docId` from the proposal payload, not a subscribed value. This is option 1 from F016's spec ("Cancel/flush the pending debounce before applying, then apply, then push the new content into the editor via setContent") — chosen over option 2 because it keeps the persisted DB row and the editor's in-memory state provably in sync at every step, rather than accepting a window where they briefly disagree.
- `applyDocEditProposal`'s staleness check compares against the DB row's live `content` (a second, independent read), while `ProposalCard`'s pre-flight check (before ever calling the server action) compares against the mounted editor's LIVE in-memory markdown via the bridge. Both use the identical `normalizeForStaleCheck` (trim trailing per-line whitespace, normalise CRLF→LF) so a client-side false-positive rejection and a server-side one can never disagree over an invisible difference. If no editor is currently mounted for that doc (e.g. the user accepted a proposal for a document that isn't the one currently open), the client-side pre-check is skipped entirely and the server's own DB-row check is the sole guard — still correct, since the DB row is the actual thing that would be overwritten.
- `applyDocEditProposal`'s read (`select("title, content")`) is needed for two reasons, not one: the staleness comparison, AND to preserve the doc's own `title` when calling `updateDoc(docId, title, proposedMarkdown)` — `updateDoc`'s signature requires a title, and this action never lets the model author or influence the title, only the body content.
- `ProposalCard`'s payload narrowing (`asDocEditProposal`) treats an unrecognised or `doc_create`-kind payload as "render nothing" rather than throwing — `doc_create` proposals cannot occur yet (F017's `create_doc` tool is unregistered, per its own out-of-scope note), but the card is defensive against a payload shape it doesn't yet know how to render rather than crashing the whole sidebar.
- Diff rendering (F015) does NOT pull in a browser diff library — it renders the diff already computed server-side by F014's `propose-doc-edit.ts` (`DocEditDiffLine[]`, built from the `diff` package's `diffLines`, which groups consecutive same-type source lines into one `value` chunk). `diff-view.tsx`'s `expandDiffLines` only splits those already-classified chunks on `"\n"` for one-row-per-line rendering — no independent diff computation happens in the browser, per F015's spec's explicit instruction not to add a dependency for something already computed.
- Used `variant="default"` (the app's one filled/bg-primary treatment) on Accept — confirmed via reading `assistant-composer.tsx` that the sidebar's Send/Stop buttons are `ghost`/`outline`, so Accept is the only filled button on this screen, satisfying the "one filled button per screen" design-system rule.

## Notes for the next worker
- `getDocEditorHandle(docId)` returning `null` is a normal, expected case (no editor currently mounted for that doc) — `ProposalCard` already handles it by skipping the client-side live-content pre-check and relying solely on the server action's own DB-row staleness check. Any future caller of this bridge should preserve that same graceful-degradation shape rather than treating a missing handle as an error.
- `normalizeForStaleCheck` (lib/actions/ai-proposals.ts) is exported and reused identically by the client-side pre-check in `proposal-card.tsx` — if the normalisation rule ever needs to change (e.g. to also collapse multiple blank lines), change it in exactly one place and both call sites pick it up.
- F017's `create_doc` proposal card, when built, should follow the same "one-time accepted/rejected collapse" shape this file establishes (`ProposalCard`'s three-branch render on `proposal.status`) for visual/behavioural consistency, even though its write path (creating a new doc row) will differ from this feature's edit-in-place path.
