## Decisions made
- Followed the orchestrator task brief's `DocCreateProposal` field shape (`{ title, markdown, folderId, templateName }`) over the on-disk `missions/20260909-ai-docs/features/F017.md`'s older wording (`{ title?, templateId?, sourceMaterial }` + `saveDocDraft`) — `lib/ai/tools/types.ts`'s actual `DocCreateProposal` type (already defined, per the task's own reading-list item 3) matches the orchestrator brief exactly, confirming the spec file on disk is stale relative to the type contract already committed to the codebase. Treated the type definition as the authoritative source over the older markdown wording, per "the clarified spec is the source of truth" combined with the more specific, more recently-consistent instruction.
- `create_doc`'s folder validation reuses `get_current_doc`'s (F003/F027) exact defence-in-depth shape: RLS-respecting `createClient()` PLUS an explicit `.eq` style workspace check in code, collapsing not-found/not-visible/wrong-workspace into one generic `ToolEmpty` message. This gives the tool a real "empty" and "cross-workspace isolation" case for AS-028's unit-test requirement, which a tool with zero DB reads could not have.
- `applyDocCreateProposal` performs two ordinary writes (`createDoc` then `updateDoc`), both pre-existing actions in `lib/actions/docs.ts` — `createDoc`'s own signature has no title/content parameters (always creates "Untitled"/""), so the AI-drafted title/markdown are applied as an immediate second write via the same `updateDoc` path F016 already established for human/AI-authored content. If the second write fails, the empty row from step 1 is left behind rather than rolled back (no cross-action transaction exists anywhere else in this codebase either) — documented in the action's own comment as an accepted, harmless tradeoff.
- `projectId` passed to `createDoc` is always `null` inside `applyDocCreateProposal` — threading the currently-open project's id from route context through `AssistantSidebar` → `ProposalCard` is out of this feature's Touches (`assistant-sidebar.tsx`, `proposal-card.tsx`, `lib/actions/ai-proposals.ts` only). `null` places the doc at the workspace's Docs root, the exact same target `components/docs/new-doc-button.tsx`/`docs-sidebar.tsx` use for their own "New doc" action outside a project route — an existing, supported location, not an invented one.
- `client_visible` is never touched by either write in `applyDocCreateProposal` — the `docs` table defaults the column to `false` at the schema level (`supabase/migrations/20260902010000_client_role_and_task_client_visibility.sql`), so an AI-drafted document is client-invisible by construction with no code path here able to override it. This satisfies the old F017.md spec's explicit "client_visible defaults to false for AI-drafted documents" rule for free, without this action needing to set anything.
- `ProposalCard`/`ProposalList` gained a new required `workspaceId` prop (threaded from `AssistantSidebar`, which already has it) — needed because `applyDocCreateProposal` requires a `workspaceId` and `doc_edit` proposals never needed one (`applyDocEditProposal` resolves everything from `docId` alone). This is the one small, necessary widening beyond the literal file list in "The card" section, called out here rather than done silently. Updated all existing `<ProposalCard .../>` call sites in `proposal-card.test.tsx` to pass a fixed `workspaceId="ws-1"`.
- `DocCreateProposalCard` is a separate component (not a branch inside `ProposalCard`) because its Accept path calls a different server action with a different result shape (`{ id } | { error }` vs. `applyDocEditProposal`'s `{ ok: true } | { ok: false; error }`) and needs the extra `workspaceId` prop — keeping the two proposal kinds' logic fully separate avoids one component juggling two unrelated write contracts.
- On Accept, `DocCreateProposalCard` never navigates itself (per spec: "do not navigate server-side; let the client decide") — it stores the returned `id` in local state and renders an "Open" link (`/w/<slug>/docs/<id>`, using the same `/w/<slug>/...` path-parse pattern `assistant-sidebar.tsx`'s `useWorkspaceSlugFromPath` already established, duplicated locally rather than exported/shared since exporting it would touch `assistant-sidebar.tsx`'s internals beyond this feature's Touches) once the accepted state renders.
- Content preview truncates at 200 chars with an ellipsis (`previewMarkdown`), matching the spec's "first ~200 chars content preview" instruction literally.
- Updated `lib/ai/__tests__/docs-agent.test.ts`'s tool-count test (four → five registered tools, alphabetical name list now includes `create_doc`) — the one pre-existing test this feature's registration step required touching, a mechanical count/name update.
