## Decisions made
- **Enter/Shift+Enter convention**: read `components/chat/message-composer.tsx` (the app's existing chat composer) and its dependency `components/editor/rich-text-editor.tsx` before writing anything, per the spec's explicit instruction. Grepped the whole repo for `pointer: coarse`, `ontouchstart`, `isTouchDevice`, and any touch/narrow-viewport-specific Enter handling — there is none anywhere in this codebase. The chat composer has exactly ONE Enter convention (Enter submits, Shift+Enter newline), applied unconditionally regardless of viewport width or pointer type, in both its plain-`Textarea` path and its rich-text (`onEnterSubmit`) path. This composer matches that single convention exactly rather than inventing a mobile-specific branch that would be the second convention for the same gesture in this app — see Out-of-scope work needed below for what a "real" mobile Enter=newline feature would require if the product wants it later.
- **`AssistantComposer` owns the whole composer DOM region**, including the AS-071 no-API-key message (not just the enabled-input path) — replaced F009's `hasApiKey ? placeholder : no-api-key-div` branch in `assistant-sidebar.tsx` with a single `<AssistantComposer hasApiKey=... />` call. AS-071 is assigned to F012 as well as F009 (F009's handoff only had to prove the branch existed structurally), so this feature owns the real copy/styling for both states end to end, following the same "the newest feature owns its DOM slot fully" pattern F010/F011 established for the thread/tool-card regions.
- **Auto-grow textarea**: no manual JS resize handler. `components/ui/textarea.tsx`'s shared primitive already ships `field-sizing-content` (a real CSS property, not a polyfill) — the SAME mechanism `message-composer.tsx`'s plain-`Textarea` path already relies on for its own `min-h-10 max-h-40` pair. Used `min-h-9 max-h-[9rem] overflow-y-auto` (≈6 rows at `text-mini`'s line-height, per the spec's "capped around 6 rows") instead of reusing chat's exact `max-h-40` figure, since this composer's spec asked for a specific row cap rather than chat's more general limit.
- **Model name**: `lib/ai/client.ts` exports `DOCS_MODEL = "claude-opus-5"` but that file's own header comment says "Do not import this from client components or the browser bundle" (it lazily constructs an Anthropic SDK client at import time) — importing it here would put the Anthropic SDK in the client bundle. Defined a local, display-only `MODEL_DISPLAY_NAME = "Claude Opus 5"` constant in `assistant-composer.tsx` instead, with a comment pointing at the server-only source of truth. See Out-of-scope work needed for a proper fix (a shared, client-safe constants module).
- **Token/cost meta figure**: `useDocAssistant` (`lib/ai/use-doc-assistant.ts`) parses `{"t":"usage","in":...,"out":...,"cached":...}` events off the wire but its `applyEvent` switch treats `"usage"` as a no-op (`case "usage": case "done": return;`) — it never accumulates or exposes a running total anywhere in its returned `UseDocAssistantResult`. This feature's `Touches` is `components/ai/assistant-composer.tsx` only (per F012.md's `## Files` list), and the hook is shared, load-bearing infrastructure several other features (F010/F011) already depend on — extending it wasn't in scope for this worker to do silently. `AssistantComposer` therefore accepts an optional `usage?: { inputTokens, outputTokens }` prop, renders a token count when given one, and renders nothing for that slot when it isn't (verified in tests: no `assistant-composer-usage` node when `usage` is omitted). `assistant-sidebar.tsx` currently passes no `usage` prop, so the meta row today shows only the model name. This is a genuine, real gap — not silently worked around — flagged below with a concrete follow-up spec, same pattern F011's handoff used for its own wire-protocol gap (tool call "arguments").
- **Colours/styling**: no hex literals, no `shadow-*`, no new `bg-primary` button (send/stop use `variant="ghost"`/`variant="outline"` respectively, per F009's handoff note on this). The composer's internal meta-row separator uses `border-line-row` (not `border-border`), matching the two-family rule — it's a row within the composer region, not a panel-level edge (the panel's own `border-t border-border` above the whole composer region, in `assistant-sidebar.tsx`, is untouched). `--text-quaternary` has no Tailwind utility wired up anywhere in `app/globals.css` (re-confirmed the same gap F009's handoff already flagged) — used `text-muted-foreground` for the meta row instead of inventing an unwired class, per the spec's explicit "follow F009's substitution, do not use it" instruction.
- Updated two `tests/unit/f009-assistant-sidebar.test.tsx` assertions whose testids this feature's DOM changes obsoleted: `assistant-sidebar-composer-placeholder` → `assistant-composer-input` (the real input F012 renders in its place) and `assistant-sidebar-no-api-key` → `assistant-composer-no-api-key` (the no-key message now lives inside `AssistantComposer`, not `assistant-sidebar.tsx` itself). Behaviour asserted is unchanged — only the DOM location of the same message moved, which is exactly what F009's own handoff predicted ("Composer internals ... F012").

## Out-of-scope work needed
- **Running token/cost usage is not tracked anywhere client-side.** `useDocAssistant` parses `{"t":"usage",...}` events but discards them. A follow-up should: (a) add `usage: { inputTokens, outputTokens, cachedTokens } | null` state to `UseDocAssistantResult` in `lib/ai/use-doc-assistant.ts`, accumulating (not replacing) across turns in the same thread since the spec asks for a *running* total; (b) if a cost figure (not just token counts) is wanted, pricing-per-token for `claude-opus-5` would need to live in a small shared constant (server- or client-safe) so the client can multiply without needing a live pricing API call; (c) pass the resulting value down through `assistant-sidebar.tsx` into `<AssistantComposer usage={...} />` — that prop already exists and is unit-tested (`tests/unit/f012-assistant-composer.test.tsx`'s "shows a running token count when usage is provided" case), so this is a pure additive wiring change with zero shape changes to this feature's own component.
- **Model name duplication.** `MODEL_DISPLAY_NAME` in `assistant-composer.tsx` is a hand-maintained copy of `lib/ai/client.ts`'s `DOCS_MODEL` ("claude-opus-5" → "Claude Opus 5"), because that file is explicitly server-only (constructs an Anthropic SDK client at import time) and can't be imported into a client component. If the model ever changes, both need updating by hand. A follow-up could extract just the model id/display-name pair into a small new client-safe constants file (no SDK import) that both `lib/ai/client.ts` and `assistant-composer.tsx` import from.
- **True mobile "Enter inserts a newline" behaviour** does not exist anywhere in this app today (verified by reading and grepping `components/chat/message-composer.tsx` and its `rich-text-editor.tsx` dependency — confirmed no touch/viewport branch). If the product actually wants that convention, it would need to be introduced as a NEW, deliberate feature applied consistently to BOTH `components/chat/message-composer.tsx` and this composer at once (using `lib/hooks/use-media-query.ts`'s existing `useMediaQuery(MOBILE_BREAKPOINT_QUERY)` hook, which already exists and is used elsewhere for exactly this breakpoint) — not something this worker should add to only one composer, per the spec's own "do not invent a second convention" instruction.
