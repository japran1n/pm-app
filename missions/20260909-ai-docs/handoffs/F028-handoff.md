## Decisions made
- History turns are validated with a dedicated Zod schema (`historyTurnSchema`: `role: z.enum(["user","assistant"])`, `content: z.string().trim().min(1)`) nested inside `requestBodySchema`'s `messages: z.array(historyTurnSchema).optional()`. An invalid role fails the existing top-level `requestBodySchema.parse()` try/catch, reusing the exact same "Invalid request body" 400 path the route already used for a missing `message` — no new failure mode was invented for malformed-role rejection.
- Turn-count and character-count caps are enforced as a second, explicit check *after* the Zod parse succeeds (not inside the Zod schema itself), because a single `.max()` on the array only bounds turn count, not aggregate character size across turns — the spec requires both. Chose `MAX_HISTORY_TURNS = 20` and `MAX_HISTORY_CHARS = 20_000` as conservative, unexciting defaults: generous enough for a real back-and-forth (F028's own worked example is 2 turns), small enough that the total per-request payload stays bounded regardless of what a client sends. No clarification file exists yet to pin an exact number, so this is an autonomous default (see below) sized to be obviously safe rather than tuned.
- Cap violations return a plain HTTP 400 JSON body (`{ "error": "..." }`), the same shape and timing as the existing Zod-parse-failure 400 — not a streamed NDJSON `{"t":"error",...}` event. Rationale: at the point these caps are checked, the NDJSON stream has not been opened yet (it opens after the membership check, further down `POST`), so there is no stream to write an `error` event into. This matches the existing convention for every other request-shape rejection in this route (missing `message`, missing `workspaceId`, unauthenticated) and is "a clear `error` event" in spirit — a single well-formed JSON error, returned promptly, never a throw/500 — even though its transport is a JSON body rather than an NDJSON line. If the orchestrator's intent was specifically an NDJSON `{"t":"error"}` for cap violations too, that would require moving the cap check inside the stream's `start()`, which conflicts with "before any model call" positioning that AS-007's precedent establishes for auth/shape checks in this route. Flagging this interpretation choice explicitly since the spec text says "error event" rather than "400 response."
- Prior-turn content is passed to `buildDocsAgentRequest` as plain string content on `BetaMessageParam` (`{ role, content: turn.content }`), matching the shape the route already used for the live user message. No content blocks, no `cache_control`, no way for a client-supplied history turn to inject a `tool_use`/`tool_result` block or reach the system prompt — the only surface a history entry can touch is the `messages` array's plain-text content, which `lib/ai/docs-agent.ts`'s Layer 3 (INJECTION_DEFENSE) system-prompt text already instructs the model to treat with suspicion for anything that looks like an embedded instruction. This mirrors the "treat prior-turn content as data, exactly as document text is treated" instruction in the spec: no new prompt text was added, and no code path lets history change the request's `system`, `tools`, or control flow — it only ever lands in `messages`.
- Did not build any `ai_threads` table, persistence, or thread lookup — `threadId` remains parsed-and-ignored, exactly as before. This feature only shapes the wire contract so a future F018/F019 worker does not need to touch `route.ts`'s core loop.

## Out-of-scope work needed
- F018 (server-side `ai_threads` persistence) and F019 (sidebar UI wiring `threadId` + accumulating/sending `messages`) are both still open — this feature only shapes the route's *acceptance* of history; nothing yet populates or resends it from the client UI. A future worker on F019 should have the docs sidebar accumulate its own turn history client-side and pass it as `messages` on each request, capped client-side too (defense in depth, not required by this feature) before hitting the route's server-side caps.
- AS-047 cannot go PASS until `ANTHROPIC_API_KEY` exists in this environment and a worker (or the orchestrator) runs a genuine two-turn exchange and inspects `cache_read_input_tokens`. Suggested follow-up captured below.
- Not addressed here (out of scope per spec): the ~1.5 KB stable-prefix-size concern the spec raises (whether the cacheable system-prompt block alone is below Anthropic's minimum cacheable prefix). This feature makes a longer prefix *possible* (history now sits in `messages` before the cache breakpoint's system blocks are sent — note the cache breakpoint is on `system`, not `messages`, so history growing does NOT actually grow the cached prefix; it only grows the *uncached* input). This is worth flagging: conversation history in this implementation is appended to `messages`, which sits entirely outside the `system` cache breakpoint's ephemeral block, so history alone does not increase the cached prefix size. If AS-047 remains unmet even with a real key and real 2-turn traffic, the fix is not more history — it is likely widening the cached breakpoint to also cover a stable prefix of `messages`, or the system layers being under the minimum cacheable size regardless.
