## Decisions made
- **Empty-state copy states the documents-only limit plainly, up front**: "This assistant can read and discuss your workspace's docs, and draft new content or edits for you to review. It can't browse the web, access files outside your docs, or take actions without your confirmation — it only knows what's written in this workspace's documents." Three sentences, per the spec's "two or three sentences" cap. Written to set the expectation before the first refusal has to say it, per the spec's explicit rationale.
- **Suggestion chips are doc-grounded when a doc is open, and doc-independent otherwise** — reusing the same `currentDocId` the context bar (AS-061, F009) already derives from the URL, no new state. When a doc is open: the spec's own two examples verbatim ("What's missing before I send this to the client?", "Shorten the introduction") plus a third genuinely useful default ("Summarize this doc in three bullet points") rather than padding to three with something advertisement-flavored. When no doc is open: the spec's third example verbatim ("Draft a new doc from material I'll paste") plus two more workspace-scoped defaults ("What docs exist in this workspace?", "Help me outline a new doc").
- **Chips call `send` directly, not the composer's local `value` state** — `AssistantEmptyState` receives `send` as a prop straight from `useDocAssistant` (the same instance `assistant-sidebar.tsx` already owns; no second hook call, matching F009's established rule). This satisfies AS-068's "submits it immediately" literally: one click, no intermediate step, unlike routing through the composer's textarea would require.
- **Usage wiring (Part 2) stayed strictly additive** to `lib/ai/use-doc-assistant.ts`: added a `UsageTotals` interface and a `usage` state slot, filled the previously-no-op `case "usage"` branch in `applyEvent` to *accumulate* (not replace) `inputTokens`/`outputTokens`/`cachedTokens` across turns in the same thread — matching F012's handoff's own explicit framing ("a *running* total") — and cleared it in `reset()` alongside the other per-thread state. No pricing/cost calculation added, per the spec's explicit "token counts only" instruction. `AssistantComposer`'s `usage` prop already existed (F012) and its rendering logic (`inputTokens + outputTokens` + `"tokens"` label) was untouched — this feature only supplies the previously-missing data source.
- **Chip visual treatment**: `border-line-row` (row separator family, since chips sit inside the thread region as list-like items, not at a panel edge — matches the two-family rule the same way the composer's meta-row separator already does), `hover:bg-muted` (no new `bg-primary` button — the "one filled button per screen max" rule is already spent on the composer's send-in-context styling, and chips are secondary actions), zero shadow, and the exact `focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50` classes copied verbatim from `components/ui/button.tsx`/`components/ui/textarea.tsx` rather than inventing a new focus treatment.
- Deleted the now-dead `assistant-sidebar-thread-placeholder` testid/paragraph F009 had used as a structural stand-in — grepped the whole repo first to confirm nothing else referenced it (F009's and F012's own test suites don't touch it either) before removing.

## Out-of-scope work needed
- **A cached-token indicator or per-message usage breakdown** is not shown — the meta row (from F012) only ever displayed `inputTokens + outputTokens` as a single "N tokens" figure, and this feature didn't change that rendering, only supplied real data for it. If a future feature wants to surface `cachedTokens` separately (now tracked in the hook's `usage.cachedTokens`, just not rendered), that's a pure `assistant-composer.tsx` rendering change, zero hook changes needed.
- **No reset-on-new-thread affordance exists yet in the UI** — `useDocAssistant`'s `reset()` (which now also clears `usage`) is exported but nothing in `assistant-sidebar.tsx` currently calls it; there's no visible "new thread" control anywhere in the sidebar today. Out of scope for F013 (not in its Files list), but worth flagging since `usage` accumulating forever within a mounted session (no reset trigger) means a very long-lived open sidebar could show a growing total across unrelated conversational turns, not just one thread. Not a functional bug — usage is display-only, no cost gate depends on it — but a future feature adding "new thread"/"clear" would want to call `reset()` (already correctly wired to zero usage too).
