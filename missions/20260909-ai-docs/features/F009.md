# F009 — Sidebar shell

## Goal
The panel itself: docked right, toggleable, context-aware.

## Files
- `components/ai/assistant-sidebar.tsx` (new)
- wiring into the workspace layout + top bar

## Design constraints (CLAUDE.md lines 85-105 — non-negotiable)
- **Zero shadow.** Sidebar is not an overlay. Elevation comes from `bg-level` changes.
- `--border` (#23252a) for the panel edge; `--line-row` (#202122) for internal separators.
  They are different families — do not interchange.
- Font weights **510** (medium) and **590** (semibold). Not 500/600.
- `--text-quaternary` only for decorative labels, never operational text.
- At most one filled `bg-primary` button per screen — the workspace already spends it.
  Every button in this sidebar is transparent with hover fill.
- **No new colour literals.** The "sand = proposed" and "green = accepted" semantics
  from the approved preview must map onto existing tokens. Find the nearest existing
  warning/attention and success tokens and use those. If genuinely none exist, add them
  to the token layer in `globals.css` following F001's conventions — do not inline a hex.

## Behaviour
- Toggle lives in the workspace top bar next to search.
- Open/closed state persisted in `localStorage`, restored on mount, wrapped in
  try/catch (private browsing throws).
- Context bar shows the currently open doc's title; updates on navigation **without
  clearing the thread** (AS-061).
- When `hasApiKey()` is false the panel still renders; composer disabled with one
  clear sentence (AS-071). Never crash or blank the workspace.

## RESOLVED BY ORCHESTRATOR (2026-09-09) — use these tokens, do not invent any
The semantics from the approved preview map exactly onto tokens that already exist in
`app/globals.css`. **No new tokens are needed. Do not add any.**

| Preview meaning | Token | Value |
|---|---|---|
| proposed / unreviewed (the "sand" card) | `--status-waiting` + `--status-waiting-bg` | `#b57a00`, 16% mix |
| accepted (the "green" collapsed row) | `--status-done` + `--status-done-bg` | `#12784f`, 16% mix |
| rejected / settled-neutral | `--muted` + `--muted-foreground` | — |
| panel edge | `--border` | `#23252a` |
| internal separators | `--line-row` | `#202122` |

Tailwind exposes these as `status-waiting`, `status-waiting-bg`, `status-done`,
`status-done-bg` via the `@theme` block at the top of `globals.css`.

Reusing the status palette is deliberate: a proposal genuinely *is* a waiting state and
an applied edit genuinely *is* a done state, so the app's existing colour language already
says the right thing. A bespoke AI palette would teach the user a second vocabulary for
the same idea — which the design system's own scope rule forbids.

## RESOLVED BY ORCHESTRATOR (2026-09-09) — where this mounts
Read `app/(workspace)/w/[workspaceSlug]/layout.tsx` before touching anything. Its shape:

```
<div className="flex h-svh">
  <AppSidebar ... />                                   ← left nav
  <div className="bg-background border border-border   ← the raised panel F003 introduced
                  rounded-lg m-2 flex-1 min-h-0 flex flex-col">
    <WorkspaceMain>
      <ClientPresentationBanner ... />
      <AppHeader ... />
      {children}
    </WorkspaceMain>
  </div>
</div>
```

**Mount the assistant as a sibling raised panel**, right of that existing one, inside the
same `flex h-svh` row — mirroring `AppSidebar`'s relationship on the left. It gets the same
`bg-background border border-border rounded-lg` treatment and its own `m-2` gutter, so it
reads as a peer panel rather than an overlay drawer. This is what makes the zero-shadow
rule work: elevation comes from the panel structure that already exists.

Do NOT mount it inside `WorkspaceMain` — that would make it scroll with page content and
lose its independent scroll region.

The layout file carries long comments explaining why the height chain is built the way it
is (`h-svh` → `min-h-0` → `flex-col`). Read them and do not break that chain; a stray
`h-full` or a missing `min-h-0` in your panel will collapse or overflow it.

**Toggle placement**: `components/nav/app-header.tsx`, next to `components/nav/header-search.tsx`.
Match the existing header control's size, hit area and hover treatment exactly.

**Width**: fixed ~380px on wide viewports. Below ~1180px the assistant panel should
overlay rather than squeeze the content panel — at that point it IS an overlay and may
take a shadow, per the shadow rule's overlay exemption. Note that decision in the handoff.

## Existing context to reuse, not rebuild
- `BreadcrumbProvider` (`components/nav/breadcrumb-context.tsx`) already tracks what the
  user is looking at. Check whether the current doc's id/title is available there before
  adding a new provider or prop-drilling from the doc page.
- `MembershipProvider` supplies the workspace and role. Use it; do not re-query.
