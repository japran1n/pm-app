# F036 — Panel containment, overlay dismissal, and the no-key path (fixes B5, B6, B3)

## B5 — the panel overflows; the comment claims otherwise
`assistant-sidebar.tsx:331` — a `div.flex.min-h-0.flex-1.flex-col` whose comment says
"Independent scroll region… must never inherit page-level scroll", and which has **no `overflow`
class at all**. Only the thread scrolls. `ToolCallList` and the error `<p>` are unshrinkable
siblings (auto height, `min-height: auto`).

With several tool cards — the route caps at 8, each expandable — the thread is squeezed toward
zero and the list **overflows the `aside`**, painting outside the rounded border, over the
composer, and off the bottom of the viewport where it cannot be reached.

Renders perfectly in jsdom. The fix is essentially one class.

**Fix:** add `overflow-y-auto` at :331, or move `ToolCallList` inside the thread's scroller and
give the error row `shrink-0`. Prefer moving the list into the scroller if it reads better — see
the note below about interleaving.

## B6 — the <1180px overlay cannot be closed
`assistant-sidebar.tsx:300` — `max-[1180px]:fixed inset-y-2 right-2 z-40 w-[380px]`. The only close
affordance is `AssistantSidebarToggle`, which lives in the header's right cluster
(`app-header.tsx:70`) — **underneath the overlay**. No close button, no Escape handler, no
backdrop, no outside-click, no focus trap, no `aria-modal`. State is persisted, so a reload
restores it still-open. At 1024–1180px the user is simply stuck.

**Fix:** a close button in the panel header (`:305`), an Escape handler, a backdrop and a focus
trap — the last three active **only** under `max-[1180px]`, where the panel genuinely is a modal
overlay. Do not add them at desktop width, where it is a peer panel and a focus trap would be wrong.

## B3 — the no-key path breaks on the first click
`assistant-sidebar.tsx:334` passes `send` to `AssistantEmptyState` unconditionally; `hasApiKey` goes
only to the composer (`:360`). The chips (`:236-246`) are neither disabled nor key-aware.

Sequence: composer correctly explains the key is missing → user clicks a chip → `send()`
optimistically appends the user turn → `messages.length !== 0` unmounts the **entire empty state
including the explanation** → the route returns `no_api_key` → a **second, differently worded**
message renders at `:345-352`. Two competing explanations, a phantom turn nobody will answer, and
no way back: `reset` exists on the hook (`:327`) but the sidebar never destructures it.

This is the **only state this environment can actually exercise**, since there is no API key.

**Fix:** thread `hasApiKey` into `AssistantEmptyState` and either disable or omit the chips when
false, so exactly one explanation is ever on screen. Expose the hook's `reset` in the sidebar so a
dead-end thread can be cleared.

**Test at the sidebar level, not the component level.** The existing F012/F013 tests render
components in isolation and structurally cannot see this interaction. Render the whole sidebar with
`hasApiKey={false}`, click a chip, assert exactly one explanatory message remains.

## Minors to fold in
- `--line-row` used as a control/panel border against the two-family rule:
  `assistant-sidebar.tsx:242` (chip outline) and `tool-call-card.tsx:148`. The `divide-line-row` on
  that same line is correct — only the `border` is wrong.
- Persistence key `"pm-app:ai-docs-sidebar-open"` (:41) is not workspace-scoped though the panel is.
- Composer is `disabled` while streaming (`:128`), dropping focus to `<body>` every turn; keyboard
  users must re-tab to reach Stop. Prefer `readOnly` or keep focus.
- `ToolCallList` and the error `<p>` sit outside the `aria-live` region, so tool activity and errors
  are never announced.
