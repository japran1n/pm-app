# F023 — Sever the service-role path from lib/ai (fixes B1)

## Why
`lib/ai/docs-agent.ts:23` imports `resolvePeople` from `@/lib/queries/people`, which calls
`createAdminClient()` (`lib/supabase/admin.ts:14` → `SUPABASE_SECRET_KEY`) and falls back to the
Auth Admin API. This runs on **every request** via `resolveDisplayName` (`docs-agent.ts:155`).
AS-001 states no code path in `lib/ai/**` may reach a service-role client. It does.

## Fix
Remove the admin-client reachability. Two acceptable options — pick one and justify it:
1. Replace the `resolvePeople` call with an RLS-scoped read of `profiles` for the caller's own
   display name (the caller can always see their own profile row).
2. Drop the display name from the prompt entirely. It buys very little and costs the mission's
   central architectural rule.

Prefer (2) if (1) still pulls in anything admin-flavoured. A prompt that says "the user" instead
of a name is a small loss; a service-role import in the prompt builder is a standing hazard.

## Also: make the guarantee testable (this is the more important half)
Write `lib/ai/__tests__/no-service-role.test.ts` that walks the **transitive import graph** of
every file under `lib/ai/**` and `app/api/ai/**` and fails if any reachable module references
`SUPABASE_SECRET_KEY`, `createAdminClient`, or `service_role`.

Resolve `@/` via the alias in `vitest.config.ts`. Follow static `import`/`export ... from`
specifiers recursively, ignore `node_modules`, and report the **full chain** on failure
(`docs-agent.ts → queries/people.ts → supabase/admin.ts`) so the next person sees the hop, not
just the leaf.

A flat text grep over `lib/ai/tools/` — which is what F014 currently plans — passes cleanly
while B1 sits one hop away. That is why this test must be transitive.

## Assertions
AS-001, and it strengthens AS-003's future grep test.

## Gate
`npx vitest run lib/` green; the new test must **fail** if you temporarily re-add the import
(verify that, then revert) — a guard that cannot fail proves nothing.
