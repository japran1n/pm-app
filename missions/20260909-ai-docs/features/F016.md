# F016 — Apply accepted edit

## Goal
The single, narrow, auditable write path.

## Files
- `lib/actions/ai-proposals.ts` (new server action)
- wiring in `components/ai/proposal-card.tsx`

## Rules
- This is an ordinary server action with `"use server"`, called from a click handler.
  It is NOT reachable from a tool, and the AI layer must not import it (AS-003 stays true).
- Signature: `applyDocEditProposal({ docId, expectedCurrentMarkdown, proposedMarkdown })`.
- **Stale check**: re-read the doc; if its markdown no longer equals
  `expectedCurrentMarkdown`, return an error telling the user the document changed and
  the proposal must be regenerated. Do not silently overwrite someone else's edit.
- Write through the existing docs update path in `lib/actions/docs.ts` so RLS,
  `revalidatePath` and any audit behaviour all apply identically to a human edit.
- Reject performs **zero** calls. Not a no-op write, not a status update — nothing
  touches the database (AS-010).
- On success the open editor view updates without a full page reload.

## Assertions
AS-009, AS-010, AS-065, AS-002

## Out of scope
Undo. Worth having, but it is a separate feature and the diff card plus normal doc
history already covers the common case.

## RESOLVED BY ORCHESTRATOR (2026-09-09) — read before writing code

### The write path already exists
`lib/actions/docs.ts:230` — `updateDoc(docId, title, content)`. Use it. Do not write a
second update path; it already does auth, RLS and `revalidatePath`.

### Storage format is plain Markdown — there is no conversion layer
`components/docs/markdown-editor.tsx` stores content as a plain Markdown string.
Its own import path is literally `setContent` + save (see the comment at ~line 271).
So applying an accepted proposal is the same operation as importing a `.md` file — reuse
that path rather than inventing one. Read the current text with
`editor.storage.markdown.getMarkdown()`, which the file already uses.

### ⚠ THE RACE — this is the part that will bite you
The editor runs a **800ms debounced autosave** (`AUTOSAVE_DEBOUNCE_MS`, ~line 81). If the
user has typed within the last 800ms when a proposal is accepted, the pending autosave and
your `updateDoc` will both fire and one will clobber the other — and the loser is
non-deterministic.

Handle it explicitly. In order of preference:
1. Cancel/flush the pending debounce before applying, then apply, then push the new content
   into the editor via `setContent` so the editor's own state matches what was persisted.
2. If the editor does not expose a way to flush, apply through the editor (`setContent`)
   and let its own autosave persist — but then the stale-check in this feature must run
   against the editor's live content, not the DB row.

Whichever you choose, say which and why in the handoff. Do **not** leave both writers
running unsynchronised and assume last-write-wins is fine — the whole point of the
Accept gate is that the user gets exactly the change the diff showed.

### The stale check
`expectedCurrentMarkdown` from the proposal must be compared against the document's
**live** content at accept time — which, given the above, may be the editor's in-memory
text rather than the DB row. Compare normalised (trim trailing whitespace per line,
normalise line endings) so an invisible difference does not produce a spurious rejection.

### MarkdownEditorProps
The component takes `docId`, `initialTitle`, `initialContent` plus a set of optional props
that each default to hiding an affordance. Follow that same convention if you add a prop:
undefined must mean "the caller hasn't been updated", and must degrade to current behaviour.
Read the prop comments — every one explains its default. Match that register.
