# F030 — Harden the AS-001 guard: it cannot see the codebase's dominant import style

## Why
`lib/ai/__tests__/no-service-role.test.ts:92-93` — `IMPORT_SPECIFIER_RE` uses `[^'"()\n]*?`.
The excluded newline means **every multi-line import is invisible to the graph walk.**

There are **430 repo-local multi-line import statements across 298 files** — it is the house style.

Measured against real import forms:
```
FOUND   single-line named / default / require
MISSED  multi-line named        import {\n  a,\n} from "@/lib/x"
MISSED  multi-line type
MISSED  dynamic                 await import("@/lib/supabase/admin")
MISSED  export * as ns from
```

**Already blind on a live edge**: `lib/supabase/server.ts:24-27` imports
`@/lib/portal/preview-cookies` across multiple lines, so that subtree is unscanned today — out of
the single most security-relevant module in the graph, the one every tool imports. If anything it
reaches ever imported `lib/supabase/admin.ts`, the guard reports clean.

The original B1 violation was a three-hop chain. A three-hop chain whose middle edge is written in
the codebase's normal style is invisible right now.

**A guard that cannot see the dominant import style is worse than no guard, because it is trusted.**

## Fix
Replace the hand-rolled regex with a real parse of the import statements — or at minimum a
multiline-tolerant pattern that also covers `import(`, `export * as ns from`, and `export … from`.

Add a **self-test**: plant a deliberate 3-hop chain whose middle edge is a multi-line import into
a fixture, assert the guard detects it, then remove the fixture. A guard's own falsifiability must
be tested, not assumed — that is the lesson of this entire milestone.

## Also
`F023-handoff.md:49` claims the test "resolves `@/` via `vitest.config.ts`'s own alias definition."
It does not — it hardcodes `REPO_ROOT + specifier.slice(2)` at lines 66-71. Functionally equivalent
today, but correct the handoff so the next reader isn't misled.
