# F033 — Make tool results real (fixes B1 / AS-063)

`route.ts:438` sends the success `tool_end` with **no `detail`**, and `summarizeToolResult`
(`:161-172`) returns the bare literal `"ok"`, discarding the body. The card therefore computes
`hasDetail=false`, disables itself, and renders an inert row reading `search_docs  ok`. Expansion
works only on failure, revealing a constant. The test passes because it invents strings the route
cannot emit.

## Fix
- Extend the success `tool_end` to carry a **bounded, sanitised** `detail` derived from
  `resultContent`, following the pattern F026/F032 established: the server computes a safe string,
  never forwards raw model output.
- Replace `"ok"` with something informative — `"3 docs"`, `"1,240 words"`, `"no results"`.
- Add a sanitised, length-bounded **argument summary** to `tool_start`, carry it through
  `NdjsonEvent` and `ToolCallView`, and render it in the expanded panel alongside `detail`.
  Arguments are model-authored from portal-writable document text, so bound length and charset
  exactly as F032 did for the tool name.

## The test change is the point
Rewrite `tests/unit/f011-tool-call-card.test.tsx` to build fixtures from the route's **actual
`send()` payloads**. Extract a shared fixture module imported by both the route contract test and
the card test, so the two can never drift again. That drift is what let B1 ship green.
