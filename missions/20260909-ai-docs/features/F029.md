# F029 — Positive controls: prove the tools actually work (closes the B2 remainder)

## Why this is a blocker
Every assertion in all six real-DB isolation describes is `status === "empty"`. **No real-DB test
ever asserts a tool returns data.** So all of these mutants pass the entire M1 suite green:

```ts
builder.eq("workspace_id", "00000000-0000-0000-0000-000000000000")  // always empty
data.workspace_id !== workspaceId                                   // always true
forRunner dropping its second argument                              // workspaceId undefined
```

That last one is live: nothing asserts `forRunner` passes `workspaceId` through to `tool.run`.
If an M2 refactor drops it, `get_current_doc` returns not-found for **every** document forever
and `search_docs` errors on the uuid cast — with a perfectly green suite.

They all fail *closed*, which is the right direction for safety. But M1's exit criterion
(`plan.md:15`) is "Tools callable and tested with no UI at all", and **callable is not tested
anywhere against a real database.** The suite proves nothing leaks and never proves anything works.

This is the mirror image of the original B2. Same defect, opposite sign.

## Fix
1. In each of the three `tests/integration/*-isolation.test.ts`, add a **positive control**: seed a
   doc / template in workspace **A**, call the tool with A's id under A's real session, assert
   `status === "ok"` and the expected row comes back.
2. In `lib/ai/__tests__/docs-agent.test.ts`, assert `forRunner` passes the request's `workspaceId`
   as the second argument to each `tool.run`.
3. Add a nonexistent-uuid case to `get-current-doc-isolation.test.ts` and diff it against the
   cross-workspace response, so AS-008's byte-identity is proven **by construction** rather than
   against a hardcoded literal (`get-current-doc-isolation.test.ts:288-292`).

## Prove they can fail
Apply each mutant above in turn, confirm the new tests go red, revert. Record the evidence.
