# F026 — Stop leaking error text; fix search query construction (M1a, M1d, M1f)

## M1a — raw error text reaches the browser (AS-105)
`app/api/ai/docs/route.ts:284`:
```ts
const message = toolError instanceof Error ? toolError.message : "Tool execution failed.";
logger.error("docs agent: tool threw", { tool: toolUse.name, id: toolUse.id });  // omits message
send({ t: "tool_end", id: toolUse.id, summary: "tool error", detail: message }); // sends it anyway
```
The asymmetry is self-indicting: line 283 was written to keep the message out of the log, and
line 284 puts it on the wire. `lib/ai/tools/types.ts:33` forbids exactly this.

Reachable via Zod v4 parse failures at line 266 — Zod v4 embeds the offending input value, and
tool inputs are model-generated downstream of document text that client-portal users can author.
Also via undici/PostgREST transport errors carrying URLs.

**Fix:** send only the generic summary. Log the detail server-side through
`lib/observability/logger` where it is useful and safe. Also remove `error.message` from the
stdout log at `route.ts:394`.

**Test:** make a tool throw an error whose message contains a marker string, and assert the
marker never appears anywhere in the emitted NDJSON. Note that the existing AS-042 test uses
`toMatchObject`, which ignores extra keys — it *observed* `detail: "boom"` reaching the client
and said nothing. Do not use `toMatchObject` for this assertion.

## M1d — PostgREST filter injection in search_docs
`lib/ai/tools/search-docs.ts:106` escapes only `%` and `_`, then line 111 interpolates into a
filter **string**:
```ts
.or(`title.ilike.${likePattern},content.ilike.${likePattern}`)
```
Comma, parentheses and dot are PostgREST grammar metacharacters and are unescaped. A query
containing a comma (`budget, revised`) injects extra top-level OR terms.

RLS still ANDs over it, so this **cannot cross a workspace boundary** — but the query text is
model-generated from potentially injected document content, and it silently breaks ordinary
punctuation for users.

The precedent cited at line 105 (`lib/actions/palette-search.ts`) uses `.ilike()` as a *method*,
where the value is a bound parameter and this grammar never applies. The convention was copied
from a context where it was safe into one where it is not.

**Fix:** restructure to use `.ilike()` methods (two queries merged, or `.or()` built through the
client's own escaping) rather than hand-interpolating a filter string. **Test with a comma, a
dot and parentheses in the query.**

Also add `.order()` — the query is currently non-deterministic about which 10 of N rows return.

## M1f — proposal detection duck-types on tool output
`route.ts:64-94` (`asProposal`) keys the proposal path on `data.kind === "doc_edit"` — model-adjacent
data. Change it to a tool-**name** allowlist: `toolUse.name ∈ {propose_doc_edit, create_doc}`.
Equally easy and strictly safer. The path is inert today (those tools arrive in F014/F017), so
this is cheap to do now and awkward later.
