# F018 — Migration: ai_threads + ai_messages

## Files
- `supabase/migrations/<ts>_ai_threads.sql` (new)

## Schema
```
ai_threads
  id uuid pk default gen_random_uuid()
  workspace_id uuid not null references workspaces(id) on delete cascade
  project_id   uuid null references projects(id) on delete set null
  doc_id       uuid null references docs(id) on delete set null   -- context at creation
  created_by   uuid not null references profiles(id)
  title        text null                                          -- first user message, truncated
  created_at / updated_at timestamptz not null default now()

ai_messages
  id uuid pk
  thread_id uuid not null references ai_threads(id) on delete cascade
  role text not null check (role in ('user','assistant'))
  content text not null default ''
  tool_calls jsonb null      -- [{id,name,summary,detail}]
  proposals  jsonb null      -- [{proposalId,kind,state:'pending'|'accepted'|'rejected',...}]
  usage      jsonb null
  created_at timestamptz not null default now()
```

## RLS
Follow the conventions of the existing migrations exactly — read
`20261106010000_scope_documents.sql` and the `docs` policies first, and match their
shape and their long explanatory header comments.
- Threads are visible to **active workspace members** only.
- A user may only insert into a thread they created, in a workspace they are an active
  member of.
- Portal clients must see nothing. Assert this explicitly in the policy, not by omission
  — the F012 portal isolation work and the migration comments in `project_scope_documents`
  explain why membership-only checks have leaked before in this codebase.
