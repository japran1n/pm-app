# F011 — Tool call card

## Files
- `components/ai/tool-call-card.tsx` (new)

## Rules
- Collapsed by default: one row — tool name (mono), a result glyph, a one-line summary.
- Expands to show arguments and result detail. Use a native `<details>`/`<summary>` or
  an existing accessible disclosure primitive from `components/ui` — do not hand-roll
  a div with an onClick and no keyboard support (AS-069).
- A failed tool renders in the same card with an error summary — never a silent gap.
- Quiet by default. This card must never compete with the assistant's text for attention;
  it exists so the user *can* audit, not so they must.

## Assertions
AS-063, AS-069, AS-070

## Out of scope
Anything that mutates.

## ORCHESTRATOR NOTE (2026-09-09) — AS-063 is only partly met, by protocol

F011's worker found and flagged, rather than papering over, that the wire protocol never sends
tool **arguments** to the client: `tool_start` carries only `{id, name}`. So the expanded card can
show `detail` but not "the arguments" the spec asks for.

Verified by the orchestrator against `app/api/ai/docs/route.ts`.

**AS-063 is therefore PARTIAL, not met.** F022 must not mark it PASS. The card is collapsible, the
summary is there, expansion works — but half of what expansion was specified to reveal does not
exist on the wire.

**Deliberately not fixed inside F011.** Widening the protocol is a route change, and sending
model-generated tool inputs to the browser deserves its own look: the arguments are LLM-authored
from document text that client-portal users can write, so they need the same length/charset bound
F032 applied to the tool name before anything renders them.

**Follow-up (post-M2):** add `args` to `tool_start`, bounded and sanitised, then extend the card.
Small, but it is a protocol change plus a sanitisation decision, and it does not belong in the
middle of the UI milestone.
