## Decisions made
- List page: task types/templates/saved views were previously batched with the tasks query (`rawFilteredTasks`) further down, which meant they waited behind the view-resolution logic (`getSavedView`, filter building) even though none of the three depend on it. Moved them up next to `workspaceMembers` — the only three-way dependency they share is the resolved `workspace` object / `projectId`, both already available right after the first batch. The tasks query itself still runs in its own later `Promise.all` with `timezone`, since it genuinely depends on `filters`/`sort` computed from the view-resolution step in between.
- Board page: `workspaceMembers` and `templates` had no dependency on each other (both only need `workspace.id`), so merged into a single `Promise.all`, matching the pattern already used for the page's first batch (tasks/workspace/timezone/columns/swimlane prefs).
- Did not touch `getSavedView`, `getMyDefaultSavedView`, or the manual-view-membership follow-up fetch (`listViewTaskIds` / extra `getProjectListTasks` call) — those have real sequential dependencies (on `workspaceMembers`-derived `validAssigneeIds`, or on the view's resolved membership) and are out of this feature's scope (AS-016 names members/saved-views/task-types specifically, not the view-resolution chain).
- No behavioural change: same data is fetched, same fallbacks (`{ active: [], pending: [] }`, `[]`) apply when `workspace` is null, same variable names flow into the rest of each page.
