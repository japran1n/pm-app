## Decisions made
- **Dual-path (slot + back-compat fallback) instead of changing `AppSidebar`'s prop contract.** `AppSidebar`/`SidebarContent` gained new optional `React.ReactNode` slot props (`notificationBellSlot`, `workspaceSwitcherSlot`, `approvalsBadge`, `requestsBadge`, `chatUnreadBadge`) that take priority over the existing numeric/array props when provided. Rationale: at least 8 existing unit test files render `<AppSidebar>` directly with synchronous `renderToStaticMarkup`, passing plain numbers/arrays (`approvalsCount={3}`, `workspaces={[...]}`, etc.) — a hard cutover to Promise/`use()`-based props would have broken every one of them, which is exactly the "no page changes what it displays" violation AS-025 forbids. The real layout now always supplies the slot props (each wrapped in its own `<Suspense>`), so in production the streamed path is what actually renders; the numeric/array props remain purely as the tested fallback for direct callers that don't supply a slot.
- **Badge markup was moved verbatim into each figure component** (`approvals-badge-figure.tsx`, `requests-badge-figure.tsx`, `chat-unread-badge-figure.tsx`) — same `Badge` classNames, same `count > 0` gate, same fail-open-to-0 convention (chat's `.catch()` handler copied byte-for-byte from the old layout call site). `app-sidebar.tsx`'s own `navGroups()` keeps an identical inline `countBadge()` helper for the back-compat path, so both routes render byte-identical markup for a given count.
- **`components/nav/figures/favorite-project-ids-figure.ts` does NOT get its own Suspense boundary.** Two independent reasons, both documented in that file's own header comment: (1) `getFavoriteProjectIds`'s result is merged into the `projects` array *before* it's handed to `<ProjectNavList>`, whose `onNavigate` callback (closes the mobile nav sheet on click) only exists client-side inside `SidebarContent` — a server-streamed slot for the merged, favourite-aware project list would either lose that behaviour (forbidden by AS-025) or require duplicating `<ProjectNavList>`'s render logic in a server component; (2) AS-017 itself carves out "figures... required to render the navigation" — the Projects section (and its favourite flags) is arguably part of the primary navigation itself, so leaving it in the required, synchronously-awaited path does not violate the assertion's wording either way. Still isolated the fetch into its own file (re-exporting `getFavoriteProjectIds`) per this feature's file-list requirement, with the reasoning documented inline for the next worker.
- **`getWorkspaceProjects` (the plain project list, not favourites) also stays awaited by the layout**, not deferred: `<ProjectSwitcher>` (Cmd+P command palette, mounted at the top of the layout, not one of the 7 named figures) needs the same list synchronously and would otherwise lose its own current behaviour.
- **`WorkspaceSwitcherFigure` calls `getCurrentUser()` for its Supabase client** rather than a new `createClient()`, matching F013's established convention — `getCurrentUser` is wrapped in React's request-scoped `cache()` (see `lib/auth/current-user.ts`), so this is a cache hit, not a second network round trip, per `tech-decisions.md`'s "Request-scoped memoisation" section.
- Passed `workspaces={[]}` as the (now-inert) back-compat prop on the real `<AppSidebar>` call site in the layout, since `workspaceSwitcherSlot` always wins there — left a comment explaining why.
