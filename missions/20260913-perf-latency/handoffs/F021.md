## Decisions made
- Replaced `redirect(`${basePath}?viewId=${defaultView.id}`)` with computing an `effectiveViewId` local (defaulting to `query.viewId`, overridden by the resolved default view's id under the exact same "no view/filter param at all" guard the redirect used) and threading it into the existing `getSavedView(...)` call that previously only used `query.viewId`. This means the same request that would previously have triggered the redirect now renders directly with the default view already applied — no second request, no re-run of the proxy or either layout.
- Removed the now-unused `redirect` import from `next/navigation` and the now-unused `basePath` local (it existed solely to build the redirect target).
- Did not add a client-side `router.replace` to reflect `?viewId=` in the URL bar. The clarified assertions (AS-021, AS-022) only require "no redirect" and "same view applied" — they say nothing about the URL needing to show `viewId` for the auto-applied-default case. Adding a client-side URL sync would require converting part of this Server Component's tree to a Client Component wrapper purely for `router.replace`, which is out of this feature's stated scope (mirrors the existing `?viewId=` explicit-open path's URL, which is unaffected and still works exactly as before). Recorded as a note in Out-of-scope work needed below in case product wants deep-linkable default-applied URLs later.
- Verified pre-existing, unrelated test failures (4 test files: `board-taskid-deeplink.test.tsx`, `f246-task-detail-sheet-copy-link.test.tsx`, and 2 others triggering the same `cookies() called outside a request scope` unhandled-rejection noise from an unrelated custom-fields fetch effect) exist identically on the pre-change commit via `git stash` + re-run, confirming they are not caused by this change.

## Out-of-scope work needed
