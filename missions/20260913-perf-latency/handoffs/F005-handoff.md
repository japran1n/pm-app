## Decisions made
- `chat.ts`'s `getWorkspaceChannels`: replaced `const supabase = await createClient();` with `const { supabase, user } = await getCurrentUser();` at the top, then reused `user?.id ?? ""` for the membership filter and removed the second, later `(await supabase.auth.getUser()).data.user?.id ?? ""` inside the DM-name-resolution branch, replacing it with the already-resolved `currentUserId` from the top of the function — this is the highest-value edit named in the spec (was 2 sequential round trips in the slowest member of the workspace layout's parallel batch, now 0 extra, since `getCurrentUser()` is `cache()`-shared with the layout's own call).
- `views.ts`, `time-entries.ts` (`getActiveTimer`), `search.ts` (`searchWorkspaceTasks`): straightforward "option 1" swap — local `createClient()` + `auth.getUser()` replaced by `getCurrentUser()`, same destructured `{ supabase, user }` shape, no signature or behavior change.
- `profile.ts`'s `getCurrentUserTimezone(supabase: SupabaseClient)`: did NOT add or change the parameter, since 6 call sites across the codebase (`page.tsx`, `my-tasks/page.tsx`, `calendar/page.tsx`, `board/page.tsx`, `list/page.tsx`, `team/[userId]/page.tsx`, plus `lib/actions/tasks/ordering.ts`) call it with their own already-constructed client, and the spec/tech-decisions explicitly forbid turning a refactor into an API change by adding a required param. Instead, only the *internal* identity resolution changed from `supabase.auth.getUser()` (a fresh network call every time this function runs) to `getCurrentUser()` (request-cached). This is safe because `getCurrentUser()`'s underlying `getRequestClient()` also wraps the same `createClient()` this file used to call directly — same session, same cookie-derived identity, just deduplicated against any earlier call in the same request (e.g. three of the six call sites — `my-tasks`, `calendar`, `team/[userId]` — already call their own `supabase.auth.getUser()` next to this call, so this alone collapses that pair down to one network round trip; the fourth-and-later duplication across those pages' OWN direct `auth.getUser()` calls is out of scope here, same as F003/F004 flagged for other leaf pages).
- `lib/queries/portal.ts`: NOT touched. See Blockers.
