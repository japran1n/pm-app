## Decisions made
- Wrapped `getWorkspaceChannels` itself in `cache()` (changed `export async function getWorkspaceChannels(...)` to `export const getWorkspaceChannels = cache(async function getWorkspaceChannels(...) {...});`), rather than wrapping only one caller — this is the correct place because all three real callers (workspace layout badge via `getWorkspaceChatUnreadTotal`, chat layout, chat page) go through this one function, and `getWorkspaceChatUnreadTotal` itself is a thin pass-through with no independent caching needed: wrapping the inner function automatically makes the wrapper's single call also participate in the shared cache.
- Did not change the return shape (`WorkspaceChannelRow[]`) at all — F013 depends on this shape staying stable per the spec's explicit prohibition. No field added, removed, or renamed.
- Did not touch the chat page's own call to `getWorkspaceChannels`. Per the spec's explicit instruction ("Drop the chat page's own call where the layout already fetched the same list and can pass it down... if passing it down would mean threading props through several components, say so and leave the page's call to cache()"): the chat *page* (`app/.../chat/page.tsx`) is a sibling route to the chat *layout* (`app/.../chat/layout.tsx`), not a child of it in a way that receives layout-computed data as a prop — Next.js layouts pass `children`, not arbitrary data, to nested pages. Making the page consume the layout's already-fetched list would require either (a) a shared context provider threaded through the layout and read via a hook in the page, or (b) restructuring the route so the page becomes a true child component of the layout's own render — both are exactly the "prop-drilling refactor... outside this feature" the spec calls out. Left the page's call in place; it will share the cache with the layout's call under the real runtime since both pass the same primitive `workspaceId` string (confirmed by reading both call sites: the layout resolves the workspace via `getWorkspaceBySlug(workspaceSlug)`, the page via its own direct `.from("workspaces").select("id")...` query — different queries, but the resulting `.id` string value is the same for the same workspace, which is all `cache()`'s argument-identity keying needs since the key is a primitive string, not the constructed workspace object).
- Confirmed the argument-identity caveat in the spec does not apply here: `getWorkspaceChannels` takes a single primitive `string` argument (`workspaceId`), not an object callers construct fresh each render. `cache()`'s default key comparison (`Object.is` per argument) works correctly for primitives — this is the same shape `getWorkspaceBySlug` (lib/queries/workspaces.ts, F001/F002) already established as the working pattern in this codebase, so no custom cache-key handling was needed.

## Notes for the next worker

F013 (which replaces the sidebar badge's *use* of this function with a single-call counter) should start cold from this file: the badge currently gets its count via `getWorkspaceChatUnreadTotal(workspaceId)` (lib/queries/chat.ts, just below `getWorkspaceChannels`), which sums every row's `unreadCount` — that summation, not the shape of `getWorkspaceChannels` itself, is what F013 is expected to replace with a direct RPC/count call.
- The three real callers in a request, for reference: (1) `app/(workspace)/w/[workspaceSlug]/layout.tsx` line ~277, via `getWorkspaceChatUnreadTotal(activeWorkspace.id)` for the sidebar badge; (2) `app/(workspace)/w/[workspaceSlug]/chat/layout.tsx` line ~40, `getWorkspaceChannels(workspace.id)` for the channel list panel; (3) `app/(workspace)/w/[workspaceSlug]/chat/page.tsx` line ~40, `getWorkspaceChannels(workspace.id)` for the `/chat` index route's own mobile channel list + auto-redirect target.
- The `cache()` testing trap (documented in every prior worker's handoff and in this feature's task spec): plain Vitest has no per-request dispatcher, so `cache()` never memoises inside a unit test — a test asserting "three callers share one execution" would fail honestly under Vitest, or would require mocking `cache` itself (testing the mock, not the behaviour). I did not write such a test. What the test suite here proves instead is structural: the function's exported identity, its argument shape, and its return shape/behaviour are all unchanged, and the existing `chat-workspace-channels-unread-count.test.ts` (which calls `getWorkspaceChannels` directly and asserts on its output) still passes byte-for-byte after the `cache()` wrap — proving the wrap is transparent to callers, not that deduplication happens (that guarantee comes from React's `cache()` + Next's per-request context under the real runtime only, same limitation F001-F007 all documented for `getCurrentUser`/`getWorkspaceBySlug`).
