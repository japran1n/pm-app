## Decisions made
- One small shared helper (`lib/actions/portal-revalidate.ts`'s `revalidatePortalProject`), as the clarified spec explicitly allows, rather than duplicating the try/catch + `revalidatePath` call seven times.
- For the 7 "single revalidate* helper" files, added the portal call *inside* that helper (same non-fatal try/catch as the existing `/w` revalidate) rather than at each of that helper's many call sites — behaviorally identical, much smaller diff.
- `time-entries.ts`: widened the `tasks(project_id, deleted_at, projects(workspace_id, visibility))` select four call sites already used to also fetch `workspaces(slug)` — this is the same round trip, not an extra one, so it satisfies "can cheaply get slug + projectId" without adding hot-path DB calls. All four (`logTimeEntry`, `editTimeEntry`, `deleteTimeEntry`, `setTimeEntryCategory`) feed the portal's client-visible Hours page (`app/(portal)/portal/[workspaceSlug]/p/[projectId]/hours`), confirmed by reading `lib/queries/hours.ts`.
- `tasks/edit.ts`'s `editTask`: widened its existing task select by one column (`client_visible`) — no extra round trip — and guarded the new portal revalidate on `taskRow.client_visible` so a non-shared task's edit never touches the portal path (kept the negative case as its own assertion in the new test).
- Did NOT touch `architecture.ts` — F003's `setPageClientVisibility`/`setSectionClientVisibility` already revalidate `/portal/${slug}/p/${projectId}/architecture` (page-scoped); no duplicate work needed there.

## Out-of-scope work needed
