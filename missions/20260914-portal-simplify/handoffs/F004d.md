## Decisions made
- Chose to read the doc's PREVIOUS `client_visible` value as a small extra `select` in `setDocClientVisibility` rather than trying to infer "was visible" from the update result — Supabase's `.update()` doesn't return the pre-image, and `setDocClientVisibility` is the only call site of `revalidatePortalForDoc` that can flip visibility off, so the extra read is scoped to exactly the one function that needs it (`deleteDoc`, `updateDoc`, etc. still call `revalidatePortalForDoc` without `force`, gated on the doc's current, unchanging-in-those-paths `client_visible`).
- `revalidatePortalForDoc`'s `force` option defaults to `false` (opt-in), so every other call site (`updateDoc`, `deleteDoc`, `moveDoc`, `setDocKind`, `setDocRelevantFrom`, `addDocLink`, `deleteDocLink`) is behaviorally unchanged — only `setDocClientVisibility` passes `force: wasVisible || parsed.data.visible`.
- For item 4, only replaced unwraps whose sole purpose is pulling a `workspaces(slug)` join's `slug` out of Supabase's array-or-object join shape. Left `Array.isArray(project) ? project[0] : project` (unwrapping a `projects(...)` join row, not a slug), `Array.isArray(task) ? task[0] : task`, `Array.isArray(rpcRows) ? rpcRows[0] : rpcRows`, and the `!Array.isArray(updates)` batch-input-shape guards untouched — `extractWorkspaceSlug` is typed specifically for the `{ slug: string } | { slug: string }[] | null | undefined` shape and isn't the right tool for those.
- Item 3 required no code or test change: the F004b test file's rejection tests for both actions were already added in a prior round (verified by grep + reading the file) with the exact assertions requested (`ok:false`, no `taskUpdateSpy`/`revalidatePath` call) for no-user, non-member, and canWrite=false (viewer and client roles) cases.
