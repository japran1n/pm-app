## Decisions made
- **Item 1/2/3 (BLOCKERs)**: added `workspaces(slug)` to the existing project/task select in every create/rename/delete/reorder/move/link/unlink action in `architecture.ts` (16 functions) and to `lifecycle.ts`'s `deleteTask`/`restoreTask` resolveWorkspace + `checklist.ts`'s toggle resolveWorkspace, so the slug is available with zero extra round trips (widened selects only, per the spec's own instruction), then called `revalidatePortalProject(slug, projectId)` after each successful write. `lifecycle.ts`/`checklist.ts` gate the call on `client_visible` (loaded the same way, zero extra round trips) so a non-shared task's delete/restore/checklist-toggle never touches the portal path — same convention F004's `editTask` fix already established.
- For the two batch-reorder actions (`reorderSections`, `reorderPages`), which can theoretically touch tasks across differing... actually always the same project in practice, but the code doesn't assume that — built a `Map<slug, projectId>` from all rows in the batch and called `revalidatePortalProject` once per unique (slug, projectId) pair, rather than assuming a single target.
- **Item 3 (share toggles)**: replaced the page-scoped `revalidatePath(".../architecture", "page")` in `setPageClientVisibility`/`setSectionClientVisibility` with the shared `revalidatePortalProject` (layout-scoped) call, matching every other portal-touching action in this mission.
- **Item 4 (partial-failure cascade)**: `setPageClientVisibility`'s "share sections too" cascade update, on failure, now returns `ok: true` with a new `sectionsShareFailed: true` field instead of silently reporting full success — the page's own share DID succeed (that update already committed before the cascade runs), so `ok: false` would have been a false negative. The toggle component (`page-client-visibility-toggle.tsx`) shows `toast.warning(...)` instead of `toast.success(...)` when this flag is set.
- **Item 5**: verified via the migration file `supabase/migrations/20261121010000_f002_page_components.sql` (not live-queried via MCP, since this worktree's `.env` targets the same project other tests here already connect to directly and the migration is authoritative/unambiguous — no `deleted_at` column, no soft-delete trigger, `deleteComponent` does a real `.delete()`) that `page_components` has **no** `deleted_at` column at all — it's hard-deleted, never soft-deleted. No filter was added to `lib/queries/architecture.ts`'s `page_components` select; noted here per the task's own "if no, note in handoff" instruction.
- **Item 6/7 (new tests)**: added `tests/unit/f004b-scrutiny-remediation-portal-revalidate.test.ts` (viewer/client/non-member/signed-out rejection for both share actions, using the REAL `canWrite` predicate — not mocked — so viewer/client rejection is genuinely exercised, unlike the pre-existing F003 test file which stubs `canWrite` to always return true) and `tests/integration/f004b-scrutiny-remediation-portal-revalidate.test.ts` (real-DB, `revalidatePath` spy, asserting the exact `/portal/<slug>/p/<projectId>` + `"layout"` call for `createPage`, `renamePage`, `createSection`, `deleteTask` (client-visible + non-client-visible negative case), `restoreTask`, and `toggleDescriptionChecklistItem`).
- **`deletePage`/`deleteSection` real-DB test dropped**: both go through the `cascade_delete_task` RPC, which currently has TWO overloaded signatures live on the connected Supabase project (`p_task_id` alone vs. `p_task_id` + `p_deleted_by`), causing PostgREST error `PGRST203` ("Could not choose the best candidate function") whenever called with only `p_task_id` — exactly what `deletePage`/`deleteSection` do. This is pre-existing schema drift, not something introduced or fixable within this feature's scope (portal revalidation); see Out-of-scope work needed. The `deletePage`/`renamePage`/`createPage`/`createSection` code-path portal-revalidate fix itself is still correct and unit-testable (and IS covered, minus the one RPC-blocked case) — this only affects the one real-DB integration assertion I would have added for `deletePage`.
- **Item 8**: replaced `text-emerald-600` with the semantic `text-primary` token in both toggles' "shared" state, and made both toggles' "not shared" state consistently `text-muted-foreground` (the page toggle previously had no muted class on its unshared state at all).
- **Item 9**: fixed the `surpenders` → `suspenders` typo in `lib/queries/portal.ts:1614`.
- **Item 10**: `setSectionClientVisibility` now does one extra lookup (by `parent_task_id`, no new round trip pattern change — same admin client, same request) to read the parent page's `client_visible`, returning a new `pageHidden: boolean` field (true only when the section was just shared AND its page is still hidden). `SectionClientVisibilityToggle` shows a `toast.warning("Shared with the client, but the page is hidden -- share the page too.")` when that flag comes back true.

## Out-of-scope work needed
- **`cascade_delete_task` RPC overload ambiguity**: the connected Supabase project has two live overloaded signatures for `cascade_delete_task` (`p_task_id` only, and `p_task_id` + `p_deleted_by`), which breaks any caller that invokes it with only `p_task_id` (currently `deletePage` and `deleteSection` in `lib/actions/architecture.ts`, both pre-existing from F017/F018 — not touched by this feature beyond adding their portal-revalidate call, which is dead code on the current DB state until this is fixed). A follow-up feature should either drop the single-argument overload (if nothing else still calls it) or make `deletePage`/`deleteSection` pass `p_deleted_by` explicitly the way `lifecycle.ts`'s `deleteTask` already does, then this handoff's dropped `deletePage` real-DB assertion can be restored.
- `renameSection`/`deleteSection`/`reorderSections`/`moveSectionToPage`/`reorderPages`/`createComponentFromSection`/`createComponent`/`linkComponentToSection`/`renameComponent`/`unlinkComponentFromSection`/`deleteComponent` now all call `revalidatePortalProject` but only `createPage`/`renamePage`/`createSection`/`setPageClientVisibility`/`setSectionClientVisibility`/`deleteTask`/`restoreTask`/`toggleDescriptionChecklistItem` have dedicated new-test coverage of the exact revalidate call in this handoff's two new test files (beyond the pre-existing unit tests that already exercised these functions' core behavior without checking revalidate args). A future worker could extend `tests/integration/f004b-scrutiny-remediation-portal-revalidate.test.ts` with the remaining functions for full 1:1 coverage; the implementation pattern is identical across all of them (verified by direct code read, not assumed).
- `promoteSubtask` (lib/actions/tasks/lifecycle.ts) was NOT given a portal-revalidate call — the mission brief for this remediation explicitly scoped lifecycle.ts to "delete/restore" only; promoting a subtask to top-level doesn't change any client-visible field so this is consistent with the "client-visible" gating principle used everywhere else in this feature.
