## Decisions made
- **Button variant mapping**: Implemented the cva exactly as specified — `default` now renders the Supabase "secondary" look (subtle bg-secondary/border), `primary` is the new solid-fill variant, `secondary` is kept as an alias identical to `default` for backward compat, and `xs`/`icon-xs`/`icon-lg` sizes are kept as backward-compat aliases mapped onto the new scale. This means any call site using the bare `variant="default"` (the majority of buttons in the app, since that was previously the solid/primary look) will visually shift from solid-primary to subtle-secondary. This is a direct, faithful implementation of the spec's literal cva strings — not a deviation — but it is the single largest visual-risk item in this feature. Flagged here for scrutiny/UX validators to check whether any primary CTA buttons (e.g. "Create task", "Save", "Send") now read as secondary/subtle and need an explicit `variant="primary"` added at the call site. That call-site audit was out of scope for this worker (spec said "keep Base UI wrapper, only edit cva string / className values" — not touch call sites).
- **Destructive button**: Per spec, destructive is now a 10%-tint pill (`bg-destructive/10` + `border-destructive/30` + `text-destructive`) instead of a solid red fill. Found 10 call sites using `variant="destructive"` (transfer-ownership-dialog.tsx, archive-project-dialog.tsx, chat-nav-list.tsx, dm-starter-list.tsx, delete-workspace-dialog.tsx, docs-folder-row.tsx, task-detail-sheet.tsx, bulk-delete-action.tsx, team-request-inbox.tsx, notification-bell.tsx). Left all of them untouched per explicit spec instruction ("do NOT revert").
- **Base UI state attributes**: checkbox/radio-group/switch already used Base UI's native `data-checked` (not Radix `data-[state=checked]`) before this feature — confirmed by reading each file first, only cva/token values needed updating, no attribute-selector rewrite was required. select.tsx and dialog.tsx/alert-dialog.tsx/popover.tsx/hover-card.tsx/dropdown-menu.tsx already used `data-open`/`data-closed`/`data-highlighted`/`data-popup-open` correctly; only added `aria-expanded:*` to select's trigger per spec (Base UI Select trigger sets `aria-expanded` natively, this app's file hadn't been styling off it yet). toggle.tsx's Base UI primitive already exposes `aria-pressed`, so only the design tokens (not the attribute) needed changing.
- **Popover z-[80] and tour-card stacking comment preserved**: `components/ui/popover.tsx` has a long inline comment explaining why the popover content uses `z-[80]` instead of `z-50` (onboarding tour z-index collision, confirmed live in browser). This is functional, not stylistic — left completely untouched, only touched the rounded/padding/shadow tokens on the same className string.
- **Sheet overlay dimming/duration preserved**: `components/ui/sheet.tsx`'s overlay uses `bg-black/40` and `duration-150` with an inline comment documenting a UX-audit-driven decision (Nalaz 1) that this dimming level and speed matter functionally, distinct from the spec's generic "duration-500" suggestion for a default Radix-ported sheet. Per CLAUDE.md's scope rule ("would a user who knows the app by heart need to learn anything new?") and the explicit in-code rationale, I did not touch the overlay's color or duration — only updated the content popup's border-radius/shadow to the shared `shadow-xs` overlay token and the close-button's touch-target rule was left alone (F265/AS-518, unrelated feature, do not touch).
- **Dialog/alert-dialog footer padding**: Dialog/AlertDialog content padding went from `p-4` to `p-6` per spec. Since DialogFooter/AlertDialogFooter previously used `-mx-4 -mb-4 ... p-4` to counteract the old p-4 content padding and hairline the footer to the card edges, I updated those to `-mx-6 -mb-6 ... p-6` and `rounded-b-md` (was `rounded-b-xl`) to keep the footer's edge-bleed behavior consistent with the new content padding, and added an explicit `border-border` (was bare `border-t`, relying on the default border color which is now the correct semantic token anyway).
- **Sheet content**: Deliberately did NOT add root-level padding to SheetContent (unlike Dialog) because SheetHeader/SheetFooter already self-pad with `p-4` — adding `p-6` at the content root would have doubled the padding. This is a divergence from the spec's literal "Content: p-6" line, but doing it literally would have broken the existing Sheet layout (header/footer/body already manage their own padding independently, unlike Dialog where header/footer are unpadded and rely on the content wrapper).
- **shadow-xs verified as an existing Tailwind v4 core utility** (no custom addition needed in globals.css) — confirmed by the build succeeding with `shadow-xs` used across select/dialog/alert-dialog/sheet/popover/hover-card/tooltip/dropdown-menu without any "unknown utility" warning.
