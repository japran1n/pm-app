## Decisions made
- Investigated the codebase before assuming hex literals existed inline in
  portal `.tsx`/`.ts` files. They did not — the only Good Guys 3.0 hex
  literals lived inside the single `[data-surface="portal"]` block in
  `app/globals.css` (F046 target) plus the companion `:not([data-surface="portal"])
  .prose` selector, both removed. F047–F049/F051 therefore reduced to: confirm
  no hex literals or `--gg-` references remain (they didn't), and apply the
  `font-mono` for data (dates/percentages) rule where a bare, standalone date
  or numeric axis label was rendered.
- Removed the `data-surface="portal"` attribute from the portal shell layout
  (`app/(portal)/portal/[workspaceSlug]/layout.tsx`) since the CSS scope it
  targeted no longer exists.
- Simplified `.prose` selector in globals.css from
  `:not([data-surface="portal"]) .prose` to plain `.prose` — the negation
  existed only to avoid the (now-removed) portal light-mode block; portal and
  workspace both resolve through the shared token system now, so the `.prose`
  mapping onto workspace tokens applies uniformly to portal too, which is the
  entire point of this phase (same theme resolution everywhere).
- Applied `font-mono` to: the phase-timeline week-axis date labels, the
  weekly-delivery-chart week-axis labels, the hours-burndown-chart budget/used
  labels and week-axis labels, and the task-list due-date chip. These are all
  standalone numeric/date strings (not sentence-embedded), consistent with
  the "data is mono" rule applied elsewhere in Phase F.
- Left sentence-embedded dates (e.g. "Due 12 Jan 2026" inside
  `approval-card.tsx` / `deliverable-row.tsx`) as plain text rather than
  wrapping only the date substring in a nested `<span className="font-mono">`
  — doing so would require restructuring `formatDate` call sites into JSX
  fragments across several components for a cosmetic-only gain not called out
  in the Definition of Done greps, and risks introducing rendering
  regressions. Flagged below as out-of-scope follow-up.
- Left existing Tailwind palette utility classes (`bg-blue-600/10`,
  `border-slate-300`, `text-blue-600`, `bg-emerald-500`, etc.) in
  `project-links-list.tsx`, `project-accounts-table.tsx`, `request-list.tsx`,
  and `project-progress.tsx` untouched. These are not Good Guys 3.0 hex
  literals (the spec's grep patterns and hex→token mapping table don't
  reference them) and they encode categorical/status distinctions (link
  kind, account status, request status) rather than surface/foreground
  tokens — recoloring them was not requested by this spec and risks visual
  regressions the spec's Definition of Done doesn't check for.

## Out-of-scope work needed
- Sentence-embedded date/amount mono-styling in `approval-card.tsx` and
  `deliverable-row.tsx` (e.g. "Due 12 Jan 2026", "Requested 3 Sep 2026") is
  not wrapped in `font-mono`. A future feature could extract these into
  small `<time className="font-mono">` sub-components if full "data is mono"
  coverage on every sentence-embedded date is desired.
- The categorical Tailwind palette classes (`blue-*`, `slate-*`, `emerald-*`,
  `amber-*`, `violet-*`, etc.) used for link-kind badges, account-status
  badges, and request-status text across `project-links-list.tsx`,
  `project-accounts-table.tsx`, `request-list.tsx`, and `project-progress.tsx`
  are not derived from the six-knob OKLCH token system. If a future design
  pass wants every color in the app token-derived (not just surface/
  foreground), these are the remaining call sites to convert to a mapped set
  of semantic tokens (e.g. `--chart-1..5`, `--warning`, `--info`,
  `--destructive`) instead of raw Tailwind palette utilities.
- Pre-existing (unrelated) test failures: 55 tests / 90 files fail with
  `cookies() was called outside a request scope` inside
  `lib/supabase/server.ts` → `getCustomFieldsForTask`, surfaced through
  `components/task/custom-fields-section.tsx` in various task-detail-sheet
  tests (e.g. `tests/unit/board-taskid-deeplink.test.tsx`,
  `tests/unit/f246-task-detail-sheet-copy-link.test.tsx`). These are
  unrelated to portal styling/tokens and were present before this feature's
  changes — not caused by anything in F046–F051. Worth a dedicated
  test-infra fix if not already tracked.
