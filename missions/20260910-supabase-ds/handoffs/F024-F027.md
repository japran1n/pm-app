## Decisions made
- Followed the spec's literal `ThemeToggle` component code (Sun/Moon icon binary toggle) rather than building a three-option light/dark/system menu, because the "Clarified implementation" spec text gave exact component code to create verbatim. `enableSystem` on the provider still means SD-022 (system preference on first/no-choice load) is satisfied even though the visible control itself only toggles explicit light/dark once a user interacts with it — this mirrors next-themes' common pattern (toggle for explicit override, `enableSystem` for the default-follow-OS behavior).
- Placed the workspace `ThemeToggle` in `components/nav/app-sidebar.tsx`'s existing top bar (next to `WorkspaceSwitcher`/`NotificationBell`) for desktop, and in the mobile sheet's top bar next to the mobile `NotificationBell`, since that file is the only real "header" surface identified for the workspace shell (confirmed via grep — no separate `AppHeader`/`WorkspaceHeader` component exists yet, consistent with an existing code comment in that file noting "no real top bar yet... per this feature's own Notes").
- Placed the portal `ThemeToggle` in `components/portal/portal-topbar.tsx`, which renders on every route under the portal shell (`PortalTopbar` sticky header), rather than the sidebar, so it's reachable regardless of route.
- Added `suppressHydrationWarning` to `<html>` in `app/layout.tsx` since next-themes intentionally sets `class`/`data-theme` client-side after the no-flash script runs, which is the documented next-themes SSR pattern to avoid a false-positive hydration warning (not a real mismatch — content is unaffected, only the theme attribute).
- Did not touch `[data-surface="portal"]` in globals.css or `components/portal/status-label.ts`, per hard constraints.
