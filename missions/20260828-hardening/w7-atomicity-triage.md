# W7 triage — functions with 2+ writes and no transaction

Generated by the orchestrator so W7 starts from a precise target list instead of
re-deriving it. 18 functions in `lib/actions/` issue two or more writes. Not all of
them need a transaction; the classification below is a starting hypothesis that W7
must verify per function, not accept.

## Tier 1 — confirmed atomicity risk, user-visible data loss

| Function | File | Writes | Failure mode |
|---|---|---|---|
| `setTaskAssigneesCore` | tasks.ts | 2 | delete-then-insert. Insert fails → all assignees silently stripped, none added. No compensation at all. |
| `createTaskFromTemplate` | templates.ts | 4 | Partial task materialisation — task exists with some of its checklist/assignees/labels missing. |
| `createProjectFromTemplate` | templates.ts | 3 | Partial project — statuses or members missing from a project that looks created. |
| `duplicateTask` | tasks.ts | 3 | Half-copied task. |
| `bulkDeleteTasks` | tasks.ts | 3 | Partial bulk delete — some tasks gone, some not, no indication which. |
| `restoreTask` | tasks.ts | 3 | Task restored but its children/relations not. |

## Tier 2 — hand-rolled compensation that can itself fail

`createChannel` (chat-channels.ts, 3 writes) already recognises the problem: if the
`channel_members` insert fails it issues a compensating `delete` on the channel it just
created. But that rollback is itself an unguarded network write, and the code only
`console.error`s when it fails (line ~99):

```
console.error("createChannel: member insert failed:", insertMembersError);
const { error: rollbackError } = await admin.from("channels").delete()…
if (rollbackError) console.error(…)
```

A failed rollback leaves an orphan channel with no members — invisible to everyone,
undeletable through the UI, and counted by nothing. This is the strongest single
argument for W7: the codebase already knows these writes must be atomic and is
hand-rolling a weaker version of what Postgres gives for free.

`acceptClientRequest` (client-requests.ts, 3 writes) and `changeWorkspaceSlug`
(workspaces.ts, 3 writes) should be checked for the same pattern.

## Tier 3 — verify, may be benign

`createWorkspace`, `editTask`, `addComment`, `editComment`, `archiveProject`,
`restoreProject`, `activateInvitedMemberships`, `toggleReaction`,
`toggleMessageReaction`.

Several of these are plausibly fine — e.g. a second write that is idempotent, or one
that only touches a denormalised mirror column that a later read recomputes anyway
(`syncMirrorAssigneeId` is in this category). W7 must confirm rather than assume, and
should say so explicitly per function in the handoff.

## Precedent to follow

This repo already does transactions correctly in three places. Copy their shape rather
than inventing one:

- `stop_timer_atomic` (time-entries)
- `reassign_and_delete_project_status` (statuses)
- `apply_status_template` (status-templates)

## Suggested sequencing

Do NOT attempt all 18 in one worker — recent workers have failed on large briefs.
Split at minimum into: (a) Tier 1 tasks.ts functions, (b) Tier 1 templates.ts
functions, (c) Tier 2 compensation-pattern functions, (d) Tier 3 audit-and-report only.

## Test requirement

Each converted path needs a test that forces the *second* write to fail and asserts the
first was rolled back. A test that only proves the happy path still works does not
demonstrate atomicity and should not be accepted as coverage for this work.
