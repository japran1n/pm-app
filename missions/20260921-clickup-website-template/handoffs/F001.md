## Decisions made
- Subtask hierarchy and phase-per-task are BOTH embedded in the existing `p_tasks` jsonb RPC parameter (no new RPC parameter, no signature change) — `children`/`phase` are just new optional keys on the same task JSON shape, so `create_project_from_template` could be edited with `create or replace` directly, no `drop function` step needed (matches this codebase's own established convention for signature-preserving RPC edits, e.g. 20260917020000).
- Task insertion is factored into a new recursive PL/pgSQL helper, `public._create_project_from_template_tasks`, because PL/pgSQL doesn't support recursive loops over an arbitrarily-nested jsonb tree within a single function body, only recursive function calls. Order is preserved via one monotonic `position` counter threaded through every recursive call (not reset per level), matching the existing flat loop's `+= 1000` convention.
- Phase resolution: every task (top-level or child) independently resolves its own `phase` name against a `{name -> id}` map built while inserting `p_phases`; a child with no `phase` of its own is passed its parent's already-resolved phase id as the recursive call's "default", giving the "children inherit if not set" behaviour without a second lookup pass.
- Restored `client_visible` to the `project_phases` insert inside `create_project_from_template`. I found, while reading the function I was about to rewrite, that `20260927020000_f013_project_template_deliverables.sql`'s full-body replacement had silently dropped the `client_visible` column from the insert (a regression against `20260917020000`'s own fix) — every phase created from a template since that migration landed has ignored a hidden source phase's visibility. Since my migration already rewrites this exact insert statement, I fixed it in the same place rather than leaving a known bug untouched next to code I was already changing. AUTONOMOUS_DECISION, documented here per the mission's own "note when you applied a default/fix without asking" convention.
- `setDefaultTemplate(workspaceId, templateId | null)` — took `workspaceId` as an explicit parameter (not resolved from the template row) because the "clear the default" case (`templateId: null`) has no template row to resolve a workspace from.
- `taskCount` in both `saveProjectAsTemplate`'s and `createProjectFromTemplate`'s return values now counts the WHOLE task tree (top-level + every nested `children` entry), not just `payload.tasks.length` — that field used to equal the total task count exactly (flat array), and silently became "top-level only" once `children` existed; fixed in the same edit rather than leaving a newly-wrong count.
- `is_default` is scoped to `kind='project'` templates by convention (enforced at the app layer in `setDefaultTemplate`, and structurally true in practice since nothing else ever sets it true on a `kind='task'` row) rather than a DB CHECK, because the partial unique index already needs `(workspace_id, kind)` as its key for the "one default per workspace" rule to make sense per-kind, and a `kind='task'` row is never actually offered a "set as default" control in the UI (`showDefaultToggle` is only ever passed for the project-templates list).
- Added a "Project templates" section to the existing `/w/[workspaceSlug]/templates` page (previously `kind='task'`-only) rather than inventing a second URL/page, since requirement 3 says "in the templates management UI" (singular) and this is the only templates management UI that exists.
