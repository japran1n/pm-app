## Decisions made
- Followed `notifications.spec.ts` and `f272-two-context-notifications.spec.ts` exactly for the auth harness: `dotenv`-style manual `.env` load, `auth.admin.generateLink({type:"magiclink"})` -> follow the link -> capture `access_token`/`refresh_token` from the `#`-fragment on the `/sign-in?error=auth_failed` redirect -> inject a `sb-<project-ref>-auth-token` cookie built the same way both existing specs build it. No new auth technique invented.
- Used TWO Playwright `Page`s in the SAME browser `context` (same client session/cookies), not two separate `browser.newContext()`s as the two-context notification spec does — that pattern exists there because it stands in for two DIFFERENT real users; this flow is ONE client user with two tabs open (one watching the overview, one on the task detail page), so a single context is the correct, simpler fit and avoids re-running the magic-link flow twice for no reason.
- Drove Approve from the task detail route (`/portal/<slug>/t/<taskId>`), not the overview page, because `components/portal/approval-actions.tsx` (F005) only ever renders there — the overview's "Waiting on you" list (F008, `portal-overview-live.tsx`) only ever shows a title + project name Link, never an inline Approve button. The spec text's "click Approve" and "assert the row leaves that section" are therefore two different pages by construction; the no-reload assertion is scoped to the overview page specifically, per AS-029's wording ("the row leaves the section without issuing a page reload" — "the section" being "Waiting on you", not the detail page).
- Chose to assert BOTH a `window`-level sentinel AND a Playwright `page.on("load")` counter (not just one), because a naive React-state-only or DOM-only check on `overviewPage` could theoretically still pass if some other, unrelated full reload happened to re-render the same final markup; the `load` event counter is the browser-level ground truth independent of anything the app's own JS does, which is what AS-029's own clarification text explicitly asks for ("assert on the absence of a navigation/reload event, not merely on the final DOM state").
- Seeded the client `workspace_members` row directly with `role: "client"`, `status: "active"` (migration 20260902010000's role check constraint) rather than going through any invite flow — matches how every other admin-seeded E2E fixture in this repo (`notifications.spec.ts`, `f272-two-context-notifications.spec.ts`) seeds membership directly.
- Confirmed server-side persistence (via a direct admin-client `select` on `tasks.pending_client_approval`) before asserting on the overview page's live removal, same "confirm the real write landed, then assert on the OTHER page's live delivery" pattern both existing two-page/two-context specs already use for their own assignment/mention flows.
