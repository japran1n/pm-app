## Decisions made
- **Diagnosed the login-helper rot first, per the assignment.** Ran `notifications.spec.ts` standalone: it fails at the identical `page.waitForURL(/\/sign-in\?error=auth_failed#/)` line the portal spec used, redirecting instead to `https://pm-app-beige.vercel.app/#access_token=...` — the linked Supabase project's Auth redirect-URL allowlist no longer includes `http://localhost:3100` (the Playwright dev server's origin), so `generateLink`'s `action_link` falls back to the project's Site URL. This is environmental/project-config rot in the shared pattern, not something specific to a `client`-role user. I did not additionally fix `notifications.spec.ts` itself (out of this feature's stated scope; flagged below).
- **Replaced the login helper with `/dev-login`** (`app/dev-login/route.ts`), exactly as suggested — verified it works under the Playwright dev server (`NODE_ENV=development` there) rather than assumed. One correction to my first attempt: `/dev-login`'s own redirect chain (`dev-login -> /onboarding -> /w/<slug> -> /portal/<slug>`) resolves as ONE browser navigation (Next.js server-side redirects), so `page.waitForURL(/\/onboarding/)` never matches an intermediate URL the browser actually stops on — waited on the real final destination instead.
- **Found and fixed a real, pre-existing application bug while making the fixture visible**: `is_project_visible_to()` (migration `20260902010000`) requires an explicit `project_members` row for a `client`-role member to see a project at all (the "everyone in the workspace sees workspace-visible projects" branch is closed for clients) — F011's fixture never inserted one, so the client's own "Your projects"/"Waiting on you" list was empty regardless of any task's `client_visible` flag. Added the insert (and a matching `afterAll` delete, since `project_members.project_id` has no cascade).
- **Found and fixed a second real, pre-existing application bug**: `approvePortalTask`/`requestPortalTaskChanges` (`lib/actions/portal-approval.ts`) both flip `tasks.pending_client_approval` through the per-request RLS-respecting client, exactly like every other mutating action in this codebase — but `is_project_workspace_writer()` (also `20260902010000`) was redefined to explicitly exclude `role = 'client'` ("a client is read-only everywhere these gates are used"), and `tasks_update_active_members` is the only UPDATE policy on `tasks`. The result: a client's Approve click always silently no-opped (0 rows updated, no Postgrest error) — the one write a client is supposed to be able to make was never actually reachable in production either, not just in this test. Fixed with a narrow `SECURITY DEFINER` RPC (`approve_portal_task_atomic`, migration `20260905130000`), mirroring the existing `accept_client_request_atomic`/`create_channel_atomic` pattern: runs as the calling client, re-verifies active `client` membership + `client_visible`/`pending_client_approval` before flipping exactly that one column. I only wired `approvePortalTask` to it (the one this feature's assertions cover); `requestPortalTaskChanges` has the identical bug and is flagged below as out-of-scope.
- **Found and fixed a third real, pre-existing bug, this one in `usePortalOverviewRealtime`**: even after both bugs above were fixed, the approval's Realtime UPDATE never reached the overview page's live subscription. Root-caused (not guessed) via direct instrumentation of the installed `@supabase/realtime-js` (`dist/module/RealtimeClient.js`, restored after diagnosis — no `node_modules` diff remains, verified via `git status`/`git diff node_modules`): on a fresh page load, `createClient()`'s Realtime socket starts with `accessTokenValue === null`; if `.channel(topic).subscribe()` runs (as this hook's effect used to, synchronously on mount) before `@supabase/ssr`'s async cookie-session hydration resolves and fires its own `onAuthStateChange` → `realtime.setAuth(token)`, the `phx_join` is sent unauthenticated. The channel still reports `"Subscribed to PostgreSQL"` (so this fails silently, no error anywhere), and an unauthenticated join receives every table-wide `DELETE` on `tasks` (Realtime does not apply RLS to `DELETE` payloads at all — confirmed by the flood of unrelated `DELETE` events from other concurrent E2E runs against the same live project, captured during diagnosis) but is filtered out of every RLS-gated `INSERT`/`UPDATE`, which is exactly the failure mode observed: the client's own approval `UPDATE` never arrived. A secondary race inside `_performAuth` (concurrent `setAuth` calls short-circuiting on an already-equal `accessTokenValue` comparison) meant even the eventual real session's `setAuth(token)` call could silently fail to push the token to an already-joined channel. Fix: the hook now explicitly awaits `auth.getSession()` and hands its JWT to `realtime.setAuth()` **before** ever creating the channel, so the very first `phx_join` already carries the real, authenticated token — no race, no silent anon fallback.
- Updated `tests/unit/portal-overview-live.test.tsx`'s mocked Supabase client to provide `auth.getSession()`/`realtime.setAuth()` (both resolving immediately) and flush the two now-awaited microtasks after render/rerender, so the five pre-existing AS-018/019/020/024 assertions in that file keep testing real behaviour against the hook's new async shape rather than silently no-op. Ran that file standalone (`npx vitest run tests/unit/portal-overview-live.test.tsx`) — 6/6 pass. Note: this file was independently touched by a concurrently-running F015 worker in this shared working tree during my session and its content ended up identical to what I wrote (confirmed via `git diff HEAD` showing zero diff after I made my edits) — it is already committed under F015's own commit (`75eab15`), not re-committed here; `git status` after my own commit shows no outstanding diff for it.
