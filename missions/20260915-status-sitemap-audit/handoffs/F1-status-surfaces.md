## Decisions made
- `bulk-status-action.tsx` was redesigned to take a `statusOptionsByProject: Map<projectId, options[]>` + `taskProjectIds: Map<taskId, projectId>` pair (mirroring `MyTaskStatusCell`'s per-project options map, exactly as the spec pointed to) rather than a single flat `statusOptions` array, because a selection CAN genuinely span multiple projects with different custom status sets — the only real-world case is the workspace-wide dashboard table (multi-project); the per-project List view is always single-project by construction, so its `statusOptionsByProject` map is synthesized as a one-entry map from its existing single `statusOptions`/`projectId` props inside `TaskListTable` — the caller doesn't have to build a map itself.
- The bulk status dropdown offers the UNION of every involved project's real statuses (deduplicated by name), not the intersection. AS-1's own wording ("scoped per-project when a selection spans multiple projects") is satisfied by the SERVER's per-task existence check (AS-2), not by hiding a legitimate choice for the subset of the selection that has it — hiding it would make bulk strictly less capable than moving each task individually.
- Extended `TaskCardTask` with an optional `projectId` field and `getWorkspaceListTasks` to select/return it, specifically so the workspace-wide dashboard table (`dashboard-task-table.tsx`) — the only real multi-project bulk-selection surface — could batch-fetch each distinct project's real statuses (one query, mirroring `my-tasks/page.tsx`'s existing `statusOptionsByProject` pattern) and wire it through. This was not explicitly named in the feature's file list but is required to make AS-1's "scoped per-project when spanning multiple projects" clause true for the one caller where it can actually happen, rather than leaving the dashboard's bulk action silently degraded to the DEFAULT_STATUS_OPTIONS fallback forever.
- `bulkUpdateTasks`'s existence check does NOT use `resolveProjectStatusName` (`lib/tasks/resolve-status.ts`). That helper's job is resolving a LEGACY DEFAULT name (`"todo"`, etc.) onto a project's real v2-renamed column for CREATE-time defaulting — a fallback/mapping behavior. Bulk's target name always comes from a real per-project options dropdown (never a legacy literal), so an EXACT match against `project_statuses` — mirroring `moveTaskStatus`'s own check exactly — is the correct semantics; silently remapping an unmatched name to some other column would reintroduce the "silent divergence" bug this feature exists to close. Documented in the audit's own item 6 as "check if it's useful" — concluded it is not, for this call site.
- The recurrence side effect (AS-3) fetches the extra `SourceTaskForRecurrence` columns unconditionally in the same UPDATE...SELECT the write already performs (no second round trip), and calls `getCurrentUserTimezone` once per batch (not per task) only when at least one recurring task actually moved into a done-category status — preserving the "no per-row network calls" performance budget for the common case (no recurring tasks in the selection).
- `task-detail-fields.tsx`'s failure-toast label for a status change now resolves through the same shared `lib/task-colors.ts` `STATUS_LABELS`/`statusOptionByValue` chain every other status surface uses, rather than this file's own separate, differently-capitalized local copy ("In progress" vs "In Progress") — this incidentally fixes the exact capitalization drift the audit's section D called out, and required updating one pre-existing test assertion (`f003-task-detail-sheet-status-optimistic.test.tsx`) to the corrected string.
