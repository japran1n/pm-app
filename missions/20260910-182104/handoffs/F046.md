## Decisions made
- Read the LIVE definitions of `is_project_visible_to`, `is_project_client`, `is_project_portal_enabled`, `is_project_workspace_writer` from the migration files that created/last modified them (`20260908010000_pin_pg_temp_on_client_visibility_predicates.sql`, `20260909010000_portal_foundations.sql`) rather than from memory, per standing decision #20. Confirmed `is_project_workspace_writer` already excludes both `viewer` and `client` (`wm.role not in ('viewer', 'client')`), so it alone satisfies both AS-157 (no client write) and AS-161 (no viewer write) on `brief_questions` — no new predicate was invented, as the feature spec required.
- `briefs`: client UPDATE policy uses `using (... and state = 'draft')` + `with check (... and state = 'submitted')` — this is what makes "only draft -> submitted" true rather than merely "only sets submitted from anywhere." A client attempting to update an already-submitted or approved brief matches zero rows in `using`, so the write is denied before `with check` is even considered.
- `brief_answers` write policies (INSERT/UPDATE) deliberately do NOT scope to `answered_by = auth.uid()`, per standing decision #15 — every client contact on the project is an equal editor of the one shared brief.
- `brief_answers` DELETE is team-only (not part of the client exception): an empty `answer_text` represents "not answered yet"; deleting the row entirely is not something the client-write exception was asked to cover, and keeping DELETE team-scoped avoids a client being able to erase `question_prompt_snapshot` history. Still gated on `state <> 'approved'` for consistency with INSERT/UPDATE.
- Tightened F045's `brief_answer_revisions_select_project_participant` policy by adding the missing `is_project_visible_to` membership conjunct to the client leg (F045's version had role + portal but not membership — its own header comment said the exact predicates land in F046). Did not touch the absence of UPDATE/DELETE policies (AS-134/AS-135), per the feature spec's explicit instruction not to weaken or add to that append-only shape.
- Followed the existing `20261106010000_scope_documents.sql` convention throughout: every client policy carries all three conjuncts (membership, role, portal_enabled) together, never membership alone; every team policy uses `is_project_workspace_writer` (which itself excludes `client`), never `is_project_visible_to` alone, so a client's request can never fall through a permissive team-shaped rule.
- Test harness: followed `tests/integration/portal-phases-rls.test.ts`'s existing pattern (real signed-in Supabase JS sessions against PostgREST, `.env`-loaded creds, `describe.skipIf(!haveCreds)`, `RLS_DENIED = '42501'`) rather than inventing a new one. Learned and fixed a real gotcha while writing it: a PostgREST UPDATE/DELETE that matches zero rows because RLS's `using` clause filtered the target row out returns `error: null` (success, nothing to report) unless `{count: 'exact'}` is passed — several of my own early test assertions produced false passes before I added `count` checks and re-verified with the admin client that no actual write occurred.
