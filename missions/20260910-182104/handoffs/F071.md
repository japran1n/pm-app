## Decisions made
- Extracted the section/quoting logic into a pure `buildBriefDocumentContent` function in a new `lib/brief/document.ts`, mirroring the codebase's existing convention (documented in tests/unit/f049-brief-question-crud.test.ts's header) of unit-testing pure logic directly and treating Supabase-client-dependent actions as an integration-test concern. This makes AS-140/AS-141 directly testable without a live DB.
- `workspace_id` (required by `docs`, not stored on `briefs`) is read from the parent `projects` row inside `generateBriefDocument`, the same resolution `createDoc` (lib/actions/docs.ts) uses for its caller-supplied `workspaceId`.
- Document content format is Markdown-ish plain text (`## Heading`, `**prompt**` + answer), matching how `docs.content` is stored/rendered elsewhere in the docs system (plain string, no serialization).
- The "Generate Document" button is shown only when the brief has at least one answer and no `docs` row of kind 'brief' exists yet for the project (a `docs` select by `project_id` + `doc_kind = 'brief'`) — `generateBriefDocument` always inserts a fresh row rather than upserting, so offering it again once a document exists would silently create a duplicate. F073 (edit the document) and F072 (hidden until shared) are separate features; this feature only creates the initial document. `docs.client_visible` already defaults to `false` in the schema, so the generated document starts hidden from the client automatically, consistent with F072's intent (not implemented here beyond the default).

## Out-of-scope work needed
- F072 (document hidden until shared) and F073 (edit the document) are separate features; not touched here beyond relying on `docs.client_visible`'s existing `false` default.
- No "regenerate" flow was built — once a document exists, the button disappears. If a future feature wants "regenerate overwrites the existing brief doc," that should be its own spec (current behavior: creating a second one is prevented by the UI, but there is no update path).
