## Decisions made
- Both features are pure scope-boundary / structural assertions with no new application behaviour to build — F042 confirms three features were deliberately never implemented, F043 confirms two routes already created by F037/M6 are genuinely separate. No product code changes were needed or made; only tests were added, matching the "verify absence" nature of these specs.
- Chose source-text inspection over rendering the components/pages in tests. Rendering `board.tsx`/`section-card.tsx` would require mocking the full dnd-kit + next/navigation + Server Action stack, and rendering the portal pages would require mocking Supabase queries/auth — with no additional confidence gained over reading the file, since the assertions ("no approval step exists", "no lock exists", "no comment UI exists", "these are separate route files") are fully determined by what code is or isn't present in the source.
- For AS-172's comment-scan, excluded two literal occurrences of "doc comment" / "comment for how it reconciles" that are pre-existing meta-references inside code comments (about JS comments, not a commenting feature), so the test doesn't false-positive on those specific existing phrases while still catching a genuine comment-thread/comment-input feature if one is added.
- For AS-171, narrowed the check to `"locked"` / `is_locked` / `"lock the board"` rather than also banning `"read-only"`, since `client-board.tsx`'s own doc comment legitimately and correctly describes itself as "read-only" (it never had editing affordances to begin with) — that phrase describes a static property of the portal view, not a board that *becomes* read-only as a result of some event, which is what AS-171 actually rules out.
