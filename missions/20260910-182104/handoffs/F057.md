## Decisions made
- `brief_answers` has no unique constraint on `(brief_id, question_id)` (verified against the real, applied migration `supabase/migrations/20261122010000_f044_brief_tables.sql`, not the spec draft's guessed `answer_value`/upsert-on-conflict shape), so `saveBriefAnswer` does select-then-branch (update if an answer row already exists for this brief+question, insert otherwise) rather than a Postgres `on conflict` upsert — same pattern this file's own `ensureBrief` helper already uses for `briefs.project_id`.
- `question_prompt_snapshot` is re-stamped from the live `brief_questions.prompt` on every save (not just on first creation), matching the schema's intent that the snapshot tracks "what the question said as of the last save" while the question still exists.
- `answered_by`/`answered_at` are set from the authenticated user and `now()` on every save (create or update) — there's no separate "first answered" vs "last edited" pair of columns in the schema, so this file treats every save as updating both.
- `useAutosave` is a generic hook (`lib/hooks/use-autosave.ts`, not brief-specific) so any future autosaved field in this codebase can reuse it.
- The debounce reset for switching between questions in `PortalQuestionnaire` (draft text must reset when `currentIndex` changes to a different question) is done during render via the "adjust state when a prop changes" pattern (comparing `question?.id` to a tracked `renderedQuestionId` and calling `setState` conditionally in the render body), not inside a `useEffect` — this repo's lint config (`react-hooks/set-state-in-effect`) treats a synchronous `setState` call inside an effect body as an error, and this avoids introducing one.
- `saveBriefAnswer` writes `null` for `answerText` when the draft is empty/whitespace-only, and always writes `null` for `answerOptions` — this component still only has the F055 textarea stub (short_text-shaped), so there is nothing meaningful to send for the choice-type `answerOptions` column yet; F059's real per-`answerType` widgets are the natural place to start passing non-null `answerOptions` for `single_choice`/`multi_choice`.
- `PortalQuestionnaire`'s `briefId` prop is optional (`string | null | undefined`) purely so F055's original render tests (which don't pass one) keep passing unmodified; the real portal route (`app/(portal).../brief/page.tsx`) always passes the loaded brief's real id now. If a project's client visits `/brief` before any brief row exists (`briefs` table empty for that project), `saveBriefAnswer` is skipped entirely (autosave is a silent no-op) rather than erroring — this mirrors the existing empty-questionnaire early-return already in that page (a client is never shown a working input with no way to persist it, since the empty-questionnaire branch returns before rendering `<PortalQuestionnaire>` at all when there are zero questions; the "briefs row not created yet but questions exist" edge case is unlikely given `ensureBrief` runs as soon as a team member adds the first question, but is handled defensively here rather than left to throw).
