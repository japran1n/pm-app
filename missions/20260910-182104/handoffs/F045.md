## Decisions made
- MCP tool functions (`mcp__supabase__*`) were not exposed in this worker's tool list, only Read/Write/Edit/Bash — same situation F002's and F044's handoffs document. Used the same remote-only Management API workflow F044 established.
- The trigger function is `security definer` with `set search_path = public, pg_temp` pinned, per 20260908010000's documented hijack surface (an unqualified `search_path` on a SECURITY DEFINER function lets a role with TEMP privileges shadow `public` objects via same-named `pg_temp` objects). This is genuinely required here (not just defensive): `brief_answer_revisions` has no INSERT policy for any role, so a plain (invoker-rights) trigger function running as `authenticated` would have its internal INSERT blocked by RLS; SECURITY DEFINER makes the INSERT run as the function owner, which is what makes the table append-only from the client's perspective while still allowing the trigger itself to write.
- Chose to SKIP writing a revision when neither `answer_text` nor `answer_options` actually changed (comparison via `is distinct from`, which correctly treats NULL-to-NULL as "unchanged" and any NULL/non-NULL transition as "changed"). Reasoning documented at length in the migration's header comment: AS-127/AS-133 are both scoped to *changing* an answer, not to *every UPDATE statement that happens to touch the row* — and the existing `brief_answers_set_updated_at` trigger from F044 already produces UPDATE statements that touch only `updated_at`, which would otherwise pollute the client-visible "izmijenjeno · <ime> · <kad>" history (draft section 4.2) with false edits.
- SELECT policy on `brief_answer_revisions` is deliberately permissive-but-project-scoped (workspace writer OR (client AND portal enabled) on the joined `brief_answers -> briefs -> project_id` chain), per the feature spec's explicit instruction to keep SELECT "permissive-but-project-scoped" here and let F046 tighten it. This does not affect AS-134/AS-135, which are about UPDATE/DELETE (permanently absent for every role, not just tightened later).
- Reused `is_project_workspace_writer`, `is_project_client`, `is_project_portal_enabled` unchanged from their existing live definitions (20260908010000, 20260909010000) rather than writing new predicate helpers, per standing decision #20 (cite live schema, don't invent parallel logic).
- Did not add an INSERT policy at all — the absence of one, combined with the trigger's SECURITY DEFINER, is what makes "only the trigger can insert" true. Explicitly verified this by attempting a direct client-role INSERT, which was rejected with `42501: new row violates row-level security policy`.
