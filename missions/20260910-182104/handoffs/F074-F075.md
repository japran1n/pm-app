## Decisions made
- Reused the existing `approval_requests` table (F007, `supabase/migrations/20260916010000_approval_requests.sql`) rather than inventing a `brief_approval_requests` table or a new `approval_subject_doc_id` column on `briefs`. That table's `subject_type` CHECK already accepts `'doc'`, and the generated brief document is itself a `docs` row (`doc_kind = 'brief'`, F071) — so "the brief document is the subject" maps exactly onto `subject_type: 'doc', subject_id: docId` with no schema change and no migration needed.
- `decision_type: 'content'` was picked from the existing closed vocabulary (`content`/`brand`/`technical`/`commercial`) as the closest fit for a written brief document.
- `requestBriefApproval` does a plain RLS-respecting insert (mirrors `lib/actions/brief.ts`'s existing "RLS gates, action surfaces a generic error" convention for every other write in the file) rather than routing through `lib/actions/approvals.ts`'s `requestApprovalImpl`/`withAuthz` — that generic team-to-client flow additionally requires a `project_decision_owners` row for the chosen decision type and the project's portal to be enabled, neither of which the brief spec's own standing decisions mention as a precondition for requesting brief approval. Verified `approval_requests_insert_team`'s actual `with check` clause only requires `is_project_workspace_writer(project_id) and requested_by = auth.uid()` (no decision-owner gate at the RLS layer), so the simpler direct-insert action is sufficient and does not bypass any DB-level enforcement.
- `approveBrief` writes directly to `briefs.state` (already a valid value per `briefs_state_check`: `'draft' | 'submitted' | 'approved'`, `supabase/migrations/20261122010000_f044_brief_tables.sql`) rather than through `approval_requests`/`decide_approval_atomic` — the brief's own state machine (`submitBrief` in this same file) already treats `briefs.state` as the source of truth for brief lifecycle, and standing-decisions.md #16 ("Approval freezes answers, enforced in RLS... withdrawing approval unfreezes") describes brief approval as acting on `briefs.state`/RLS directly, not through the generic client-portal approval queue.
- Buttons on the team brief page (`app/.../brief/page.tsx`) are shown only once a brief document exists (`existingDocument`) and only while `brief.state !== 'approved'` — matches the "nothing to request/approve before a document exists, nothing left to do once approved" framing implicit in both assertions.
- Followed this codebase's established test precedent (see `tests/unit/f049-brief-question-crud.test.ts`, `tests/unit/f071-generate-brief-document.test.ts` headers): actions that call `createClient()` from `@/lib/supabase/server` need a real request context, so `requestBriefApproval`'s DB round trip is an integration concern; AS-146's subject-recording behaviour is instead pinned down via a pure, directly-unit-testable `buildBriefApprovalRequestPayload` helper extracted specifically for this purpose. `approveBrief` was additionally verified against a mocked Supabase client (asserting the literal `{ state: 'approved' }` update payload) since AS-147's exact target value is easy to pin down that way without a live DB.
