## Decisions made
- Implemented exactly the pattern the clarified spec/tech-decisions specify: `data-hover-component` on the board root, `data-component` on each card (already present from F008/F027/F032), and a vanilla `mouseover`/`mouseleave` DOM listener attached in a `useEffect` against a `useRef`'d board root — never touches React state, so hover never triggers a re-render.
- The listener also writes `data-component-active="true"` on every card sharing the hovered id (and removes the attribute otherwise) so the CSS can select "the active set" without needing per-id CSS rules (which isn't feasible with static CSS since component ids are dynamic). This is still zero React state — `dataset` writes are plain DOM mutations.
- Used `closest("[data-component]")` on `event.target` inside the `mouseover` handler (event delegation on the single board root) rather than attaching a listener per card — one listener for up to 480 cards, matching the tech-decision's performance constraint.
- CSS: dimmed non-active linked cards to `opacity: 0.6` with `border-color: var(--border)` (falls back to the plain border) while the active set gets `var(--component-border-hover)` and a `color-mix` background tint using the existing `--component` token — no hex literals, both themes resolve because `--component`/`--component-border-hover` are already theme-token-driven (F001).
- AS-072 falls out structurally: unlinked sections never carry `data-component` at all (decision made back in F008/F032), so the `mouseover` handler's `closest("[data-component]")` lookup returns `null` for them, resolving to an empty hover id — the CSS guard `:not([data-hover-component=""])` then keeps every rule inert board-wide.
