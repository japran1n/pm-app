## Decisions made
- `changePageKind` mirrors `createPage`'s pattern exactly: re-validate membership/write-permission server-side via the task's real owning workspace (looked up through `tasks.project_id -> projects.workspace_id`), never trusting a workspace id from the caller.
- Added a guard confirming the target task actually has `page_slug` set (i.e. is a page) before allowing the kind change, consistent with standing decision 1 (a page IS a task with `page_slug` set).
- `PageKindSelector` wraps the existing `PageKindBadge` (F007) as the trigger button and shows a small popover with the three kind options; clicking the current kind is a no-op. Chose a lightweight custom popover (no new dependency) per standing decision 18 ("no new npm package").
- Used `useTransition` + `router.refresh()` rather than local optimistic state, matching the `router.refresh()` pattern already used by `createPage`'s callers, so the whole board re-fetches consistent server state after a change.
