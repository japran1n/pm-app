## Decisions made
- `reorderPages` mirrors `reorderSections`'s exact pattern (batch position update, per-workspace membership/write-permission cache, whole-batch rejection if any id fails validation) rather than introducing a new convention, since a page is the same `tasks` row shape (standing decision 1) just filtered by `page_slug` being set instead of `parent_task_id`.
- Column drag vs section drag is distinguished by `data: { type: "page" | "section" }` on each `useSortable` call rather than a second `DndContext`, because dnd-kit requires a single shared `DndContext` for cross-container drags (F021 already established this for cross-column section drags) and a column drag never needs to interoperate with a different container.
- The column's whole draggable surface is the grip button only (not the full column), matching `SortableSectionCard`'s existing pattern of a dedicated handle so the card's own click targets (rename, kind selector, delete) aren't fought over by dnd-kit's pointer listeners.
- Kept `SortableContext` for pages using `horizontalListSortingStrategy` since columns lay out left-to-right (`flex` row in board.tsx), mirroring `verticalListSortingStrategy` used for the vertical section lists.
