## Decisions made
- Root cause of the contrast bug: `--component-foreground`/`--cms-foreground` were computed with `oklch(from var(--component) clamp(0.12, calc((0.62 - l) * 100), 0.99) ...)`, i.e. they assumed the accent color itself (`--component`/`--cms`, lightness ~0.55–0.75 in both themes) was painted as a solid fill and picked a contrasting lightness against *that*. In practice the only real usages (components/architecture/section-card.tsx `hover:bg-component/10`, components/architecture/page-kind-badge.tsx `bg-[var(--cms)]/10`) apply the accent color at 10-15% opacity over `--card`, so the effective background stays close to `--card`'s own lightness (near-white in light theme, near-black in dark theme) — not the accent's lightness. The old formula produced foreground lightness 0.12 (dark text) in dark mode and ~0.99 (near-white text) in light mode — both backwards relative to the actual near-`--card` background, i.e. failing WCAG AA in both themes.
- Fix: derive `--component-foreground`/`--cms-foreground` lightness from `--foreground` (already guaranteed AA-compliant against `--card`/`--background` per the base Supabase design system semantic.css derivation) and only borrow the accent's hue via `var(--component-hue)`/`var(--cms-hue)`, with a small chroma boost (`calc(c * 0.3 + 0.03)`) so the text still reads as tinted rather than plain gray.
- Confirmed `--component`/`--cms` (the "fill" tokens the spec calls `--component-fill`/`--cms-fill`; no literal `-fill`-suffixed token exists in this codebase) and their `-lightness` companions already resolve distinctly in both `:root` and `[data-theme='dark']` — no missing-token gap, only the foreground formula needed fixing.
- AUTONOMOUS_DECISION: Treated the spec's `--component-fill`/`--cms-fill` naming as referring to the actual `--component`/`--cms` tokens (used as backgrounds via `bg-component/NN`), since no `-fill`-suffixed token exists anywhere in the codebase or F001's original spec. Documented this in the test file's comments.
