## Decisions made
- Added `linkComponentToSection(sectionTaskId, componentId)` to lib/actions/architecture.ts, mirroring `createComponent`'s membership/canWrite checks and generic-error convention. AS-062 (one component per section) falls out for free from `tasks.component_id` being a single nullable column — the update always overwrites whatever was there, no join table to dedupe. Confirmed this exactly matches the shape an already-checked-in F031 test (tests/unit/f031-component-guards.test.ts, not written by me, present in the tree from a parallel/future worker) expects — that test passes unmodified against this implementation.
- Cross-project guard: `linkComponentToSection` verifies the looked-up component's `project_id` matches the section's `project_id` before updating, returning a generic error otherwise (covers what F031's AS-064 tests exercise).
- `ComponentPicker` (new Client Component) uses the app's existing `Command`/`cmdk` primitive (components/ui/command.tsx) inside a `Popover`, the same "search or create" pattern already used by `components/command/project-switcher.tsx`. `shouldFilter={false}` because filtering is done manually against the `components` prop (client-side, no extra fetch) so the "Create" row logic can inspect the same filtered/unfiltered sets.
- Threaded the board's already-existing `components: BoardComponent[]` prop (previously unused, called out in board.tsx's own header comment as intentionally pre-wired for a later feature) down through `PageColumn` → `SortableSectionList` → `SortableSectionCard` → `SectionCard`, each with an optional `components?: BoardComponent[]` default `[]` so existing callers/tests that don't pass it (e.g. tests/unit/f020-reorder-sections.test.tsx) keep compiling.
- Added a "Link component" button (Link2 icon) next to the existing "Create component" (Boxes icon) button in `SectionCard`, shown only when `section.component === null`, opening the picker in a Popover anchored to that button.
- Test file follows the pre-existing action-mock convention (mocking `next/navigation`'s `useRouter` and the action module directly) rather than the deep Supabase-admin-client stub convention used by action-level tests, since this is a component test — it verifies picker behaviour (list, filter, create-option, call sequencing), not the server action's own internals (already covered by tests/unit/f025-create-component.test.ts and the pre-existing tests/unit/f031-component-guards.test.ts).
