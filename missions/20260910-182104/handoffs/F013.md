## Decisions made
- `createSection`'s signature matches the spec exactly: `(pageTaskId, projectId, title)`. Internally it re-validates via `createSectionSchema` (title + page_id), re-checks project membership/write permission server-side (defense in depth, same convention as `createPage`/`changePageKind`), and confirms the parent task is actually a page (page_slug set, parent_task_id null) scoped to the given projectId before attaching a section.
- Sections use the same workspace `page` task type as their parent page (resolved via `ensure_task_type`), matching `createPage`'s own resolution — sections and pages share one task_type taxonomy entry per standing decision 1 (a page/section are both just tasks).
- `AddSectionButton` reads `projectId` from the route params (`useParams<{ projectId: string }>()`) rather than being passed as a prop threaded through `ArchitectureBoard` -> `PageColumn`, since `BoardPage` (lib/queries/architecture.ts) does not carry a `projectId` field and the architecture board route is always scoped to a single project (`/projects/[projectId]/architecture`). This avoids widening the `ArchitectureBoard`/`PageColumn` public contracts, which are out of this feature's declared scope.
- Empty/whitespace-only section name on submit is a silent no-op (AS-040) — the inline input stays open rather than showing an error, since `createSectionSchema` already treats this as invalid and the UX goal is simply "don't create a blank section," not to surface a validation message for a state the UI itself prevents via the disabled Enter/click no-op.
