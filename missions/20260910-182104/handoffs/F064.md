## Decisions made
- Reused the already-built `getBriefForClient` read (F048, `lib/queries/brief.ts`) rather than adding a new query — it already returns `{ brief, questions, answers }` for the client, RLS-scoped exactly like every other portal read this file composes over. `build-waiting-on-you-items.ts`'s own header documents that this module is "pure composition over already-fetched lists, no query of its own" — the brief read follows that same rule by being fetched once in `page.tsx` alongside the other Promise.all reads and passed in as a small `{ state, questionCount }` shape (not the full `BriefWithQuestionsAndAnswers`), matching how `deliverables`/`accounts` are passed as their own already-typed lists.
- Predicate is `state === "draft" && questionCount > 0` — this single check satisfies both AS-163 (draft + has questions => outstanding) and AS-164 (submitted/approved => not outstanding) without a separate "is this submitted" negative check, since `draft` is the only state this predicate matches.
- A draft brief with zero questions does not surface (per the F064 spec text: "no questions to answer = nothing to do"). Covered by its own test even though not one of the two named assertions, since it's the DoD-style edge the spec explicitly called out.
- `brief` param on `buildWaitingOnYouItems` is optional (`brief?: BriefOutstandingInfo`) so existing callers/tests that don't pass it (e.g. `lib/portal/build-waiting-on-you-items.test.ts`) keep compiling and behaving as before (no brief item added when omitted).
- Added a `brief: FileQuestion` entry to `waiting-on-you-block.tsx`'s `KIND_ICON` map (required by `Record<WaitingOnYouItemKind, ...>` after adding the new kind) using `lucide-react`'s `FileQuestion` icon, consistent with the file's own "every kind gets its own distinct icon" rule. `agedLabel` needed no change: brief items are given `daysWaiting: 0` (no natural "raised at" timestamp on a brief the way approvals/tasks have `requestedAt`), which already falls through to the existing "Asked today" copy for non-account, non-deliverable, day-0 items — same reasoning `account` uses for why it can't claim an age, but brief's neutral copy already existed for day 0 so no special case was needed.
