## Decisions made
- `submitBrief(briefId)` is idempotent: if the brief is already `'submitted'`, it returns success without a second write, matching AS-126's "resubmitting is fine" framing rather than erroring.
- `submitBrief` only transitions `'draft' -> 'submitted'`; it explicitly refuses (returns an error) if the brief is in any other state (e.g. `'approved'`), and never writes `'approved'` itself, per the spec's "submission is not a freeze; approval is [separate]" note.
- Required-question validation before submit is done client-side in `PortalQuestionnaire`: the current question's in-progress `draft` state is checked (since debounced autosave may not have flushed yet), and every other question is checked against its last-saved answer from `initialAnswers`. This mirrors the same `isAnswered` helper F060 already introduced, applied across all questions rather than just the current one.
- No RLS/schema change was made — F046's existing `briefs` RLS policies (client can update `state` while not `'approved'`) are the enforcement boundary; this action just performs a guarded update through the RLS-respecting `createClient()`, same pattern as every other action in this file.
- AS-126 is satisfied by simply never disabling any input after submit — `submitted` is pure UI state that swaps the button for a message; it does not gate `AnswerInput`, `saveBriefAnswer`, or the Previous/Next controls.
