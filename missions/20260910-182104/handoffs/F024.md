## Decisions made
- The board's `handleDragEnd` already returned early with no state mutation when `over` is null (drop outside any droppable target), and dnd-kit's `onDragCancel` (Escape key) was never wired at all — so cancellation already left `orderByPage` untouched by omission. Per the spec's "if already correct, verify and document" instruction, I made this explicit rather than relying on the absence of a handler: added `onDragCancel={handleDragCancel}` to the `DndContext`, where `handleDragCancel` re-derives `orderByPage` from the `pages` prop (the same snapshot logic already used for prop re-sync), so it can never observe or persist any in-flight drag state.
- Tests simulate drag cancellation and a null-`over` drag end by mocking `@dnd-kit/core`'s `DndContext` to capture the `onDragCancel`/`onDragEnd` props the board passes in and invoking them directly — jsdom has no real pointer-drag simulation, and this is the same class of approach the existing F021 move-section test uses for its own Server Action boundary.
- Also mocked `next/navigation` (`useRouter`, `usePathname`, `useParams`) and `changePageKind`/`reorderPages` from `@/lib/actions/architecture` in the new test file because rendering `ArchitectureBoard` now pulls in `PageColumnHeader` and `AddSectionButton`, which call those hooks/actions — this is boilerplate required to render the tree in a unit test, not new application behavior.
