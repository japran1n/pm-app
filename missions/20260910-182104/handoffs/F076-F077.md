## Decisions made
- No new migration was needed for RLS: read `supabase/migrations/20261122040000_f046_brief_rls.sql` (F046) and confirmed its `brief_answers_insert`/`_update`/`_delete` policies already AND `b.state <> 'approved'` into every write leg, for both the client and team-writer branches, with the migration's own header comment explicitly calling out that this was written in anticipation of F076/AS-148/149/150. No `20261124010000_f076_brief_approval_lock.sql` was created since there was nothing to add.
- `saveBriefAnswer`'s new guard queries `briefs.state` directly (a second, cheap query) rather than trying to infer lock state from the RLS failure shape, so the action can surface "Brief is approved and answers are locked." instead of a generic RLS-denial message — matches this file's existing convention of a friendly action-level message backed by RLS as the real boundary.
- `withdrawBriefApproval` reverts to `submitted`, not `draft` — the brief was already submitted before it could be approved, and withdrawal is "undo the approval decision," not "undo the client's submission." Matches the spec's own instruction (`UPDATE briefs SET state='submitted' ... AND state='approved'`).
- Updated `tests/unit/f068-change-notification.test.ts`'s `test_AS_136_also_notifies_when_brief_is_approved` test, which pre-dated F076 and asserted that changing an answer on an approved brief still succeeds and notifies. F076 makes that impossible (the write is now locked before it reaches the notification path), so the test was rewritten to assert the new, correct behaviour (write rejected, no notification) rather than left failing.
- `AnswerInput` gained an optional `disabled` prop threaded through every answer-type branch (input/textarea/radio group/checkboxes); `PortalQuestionnaire` gained an optional `briefState` prop (defaults to non-locked behaviour when omitted) so every pre-existing render test that doesn't pass `briefState` keeps passing unmodified.
