## Decisions made
- Both F038 and F039 were already satisfied by existing code shipped in earlier features (F004/F037 for AS-098; the pre-existing `p/[projectId]/layout.tsx` shell for AS-095/AS-096). No source changes were needed — only test coverage was added, per the feature specs' own framing ("If it already does, document it").
- For F038's test, reused the shared `tests/unit/helpers/query-filter-mock.ts` (`eqFilter`/`applyFilters`) convention already established by `portal-phases-query.test.ts` — a mock that ignores its own filter arguments cannot prove the filter is applied, so the mock genuinely filters the fixture row set by every recorded `.eq()` predicate.
- For F039, rather than mocking the Architecture page directly (which forwards render entirely to the shared layout with no guard logic of its own to test), the test targets `p/[projectId]/layout.tsx` — the actual choke point where both AS-095 (portal disabled) and AS-096 (non-member) collapse to the identical "project absent from `getPortalProjects`'s result" case. This is consistent with the layout's own header comment and with `tests/integration/f003-portal-shell.test.ts`, which already covers the same guard end-to-end against a live Supabase project.
- Full suite run (`npx vitest run`, no path filter) was also attempted; it includes many `tests/integration/*` suites that talk to a live Supabase project and are independently flaky/slow in this environment (statement timeouts, `revalidatePath` "no active request/render context" warnings, RLS test flakiness) — none touch `lib/queries/architecture.ts` or the portal project layout, and none are new failures introduced by this change. Scoped `tests/unit` run (2428 passed / 18 pre-existing failures, none from this feature) is the actionable evidence.
