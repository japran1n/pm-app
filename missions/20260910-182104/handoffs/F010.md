## Decisions made
- `createPage(projectId, data)` does NOT accept a `workspaceId` parameter, even though the feature spec's sketch signature was `createPage(projectId, workspaceId, data)`. Same reasoning as `createTaskForUser` (lib/tasks/create.ts): the project's owning `workspace_id` is looked up server-side from the `projects` table so authorization is always checked against the *real* workspace, never one a client could pass in. A caller-supplied `workspaceId` would either be redundant (if it must match the looked-up value, why accept it) or a security foot-gun (if it were ever trusted instead). No caller in this codebase currently has a `workspaceId` in scope at the architecture page anyway (`app/.../architecture/page.tsx` only receives `projectId`/`workspaceSlug` params), so this also avoids a needless second lookup on the caller side.
- The workspace's `page` task type is resolved via the existing `ensure_task_type` Postgres RPC (`supabase/migrations/20261104040000_f116_self_healing_system_type_lookup.sql`) with `p_system_key: "page"`, matching the exact name/color the original seed uses (`'Page'`, `'#3670e1'` — `supabase/migrations/20260912010000_task_type_system_key.sql` / `20261104010000_f116_task_type_taxonomy.sql`). This lazily repairs any workspace that predates the seed, same as `createTaskForUser`'s own `delivery` lookup — no new migration needed since this RPC already exists and is `security definer` + granted for this use.
- Position (AS-037): per the feature spec's literal instruction ("position: count existing page tasks for this project + 1"), not `lib/board/position.ts`'s fractional-index `calculatePosition` — pages are a fixed left-to-right column order with no drag-reorder in this feature's scope, so a simple integer append is correct and matches `lib/queries/architecture.ts`'s own `page.position` sort key.
- The "page task" count query filters `parent_task_id is null and page_slug is not null and deleted_at is null` — the exact predicate `lib/queries/architecture.ts`'s `buildBoardFromRows` uses to split rows into pages, so the new page always sorts after every row the board will actually render as a page.
- `CreatePageDialog` uses the trimmed `name` as the `slug` for now (F011's scope is proposing/editing a real slug per standing decision 3) — called out explicitly in the dialog's own file comment so F011's worker doesn't need to re-derive this from the diff.
- `ArchitectureBoardEmptyState` was promoted from a plain function component to `"use client"` since it now owns the dialog's open/close state — the smallest client boundary available (page.tsx itself stays a Server Component).
