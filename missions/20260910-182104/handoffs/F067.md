## Decisions made
- Fetched full revision history server-side in the brief team page (one `getBriefWithRevisions(brief.id, question.id)` call per question that already has `hasRevisions: true` from F066's batched flag, so unedited questions cost nothing extra), then passed the result down as a new optional `revisions?: BriefAnswerRevision[]` field on `TeamAnswersViewQuestion` — matches the spec's "simpler approach" recommendation and keeps `team-answers-view.tsx` a pure presentational Server Component with no new client data-fetching.
- `<RevisionHistory>` is the one client component in this feature (`"use client"`, `useState` for the toggle). It receives revisions as a prop rather than fetching on demand — no new API route needed, and it satisfies F070's "isolated presentation" requirement by construction: expanding it never touches the project activity feed, it just toggles the visibility of data already resolved on the page.
- Collapsed by default; renders `null` entirely when `revisions` is empty, so it's a no-op for every unedited answer already on the page.
- Each entry renders "Changed by {name} on {date}: '{previous value}'" per the spec's exact template; falls back to "Unknown" when `changedByName` is null (matches F065's documented nullable shape) and to the joined `previousOptions` or "(empty)" for choice-type answers whose `previousText` is null.
