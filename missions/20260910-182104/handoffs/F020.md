## Decisions made
- reorderSections takes `{ id, position }[]` and does a `Promise.all` of individual `.update()` calls per the spec, after first re-validating every id server-side (belongs to a live section — `parent_task_id` set, no `page_slug` — and the caller has active, write-capable membership in that section's workspace). Chose "reject the whole batch if any single id fails validation" over "apply what's valid" so a stale/tampered client payload can't partially reorder a page it doesn't fully control.
- SortableSectionCard puts the drag handle in a small absolutely-positioned button to the left of the card (mirrors project-nav-list's "dedicated handle, not the whole row" reasoning) — SectionCard's title is its own click target for F015's inline rename, and dnd-kit listeners on the full card would otherwise compete with that click.
- SortableSectionList mirrors ProjectNavList's "optimistic local order, re-synced only when the underlying SET of ids changes, rolled back on server failure" convention exactly, including the "component id, not prop order" position numbering (`index + 1` after `arrayMove`).
- page-column.tsx's raw `.map` over `page.sections` was replaced entirely by `<SortableSectionList sections={page.sections} pageId={page.id} />` — SectionCard itself is untouched (F008/F015 continue to own its rename/delete/component-name rendering); this feature only wraps it.
