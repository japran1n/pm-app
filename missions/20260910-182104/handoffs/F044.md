## Decisions made
- MCP tool functions (`mcp__supabase__*`) were not exposed in this worker's tool list, only Read/Write/Edit/Bash — same situation F002's handoff documents. Per the worker-mcp-usage skill's fallback guidance, used the repo's established remote-only workflow instead: the Management API `database/query` endpoint (same one `scripts/apply-migration.mjs` and `scripts/gen-types.mjs` use, authenticated via `SUPABASE_ACCESS_TOKEN`) for schema introspection, `npm run db:apply` for applying the migration, and the same endpoint again for the negative-case verification queries. No credential value was ever printed.
- Confirmed live (not from memory) before writing: `projects.id` and `docs.id` are both `uuid` primary keys; `docs.doc_kind` is a `text` column with an existing CHECK that this migration does not touch (F047's job); `set_updated_at()` exists live and is the schema-wide reused trigger function — applied it to `briefs` and `brief_answers` (the two tables with an `updated_at` column). `brief_answer_revisions.changed_at` has no trigger since the column is set at insert time by the (future, F045) revision trigger and rows are never updated in place.
- `briefs.project_id unique` doubles as AS-099's enforcement and its own supporting index (unique constraints create their own index), so no separate `create index` was added for that column.
- Indexed `brief_questions.project_id`, `brief_answers.brief_id`, `brief_answers.question_id`, and `brief_answer_revisions.answer_id` — the FK/lookup columns each table's future RLS (F046) will join through, per the convention documented in `20260818040214_create_comments.sql` and applied schema-wide by `20261120040000_index_unindexed_foreign_keys.sql`.
- Added not-empty CHECKs on `brief_questions.prompt` and `brief_answers.question_prompt_snapshot` per the feature spec's explicit instruction, following the `not null` + explicit CHECK pattern this schema uses everywhere text must not be blank (e.g. `comments_text_not_empty`, `projects_name_not_empty`).
- Enabled RLS on all four tables with zero policies (deny-by-default), no FORCE ROW LEVEL SECURITY — matching the schema-wide convention that privileged server-side access goes through the secret key, which bypasses RLS by design. No policies were written; RLS/policies are explicitly F046's scope.
- Did not write the revision trigger (F045) or touch `docs_doc_kind_check` (F047), per the feature spec's explicit exclusions.
