## Decisions made
- Used the existing `notifications` table + `create_notification` SECURITY DEFINER RPC (F206) rather than inventing a new mechanism, per F069's context note that this feature should use `project_decision_owners` for now (F069 will make recipients configurable later). This is the same "direct call, bypasses computeFanoutRecipients" pattern already established for `PortalNotificationKind` and `ChatNotificationKind` in `lib/notifications/fanout.ts`.
- Added a new closed-vocabulary kind, `brief_answer_changed`, via a migration widening `notifications_kind_check` (mirrors every prior widening migration's pattern, e.g. `20261104900000_faza_d_chat_notifications.sql`). Added a matching `BriefNotificationKind` TypeScript type and included it in `CreateNotificationParams.kind`'s union in `lib/notifications/create-notification.ts`.
- Notification only fires from `saveBriefAnswer`'s `existing`-row (update) branch, not the first-time insert branch — "changing an answer" implies an answer already existed. This is stricter than the spec's literal `saveBriefAnswer` example but matches the assertion text ("changing an answer") more precisely; the spec's inline code sample would also have fired on a first-ever answer, which isn't a "change".
- Notification send is non-fatal (wrapped by `createNotification`'s own try/catch — logs and returns `{ ok: false }` rather than throwing), so an RPC failure or missing decision owners never fails the underlying answer save, matching every other fan-out call site's convention in this codebase.
- Did not gate on `notification_preferences` (the `*_in_app` per-kind opt-out table) — this is a new closed-vocabulary kind not yet added to `IN_APP_COLUMN_BY_KIND`, and none of the three prior "direct call, bypasses fan-out" kinds (`PortalNotificationKind`, `ChatNotificationKind`) are gated by preferences either. This is a real limitation: `brief_answer_changed` recipients currently cannot opt out via the standard in-app toggle. Flagged in Out-of-scope below.

## Out-of-scope work needed

F069 should decide whether that stays the source of truth or whether a new configurable-recipients concept replaces/augments it, and should update `notifyDecisionOwnersOfAnswerChange` in `lib/actions/brief.ts` accordingly.
- A future feature may want to add `brief_answer_changed_in_app`/`_email` columns to `notification_preferences` and wire `IN_APP_COLUMN_BY_KIND` (`lib/notifications/preferences.ts`) if this kind should be individually mutable, consistent with every fan-out kind computed via `computeFanoutRecipients`. Not done here since the three prior "direct call" kinds also skip this, and the spec did not ask for it.
- No UI surfaces the notification's `payload` (`project_id`/`brief_id`/`question_id`/`changed_by`) yet beyond the generic notification panel already built for F209/etc — a future feature could add a brief-specific notification message/deep-link if desired.
