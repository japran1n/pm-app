## Decisions made
- Read the real, live migration files (`20261122010000_f044_brief_tables.sql`, `20261122040000_f046_brief_rls.sql`) rather than trusting the spec's assumed shape. Key correction: `brief_questions` carries `project_id` directly (not `brief_id` — the table has no `brief_id` column at all), per standing decision #12 ("the questionnaire is per project, never a shared workspace-level template"). `createBriefQuestion(projectId, data)` therefore inserts with `project_id` directly; `ensureBrief` still runs first (per the spec's explicit instruction to create the brief if it doesn't exist) so a `briefs` row exists for later features (answers, submit/approve) to hang off, but it does not gate or scope the question insert itself.
- `ensureBrief` is implemented as a private (non-exported) helper inside `lib/actions/brief.ts`, per the spec's own phrasing ("helper, not exported separately if not needed").
- Followed `lib/tasks/create.ts`'s exact append-to-end pattern for `position`: look up the current last question's position for the project (`order position desc limit 1`), then call `lib/board/position.ts`'s `calculatePosition(lastPosition ?? null, null)` — same function, not a reimplementation, so an empty questionnaire and floating-point edge cases behave identically to the board's own proven code path.
- Auth model: no explicit "is this user a workspace writer" re-check was added in application code, unlike `lib/actions/tasks/create.ts`'s documented (but here, absent) "defense in depth" re-check. Reasoning: F046's RLS (`brief_questions_insert_team`/`_update_team`/`_delete_team`, all requiring `is_project_workspace_writer`) is the sole write boundary this feature's spec assigns to AS-101/AS-161, and `lib/actions/docs.ts` (the closest analogous "plain RLS-respecting write, no app-side role re-check" convention in this codebase) does the same — relying on RLS alone, not duplicating a role check in TypeScript. A non-writer's write attempt fails the `with check`/`using` clause and surfaces here as a generic "couldn't add/save/delete... you may not have permission" error, same ambiguity every other RLS-gated action in this codebase (docs, etc.) already accepts.
- `updateQuestionSchema` is a plain `.partial()` of `createQuestionSchema` per the spec's literal instruction. Verified `.partial()` correctly leaves `required` `undefined` (not forced to its `false` default) when omitted from an update payload — confirmed via the "single-field update" and "empty object" test cases — so a partial update never silently resets `required` to false.
- `deleteBriefQuestion` does not write any explicit snapshot logic — the spec's "soft-awareness" instruction is already fully satisfied by the schema itself: `brief_answers.question_id` has `on delete set null` and `question_prompt_snapshot` is populated independently at answer-write time (a later feature, not F049), so this action is a plain `delete` and a comment documents why no additional code is needed.
- `reorderQuestionsSchema` was added per the spec's explicit "3. reorderQuestionsSchema" instruction, but no `reorderBriefQuestions` server action was implemented — no assertion in this feature's Covers list (AS-101, AS-112) requires reordering behaviour, and the spec's action list (item "2. lib/actions/brief.ts") only names `createBriefQuestion`/`updateBriefQuestion`/`deleteBriefQuestion`/`ensureBrief`. Left as a validation-only schema for a future reorder feature to consume, consistent with "implement only what your feature spec covers."
