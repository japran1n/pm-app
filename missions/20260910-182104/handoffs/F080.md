## Decisions made
- Found the project template system: a single `task_templates` table with a `kind` discriminator (`'task' | 'project'`), an opaque `payload` jsonb column. `kind='project'` payloads are validated by `projectTemplatePayloadSchema` (lib/validation/templates.ts) and already carry `tasks`, `phases`, `deliverables` sections, each added incrementally with the same "optional/defaulted, not `.optional()` alone" backward-compatibility pattern for old stored payloads. Added `briefQuestions` following that exact established convention.
- Chose to seed the new project's `brief_questions` via a plain best-effort `INSERT` in the `createProjectFromTemplate` Server Action AFTER the `create_project_from_template` RPC returns, rather than adding a new `p_brief_questions` jsonb parameter to that Postgres function. Rationale: the RPC's atomicity guarantee exists specifically for the project + its tasks (so a malformed task never leaves an orphaned project) — `saved_views` and `project_decision_types` are already seeded the same "outside the RPC, best-effort, logged-not-fatal" way immediately after the RPC call for the identical reason (they are enrichment, not core to "does this project exist with its tasks"). Brief questions are the same category of enrichment, and this avoids a `DROP FUNCTION` + new-signature migration (the RPC's own migration history shows every parameter addition requires dropping and recreating the function since Postgres treats a different arg list as a distinct overload) for a feature whose Definition of done does not call for cross-entity transactional atomicity with the project/task creation.
- Did not add any read from `brief_answers` anywhere in the snapshot or copy path — `brief_answers` is keyed by `brief_id` (which only exists once a `briefs` row exists for a real project), so there was never a code path that could pull answers into a template in the first place. AS-167 holds structurally, not by an explicit exclusion check.
- New project's `brief_questions.position` is reassigned 0-based (`index * 1000`) in template order, not copied from the source project's original position values, which have no meaning once rows belong to a different project — same convention the existing phases-seeding loop in the same RPC/action already uses for its own 1-based position reassignment.

## Out-of-scope work needed
- No UI surface currently exists for a workspace member to add/view a template's brief questions before applying it (the "save project as template" / "create project from template" dialogs are pure name-entry forms today, per the existing `saveProjectAsTemplate`/`createProjectFromTemplate` call sites). This feature's spec only asked for the copy behaviour at the data layer (AS-165/166/167 are all about templates "carrying" and "copying" data, not about a template editor UI), so no UI changes were made. A future feature could surface "N brief questions will be copied" in the create-from-template dialog.

## Autonomous decisions
AUTONOMOUS_DECISION: Implemented the brief-questions copy as a best-effort post-RPC insert (matching the existing `saved_views`/`project_decision_types` pattern in `createProjectFromTemplate`) rather than extending the `create_project_from_template` SQL function's signature, since the spec's own "What to build" section described it as "gets the source project's brief questions... copies them... does NOT copy brief_answers" without requiring the same all-or-nothing transactional guarantee the RPC provides for tasks. This keeps the change additive (no migration, no `DROP FUNCTION`) and consistent with two other post-RPC enrichment inserts already in the same function.
