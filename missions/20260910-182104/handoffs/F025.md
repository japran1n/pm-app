## Decisions made
- Added `createComponentFromSection(sectionTaskId, projectId)`: looks up the section's owning workspace server-side (never trusts the caller-supplied `projectId` for permission checks, only for scoping the insert once membership is verified — same convention as every other action in this file), confirms the task is actually a section (parent_task_id set, page_slug null), and returns "Section already linked to a component" if `component_id` is already set, before ever attempting an insert.
- Added `createComponent(projectId, name)` as a general-purpose sibling, following `createPage`'s membership/permission/position-append pattern. Both actions rely on the existing `page_components_project_id_lower_name_idx` unique index (`supabase/migrations/20261121010000_f002_page_components.sql`, from F002) for AS-065 and translate its `23505` violation into a friendly "A component with this name already exists." error rather than a 500.
- `section-card.tsx`: added a "Create component" icon button, shown only on hover (matching `DeleteSectionButton`'s existing hover-reveal convention) and only when `section.component === null`. Reads `projectId` from `useParams()` rather than threading it as a new prop through `ArchitectureBoard -> PageColumn -> SortableSectionList -> SortableSectionCard -> SectionCard` — this mirrors `AddSectionButton`'s (F013) own documented reasoning for the identical tradeoff (the board route is scoped to one project already).
- **Pre-existing test breakage surfaced by this change**: `SectionCard` now also calls `useParams()`, in addition to the `useRouter()` it already called. Two test files that render `<ArchitectureBoard>`/`<SectionCard>` with a hand-rolled `next/navigation` mock (`tests/unit/f015-rename-section.test.tsx`, `tests/unit/f020-reorder-sections.test.tsx`) only stubbed `useRouter`, so they started failing with "No useParams export is defined on the next/navigation mock." I added `useParams: () => ({ projectId: "test-project-id" })` to both mocks — a minimal, in-scope fix since my own change is what introduced the new dependency these mocks needed to cover. `f006`/`f008`/`f009`'s architecture tests do NOT mock `next/navigation` at all and were already failing before this feature (confirmed via `git stash`) with the same "invariant expected app router to be mounted" error from the pre-existing `useRouter()` call — untouched, out of scope for this feature.
